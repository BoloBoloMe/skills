# 方案设计与审批阶段

## 这个阶段要做什么
比较可行方案，给出推荐路径，并明确哪些内容需要用户决定或批准。

## 推荐方案
- 名称：新增只读规划资产归档阶段。
- 核心思路：在执行交接成功后自动触发 `hilp-archive`，只生成版本化 `stage-7/archive-manifest@vN`，用阅读角色整理当前变更目录内资产；归档不修改任何上游资产、不移动文件、不生成 `CURRENT.md`、不新增规划判断。
- 为什么推荐：该方案直接解决阅读混乱，同时最小化对现有审批状态机、蓝图确定性纪律和执行交接门槛的影响。它把“文档怎么读”与“资产是否批准”分离，避免把最终批准资产错误改成 `archived`。

## 备选方案
### 方案 A：只在执行交接中增加一个归档小节，不新增模块
- 核心思路：不新增 `hilp-archive`，仅让执行交接资产末尾列出最终阅读入口。
- 优点：改动最小。
- 代价：缺少独立模板、入口条件、失败条件、手动重新触发规则和阅读角色体系，后续治理容易再次分散。
- 不选原因：不能稳定解决多版本目录的长期阅读治理问题。

### 方案 B：新增归档阶段并移动旧文件到 archive 子目录
- 核心思路：通过目录迁移把旧版本和当前版本物理分离。
- 优点：目录视觉上更清爽。
- 代价：会改变既有资产路径，破坏跨阶段引用稳定性，增加误移动和历史引用失效风险。
- 不选原因：用户已明确不希望移动文件；该方案也超出了“只解决阅读混乱”的边界。

### 方案 C：把所有非当前资产状态改为 `archived`
- 核心思路：归档时批量改写旧资产状态。
- 优点：状态上看似更统一。
- 代价：会混淆资产审批状态与阅读活跃性，可能破坏 `approved` 资产作为历史批准基线的语义。
- 不选原因：用户已明确要求保持 approved；该方案风险高且与审批纪律冲突。

## 关键取舍
- 正确性 / 安全性：归档只读，不改变设计、蓝图、交接内容或上游状态，降低越权风险。
- 可回退性：新增 manifest 是增量文件；若归档失败或不满意，可生成更高版本 manifest，不覆盖旧文件。
- 改动范围：需要更新多个 HILP 规则文件并新增 `references/archive.md`，但不触碰业务代码。
- 可维护性：将归档规则集中到独立参考文件，主入口和契约只保留必要索引和门槛。
- 未来扩展性：后续可增加更多阅读角色或压力测试样例，但当前设计不引入目录迁移和状态改写。

## 需要用户决定什么
- 是否存在：无。
- 是否会阻止继续：无阻断项。
- 问题描述：无必须人工裁决的问题；当前仅需要用户批准该设计资产。
- 可选项：批准推荐方案 / 要求修订方案。
- 建议：批准推荐方案，然后进入实施蓝图阶段。
- 默认路径：无。
- 用户是否已选择：未选择。
- 不得写成既定事实的内容：在用户明确批准前，不得把本设计视为已批准，也不得生成绑定性实施蓝图。
