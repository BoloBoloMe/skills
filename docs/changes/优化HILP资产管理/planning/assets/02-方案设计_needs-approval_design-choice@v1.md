# 方案设计与审批阶段

## 这个阶段要做什么

比较 HILP 资产管理优化方案，形成可审批的推荐设计，重点降低审核者查找当前待审资产的负担，同时保留版本审计链。

## 需求边界与事实基础

- 目标：让审核者不再从多个历史版本文件中人工查找当前待审文件。
- 范围：HILP 新产生规划资产的目录组织、当前入口、审核包、索引和版本状态管理规则。
- 非目标：不迁移旧目录中的历史资产；不在本阶段展开具体文件级修改蓝图；不改变“只有明确人工批准才能进入已批准状态”的审批纪律。
- 成功标准：
  - 审核入口唯一且稳定。
  - 历史版本可追溯。
  - 当前待审版本、已批准版本和历史修订版本能够被索引清晰区分。
  - 资产引用不因审批状态变化而频繁失效。
- 事实基础：现行规则把多个版本资产放在同一变更目录中，且文件名包含审批标记；审核不通过会产生新版本，导致审核者需要在多个文件中查找当前待审对象。
- 影响面：至少涉及资产落盘规则、审批状态表达、归档阅读索引、审核包生命周期和用户可见输出纪律。
- 核心未知项：无阻断设计比较的未知项；具体实现文件和规则文本改动留到实施蓝图阶段确定。

## 推荐方案

### 名称

不可变资产库 + 当前入口 + 审核包 + manifest 索引。

### 核心思路

在每个 HILP 变更目录下建立职责分离的资产结构：

```text
docs/hilp/<变更概述>/
  manifest.md
  _current/
    当前待审.md
    当前已批准.md
  review-pack/
    <stage-artifact>@vN-review.md
  assets/
    <stage-artifact>@vN.md
```

- `assets/`：保存正式阶段资产版本，采用追加式版本库模型。进入审核或被下游引用后的版本原则上不原地修改；内容修订必须产生新版本。
- `_current/`：保存面向人的稳定入口。审核者优先打开 `_current/当前待审.md`，不需要在历史版本中搜索。
- `review-pack/`：保存每一次审核尝试的审核包。审核结束后标记关闭并保留，作为审计记录。
- `manifest.md`：保存全局索引，记录每个资产版本的当前状态、是否当前待审、是否当前有效、关闭原因和引用路径。

### 为什么推荐

该方案把“审计资产”和“审核入口”分离：历史版本继续完整保留，但审核者只面对当前入口和当前审核包。它同时解决查找负担、引用稳定性和状态追踪问题，并为后续自动归档或重审提供统一索引基础。

## 备选方案

### 方案 A：按状态拆目录

- 核心思路：把待审、历史、已批准资产分别放入 `current/`、`history/`、`approved/`。
- 优点：目录直观，当前待审资产容易找到。
- 代价：资产随状态移动，可能导致已落盘引用失效或需要同步重写引用。
- 不选原因：HILP 依赖带版本资产引用；频繁移动文件会放大引用维护成本。

### 方案 B：只新增审核包，不调整资产库

- 核心思路：保留现有平铺目录，仅在每次待审时生成 `review-pack`。
- 优点：改动较小，兼容现有目录习惯。
- 代价：历史资产仍混在主目录，审核者若绕过审核包仍会看到混乱目录；状态追踪仍依赖文件名和人工判断。
- 不选原因：只能缓解审核入口问题，不能系统解决版本状态和引用稳定性问题。

### 方案 C：只维护 manifest 索引

- 核心思路：保留现有文件结构，通过 `manifest.md` 标明当前待审和当前有效版本。
- 优点：实现成本较低，审计视图清楚。
- 代价：审核者仍需要从 manifest 跳转到多个文件，缺少专门的审核上下文和审批提示。
- 不选原因：改善定位，但审核体验弱于“当前入口 + 审核包”的组合。

## 关键取舍

- 正确性 / 安全性：推荐方案保留所有版本和审核尝试记录，不通过删除或覆盖历史来换取目录简洁。
- 可回退性：历史资产和已关闭审核包保留，可通过 manifest 回溯任意版本的状态变化和审核意见。
- 改动范围：比单纯新增审核包更大，因为需要调整资产落盘规则和索引规则；但能一次性消除审核入口混乱和引用不稳两个问题。
- 可维护性：通过目录职责分离降低人工查找成本；代价是每次资产状态变化必须同步更新 manifest 和 `_current`。
- 未来扩展性：manifest 可作为后续自动归档、重审入口、审计报告和工具化展示的统一数据来源。

## 需要用户决定什么

- 是否存在：建议人工裁决。
- 是否会阻止继续：无阻断项。
- 问题描述：是否接受“资产文件名不再承载审批状态，审批状态转移到 manifest / review-pack / 当前入口表达”的规则方向。
- 可选项：
  - 选项 1：采纳稳定资产文件名，状态由 manifest 记录。
  - 选项 2：继续保留状态型文件名，但通过 manifest 覆盖真实状态。
- 建议：选择选项 1。这样资产路径更稳定，审批状态变化不需要改名或复制同内容文件。
- 默认路径：选择选项 1，并在过渡规则中声明旧资产不迁移，新资产适用新命名纪律。
- 用户是否已选择：已选择。用户已赞同推荐设计方向。
- 不得写成既定事实的内容：在用户明确批准当前资产版本前，不得把该设计作为已批准方案交给实施蓝图阶段。

## 关键规则草案

### assets 规则

- `assets/` 是正式资产版本库，不是审核入口。
- 内容性修订必须创建新版本。
- 进入审核或被下游引用后的资产版本原则上冻结内容。
- 单纯状态变化不改写资产正文；由 `manifest.md`、审核包关闭记录和 `_current` 入口表达。
- 旧资产不迁移；新资产采用新目录结构和新索引规则。

### review-pack 规则

- 每次资产进入待审批状态时生成一个审核包。
- 审核包包含当前待审资产链接、上一版本链接、变更摘要、上次不通过原因、本次需要审核的问题和明确审批模板。
- 审核完成后，审核包进入关闭状态并保留。
- 审核不通过时，旧审核包保留为关闭记录，新修订产生新资产版本和新审核包。

### _current 规则

- `_current/当前待审.md` 永远指向当前唯一待审审核包；无待审项时写明当前无待审资产。
- `_current/当前已批准.md` 指向当前有效的已批准资产集合。
- `_current` 中的文件是面向人的入口，可随状态变化更新；不作为不可变版本资产。

### manifest 规则

- `manifest.md` 是当前变更目录的资产索引。
- 每个资产版本至少记录：资产 ID、阶段、版本、状态、路径、是否当前待审、是否当前有效、来源版本、关闭原因和相关审核包。
- manifest 是状态查询的权威入口；资产文件名只表达阶段、类型和版本。
