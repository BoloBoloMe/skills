# 方向侦查 02: present 展示与容器 web 服务的无感访问形态

性质: 只调研分析, 不实施. 访问位置两档: 本机 = 宿主 A 有 Linux Wayland 桌面, 人就在宿主前; 远程 = 人在局域网设备 B (Linux Wayland 桌面). 场景两档: A = present 展示 HTML, B = 容器内 dev server 类 web 服务.

## 结论 (先行)

1. **现状有一处硬缺口**: swt create 只发布 22 (0.0.0.0, 动态宿主端口) 和 6080 (宿主回环, D040); 镜像 `EXPOSE 22 8800 6080` 里的 8800 (present 专用, image-prep.py 注释明言 "诞生时 -p <容器端口> 动态分配") **从未被 swt.py 发布**. present 容器分支文档的主路径 ("host 侧 `podman port` 发现映射端口组装 URL") 在真实 swt 容器里走不通 — M10 轮 handoff 已两次记录此 known gap ("present 8800 仅容器 IP 可达"). 而 pasta 下容器 IP 从 host 直连本就不可达 (M08 实测 000), 所以缺口的实质是: **A 场景今天没有任何文档化的可用外部路径**.
2. **今天唯一物理可用的形** (未文档化): ssh -L 隧道穿容器 sshd. ssh 入口落在容器内, 隧道目标 `127.0.0.1:<端口>` 在容器侧解析, 所以哪怕服务只绑容器回环也能到达, 不依赖任何发布. 代价是全手工: 人拼两条命令.
3. **推荐主形态 (A/B 共形)**: 钉死容器内端口 8800, birth 补 `-p 8800` (0.0.0.0 动态宿主端口, 修缺口), STATE 登记宿主端口, 交付包直接给本机/局域网两条现成 URL, 本机场景 host 侧顺手 `xdg-open`. A 完全落在 ADR 0005 已接受的 "网段可读" 取舍内, 无新增原则. **B 采纳同一形是本侦查对挂起议题的回答: 端口直达可行且最简, 但它把 ADR 0005 的取舍从 "agent 生成的静态页" 扩到 "无认证的应用服务", 安全面实质扩大, 须用户明示拍板** — 这是本次要带到讨论桌上的核心决策点.
4. **保守备选**: 回环发布 (`-p 127.0.0.1::8800`, 与 D040 完全同构) 或不发布, 远程一律走 ssh -L 隧道 (交付包给模板, 与 noVNC 隧道并列). LAN 零新增暴露, 门槛 = 容器 ssh 凭据.
5. **传话通道是加速器不是底座**: 它能自动化 "跨会话报信/建隧道/在正确的屏幕上开浏览器", 但不解决网络可达性 (B 的浏览器终究要有一条到容器的通路). A/B 方案应设计成不依赖它也成立.
6. **不推荐**: pasta 自动端口转发 (`-t auto`, 侵蚀 D040 回环-only 与白名单显式心智, 见选项表); 固定宿主端口 (`-p 8800:8800`, 多容器并存必撞, 违 D040 动态回落先例).

## 机制盘点 (端口/网络事实底座)

以下为本机 (podman 5.7.0, rootless + pasta) 核实的事实, 来源标注:

- **create 发布面**: `swt.py` 创建容器只带 `-p 22` (0.0.0.0, 宿主端口动态) 与 `-p 127.0.0.1:6080:6080` (宿主 6080 被占回落 `127.0.0.1::6080` 动态, D040); 无第三个发布 (swt.py L1505-1509, L1532; ops.md 容器命令收拢同). 8800 仅是镜像 EXPOSE 元数据, **发布与 EXPOSE 无关**, 不发布就不可达.
- **pasta 默认关自动转发**: podman 明确向 pasta 传 `-t none -u none -T none -U none`, 即关闭 pasta 固有的 "按命名空间内实际绑定的端口自动转发" (man podman-run, 本机 5.7.0). 容器内随手绑的端口 host 侧不可达; 打开自动转发需在 create 时改 `--network pasta:...`, 是一次性容器级决定.
- **容器 IP 直连不成立**: pasta 把 host 地址复制进容器, host 访问该地址走本机回环, 进不了容器 (M08 实测 `192.168.216.53:53417` → 000). "绕过发布直达容器 IP" 在 pasta 下是死路.
- **发布端口的双地址可达**: `-p` 发布在 0.0.0.0 时, 宿主回环与 LAN IP 同端口均可达 (M08 实测 127.0.0.1 与 192.168.31.252 双 200). 所以 "端口直达" 对本机/远程两档是同一个宿主端口, 无需两套.
- **白名单防火墙只管出向**: `inet swt` 表按容器源地址限定容器流出; 设备 B → 宿主发布端口 → 容器是入向, 不占白名单条目 (与 waypipe ssh 入向同一逻辑, 调研报告 §6).
- **容器内端口占用**: 22 = sshd (pid 1), 6080 = websockify (显示栈常驻). present 容器分支 "必须复用 create 时已映射端口" 的规则下, 当前两端口皆有主 — 印证缺口 1, 也说明新端口必须走 "birth 补发布" 而非 "复用旧端口".
- **ssh -L 穿容器 sshd 的特殊能力**: 隧道目标在 sshd 所在网络 (容器内) 解析, 服务绑容器回环也能到达; 对绑址不挑 (0.0.0.0 或 127.0.0.1 均可). 这是与发布路径的关键不对称: 发布只达绑 0.0.0.0 的服务, 隧道两者皆达. (机制推断成立, 该精确路径未实测, 见遗留疑问.)
- **web_server.py 相关约束**: 端口参数由调用方指定 (skill 缺省 49152-65534 随机, 容器分支覆写为钉死端口); bind 必须 0.0.0.0 (容器分支); 控制面 `/__control__/*` 仅回环源; 空闲 24h 自退 (env 可覆写); 运行时状态随容器生灭. M08 实测: 容器内换端口重启即失联, add-dir/复用/stop 全可用, 随容器 rm 自动回收.

## 现状链路四格 (用户手工步骤, 精确到命令)

容器侧步骤四格相同, 差异在 host/设备侧, 先列公共前段:

- 容器内 agent (A): 生成 HTML → `uv run python ~/.agents/skills/present/scripts/web_server.py start 8800 <页面目录> --bind 0.0.0.0` → 在 chat 报告容器端口与挂载目录.
- 容器内 agent (B): 起服务, 如 `npm run dev -- --port 8800 --host 0.0.0.0` (绑址/端口无约定, 各项目自便).

### A x 本机 (present, 人在宿主桌面前)

1. 人把容器 chat 里的端口号转给 host 侧会话 (或自己开终端) — 跨会话人工报信.
2. `podman port <容器名> 8800` — **现状输出为空 (无映射), 链在此断** (硬缺口).
3. (若映射存在) host 侧组装 `http://127.0.0.1:<宿主端口>/` 交给人, 人点击.
4. 无任何自动化打开; 浏览器完全人手开.

退化可用形 (未文档化): `ssh -p <ssh宿主端口> -L 8800:127.0.0.1:8800 bolo@127.0.0.1` 然后开 `http://127.0.0.1:8800/` — 为了看个静态页敲一条双变量隧道命令.

### A x 远程 (present, 人在设备 B)

1. 同上第 1 步的跨会话报信.
2. 同上第 2 步, 链断 (缺口同).
3. (退化形) B 上拼隧道: `ssh -p <ssh宿主端口> -L <B本机空闲端口>:127.0.0.1:8800 bolo@<host-LAN-IP>`, 浏览器开 `http://127.0.0.1:<B本机空闲端口>/`. 交付包里没有这条模板 (只有 noVNC 的 6080 版), 变量全靠人记.
4. noVNC 兜底路径反而更顺 (交付包有现成隧道命令): `ssh -p <ssh宿主端口> -L 6080:127.0.0.1:<vnc宿主端口> bolo@<host-LAN-IP>` → 开 `http://127.0.0.1:6080/vnc.html?resize=scale` — 但那是 "隔两层的虚拟桌面", 不是 present 的 URL 交付.

### B x 本机 (dev server, 人在宿主桌面前)

1. 现状无约定形态: 容器内起的服务对外**不可达** (无发布 + 容器 IP 不可达 + pasta 自动转发被 podman 关闭).
2. agent 在容器内自查 (curl) 可以, 人看页面没有任何路径.
3. 退化形: 同 A x 本机的隧道命令, 目标换服务端口; 服务绑 127.0.0.1 也能通 (隧道对绑址不挑).
4. 调研报告遗留的挂起议题正是这一格: 端口直达 vs 其他, 本报告下文给排序, 最终由用户拍板.

### B x 远程 (dev server, 人在设备 B)

1. 同 B x 本机, 外加远程位置: 退化形隧道命令再加 LAN IP 变量.
2. 若未来采纳 "发布 0.0.0.0": B 浏览器直开 `http://<host-LAN-IP>:<宿主端口>/`, 免隧道 — 这是直达形对远程档的最大收益.
3. HMR/websocket 经隧道或直达均无碍 (普通 TCP 转发).

## A 与 B: 分治还是共形

**共形, 一个端口两用**: 8800 钉死为 "容器内对外 web 端口" — present 用它, dev server 也被约定到它 (vite/next/uvicorn 都可 `--port 8800`). 理由:

1. 发布是 create 时的一次性决定, 事后不可追加 (重建容器才变). 钉死一个端口让 birth 一次补齐, A/B 永不再碰 create.
2. 端口钉死后, "容器内 agent 在 chat 报端口" 变得多余 (端口是常识), host 侧 `podman port <容器> 8800` 可程序化, 跨会话报信这个最烦的手工步骤自然消失.
3. URL 形态统一: 人只需要记住 "容器页 = host 的 8800 映射端口", 本机/远程同一 URL.

**分治点只剩一处 — 暴露档位**: A 按 ADR 0005 直达 (0.0.0.0) 无新原则; B 直达是新取舍 (无认证应用服务 LAN 可见), 应作为决策点交用户: 接受则 A/B 完全共形 (推荐), 保守则 B 落 O2/O3 隧道形 (此时 A 可仍走直达, 两档并存但模板齐备). 另注意 B 直达的前提是 dev server 绑 0.0.0.0, 需在容器 agent 侧立约定 (很多 dev server 默认绑 127.0.0.1, 不约定则 "发布了也只在隧道下可达").

## 推荐排序与理由

1. **O1 + O9 + O5 (主形, A/B 共形)**: 一次 birth 修补 (`-p 8800`) 同时救活 A 的断链和 B 的挂起议题; 端口钉死消除跨会话报信; 交付包双 URL + STATE 登记消除组装; 本机 xdg-open 补最后一击. A 零新原则, B 一个明示拍板. 用户操作量四格里三格归零, 远程格 = 点一下 URL.
2. **O2/O3 (保守形与严格模式)**: 作为 "只给自己看" 的备选与 B 未拍板前的缺省兜底; 与 noVNC 隧道心智同构, 模板进交付包即成本极低. O3 额外是不依赖任何实施的物理兜底.
3. **O7 传话通道 (叠加加速器)**: 落地后把远程格的 "点 URL" 也省掉, 并顺带解决 "页面就绪事件推送". 设计上 A/B 不依赖它 — 通道难产不伤主形.
4. **O6 chromium 直通窗口 (可选增强)**: A x 本机且 D051 在场时体验最好 (原生窗口 + 状态回读都在), 但把 present 耦合进显示栈与 playwright 容器环境, 且远程档绑死 Linux Wayland; 立为主形之上的可选项, 不立为主路径.
5. **O4 / O8 (明确不推荐)**: O4 隐性扩大暴露面且破坏既有安全模型; O8 多容器必撞, 违自家先例.

## 遗留疑问

1. ssh -L 穿容器 sshd 到容器回环绑址的路径是机制推断, 未实测; 实施前用一次性容器验证 (含 HMR websocket).
2. browser_session (access-web browse 环境) 在容器内能否跑通 (O6 前提): display 层有 playwright chromium 但 uv sync 状态未验.
3. B 暴露档位的拍板: 直达 (共形) vs 隧道 (保守), 以及 dev server 绑 0.0.0.0 的约定写在容器 agent 母本还是 SKILL 层.
4. 8800 发布缺口修在 birth (swt.py create) 即可, 镜像层无动作 (EXPOSE 已有); 但 base/display 不动时旧项目镜像新建容器同样受益, 无级联重建 — 该判断待实施阶段确认.
5. 多容器并存时交付 URL 端口各不相同, 交付包呈现形态 (每容器一组?) 待定.
6. 传话通道落地后, "页面就绪" 事件的消息格式与设备侧执行器的命令白名单接口, 与并行侦查 (容器→设备传话通道) 对齐.
