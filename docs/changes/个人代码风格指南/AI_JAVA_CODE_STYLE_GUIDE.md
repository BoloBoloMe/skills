# AI Java 代码风格指南

## 定位

这份文档用于指导 AI 在 Java 项目中编写代码, 目标是写出接近我的个人代码风格的实现.

它不是格式化规范, 不是框架模板, 也不是洁净架构手册. 它优先回答: AI 在面对一个 Java 需求时, 应该如何选择边界, 抽象, 控制流, 数据模型, 错误处理和验证方式.

适用范围不限于某个仓库. 使用时必须先服从当前项目已有约束, 包括 `AGENTS.md`, README, Checkstyle, Spotless, ArchUnit, Maven/Gradle Java 版本, 框架约定和已有代码风格.

## 核心目标

写业务语义和运行时行为优先的实用型分层代码.

代码应做到:

1. 行为明确, 不实现推测需求.
2. 改动最小, 不顺手重构无关代码.
3. 边界可辨识, 但不追求架构形式完备.
4. 流程可定位, 失败可解释, 日志可排查.
5. 性能, 并发, 超时, 降级和资源释放在需要时属于设计内容.
6. 在项目 Java 版本允许范围内使用合适语法, 但基线至少兼容 JDK8.

## 优先级

遇到冲突时按以下顺序决策:

1. 用户本次明确要求.
2. 当前项目显式规范和构建约束.
3. 当前模块已有代码风格.
4. 本指南.
5. AI 自己的默认偏好.

不要为了执行本指南而破坏项目已有约束.

## 开始前流程

### 1. 确认行为已定

开始写代码前, 先确认需求来源清楚:

- 入口是什么.
- 输入, 输出和副作用是什么.
- 错误时应返回, 抛出, 记录, 降级还是隔离.
- 是否有事务, 幂等, 权限, 审计, 并发或性能边界.
- Java 版本是多少.

行为未定时, 先按最合理默认值推进. 只有缺失信息会导致错误实现时才停下来提问.

### 2. 读现有代码

至少读这些上下文:

- 同类入口代码, 例如 Controller, CLI, Listener, Job.
- 同类业务编排代码, 例如 Service, UseCase, Handler.
- 同类持久化或外部系统代码, 例如 Repository, DAO, Client, Gateway.
- 同类 DTO, Result, Config, Exception 和测试.

目标是复用项目已有命名, 返回结构, 异常语义和日志方式, 不是发明一套新风格.

### 3. 跑实现阶梯

按顺序选择第一个站得住的方案, 选中后停止加码:

1. 不写代码: 已有代码, 配置, 数据库约束或框架机制已经覆盖行为.
2. 用 JDK 标准库: 标准库能解决时不新增依赖.
3. 用平台原生能力: Spring, Jakarta, MyBatis, JPA, Bean Validation, 数据库约束等已有能力优先.
4. 用项目已装依赖: 已有依赖能解决时, 不新增同类库.
5. 写最小可工作代码: 只实现已确定行为.
6. 抽象或扩展框架: 只有真实变化点, 多实现, 跨边界隔离或测试 seam 明确存在时才做.

懒是少写无负担代码, 不是省略风险边界.

## 分层风格

按项目现有层次命名. 若项目没有明确约定, 默认按以下职责分配:

- Controller/Endpoint: 协议接入, 参数绑定, 简单校验, 委托 Service. 保持薄.
- Service/UseCase: 用例编排, 事务边界, 权限校验, 失败分类, 调用 Repository/Component/Client.
- Component/Domain Service: 业务算法, 策略执行, 计算, 状态转换, 可复用业务能力.
- Repository/DAO: 持久化查询和写入, 数据库条件构造, entity 和业务模型转换.
- Integration/Client/Gateway: 外部系统, HTTP/RPC/MQ/缓存/文件系统等基础设施.
- Model/DTO: 请求, 响应, 参数, 配置, 值对象, 运行上下文.

分层用于让职责可辨识, 不用于制造形式. 不要机械创建 `controller -> service interface -> service impl -> manager -> helper` 链条.

## 抽象规则

只在以下情况引入接口或抽象类:

- 已有两个或更多真实实现.
- 运行时需要按策略, 类型或配置选择实现.
- 需要隔离外部系统, 持久化或框架边界.
- 该边界已经稳定, 调用方收益明确.
- 测试需要 seam, 且无法用更小方式处理.

不要引入抽象的情况:

- 只有一个实现.
- 只是为了显得符合设计模式.
- 只是因为类有点长.
- 只是为了未来可能扩展.
- 只是为了把一段清楚代码移动到另一个名字下.

允许一个稳定模板集中编排复杂流程. 大类和长方法不是目标, 但也不是单独的罪. 只要流程按业务阶段清楚, 状态生命周期明确, 局部复杂度可读, 不必为了短而拆.

## 控制流

偏好线性叙事和 guard clause:

1. 校验输入和前置状态.
2. 不满足条件时提前返回或抛出明确异常.
3. 准备上下文和中间数据.
4. 执行业务核心逻辑.
5. 汇总结果, 记录 trace 或触发后续动作.

简单失败分支可以写成单行 `if (...) return ...;`, 前提是项目格式允许.

Stream 使用边界:

- 适合简单 map, filter, group, collect, anyMatch, allMatch.
- 不适合复杂状态机, 多处副作用, 热路径优化, 需要索引, 需要提前 break/continue 的流程.
- JDK8 项目不要使用 `Stream.toList()`, 用 `collect(Collectors.toList())`.

普通循环是正常工具. 不要为了函数式外观牺牲可读性, 性能或异常定位.

## 数据模型

### DTO 和参数对象

请求, 响应, 查询参数, 运行配置可以使用可变 DTO. 如果项目使用 Lombok, 可遵循项目已有注解习惯, 例如 `@Data` 和链式 setter. 如果项目不用 Lombok, 使用普通 JavaBean 或构造器即可.

DTO 设计要点:

- 字段名表达业务含义.
- 输入和输出分开, 不复用一个大对象混装所有场景.
- 参数对象可变没问题, 但不要跨线程共享可变 DTO.
- 默认值应是业务默认值, 不要用魔法值遮盖缺失输入.

### 值对象和内部 key

明确不可变语义时, 使用不可变值对象.

JDK8 基线写法:

- `final class`.
- `private final` 字段.
- 构造器完成校验.
- 必要时实现 `equals`, `hashCode`, `toString`.

JDK16+ 且项目允许时, 可以使用 `record` 表达值对象, 内部 key, 计算结果和局部载体.

不要把所有 DTO 都改成不可变. 可变 DTO 和不可变值对象可以并存, 关键是生命周期和边界清楚.

### 运行上下文

一次请求, 一次任务或一次批处理需要共享状态时, 可以建立明确的 Context 对象.

Context 可以承载:

- 输入.
- 输出.
- 请求内缓存.
- trace/耗时/执行记录.
- 回调 Future 或异步句柄.

Context 的约束:

- 生命周期必须明确.
- 不要作为全局变量长期保存.
- 并发写入时使用线程安全集合或明确同步.
- 不要把无关模块的临时数据都塞进去.

## Java 版本策略

默认按 JDK8 编写, 除非项目构建文件明确允许更高版本.

JDK8 可用基线:

- lambda, method reference, Stream.
- `Optional`, 但不要滥用为字段类型或参数类型.
- `CompletableFuture`.
- `java.time`.
- default method.
- try-with-resources.

JDK8 禁用高版本写法:

- `var`.
- `record`.
- sealed class/interface.
- switch expression.
- pattern matching.
- text block.
- `List.of`, `Map.of`, `Set.of`.
- `Optional.isEmpty`.
- `Stream.toList`.
- virtual thread.

高版本项目中可以使用新语法, 但只在它带来明确收益时使用:

- `record`: 小型不可变值对象.
- sealed type: 封闭类型族.
- switch expression: 简化枚举或封闭类型分派.
- `var`: 局部变量类型右侧已经非常明确时.
- virtual thread: IO 密集且项目运行时, 监控和线程模型允许时.

不要为了追新而批量改写旧代码. 不同模块可以因为兼容边界而使用不同语法.

## 错误处理

失败处理要分类, 不要只写 happy path.

优先区分:

- 输入错误: 参数缺失, 格式错误, 状态不允许.
- 业务失败: 规则不满足, 资源不存在, 冲突, 重复.
- 外部失败: 网络, 超时, 第三方错误, 限流.
- 系统失败: 数据库, 序列化, 线程中断, 未预期异常.

处理原则:

- 信任边界必须校验输入.
- 能在边界转成结构化结果的, 按项目已有 Result/Response 风格返回.
- 需要调用方感知的错误, 抛出或返回明确类型, 不吞掉.
- 局部任务失败不应拖垮无关任务时, 在单项, 单批次或单回调边界隔离.
- 批量操作是全有全无, 部分成功还是逐项失败, 必须由业务语义决定.
- 捕获 `InterruptedException` 时恢复中断状态, 除非项目已有明确封装.
- 不要 `catch (Exception e)` 后只打印日志继续运行, 除非这是刻意的隔离边界.

## 日志和可观测性

日志是运行模型的一部分, 不是事后装饰.

日志应说明:

- 发生了什么.
- 关键业务标识是什么.
- 失败类型是什么.
- 影响边界是什么.
- 必要的耗时, 批次, 数量, 策略或外部请求信息.

推荐格式:

```java
log.error("description`tenant={}`eventCode={}`status={}", tenant, eventCode, status, e);
```

约束:

- 变量放在消息末尾.
- 使用 `name={}` 形式.
- 多个变量用反引号分隔.
- 异常对象放在最后一个参数.
- 热路径 debug 日志先判断日志级别或确保构造成本很低.
- 不记录密钥, token, 密码, 完整身份证号等敏感信息.

日志语言跟随项目. 如果项目没有约定, 生产日志优先用英文短句, 业务注释可以用中文说明意图.

可观测性优先放在业务执行上下文中:

- traceId/requestId.
- 开始时间, 结束时间, cost.
- 条件结果, 命中结果, 降级结果.
- 外部调用状态.
- 异步任务 Future 或回调结果.

## 性能和并发

不要提前优化, 但一旦需求涉及并发, 缓存, 批量, IO 或热路径, 性能就是设计内容.

必须明确:

- CPU 密集还是 IO 密集.
- 串行, 并行还是异步.
- 最大并发数和队列上限.
- 超时和取消策略.
- 拒绝策略.
- 资源关闭方式.
- trace 上下文如何传播.
- 失败是否隔离.

JDK8 并发基线:

- `ExecutorService`.
- `CompletableFuture`.
- 有界线程池.
- try/finally 或生命周期组件关闭资源.
- `ConcurrentHashMap`, `Atomic*`, `CountDownLatch` 等标准工具.

高版本项目可使用 virtual thread, 但不要把它当作无上限并发. 外部系统, 数据库连接池, 限流器和内存仍然是边界.

缓存规则:

- 有明确 key.
- 有容量或过期策略.
- 明确一致性要求.
- 长 key 可考虑 hash, 但要理解碰撞和可排查性.
- 不用缓存掩盖错误或权限问题.

## API 设计

API 应让调用方直接表达业务意图.

可接受:

- 便利重载委托到完整重载.
- Builder 表达多可选参数.
- 静态工厂表达具名策略.
- 业务默认值.
- 单次调用覆盖默认配置.

避免:

- 过多等价入口.
- 为未来扩展暴露暂时无用的参数.
- 用 `Map<String, Object>` 替代稳定模型.
- 用布尔参数隐藏业务语义, 可改用枚举或具名方法.
- 为单调用方设计庞大公共 API.

JDK8 Builder 可以使用普通 fluent setter. 高版本允许 record + compact constructor, 但不要牺牲兼容性.

## 命名

命名优先表达业务角色, 可以接受较长名称.

常见后缀建议:

- `*Request`/`*Parameters`/`*Command`: 输入.
- `*Response`/`*Result`: 输出.
- `*Params`: 内部转换参数.
- `*Config`/`*Options`: 配置.
- `*Context`: 一次执行生命周期状态.
- `*Repository`/`*Dao`: 持久化.
- `*Client`/`*Gateway`/`*Api`: 外部系统.
- `*Template`/`*Executor`/`*Evaluator`: 稳定编排或执行能力.
- `*Impl`: 项目已有接口实现命名采用该后缀时使用.

避免空泛名称:

- `Manager`.
- `Helper`.
- `Util`.
- `Processor`.
- `Handler`.

这些名称不是禁用, 但必须有具体职责. 如果名字不能说明职责, 优先换成业务名.

不要为了英文更漂亮而大范围改历史命名. 除非用户要求或当前改动必须触碰该 API, 否则兼容性优先.

## 注释

注释解释意图, 业务语义, 执行阶段和取舍, 不复述代码.

适合注释的情况:

- 复杂业务规则.
- 非显然的并发或缓存选择.
- 失败隔离边界.
- 性能取舍.
- 兼容性限制.
- 临时简化及升级条件.

刻意简化可以使用类似注释:

```java
// lazy-code: single JVM lock is enough for current deployment. Replace with distributed lock when multiple writers appear.
```

不要给每个 getter, setter, 简单 if 或直观赋值写说明.

## 测试和自检

测试覆盖随风险增加.

最低要求:

- 非琐碎分支, 循环, 解析, 金钱/订单/审计/权限逻辑, 至少保留一个可运行验证.
- 修 bug 时优先补一个能失败的回归测试.
- 并发, 缓存, 超时, 降级和批量语义要验证边界.
- 只改文档或注释时不需要运行代码测试, 但要做文本检查.

测试风格:

- 优先行为命名, 例如 `missingUserId_shouldReturnBadRequest`.
- 单元测试可用 mock 或 fake 隔离外部依赖.
- 集成测试只在确实需要框架, 数据库, Redis, HTTP 或容器时使用.
- 不用 `System.out` 代替断言.
- JDK8 项目按项目已有 JUnit/Mockito/AssertJ 版本编写, 不引入新测试框架.

不要为了覆盖率数字写脆弱测试. 测试应证明业务边界和失败语义.

## 禁止倾向

AI 不要把代码写成以下风格:

- 洁净架构或洋葱架构原教旨.
- 单实现接口泛滥.
- 小类短方法洁癖.
- 全函数式或全面不可变洁癖.
- 设计模式展示代码.
- 只写 happy path 的样例代码.
- 全仓库格式化或 import 整理.
- 无请求的大重构.
- 为未来需求搭脚手架.
- 引入依赖只为少写几行普通代码.
- 用新 Java 语法批量改旧模块.
- 用日志替代错误处理.
- 用注释解释本可以删掉的复杂代码.

## 输出代码前自检

交付前逐项检查:

1. 是否只实现了已确定行为.
2. 是否停在了实现阶梯中最早可行台阶.
3. 是否遵守项目 Java 版本, 至少不破坏 JDK8 项目.
4. 是否没有新增无真实变化点的接口或抽象.
5. 是否没有无关格式化, 重命名或重构.
6. 是否输入边界, 错误分类和失败隔离足够明确.
7. 是否日志能帮助定位问题, 且没有泄露敏感信息.
8. 是否并发, 超时, 资源关闭和缓存边界被交代.
9. 是否命名表达业务语义.
10. 是否为非琐碎逻辑提供了合适验证.

## AI 回复方式

实现代码时, 代码和验证结果优先. 回复只写高信号内容:

- 改了什么.
- 为什么停在这个抽象层级.
- 运行了什么验证.
- 有什么剩余风险.

不要写长篇设计说明, 不要复述代码, 不要为每个显然选择辩护.
