# swt 信箱 mesh 化重设计 Product Spec

## 背景

swt 信箱是容器/设备间传话通道, 现有实现是 pi 专属扩展 + node 取信脚本 + host 常驻单体服务 (systemd 托管), 存在四个问题: (1) 同设备每个 pi 会话都自动后台取信, 多会话抢信重复处理; (2) 容器内 agent 可能是 codex/kimi, pi 扩展覆盖不到, 它们永远收不到回信; (3) 服务端 systemd 部署侵入性强; (4) 投递语义在断网时会静默丢信. 本变更把全部能力重构为一个纯标准库 python 脚本, 拓扑改为信箱 mesh 全互联, 信件改全内存. 提出方与受益者: 用户 (唯一利益方), 所有 agent 会话 (pi/codex/kimi 跨平台统一取发信).

## 目标

- G-001: 信箱全部能力 (取信/发信/配置/状态/服务端) 合一为纯 stdlib python 脚本, 任何能跑命令的 agent 会话 (pi/codex/kimi/裸终端) 均可用
- G-002: 取信会话由用户显式指定 — 谁调脚本谁取信, 未调用的会话零后台活动
- G-003: 任意 agent (设备/容器/host) 可经信箱与其他任意 agent 双向通信
- G-004: 消息投递不因断网/取信方崩溃静默丢失 (租约重投, 内存模型下信箱重启除外); 服务端有并发保护
- G-005: 旧 pi 扩展/node 取信脚本/触发文件机制退役, 配置自动迁移新路径
- G-006: 信箱 mesh 全互联路由 — 每台设备跑本机信箱 (serve 手动启动), agent 只连本机信箱, 跨设备信经邻居洪泛转发, 无中心单点; LLM 中转每台跑容器的机器各一

## 非目标

- NG-001: 不做取信会话唯一性强制 (锁/抢占), 多会话散落自担. (理由: 用户哲学宁要简单不要守护机制)
- NG-002: 不做消息类型按发件方身份限制, exec 安全全靠服务端指令集白名单兜底. (理由: 内容级防线比身份级更精确)
- NG-003: 不做设备发信与取信的密钥分离. (理由: 设备都是用户自己的, 威胁模型内已持完整凭证)
- NG-004: 不做自动首启 (提示词不写死取信循环). (理由: 设备全局指令跨项目共享, 写死会抢取信)
- NG-005: 不追溯: 存活容器重建才取得新机制; 运行中的旧会话重启后新机制才生效. (理由: 既有纪律)
- NG-006: 容器→设备方向 4 类型协议语义不变 (仅投递层加租约). (理由: 既有行为保持)
- NG-007: 不做任何开机自启/守护机制. (理由: 用户认为侵入性强)
- NG-008: 不保证信箱进程重启不丢排队信 (全内存模型, D008); 发信方需自行重发; 凭证与配置持久化不受影响. (理由: 用户选择即时通信语义)
- NG-009: 不做信箱间路由的持久化存储 — 邻居不可达时待转发信只在内存暂存. (理由: 同 NG-008)

## 业务规则

- BR-001: 一条信同一时刻至多租给一个取信方 (租约独占). (领域)
- BR-002: 来信正文按不可信输入处理, 取信脚本输出的处理指引中声明. (领域)
- BR-003: 路由目标为 session.id, 容器 session.id 含一次性随机后缀, 终结即从 sessions 池注销. (领域)
- BR-004: 洪泛转发排除来源邻居, 凭 seen-id 防循环. (领域)
- BR-005 (审计): 空闲等待不产生 LLM 调用.
- BR-006 (审计): 密钥不走命令行参数, status 只显前 8 位.
- BR-007 (审计): 脚本零第三方依赖.
- BR-008 (审计): 不提供 systemd 单元或任何自启机制, 服务仅经 serve 子命令手动前台启动.
- BR-009 (审计): 服务端 SQLite 只存凭证与配置, 不存信件.
