> 盘问日期: 2026-09-17 ~ 2026-09-18. 多轮盘问 (含反方攻击与两次方案大转向: pi 扩展命令 → python 脚本 → mesh 路由), 本账本记录最终收敛的全部有效决策; 中途被推翻的方案在对应决策的 "已排除候选" 中保留.

### D001 信箱全部能力合一为纯 stdlib python 脚本
- 状态: 当前有效
- 约束性: 必须遵守
- 内容: 取信/发信/配置/状态/服务端全部能力并入一个纯标准库 python 脚本 `swt-mailbox.py`, 放 skill 的 scripts/ 目录, 随 skill 库自动到位设备 (sync-to-pi) 和容器 (只读挂载). 缺省动作 = 取信 (阻塞长轮询, 小故障内部自动重试, 有消息才返回); 子命令: send (发信) / config (配置管理) / status (状态) / serve (启动服务端). 不依赖 pi 或任何特定 agent — 任何能跑命令的 agent 会话 (pi/codex/kimi/裸终端) 均可用. 理由: (1) 容器内 agent 不一定时 pi, 扩展方案只覆盖 pi, codex/kimi 会话永远收不到回信; (2) python 脚本跨 agent 跨平台; (3) 用户不喜欢 pi 绑定. 已排除候选: (a) pi 扩展命令 /swt-relay + triggerTurn 自动唤醒 — 被脚本方案整体取代 (用户提出, 经反方攻击后确认方向); (b) 发信做成 pi 注册工具 — 用户拒绝 pi 绑定; (c) 取信/发信两个脚本 — 合并为一个, 凭证探测/配置读写/签名代码只写一份.

### D005 Session 统一身份模型
- 状态: 当前有效
- 约束性: 必须遵守
- 内容: 从信箱取信和发信的行为主体统一定义为 Session 类, 一个 Session 实例对应一个 agent 会话 (容器内 agent session / host agent session / 设备 agent session). Session 是逻辑身份而非进程 — "yoga-host" 是一个 session, 不管后面开了几个 pi 进程. 每个 Session 有: id 字段 (字符串, 人类可读, 有意义), 密钥对 (签名+验签, 注册时信箱发放), 允许的消息类型. Letter 的发件人和收件人填 session.id, 信箱根据 session.id 找到收件人. Mailbox 维护 sessions 池: 所有向信箱注册的会话, 通过 session.id 查找. 此决策统一了现有的三个身份概念 (设备名/容器 key/容器实例 id). session.id 命名: 容器 = `<容器名>-<8位hex随机>` (一次性, 防同名容器错投), host = `<hostname>-host`, 纯设备 = `<hostname>`. 理由: 三类通信端点权利对等 (都能投能取), 统一消除角色分支逻辑.
- 依赖事实: F001
- 预计影响: swt-mailbox.py (Session 类), swt.py birth (session 注册)
- 实际影响: 待实现后补记

### D006 消息类型不按发件方身份限制
- 状态: 当前有效
- 约束性: 必须遵守
- 内容: 不按 session 身份 (容器/host/设备) 限制可发的消息类型. 所有 session 均可发 4 类型 (notify/open_url/exec/request), 安全防线是服务端指令集白名单: exec 类型信在任何信箱都过指令集校验, 不在白名单内自动降级为 request 走收件侧权限流程. 理由: 白名单是内容级防线, 比身份级更精确; 注册时声明 allow_types 增加了配置复杂度. 已排除候选: 注册时声明 allow_types, 自动注册的本机 session 限 notify+request — 用户选择不按身份限制.
- 依赖事实: F001
- 预计影响: swt-mailbox.py 服务端
- 实际影响: 待实现后补记

### D007 Mailbox mesh 全互联路由
- 状态: 当前有效
- 约束性: 必须遵守
- 内容: 内网中所有 Mailbox 实例彼此是 Neighbor (邻居), 每个 Mailbox 有 neighbors 字段记录邻居连接 (地址+端口+机器级共享密钥). Mailbox 不在程序上标识自己是 "内网总信箱" 还是 "本机小信箱" — 所有信箱对象地位平等, 差异只在邻居表配置. 信件路由规则: 收到发信请求 → 根据信件上的收件人 session.id 从本机 sessions 池查找 → 找到则排队等取 → 没找到则将信件转发给每个邻居 (排除来源邻居, 凭 seen-id 防循环). 洪泛转发在 3-5 台机器的内网规模下流量可忽略. 中心单点消失: 任何一台信箱关机, 其余信箱间通信不受影响. 邻居不可达时待转发信在内存暂存, 邻居恢复后自动重发. 理由: (1) agent 只需连本机信箱, 配置极简; (2) birth 全在本机信箱完成, 无跨机 ssh; (3) 去中心化, 无单点; (4) 用户以面向对象思路提出, 程序结构清晰. 已排除候选: (a) hub-spoke 拓扑 (Workstation 总信箱居中, 小信箱转发+拉取) — 被 mesh 取代, 中心单点且拓扑知识集中; (b) 两层直连 (agent 双端点连本机+总信箱) — agent 要配两个地址, birth 要跨机申领; (c) 最初单信箱 (所有设备直连) — Yoga 离网时本机通信断.
- 依赖事实: F002, F003
- 预计影响: swt-mailbox.py (Mailbox/Neighbor 类, 路由逻辑)
- 实际影响: 待实现后补记

### D008 信件全内存不持久化
- 状态: 当前有效
- 约束性: 必须遵守
- 内容: 信件 (排队中的消息) 只存内存, 不写 SQLite 或任何持久化存储. 信箱进程重启 = 内存中排队信全部丢失. 发信方需自行重发. 凭证 (session 密钥/邻居密钥) 与配置照常持久化, 重启不丢. 租约机制仍在内存中运作: 投出超时未回执的信收回内存队列重投, 防投递层 (断网/取信方崩溃) 丢信; 信箱重启是独立的丢信窗口, 不在保障范围. seen-id (防洪泛循环/防重投重复) 也在内存, 重启后短暂可能出现重复转发, 由取信脚本侧的已见 id 去重兜底. 理由: 用户明确选择 — 信件是即时通信, 过期作废; 去掉消息持久化 massively 简化实现. 已排除候选: 只有跨信箱转发队列不持久化, 本地排队持久化 (SQLite) — 用户选择全内存.
- 依赖事实: F001
- 预计影响: swt-mailbox.py (无消息表), 推翻 M01 D001 的 "消息存 host SQLite, 容器删除不丢信" 卖点
- 实际影响: 待实现后补记
- 需要调整: docs/changes/swt-cross-host-access/milestone-01/DECISIONS.md D001 的持久化语义 (标记待修订)

### D009 租约投递机制
- 状态: 当前有效
- 约束性: 必须遵守
- 内容: 服务端把信租给取信方并计时 (缺省 30 分钟, 服务端可配), 限时内没回执自动收回内存队列重投. 断网/取信方崩溃/工具输出丢失只是 "信晚点到", 不静默丢失 (在信箱进程不重启的前提下). 重投去重: 取信脚本按消息 id 记最近 100 条已见, 重复取到的信自动回执不呈现给 LLM. 理由: 修反方攻击确认的静默丢信漏洞 (服务端投出即标 delivered, 响应丢失则信卡死无恢复路径); 租约是消息系统标准件.
- 依赖事实: F004
- 预计影响: swt-mailbox.py 服务端投递逻辑
- 实际影响: 待实现后补记

### D010 serve 手动前台启动, 无自启
- 状态: 当前有效
- 约束性: 必须遵守
- 内容: 服务端由 `swt-mailbox.py serve` 子命令前台启动, 跑在终端里, 关终端即停. 不提供 systemd 单元, 不做开机自启, 不做守护. 每台设备 (含纯设备) 都需 serve 运行才有信箱能力; 未运行时取信脚本安静等待, serve 启动后自动恢复. 跑容器的机器 serve 同时启动信箱 + LLM 中转; 纯设备只启动信箱. 理由: 用户认为 systemd user unit + linger 侵入性太强. 代价 (用户已接受): 主机重启后必须有人先跑 serve, 否则信箱与 LLM 中转全断.
- 依赖事实: F001
- 预计影响: swt-mailbox.py serve 子命令, 删除 scripts/swt-base-server.service
- 实际影响: 待实现后补记
