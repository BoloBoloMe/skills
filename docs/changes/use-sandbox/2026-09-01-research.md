## 1. 需求定义

**一句话**: 构建新 skill `use-sandbox` — 给 agent 一个容器化工作试验场: 容器内 clone 仓库, 容器里干活, 产物经 git 回流; host 不落盘, 无重复下载, 与真实环境硬隔离.

**设计哲学 (本阶段定型)**: 硬约束交给环境. agent 在沙盒内可以肆意驰骋, 容器内的 pi 取消所有拦截门禁; 一切 "不能做的事" 由容器外环境在必经之路上强制执行.

**隔离的边界**: 沙盒隔离文件系统, 但网络不天然隔离. 需求最低覆盖:

- IP 黑名单: 特定 IP 禁止访问 (如特定环境的数据库/redis)
- git 分支写门禁: agent 只能对一个分支做写操作, 读其他分支不受限; 门禁必须是 agent 用任何方式绕不开的硬约束, 不依赖 pi 钩子 (容器内钩子属 agent 可及范围, 天然可绕)

**演进脉络** (需求如何走到今天):

1. 起点: 给 pi subagent 工具集成容器能力, 调研 sandcastle → 判定不科学, 放弃
2. 转向 use-worktree 容器选项 → 用户选路线 B "真·容器内 clone" (更干净)
3. 补齐使用形态: ssh 入容器, 全 skill 库兼容审查, 展示链 (present web_server) 与登录墙 (Xvfb/noVNC) 闭环 → 设计 100%
4. 本阶段: sandcastle 深度研究 (找参照系) + 硬约束实测 (网络门禁/git 门禁) → 本文

## 2. sandcastle 调研结论 (参照系)

对象: @ai-hero/sandcastle 0.12.0 (mattpocock), TS 库, 容器沙箱内编排 AI coding agent. 完整报告: `2026-08-31-sandcastle-design.html` (同目录) 与 /tmp/report-sandcastle-design.md (易失).

**怎么操作容器**: 拼 CLI 命令起子进程 (child_process → podman/docker 二进制), 零容器 API; 云端 provider (vercel/daytona) 反走 SDK. 核心抽象 SandboxProvider = tagged union: bind-mount / isolated / none 三形态 + handle 契约 (exec 强制逐行流式 onLine, stdin 规避 128KB 参数上限, copyIn/Out, close). 长驻容器 = `podman run -d --entrypoint sleep infinity`, 动作全经 `podman exec` 注入; `--userns=keep-id` 对齐宿主 UID; 清理双保险 (handle.close + shutdownRegistry 退出钩子). 本地 provider 无任何端口映射.

**镜像策略**: 不用现成也不随包发布 — init 时按所选 agent 生成 Dockerfile 写入用户 `.sandcastle/`, 本地 build. `FROM node:22-bookworm` + apt (git/curl/jq) + build-arg 对齐宿主 UID/GID + agent CLI + `ENTRYPOINT sleep infinity`. 镜像名 `sandcastle:<repo-dir>`, 运行前 `image inspect` 预检. 理由: UID 因机器而异, agent 选择是用户决策, Dockerfile 是生成物而非制品. 未知点: 云端 isolated 形态下 agent CLI 如何就位, 代码无答案.

**模块设计**: 四层, 依赖自上而下 — L1 编排 (run/interactive/createSandbox/createWorktree/cli), L2 沙箱生命周期 (SandboxFactory tag 分发, acquireUseRelease 事务, syncIn=git bundle 进 / syncOut=format-patch→git am 出), L3 agent 适配 (AgentProvider 契约 + 6 实现, SessionStore 跨界搬运会话 JSONL), L4 基础设施 (EnvResolver/errors/shutdownRegistry/boundedTail/Prompt*). 两条贯穿事实: 外部纯 Promise 内部 Effect-ts (桥在 SandboxFactory); 契约前置 (纯类型文件定义扩展点, 新 provider 200-500 行即可接入, ADR 编号存档).

**对 use-sandbox 的印证与借鉴**:

- 印证: "拼 CLI + sleep infinity 长驻容器" 足以支撑严肃沙箱编排 — 这正是我们方案的地基
- 可借鉴: git bundle 进仓 (免网络, 已列备选), image inspect 预检, --userns=keep-id, shutdownRegistry 思路
- 它没有的恰是我们的增量: ssh 登录, 端口映射 (展示链), 浏览器登录墙 — 不算重复造轮子

## 3. 定型方案骨架 (设计侧, 未落地)

**fat 镜像** (build 一次, 秒级启动): ubuntu base + git + jdk + maven + uv/python + node + pi CLI + playwright/chromium (--with-deps) + openssh-server + authorized_keys + Xvfb/x11vnc/novnc/websockify + fonts-noto-cjk. 分层: 稳定在前 (jdk/maven), 常变在后.

**运行时**:

```bash
podman run -d --shm-size=1g \
  -p 2222:22 \                    # ssh (rootless 高位端口)
  -p 8800:8800 \                  # HTML 展示 (present web_server)
  -p 6080:6080 \                  # noVNC (登录墙人工操作)
  -v ~/.m2:/home/agent/.m2 \      # Maven 缓存复用 (同策略 ~/.gradle 等)
  -v <host-repo>:/mnt/repo:ro \   # 仓库只读挂载 → 容器内本地 clone → remote 指向 gate (见 §4)
  -v ~/.pi/agent:~/.pi/agent:ro \ # pi auth/settings
  -v sandbox-profile:/tmp/access-web \  # 浏览器 profile 持久化
  <image>
```

**工作流**:

- 仓库: 只读挂载 + 本地 clone (备选 git bundle); origin 指向 gate (§4), 不直连真远端
- 展示链: present 的 web_server.py `start <port> <root> --bind 0.0.0.0`, add-dir 动态挂目录; host 浏览器开对应端口; present SKILL.md 需加容器分支 (web_server.py 已齐备未接线; 其 stop/add-dir/复用挂载 = ISSUE-02/04 未实现, 已在另一会话跟踪)
- 登录墙: `Xvfb :99 & x11vnc -display :99 & websockify 6080 localhost:5900` + `DISPLAY=:99 BROWSER_HEADED=true` → host 浏览器 :6080 人工操作, 登录态落 profile volume, 之后回 headless; access-web 代码零改动
- 展示链覆盖: present / explain-diff / probe / improve-codebase-architecture / teach 跟随 present 容器分支

## 4. 硬约束调研 (本阶段核心)

### 4.1 网络约束: 白名单可达硬约束

实测环境: rootless podman 5.7, netavark, 默认 pasta. 证据: /tmp/report-podman-net-hardening.md (易失, 结论已沉淀于此).

- **pasta 是纯 NAT, 无任何过滤能力** — man 文档无 filter/deny/block, 此路不通
- **最优注入点 = 桥 netns (rootless-netns) 的 netavark 表**: 实测 `nft insert ... ip saddr <容器IP> ip daddr 1.1.1.1 drop` 对**容器内 root 也拦截**; agent 因 userns + netns 双重边界物理不可达该层 — 这是最硬的一档
- 容器内 iptables 注入也可行 (非 root agent 删不掉), 但容器内 root 可动, 弱一档, 作备选
- **绕开向量实测全灭**: sudo/su 需口令; `unshare -Urn` seccomp 放行但新 netns 仅 lo DOWN, 出不了网; `nsenter -t 1 -n` permission denied; 无有效 caps; setuid 二进制均需口令
- **IPv6**: 默认无全局地址/路由, 天然不通; 补 `ip6tables -A OUTPUT -j DROP` 兜底
- **弱点与对策**: 规则不持久 (容器 stop/start 后 netns 重建, 规则全失) + 容器 IP 会被 DHCP 重分配 (.5→.6 实测) → 编排侧每次启动后重注入 + `podman network create --subnet` + `run --ip` 静态 IP
- `--network=none` 彻底断网 (仅 lo), 作最强档位备选

**形态建议**: 白名单优于黑名单 — 门禁架构下容器只需到 gate 一个端点, 默认拒 + 单放行比维护黑名单清单更强且更简单 (待拍板, §7).

### 4.2 git 分支写门禁: 网关仓库方案成立

原理链 (git 原生能力, 零扩展): origin 只是 URL; git 世界无服务器/客户端之分, 任何仓库天生可被网络对端当 origin; push = 发送侧 send-pack → 接收侧 receive-pack (同一 git 二进制); **pre-receive 钩子是 receive-pack 的内置行为**, 在更新 refs 前执行, 拒绝则一个字节不落地. 钩子运行在 push 的**网络对端** — agent 一切持久化写必经该端点, 与 pi 钩子 (agent 体内, 可绕) 有本质区别. GitHub protected branches 是同一机制的外包版.

**拓扑** (拓扑即门禁 — 实测教训, 见 T7b):

```
agent 容器 (无 root, 无凭据)
  │ 网络白名单: 仅放行 → gate:9418 (git daemon --enable=receive-pack)
  ▼
gate 仓 (host, pre-receive 钩子: 仅 refs/heads/sandbox/work, 必须 fast-forward, 拒新分支/tag/删除)
  ▼ host 侧单向同步, 凭据只在 host
真远端
```

实测矩阵 (全过): clone 读全 ref OK; sandbox/work 追加 push 接受; amend 后 force-push 拒 (non-ff); 新分支拒; tag 拒; 删分支拒; origin 改指真远端 (git daemon 不开 receive-pack) push 协议层拒而 fetch 通 — 即便绕开 gate, 真远端对容器仍只读; 钩子在 host fs, 容器物理不可触达.

**T7b 关键发现**: git daemon `--export-all` 共享 base-path 时, 9418 端口可直接 push `/real.git` **写穿真远端绕过钩子**. 教训: **门禁由拓扑保证, 不由钩子保证** — real 仓库绝不能落在任何可写服务端点的路径内; 服务目录白名单 + 显式 export-ok.

**读不受限的原理**: git 钩子只存在于写方向 (push); 读方向 (fetch/clone) 天生无钩子完全开放, gate 是真远端完整镜像故全分支可读.

### 4.3 工作树 gate 变体 (方向共识, 细节待拍板)

**用户提出**: 不用裸仓, host 上建一个工作树分支目录直接当 gate. 实测成立, 且是更优形态:

- 非裸仓天生可做 origin (clone/fetch 无区别); 默认 `receive.denyCurrentBranch=refuse` 拒绝向检出分支 push (保护工作树一致性), 设为 `updateInstead` 后: **push 被接受的瞬间, host 工作树文件自动更新成 agent 成果**
- 甜头: 门禁与落地窗口二合一 — agent 每次合规 push 直接变成 host 上可打开/编译/运行的文件; 回流 = host 侧审阅该目录 → merge 到 main → push 真远端, 即天然的人工确认点
- 实测细节: git daemon 默认只开读, push 需 `--enable=receive-pack` (协议层默认只读, 符合安全预期); gate 工作树脏 (有未提交改动) 时 push 被拒 — 自带保护, 但 agent 报错不透明, host 侧须保持 gate 干净

**形态注意**:

1. 钩子作用域: `git worktree add` 形态的钩子在共享 hooks 目录, 对主仓所有 push 生效 (自己 push main 也被拦) — 实测用 worktree 形态验证概念, 生产建议 gate 用**独立 clone** (钩子只管自己, 拓扑最干净, "real 不在可写端点路径内" 更易守)
2. sandbox/work 被 ff-only 锁死后, 新会话需要新起点 → 分支生命周期待设计 (如每会话 reset 到最新 main)

### 4.4 两约束咬合后的全貌

```
agent 容器 (无 root, 无凭据, pi 取消全部拦截)
  │ 桥 netns netavark FORWARD: 默认拒, 仅放行 gate:9418
  ▼
gate 工作树仓 (host; pre-receive: 仅 sandbox/work + ff; updateInstead 落地文件)
  ▼ host 人工审阅 → merge → push (凭据只在 host)
真远端
```

agent 对共享侧的持久化写被压缩为一种动作: "sandbox/work 上的 fast-forward 追加". 语义边界: agent 本地 .git 内任意折腾 (改历史/本地分支) 不受门禁 — 门禁只守 "到达共享侧的写", 这正是 "容器内肆意驰骋" 的准确含义.

## 5. VNC 通道实测记录 (2026-09-01, 独立于本会话)

/tmp 用干净自建镜像 (vnc-demo) 实测 Xvfb+noVNC 闭环, 结论:

## 8. 技术备忘 (坑与事实)

**网络**:

- rootless pasta 端口映射只监听 IPv4 `*:<port>`; 访问 host 服务优先解析 ::1 会失败 → 用 127.0.0.1 或局域网 IP
- 容器访问 host 服务: 走 pasta 网关 `169.254.1.2` (实测可达); host 局域网 IP 反而不通; host 的 127.0.0.1 监听服务容器到不了, 须全地址监听
- 本机局域网 IP: 192.168.131.194 (旧文档 192.168.31.252 已过时)
- 防火墙 ufw 状态未知 (sudo 需交互), 对外暴露端口前先确认

**容器**:

- chromium 需 `--shm-size=1g`; 中文 fonts-noto-cjk; 容器内 HTTP 服务必须 bind 0.0.0.0
- build vs run: RUN/COPY 仅 build 时执行, 启动零安装
- rootless podman 5.7 stop/restart/rm 偶发 `rootless netns: kill network process: permission denied`, SIGKILL 兜底可清
- skills 同步进容器: sync-to-pi.py 本就 ignore .venv/tests, 容器内重新 uv sync; host .venv 不可复用 (python 路径硬编码)
- Xvfb 启动需 `-ac -noreset`, 分辨率由 GEOM env 控制; x11vnc 用 `-nopw`; 容器 stop 时 SIGTERM 10s 超时升 SIGKILL (xterm/cmatrix 不响应 SIGTERM); noVNC 保留 vnc.html→index.html 软链兜底旧版
- present web_server 复用挂载 (ISSUE-04) / add-dir (ISSUE-02) / stop 均未实现, 见 present-web-server 会话

**git**:

- git daemon: `--export-all` 共享 base-path 是拓扑漏洞源; 生产用目录白名单 + export-ok; push 需显式 `--enable=receive-pack`; ff 判定 `git merge-base --is-ancestor`
- 非裸仓收 push: `receive.denyCurrentBranch=updateInstead`; 脏工作树拒收
