## 三. 三个假设场景的实际决定

### R1 无 issue/Roadmap, 无人给评审起点, 作者直接选当前 HEAD 生成空测试清单
- 决定: 不接受空清单, 该环节保持待验收.
- 依据: `tests.md:99` 要求 "先核实并记录本次改动前的提交, 无法核实先报缺口"; `:100` 无相关变更须 "记录比较范围与理由"; `drive-execution/SKILL.md:23` 明确不能默认当前 HEAD 就是起点.
- 理由: 若本次改动已提交在 HEAD, 取 HEAD 当基线 diff 为空, 空清单就是漏项而非 "无相关变更"; 若改动还在工作区, HEAD 可以是改动前提交, 但清单必须覆盖工作区改动, 仍不能凭 HEAD 直接得出空清单. "直接选" 缺核实, 不成立.
- 下一步: 要求作者给出基线的核实依据 (你指定 / 本次首个改动提交的父提交 / 分支起点), 写清 diff 命令与范围, 比较范围覆盖未提交改动; 核实不了按缺口上报, 不写 "无相关变更". 若作者确认改动未提交, 可记 HEAD 为基线, 但清单必须含工作区 diff, 空清单需附该 diff 依据.
- 残余风险: 基线正确性仍由作者自证, 无你确认环节; 建议至少在清单头部展示基线引用与 diff 命令, 供你抽查; 规则文本可补 "基线须早于改动, 比较须含未提交改动" 一句.

### R2 drive 已在 task 目录留下绑定版本的人工接受记录, navigate 最终验收要把整份记录重抄到验收 Milestone 目录
- 决定: 不重抄. 引用原件, 在验收报告里记结论与指针.
- 依据: `tests.md:103` 明写 "后续验收引用原件, 不另写一份"; `ACCEPTANCE-GUIDE.md:22` "已有绑定本轮版本的人工接受记录时直接引用, 不重复抽查"; `:19` 复用前须核三件 (覆盖提交是本轮交付提交, 所引标准版本一致, 必验项覆盖全部); `:26` 验收报告与关闭摘要记录两类确认结果.
- 下一步: 先核三件. 通过则验收报告写: 测试代码验收结论, 原件路径, 绑定的目标提交, 你的选样与接受结论; 关闭摘要记两类确认; 不复制正文. 核对不通过 (尤其 drive 记录绑定的是 task 提交而最终交付提交已前移) 就按缺口上报, 由你决定复抽或补证, 不自动沿用,也不靠重抄掩盖版本差异. 原件缺失才按 `tests.md:103` 在指定产物根目录补留档.
- 理由: 重抄会产生两份可漂移的副本, 违反 "不另写一份", 也让 "绑定版本" 失效.

### R3 产品核验全绿, 用户未选样/接受, 总指挥想在 RUN-REPORT.md 只写产品通过并按正常收尾
- 决定: 不允许, 不算正常收尾.
- 依据: `orchestration.md:27` 要求汇报含 "测试代码验收" 项; `:33` "测试代码验收尚待抽查/返工时, 不按正常收尾汇报, 只报缺口, 已备材料与所需决定"; `:80` AFK 授权不含正式人工验收与测试代码抽查的选样/接受; `tests.md:100` 未选样记待验收; `ACCEPTANCE-GUIDE.md:25` 未确认项保持未通过.
- 下一步: RUN-REPORT.md 仍写 (AFK 唯一汇报形式), 但按 "缺口 + 已备材料 + 所需决定" 写: 产品核验结果绿为一项; 测试代码验收=待抽查, 写清单/证据路径, 目标提交, 待确认事项单列 (请你选样与接受); 不宣布交付, 不关闭验收, 不代选样本. AFK 决定的记录仍进 `UNAUTHORIZED_DECISIONS.md`.
