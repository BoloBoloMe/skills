# 超范围执行确认门修改功能性审核

## 审核对象

本报告只从功能性角度审核以下 3 个超出原蓝图范围的修改，不再要求回滚：

- [human-in-loop-execution/references/execution-routing.md](../../../../human-in-loop-execution/references/execution-routing.md)
- [human-in-loop-execution/references/executing-plans.md](../../../../human-in-loop-execution/references/executing-plans.md)
- [human-in-loop-execution/references/subagent-driven-development.md](../../../../human-in-loop-execution/references/subagent-driven-development.md)

## 总体结论

这些修改**有利于改善 skill**。

原因是：它们把“执行计划写入后必须等待用户确认”的规则，从顶层说明和计划编写阶段，进一步下沉到执行路由、inline 执行和 subagent 执行入口。这样可以减少绕过确认门直接执行的风险，使 execution skill 的安全边界更完整。

结论级别：**建议保留，但后续应补一轮小修订来明确确认证据与计划版本绑定规则。**

## 各文件功能效果

### 1. execution-routing.md

新增内容：

- 输入契约增加“当前计划确认状态”。
- 路由优先级改为三段：
  1. 没有计划时先写执行计划。
  2. 计划已保存但用户未确认时进入执行计划确认阶段。
  3. 用户确认后再进入 subagent 或 inline 执行。
- 阶段名增加“执行计划确认阶段”。
- 检查清单增加“已确认用户是否明确确认当前计划文件”。

功能效果：

- 原先如果调用者直接从“已有计划”进入 inline 或 subagent，确认门可能只存在于顶层文档和写计划规则里，执行路由本身不够强制。
- 修改后，路由层会把“计划是否确认”作为决定是否执行的必要输入，能阻止计划刚生成就被自动执行。

评价：**正向改进。** 这是确认门最应该落的位置之一，因为路由是所有执行分支的共同入口。

### 2. executing-plans.md

新增内容：

- 输入契约要求“用户已明确确认当前执行计划路径”。
- 执行规则第 1 条要求未确认时停止在执行计划确认阶段。
- 检查清单增加确认项。

功能效果：

- inline 执行不再只依赖“已保存执行计划路径”。
- 即使用户或 agent 直接进入 inline 执行参考文件，也会先检查确认门。
- 降低“计划写完后同轮直接修改目标文件”的风险。

评价：**正向改进。** 它把确认门落到实际执行动作之前，能有效防止 inline fallback 绕过计划确认。

### 3. subagent-driven-development.md

新增内容：

- 输入契约要求“用户已明确确认当前执行计划路径”。
- 执行规则第 1 条要求未确认时不派发 subagent，停止在执行计划确认阶段。
- 检查清单增加确认项。

功能效果：

- subagent 执行不再只依赖“执行计划已存在”和“任务独立”。
- 避免控制者在计划未获用户确认时并行派发实现任务。
- 对多 agent 场景尤其重要，因为一旦派发，修改扩散速度更快，回收成本更高。

评价：**强正向改进。** 这是本次 3 个超范围修改中最有价值的一个，因为 subagent 执行的误启动风险最大。

## 是否改善 skill

是，主要改善点如下：

1. **确认门更完整**  
   从“写计划后停止”的单点规则，扩展为“路由、inline、subagent 都必须确认”的多层防线。

2. **降低误执行风险**  
   用户未确认计划时，执行层只能停在确认阶段，不能进入任务执行或派发 subagent。

3. **提升人在回路语义一致性**  
   计划不是自动执行许可；用户确认当前计划文件才是执行许可。这一点在三个执行入口中都被显式表达。

4. **更适合 agent 安全操作**  
   agent 可能只读取某个局部 reference 文件。把确认门写入局部执行文件，可以降低漏读顶层规则造成的误执行。

## 剩余风险

### 风险 1：确认对象仍不够强绑定

当前写法是“用户已明确确认当前执行计划路径”或“当前计划文件”。这比没有确认门好，但还没有明确绑定：

- 计划文件路径
- 计划内容版本或最后修改时间
- 用户确认语句
- 确认发生的时间

如果计划文件在用户确认后被修改，现有规则没有明确要求重新确认。

建议后续补充：

```text
用户确认必须绑定当前计划文件路径及其当前内容版本；计划文件内容发生修改后，确认状态失效，必须重新请求用户确认。
```

### 风险 2：计划头状态没有 confirmed 形态

`writing-plans.md` 固定计划头目前写：

```text
执行确认状态: waiting-for-user-confirmation
```

但执行后续阶段要求“用户已明确确认当前执行计划路径”。当前没有规定确认后是否要把计划头更新为类似：

```text
执行确认状态: confirmed-by-user
确认时间:
确认人:
```

如果完全依赖对话上下文，跨会话执行时可能难以复核。

建议后续补充一种确认记录方式，但不要引入 planning 式审批状态机。

### 风险 3：顶层与局部文件的术语略不统一

当前存在两种表述：

- “当前计划文件”
- “当前执行计划路径”

语义基本一致，但后续最好统一为“当前执行计划文件”，并在需要精确绑定时同时写路径。

## 建议后续改进

建议保留本次 3 个文件修改，并另起一次小型 HILP 变更，专门补强执行确认门的确认证据规则：

1. 在 `writing-plans.md` 中定义确认后记录格式。
2. 在 `execution-routing.md` 中说明计划内容修改会使确认失效。
3. 在 `executing-plans.md` 和 `subagent-driven-development.md` 中统一术语为“当前执行计划文件”。
4. 在 `hilp-handoff-intake.md` 或 execution 总入口中说明跨会话恢复时如何判断计划是否已确认。

## 最终判断

从功能性看，这 3 个超范围修改是**正确方向**，并且确实改善了 skill 的安全性和一致性。

不建议回滚。建议把它们视为合理的安全补强，并在后续补一轮小修订，使“用户确认”从自然语言上下文进一步变成可审计、可恢复、可失效重算的轻量记录。
