# 执行入口阻断复盘：设计资产状态未同步

## 摘要

执行层在入口检查阶段阻断是正确的。阻断原因是 HILP planning 在记录用户批准 `stage-3/design-choice@v3` 时，只更新了 manifest、审核包和当前入口，没有同步更新设计资产文件自身的 front matter 与正文状态，导致执行层读取实际资产时发现设计仍是 `ready-for-approval｜待审批`。

本次已修正目标资产状态：

- 修正资产：[02-方案设计_design-choice@v3.md](../planning/assets/02-方案设计_design-choice@v3.md)
- live manifest：[manifest.md](../planning/manifest.md)
- 已批准入口：[当前已批准.md](../planning/_current/当前已批准.md)

## 前因

1. 用户批准了 `stage-3/design-choice@v3`。
2. HILP planning 记录批准时，更新了：
   - [02-design-choice@v3-review.md](../planning/review-pack/02-design-choice@v3-review.md)
   - [manifest.md](../planning/manifest.md)
   - [当前已批准.md](../planning/_current/当前已批准.md)
3. 但遗漏了目标资产自身：
   - [02-方案设计_design-choice@v3.md](../planning/assets/02-方案设计_design-choice@v3.md)
4. 后续执行交接资产引用了已批准设计：
   - [05-执行交接_execution-handoff@v1.md](../planning/assets/05-执行交接_execution-handoff@v1.md)
5. 执行层读取实际设计资产 front matter，发现状态仍为待审批，于是停止执行。

## 直接原因

批准状态更新不是原子操作。目标资产、manifest、审核包和当前入口之间缺少强制一致性校验。

具体不一致为：

| 位置 | 阻断前状态 | 期望状态 |
|---|---|---|
| 设计资产 front matter | `ready-for-approval｜待审批` | `approved｜已批准` |
| 设计资产正文 asset_ref | `ready-for-approval｜待审批` | `approved｜已批准` |
| manifest | `approved｜已批准` | `approved｜已批准` |
| 审核包 | `approved` | `approved` |
| 执行交接引用 | `approved｜已批准` | `approved｜已批准` |


检查重点：目标设计资产 v3 不再出现自身状态为 `ready-for-approval｜待审批` 的记录。

## 对 skills 的改进要求

### 1. human-in-loop-planning：批准事件必须原子更新

应修改：

- [human-in-loop-planning/SKILL.md](../../../../human-in-loop-planning/SKILL.md)
- [event-action-rules.md](../../../../human-in-loop-planning/references/event-action-rules.md)
- [handoff-contracts.md](../../../../human-in-loop-planning/references/handoff-contracts.md)

要求：处理 Human Approval Granted 时，必须一次性更新并验证以下对象：

1. 目标资产 front matter。
2. 目标资产正文中的 `asset_ref`、当前状态、是否需要审批、下一步。
3. live manifest。
4. 对应 review-pack。
5. `_current/当前待审.md`。
6. `_current/当前已批准.md`。

任一对象写入失败或验证不一致时，不得继续生成下游蓝图、执行交接或归档资产。

### 2. human-in-loop-planning：新增批准后一致性检查

应在设计批准和蓝图批准后追加强制检查：

```text
同一 asset_ref 的状态必须在以下位置完全一致：
- 目标资产 front matter
- 目标资产正文 asset_ref
- manifest current_state/current_state_label
- review-pack close_result/target_asset_ref
- _current/当前已批准.md
```

检查未通过时，当前阶段必须停留在审批状态修复，不得进入下一阶段。

### 3. hilp-blueprint 与 hilp-execution-handoff：不得只相信 manifest

应修改：

- [blueprint.md](../../../../human-in-loop-planning/references/blueprint.md)
- [execution-handoff.md](../../../../human-in-loop-planning/references/execution-handoff.md)

要求：进入实施蓝图或执行交接前，不仅要读取 manifest，还必须读取绑定上游资产文件本身，核对 front matter 与正文状态。

### 4. human-in-loop-execution：保留当前阻断行为，并补充恢复提示

应修改：

- [hilp-handoff-intake.md](../../../../human-in-loop-execution/references/hilp-handoff-intake.md)

要求：执行入口检查遇到 manifest 与资产文件状态不一致时继续阻断，并输出固定恢复建议：

```text
回到 HILP 变更重审，执行“审批状态一致性修复”；若用户批准事实明确，不生成新内容版本，只同步同一版本的状态字段和当前入口。
```

### 5. 增加可复用状态一致性校验清单

建议在 planning skill 中加入一段“下游交接前状态一致性清单”：

```text
- [ ] design asset front matter 为 approved
- [ ] design asset 正文 asset_ref 为 approved
- [ ] blueprint asset front matter 为 approved
- [ ] blueprint asset 正文 asset_ref 为 approved
- [ ] manifest 对应行均为 approved
- [ ] review-pack 已关闭且 close_result=approved
- [ ] _current/当前待审.md 为当前无待审资产
- [ ] _current/当前已批准.md 包含设计与蓝图
```

执行交接只有在清单全部通过时才能生成。

## 防复发原则

- manifest 是索引权威，但不能替代资产自身状态。
- 审批状态变化不是内容修订，不需要递增版本，但必须同步同一版本资产的元数据和正文状态。
- 下游阶段必须绑定“实际文件状态一致”的资产，而不是只绑定自然语言批准或 manifest 行。
- 执行层阻断不是失败，而是防止待审批资产被误当作已批准输入的安全门。
