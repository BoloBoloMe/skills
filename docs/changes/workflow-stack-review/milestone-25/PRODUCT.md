# codebase-map v1 Product Spec

## 背景

用户想自己看一眼手里的代码库长什么样: 哪些模块互相依赖, 分层有没有被破坏. 现有工具里只有 CodeCharta 能给出这种"城市地图"观感, 也能给出每个文件/目录的层号, 环和向上依赖. 但它的分析端要 Java 22 + Node 22.19, 前端要 npm 构建, 直接装在宿主机上代价太大.

milestone-13 到 milestone-24 已经把路探清并逐条裁决: 分析端借官方镜像在宿主 podman 里跑, 前端用官方现成的静态包, 外面套一个自建 python 常驻单例服务负责起停与托管, 交付给用户的是局域网 URL. 第一版只用官方英文前端, 汉化是它之后的技术切片. 本节点只把第一版的行为定清楚, 不写实现.

真实受益者只有用户本人: 手动调起, 手动看, 不进任何工作流.

## 目标

- G-001: 在宿主机上不必安装 JDK 与 Node, 就能把目标代码库变成可交互的结构地图.
- G-002: 交付可直接点开的局域网 URL, 打开后 3D 城市图与官方依赖视图都真实渲染本次分析的库.
- G-003: 同一台宿主上只有一个服务实例, 占一个固定端口; 多个库靠 URL 参数区分, 同一个库重跑后 URL 不变.
- G-004: 服务状态可核实可复原: 实例死了能被识别并重启; 端口被别的程序占用时如实报错, 不悄悄换端口.
- G-005: 交付时如实交代依赖抽取的局限与统计分母, 用户不会把退化的图当成可信结果.
- G-006: 分析数据跟着被分析的库走, 本仓库不攒别人代码库的结构快照.

## 非目标

- NG-001: 不做界面汉化. (理由: 汉化要维护约 900-1000 条词表, 归 milestone-21 的第二片; 第一版的目的是尽快看到真实的图.)
- NG-002: 不做架构评审, 不出重构建议, 不参与任何验收判断. (理由: 用户只要自己看代码, 这个工具不进工作流.)
- NG-003: 不在沙箱容器内运行, 不做容器内调用宿主服务的接口, 不做没有 podman 时的 python 兜底分析器. (理由: 用户只在宿主用; 兜底分析器拿不到层号与环, 等于伪造能力.)
- NG-004: 不做大库自动按目录聚合, 不设文件数阈值. (理由: 用户要先看真实的图, 聚合会偷偷改口径; 可读性交给前端已有的搜索与过滤.)
- NG-005: 不自算层号, 环与向上依赖. (理由: 自算只有在"要与官方不同"时才有意义, 当前没有这种需求.)
- NG-006: 不把层号拷进官方指标, 不改官方默认 URL 参数, 不做 build 后处理. (理由: 用户选择"按官方的来"; 实测显式绑层号会被前端静默改写.)
- NG-007: 不引 nginx, 不做 HTML5 深链回退. (理由: 官方前端是 hash 路由, 服务端只会看到 `/`, 普通静态托管就够; 真需求是常驻单例与状态记录.)
- NG-008: 不提供 `--include-tests` 之类改变分析范围的开关. (理由: 第一版先把主流程跑顺, 分母在交付说明里讲清即可.)
- NG-009: 不加认证, TLS, 多用户与访问控制. (理由: 局域网内部工具, 无认证开放的取舍已被同类服务接受.)
- NG-010: 不在仓库内保存任何 cc.json, 前端产物或私有库路径. (理由: 它们都是可重建派生物, 入库只会泄露别人的代码结构.)

## 业务规则

- BR-001: 服务在宿主上单例: 同一时刻只有一个实例, 占一个端口, 首选端口 8090.
- BR-002: 启动前先取文件锁并探活; 已有存活实例就复用, 不为并发再起第二个实例.
- BR-003: 首选端口已被别的程序占用时报错并交用户裁决, 不静默顺延到别的端口.
- BR-004: 首选端口只用于第一次启动; 端口默认值取上回用过的那个, 没有才用 8090, 避免 stop 之后静默退回旧端口让书签失联. `serve --port <N>` 可指定本次端口, 没有存活实例时可用 (首次运行也行); 有存活实例时要求先 `stop`. 换端口后必须报告旧地址已失效.
- BR-005: 服务绑定 `0.0.0.0`, 因为页面要由局域网内其它设备访问.
- BR-006: 运行状态的唯一真值是宿主 `~/.agents/codebase-map/state.json`, 记端口, pid, 启动时间, 可执行路径, serve-root 与当前数据键清单.
- BR-007: 读取状态后必须真实探活 (进程在, 端口在听, 一次请求可达) 才算存活; 残留的状态文件不算存活.
- BR-008: 状态里的端口或 pid 与实际探活结果对不上时不静默接管, 报错交用户裁决; pid 还活着但端口无人应答也算对不上.
- BR-009: 服务启动后不自行退出, 只有显式 `stop` 或宿主重启才终止.
- BR-010: cc.json 的权威原件在被分析库的 `.codebase-map/cc.json`; serve-root 里放的是副本; 两者不一致时以重新 `build` 为准.
- BR-011: 数据键固定为 `<库名>-<8 位路径哈希>.cc.json`: 同名不同库不会互相覆盖, 同一个库重跑得到同一个键.
- BR-012: 官方前端产物与数据副本都在宿主 `~/.agents/codebase-map/serve-root/` 下, 数据文件必须与 `index.html` 同目录, 否则前端取不到数据.
- BR-013: 命令形状固定三个对外子命令: `build` 只分析并产出数据, `serve` 起或复用服务并交付 URL, `stop` 停整个服务; 三者不合并, `stop` 没有"只停某一个库"的语义. 内部守护进程入口不算对外子命令, 不写进文档用法.
- BR-014: 同一库重跑覆盖数据并复用同一个服务实例, 页面刷新即看到新数据, URL 不变.
- BR-015: 默认排除 `node_modules`, `.git`, `dist`, `build`, `target`, `vendor` 与 `.codebase-map`; `--exclude <glob>` 用 glob 语义 (脚本负责转成分析端能吃的正则并转义), 排除口径同时作用于容器内分析与宿主的目录树扫描; 分析端自己的 `.gitignore` 与测试/build 默认过滤不逐文件复刻, 统计里单列为"工具默认过滤"一类.
- BR-016: 分析端固定官方镜像 `codecharta/codecharta-analysis:2.3.0` (纯数字 tag), 版本以镜像的单架构清单 digest 核对 (多架构清单 digest 只记录不阻断), 不采信镜像内自报的版本号.
- BR-017: 分析容器固定以 rootless podman 运行, 必须带 `--userns=keep-id` (否则写不出文件), 源码只读挂载, `--network=none`, 用完即删.
- BR-018: 指标按官方默认, 层号, 环与向上依赖通过官方依赖视图查看.
- BR-019: 交付给用户的必须是局域网 URL (宿主已确认地址加实际端口), 不给 loopback 地址, 不给文件路径.
- BR-020: 地址来源只用宿主已确认的局域网地址记录; 没有已确认值就报阻塞并给出候选地址, 你确认后用 `serve --address <已确认地址>` 重新交付, 不猜地址.
- BR-021: 环境不足 (没有 podman, 镜像不可用, 目标目录不存在, 缺前端产物又没网络) 一律报错停下, 不静默降级, 不伪造数据.
- BR-022: 交付门禁: 依赖边数为 0, 或文件层号少于 3 种, 一律拒绝交付并说明缺什么.
- BR-023: 交付说明必须包含"依赖抽取完整性未量化"这句判断, 不得宣称分层完全可信.
- BR-024: 交付说明必须给出分母口径: 依赖树里的文件数, 零声明文件不进依赖树, 测试目录与 build 目录默认不扫, 分析端自带的忽略规则单列为工具默认过滤.
- BR-025: ccsh 没解析出依赖的语言只在命令输出与交付消息里说明, 页面保持官方原样.
- BR-026: 第一版按 Java 目标库验收; 其它语言顺带能用但不在验收范围.
- BR-027: 首次初始化 (拉镜像, 取官方前端) 由 `build` 负责, 并在输出里用固定字段说明这是慢操作; `serve` 与 `stop` 不做网络动作.
- BR-028: 前端版本固定 `vis-2.9.1` 的官方 `web.zip`, 下载后校验 sha256; 校验不过就停.
- BR-029: 服务没有认证也没有 TLS, 局域网内可读; 只托管愿意公开的结构数据, 不托管仓库根或敏感目录.
- BR-030: `serve` 以状态清单与磁盘副本的交集判断有没有数据: 交集为空就报错并区分"还没 build 过"与"副本被删了"; 磁盘上有未登记的文件只提示, 不自动收编.
- BR-031: 被分析的目标目录保持只读: 除了在目标库写 `.codebase-map/cc.json`, 运行过程不修改目标库里的其它文件.
- BR-032: 数据键的库名取目标目录名并清洗成 URL 安全形态, 路径哈希取目标目录真实绝对路径, 清洗后为空时用 `repo`.
- BR-033: (审计) 本变更不新增第三方依赖, 脚本只用 python 标准库.
- BR-034: (审计) skill 只由用户手动调用: frontmatter 带 `disable-model-invocation: true`, 并有 `agents/openai.yaml` 的 `policy.allow_implicit_invocation: false`; 任何 skill 都不调用它.
- BR-035: (审计) 仓库内只留规格与代码, 不留 cc.json, 前端产物, 被分析库的完整路径.
- BR-036: `build`, `serve`, `stop` 都不自动删除其它库的数据副本, 也不做"只留最近一个"的清理; 清理入口写在 SKILL.md 里, 由用户手动执行.
- BR-037: 交付消息的内容来自 `serve` 的输出摘要 (含三类说明与每个库的完整 URL), 调用会话原样转述, 不自行改写其中的数字与判断.
