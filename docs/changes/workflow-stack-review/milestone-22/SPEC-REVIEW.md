## 发现

### B01 [阻断] 容器交付 URL 被要求同时使用映射端口和监听端口

- 位置: T:18,22 模块接口; T:68 非功能要求-记录一致性; T:74 关键流程. 对照 P:79-83,196-200 的 AC-001/AC-004 容器场景.
- 依据: D004/D005/D011, AC-15-01/04; P BR-003/006 已明确区分端口.
- 问题: T:31/69 要求容器 URL 使用 SWT_HOST_WEB_PORT, 但 T:18/22/68/74 无环境限定地要求 URL 使用实际监听端口/等于记录 port. 容器例子中记录 port=8800, URL 端口=50021, 两个要求不能同时成立. T:68 的直接验证口径会把正确容器交付判错.
- 建议处理: 明确 `port` 永远表示服务监听端口. URL 在宿主用该 port, 在容器用已确认的 8800 宿主映射端口. 记录/监听一致性与对外交付 URL/映射一致性分别验证, 不新增第二份监听端口记录.

### B02 [阻断] 本次显式宿主地址在 status/重建入口没有传递路径

- 位置: T:17 `start --lan-host`; T:22 无参数 status; T:29-30 地址解析; T:74 重建. 对照 P AC-001 显式地址场景与 AC-004 换口更新 URL 场景.
- 依据: D011 的本次明确指定优先, D005 的重建后交付正确新 URL; AC-15-01/04.
- 问题: 唯一显式地址入口只有 start 的 `--lan-host`. status 无对应参数, 地址又明确不持久化. 例如本次明确指定 .31, 现有记录地址为 .20: start 输出 .31, 随后 status/重建重新解析只能得到 .20. 若没有地址文件则从已明确指定退回 address_missing. 规格没有说明调用会话如何把同一次展示的显式选择带入查询/重建, 或如何不使用 status 的错误 host 组装最终 URL.
- 建议处理: 明确地址选择属于一次交付的上下文, 并设计 status/重建结果到最终交付的传递办法. 可以让同一解析入口接收该上下文, 或由调用方按已选地址与 status 实际端口组装, 但两处不能各自重新选择地址. 不为解决此问题擅自新增地址持久化来源.

### B03 [阻断] 把防越界写成拒绝所有含 ../ 的路径, 改变保留行为

- 位置: P:36 BR-012; T:62 安全策略-越界防护.
- 依据: D007/D008/F008, AC-15-03/06 要求保留既有目录行为和越界防护. 源码 `web_server.py:622-647` 先 resolve 再做 containment; `test_web_server_content.py:302-337` 明确要求 `/sub/../` 返回 HTTP 200 并集 listing.
- 问题: 两份 spec 都写成含 `../` 一律 404. 旧行为拒绝的是逃出挂载根, 不是所有含双点的合法根内路径. P 的 AC-006 越界场景本身只要求外部 secret 不可读, 并不支持这个更强限制. T 又说内容面沿用/只改地址, 与这里必然要求修改 handler 相冲突.
- 建议处理: 改为规范化后逃出挂载根返回 404, 保留根内规范化路径行为. 如确实要禁止所有双点段, 须先交用户确认产品变化, 同步既有测试及 _Handler 条件回归, 不能静默当作保留安全规则.

### B04 [阻断] 自检失败场景新增了失败页面必定不在服务上的要求

- 位置: P:107-111 AC-002 `页面自检失败时不交付`; T:6/44 内容面沿用, T:70 页面自检.
- 依据: 现状 SKILL.md 本地展示流程第 1 步和 REMOTE.md 开头只要求自检失败不交付; D008 保留整目录增挂/复用且不新增 remove-dir; AC-15-03 保留目录服务.
- 问题: 场景除不交付 URL 外, 还要求 `展示服务上不出现 broken.html`. 同话题 output_dir 可以复用并已经挂载, 在该目录写入 broken.html 后静态服务就可读取, 自检不会改变这一事实. 技术设计没有逐文件发布/撤回机制, 也不应为此新增机制. 即使新目录尚未挂载, 当前场景也没有这个前提.
- 建议处理: 恢复为自检失败不交付的已确认要求. 若只想观察新目录不被提前挂载, 给该场景补充明确的未挂载前提并只约束本次挂载动作. 不把它提升为已挂载目录的逐文件屏蔽保证.

### B05 [阻断] 本机控制面场景要求返回挂载清单, 没有既有只读 HTTP 接口承接

- 位置: P:237-240 AC-006 `本机来源可调用控制面`; T:42-46 HTTP 面.
- 依据: D007/F013 与 OPPOSITION-RESOLUTION A-04 只确认本机来源放行规则. `web_server.py:550-556` 的 GET `/__control__/ping` 返回 service/pid; `web_server.py:575-612` 的 POST `/__control__/add-dir` 才返回 roots, 同时必须给目录并执行增挂; CLI status 可返回 roots.
- 问题: 场景只给"请求控制面端点", 就要求 HTTP 200 与当前挂载清单. 对应只读 GET 端点不存在. 若用 add-dir, 则方法/输入/动作缺失. 直接照此落测试可能凭空增加查询控制面接口, 超出保留既有接口的决定.
- 建议处理: 固定为 GET ping, 观察 HTTP 200 与 service/pid; 挂载清单另由 CLI status 观察. 或明确用有效目录做 POST add-dir 并观察 roots. 不新增未确认 HTTP 查询接口.

### B06 [阻断] AC-007 把检查必须通过弱化为只要记录通过或失败

- 位置: P:283-287 AC-007 `验收记录含检查命令与实际结果`; P 全部业务规则; T 非功能要求/测试模块.

- 问题: P 只假定检查"已执行", 然后允许记录"通过或失败结果". 即使所有检查失败, 这个场景仍可通过. P/T 没有其他条款补上"这些检查通过才能算本次验收满足"的门槛. 记录失败的诚实性是必要的, 但不能替代通过要求.
- 建议处理: 保留命令/版本/原始结果/缺口记录, 同时明确直接相关检查通过的完成门槛. 失败场景应导致该项不通过, 不能只要写入报告即满足. 给出仓库 skill 格式检查的明确入口或交给 EXECUTION 指定, 不把检查动作本身当通过证据.
