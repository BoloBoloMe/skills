# 产物机械化改造方案

状态: 方案已由用户确认, 尚未实施, 尚未完成独立复核.
本次授权: 将已对齐方案写入本仓库并创建新分支, 不启动编码或修改真实 agent skills.
需求原文见 [REQUEST.md](REQUEST.md), 完整决策与理由见 [DECISIONS.md](DECISIONS.md), 架构决策见 [ADR-0028](../../adr/0028-artifact-mechanization-and-unified-presentation.md).

## 1. 目标与范围

将决策账本及规格到验收整条消费链一起机械化, 不只把 to-spec 输出的文件后缀换成 JSON. LLM 负责真正的内容与语义检查, 程序负责结构, 引用, 版本, 可确定判断的检查和状态流转, 用户负责裁决与验收.

机械化的是流程需要的数据和约束, 不是把所有内容都塞进 JSON. 结构化产物通过程序读写, Markdown 报告及其他非结构化原件直接读取. 输出形式由环节职责决定: to-spec 可以直接读取已确认的需求文档, 再通过程序生成结构化规格; 调研或评审报告仍输出 Markdown.

本次不做:

- 不把调研, PoC, 评审和验证报告的全文拆成 JSON 字段.
- 不把产品代码, 测试代码, 日志, 截图或实验数据改成 JSON.
- 不提供历史产物批量迁移器, 不长期维护新旧两套规格/执行模式.
- 不要求先建立路线图才能使用其他 skill 或查看产物.
- 不新增自动派工或自动推进的常驻工作流引擎.
- 不因所有产物都能在网页查看而增加逐份人工审批.
- 不重定义现有实施, 代码评审, 独立验证, 人工验收, 安全与无人值守授权规则.
- 不合并邮箱通信或产品自身的运行服务; 本次统一的是网页展示服务.

## 2. 职责划分

| 部分 | 负责 | 不负责 |
| --- | --- | --- |
| 工作流共用产物程序 | 结构化数据读写, 编号, 引用, 校验, 版本, 确认记录, 状态检查, 报告与证据登记 | 替 LLM 编写需求, 判断全部语义, 自动派工 |
| 各工作流 skill | 当前任务内容, 语义检查, 必要裁决, 实施/评审/验证组织, 调用产物程序 | 手写最终结构化文件格式, 各自重复实现公共数据规则 |
| present | 唯一展示后端, 统一网页应用, 资源访问和已确认地址交付 | 批准规格, 推动任务, 根据报告措辞自动判通过 |

共用产物程序按需运行, 不另起后端进程. 它归工作流侧, 不将工作流写入和审批操作塞入 present 的文件读取服务.

## 3. 产物划分

以下文件名仅用于说明逻辑产物, 实际文件组织属于可调整实现选择. 由程序固定并生成, 不要求 LLM 背诵或自行拼装命名模板.

| 逻辑产物 | 结构化内容 |
| --- | --- |
| 决策账本 | 完整决策/事实, 理由, 来源, 约束性, 状态, 替代关系和影响记录 |
| 产品规格 | 背景, 目标/非目标, 业务规则, 审计要求, 验收场景与例子 |
| 技术规格 | 必须遵守的技术约定, 可调整做法, 模块/接口, 接缝与依赖, 安全/非功能要求, 待验证事实 |
| 验证方案 | 判据来源, 每个场景及全部例子的步骤, 入口, 预期观察, 证据要求和确认版本 |
| 执行计划与 issues | 全局允许/禁止范围, 切片, 依赖, 覆盖关系, 验证契约, 评审起点, 实施与交付记录 |
| 评审登记 | 目标提交, 评审方向, 结论, 待处理项及 Markdown 报告引用 |
| 独立验证记录 | 目标提交, 方案版本, 逐项结果, 验证者及未参与事实, 证据与报告引用 |
| 验收记录 | 判据与证据关联, 用户逐项决定, 适用的测试代码抽查记录 |
| 路线图 | 保留现有领航数据职责, 明确引用输入与产物并组织里程碑 |

调研, PoC, 代码评审, 独立验证, 影响调查和运行汇总等报告保留 Markdown. PoC 可以交付小程序, 实验数据或文档, 不强行变成单个结构化文件. 领域词汇, ADR 和 README 等长期源文档保留原有形式.

报告正文由 LLM 直接读写, 通过脚本登记位置, 对应版本, 关联任务及流程需要的结论. 程序不解析自由报告正文来判断是否通过. 论证留在报告, 流程状态进入结构化记录, 不将全文再复制成第二份权威正文. 正文和登记结论是否一致仍由 LLM 核对.

报告登记绑定内容与目标版本. 登记后修改正文需要重新登记; 已被用于完成或验证记录的报告版本须保留, 不静默覆盖.

## 4. 产物根目录, 引用和独立使用

沿用现有软件工程共识的产物根目录规范:

- 默认 docs/changes/<feature-slug>/, 调用方可以指定其他位置.
- 同一交付单元的多个里程碑可以共用根目录, 不按里程碑编号强制拆目录.
- 本变更产物之间的相对引用基于产物根目录解析; 外部资料和上游账本按实际位置解析.
- 不要求来源或账本一定在产物根目录内.

结构化产物使用稳定 ID. 引用说明具体产物, 条目或范围, 对应版本及用途, 区分判据, 操作依据和证据. 不再用固定 Markdown 节名交接, 不复制整段上游正文. 外部文档使用实际路径, 章节等定位信息和内容版本依据, 不强制给原文补一套编号.

产物列表由程序生成, 不让 LLM 手工维护第二份索引. 里程碑显示哪些输入和产物以明确引用为准, 不能因共用目录而把目录内全部文件算成该里程碑产物.

路线图是产物的使用方, 不是其他 skill 的前置依赖. 没有路线图时, 仍能独立使用 to-spec, to-execution 等, 并直接浏览交付单元或单份产物. 已有合格输入可以复用, 不强制每次补走整条主链.

## 5. 程序接口与校验分工

共用程序提供创建/编号, 按条目查询, 批量修改, 校验, 冻结审阅版本, 记录明确确认, 转正, 报告/证据登记和状态更新等少量操作. 具体命令名和物理文件布局属于实现选择, 不作为用户固定的技术约束.

查询只返回当前任务需要的内容; 写入成功返回变更结果和版本, 不反复回传全文. 写入失败给出可定位的问题, 不以无效数据覆盖上次有效内容. 并发写入需要原子落盘及版本冲突检查, 防止丢失修改. 不同工作树继续按现有分支协作, 合并后重新核对引用和版本, 不把文件锁误当成跨分支合并保障.

### 程序可以强制

- 字段类型, 必填信息, 合法状态, ID 唯一性及稳定引用.
- 引用存在且类别正确, 行为要求与审计断言归类可区分.
- 已声明的覆盖关系完整, 任务依赖无环.
- 操作所需的确认和检查记录齐备, 目标版本对应.
- 当前状态允许操作, 不能借普通字段修改绕过转正等必要检查.
- 输入版本过期或报告内容发生变化时不能静默沿用.

草稿允许暂时不完整. 编辑时检查写入合法性, 提交审阅/转正/领取任务时再检查该阶段所需完整性. 路线图可以记录预期输入, 但领取时不能把预期材料当作已经存在且有效的材料.

### 仍由 LLM 检查

- 已确认决策是否被准确落实, 是否有无依据新增或遗漏.
- 场景是否真的覆盖目标, 规则, 分支和全部例子.
- 单个动作字段里是否实际塞入多个刺激, 结果是否可观察.
- 数值和约束是否有依据, 要求是否冲突, 参考做法是否被误当硬要求.
- 登记结论是否与报告一致, 证据是否实际支持结论, 是否有漏记影响.

删除 Gherkin 唯一关键字, 固定节名/节序和确认注释等纯形式要求. 保留明确角色/前提/动作/结果, 有依据的数据, 可观察点, 覆盖关系与约束强弱等内容纪律. 不用简单关键词禁令冒充语义检查.

程序通过不等于语义正确, 检查记录存在也不等于已经证明内容合格.

## 6. 草稿, 确认, 转正和上游变化

需要用户确认的产物遵循: 编辑草稿 -> 程序检查与 LLM 内容检查 -> 冻结并展示 -> 用户明确确认 -> 同一版本转正 -> 下游引用正式内容.

- 展示绑定固定版本, 不展示随时变化的草稿作为待确认对象.
- 修改已展示输入产生新版, 重新展示并取得明确采纳.
- 转正直接使用被确认内容, 不让 LLM 重新誊写.
- 程序能核对版本一致, 不能证明用户实际看过或同意过. LLM 依据用户明确答复记录确认, 沉默或部分认可不算整版采纳.
- 决策, 产品判据及必要上下文, 验证方案和最终验收沿用各自现有确认要求. 执行拆分/issues 不新增人工审批.
- 确认只绑定本次待确认内容及其必要上下文, 不把无关进度和报告变化纳入同一次确认.
- 可调整的内部实现由实施者选择并验证, 不因没有预写内部机制而阻塞.

正式采用新版上游输入后, 按已登记的条目依赖和全局约束暂停受影响的下游及其依赖. 未受影响工作不自动暂停. 旧结果保留原版本并标明需复核, 更新或核对后再推进新版. 关系不清时报告并停下核对, 不猜测没有影响. 程序只能检查已登记的关系, 隐含影响仍由 LLM 调查.

仅编辑草稿不打断使用正式版本的工作. 稳定 ID 不等于内容版本, 旧证据不能因编号未变就自动沿用, 也不能将旧结果改写为新提交上的实跑结果.

## 7. present 的唯一展示后端

保留并复用 present 已有的已挂载目录文件读取能力, 不新增重复的 JSON/Markdown 读取接口. 工作流文件的访问地址须保留不同根目录的区别, 不能因挂载方式读到另一个需求的同名文件; 这不改变本地产物根目录规范, 具体映射方式可调整.

- 文件不得越出明确登记的公开范围, 不为便利公开整个仓库或家目录.
- 启动, 复用, 恢复, 实际端口与已确认局域网地址交付都归 present.
- 同一运行环境只有一个展示实例. 宿主同用户复用一个, 各容器分别复用自己的实例, 全部使用同一份 present 实现.
- navigate 的展示后端明确合入, 不保留一个由 present 转发的 navigate 后端.
- codebase-map 保留分析和专用可视化, 展示托管合入 present, 不再自建展示进程.
- 网页只读, 修改结构化数据走程序, 报告正文直接编辑. 不新增网页审批或工作流写入接口, 反馈与确认仍在 chat.
- 保留 present 现有公开范围与风险约定. 控制操作不能随文件读取一起对网段开放.

本次统一展示后端和生命周期, 不吞并其他工具的通信服务或产品自身运行服务.

## 8. 统一网页与独立产物查看

现有 navigate 路线图前端迁入 present 并扩展, 保留现有 UI 视觉设计. 统一网页和产物模板也归 present, 不再由每个工作流 skill 分别维护一套展示前端.

路线图入口的交互:

1. 点击里程碑, 展开填满网页的弹窗页.
2. 页面显示当前里程碑的输入信息和结构化/Markdown 产物列表.
3. 点击一行再按需读取相应文件, 将原始数据填入对应页面模板.
4. JSON 以规格, 任务, 结果等可读模板呈现, Markdown 渲染为文档, 不默认铺原始代码.
5. 支持返回列表, 关闭弹窗并保留地图位置, 键盘操作可用.

独立入口与上述页面使用同一套产物查看器:

- 可以直接打开交付单元或单份产物, 不要求存在 ROADMAP, 不补造里程碑, 不显示空地图.
- 独立调用 to-spec 后, 由程序生成规格, 调用 present 登记可公开资源并启动/复用服务, 返回可直接打开的已确认局域网 URL, 由 to-spec 在 chat 交付.
- 用户直接看到排版后的规格, 可切换产品/技术内容及关联产物, 不需要自行拼 URL 或先调用 navigate.
- 待确认版本使用固定快照链接; 普通浏览可打开当前正式版本, 页面清楚标示草稿/正式状态和版本.
- Markdown 报告也能通过独立入口用文档模板打开.

已知类型使用专用模板, 其他 JSON 使用通用字段视图而不假装理解其业务含义. 模板不改写判据, 不隐藏场景分支或例子. 外部内容安全渲染, 不执行 Markdown 中的任意 HTML/脚本. 最新进度可以刷新, 正在审阅的固定版本不能自动替换. 网络失败, 文件缺失, 版本过期或缓存内容必须明确提示, 不让旧页面冒充当前结果.

## 9. 各 skill 的适配

| 范围 | 改动 |
| --- | --- |
| decision-ledger / deliberate | 账本改程序维护, 保留完整理由, 来源, 替代历史与原有裁决规则 |
| to-spec | 替换 Markdown/Gherkin 生产和转正流程, 保留内容检查, 展示, 明确采纳及独立自洽检查 |
| verify-change | 验证方案和逐项结果改结构化, 报告仍写 Markdown, 保留对其他已确认权威输入的支持 |
| to-execution | 结构化执行计划/issues, 程序检查引用, 覆盖, 依赖和必需验证信息 |
| drive-execution | 程序查询可执行任务, 登记实施/合并/开发验证/评审结果, 不接管成品独立验证 |
| code-review | 按类型读取结构化输入和原件, Markdown 报告加对应流程登记, 保留各评审方向及门槛 |
| navigate | 保留领航和路线图数据管理, 适配输入/产物引用, 删除独立展示后端和重复前端 |
| codebase-map | 保留分析和专用页面, 展示托管委托 present, 移除独立服务管理 |
| 共享约定及其他消费者 | 修改旧文件名/节名读取方式, 更新输出契约, 不为接入而重写报告正文 |

共享概念, 模板, 调用说明, README 与相关 ADR 同步更新. 不保留程序已换新而 skill 仍要求旧产物的双轨状态. 非作者验证要求, 修复/复验, 安全底线和 AFK 授权原样承接, 代裁决不得伪装成用户已明确确认的决策.

## 10. 部署, 历史切换与实施顺序

- 不批量修改历史产物. 旧规格或计划可以直接作为资料读取, 继续任务时由 LLM 核对并通过新程序重新整理, 不做旧格式自动执行器.
- navigate 现有固定端口恢复和容器转发说明一起处理, 不能只删服务器文件. 容器展示统一使用 present 现有入口, 不再要求 navigate 单独架桥.
- codebase-map 的停止操作不得误停所有页面共用的 present. 共用服务只按 present 生命周期规则管理, 停止前说明影响, 收工不停止.
- 切换旧服务可能影响已打开页面, 需先列明影响, 不擅自杀掉现有实例或占用者. 需要稳定访问地址的场景不得静默端口漂移后继续交付旧链接.
- 共用代码必须随 skills 正确部署, 不依赖只在仓库中存在的目录层级. 同时验证源码目录和模拟部署目录, 不直接修改真实 agent skills.
- 本次改造自身先用当前可用流程留下起始依据, 不依赖尚未实现的新工具.

建议按以下可调整顺序实施, 不是只交付前几步就算完成:

1. 共用产物能力接入账本和规格, 能独立生成并展示真实规格.
2. present 统一网页接入, 路线图能打开真实产物.
3. 验证方案, 执行拆分和 issues 接入.
4. 实施记录, 评审登记, 独立验证和验收记录接入.
5. 收拢旧展示服务及部署说明.
6. 真实整链演练, 修正并复验后再呈交用户验收.

## 11. 验证与交付标准

至少留下以下可复查证据:

- 从已确认 Markdown 输入出发, 完成一项真实变更的规格到验收全链路, 不只验证文件能解析.
- 不创建任何路线图, 仅调用 to-spec, 仍能获得网页链接, 浏览并确认本次产品/技术规格; Markdown 报告也能独立查看.
- 修改已展示版本后, 旧确认不能用于转正新版; 页面固定版本不被最新草稿替换.
- 正式输入变化只暂停登记上受影响的链, 不静默沿用失效记录; 全局约束也纳入依赖.
- 两个需求有同名文件时网页不串读, 目录规范保持不变, 路径逃逸不可读取.
- 并发写入不丢修改, 版本冲突明确失败; 工作树合并后引用和版本仍可校验.
- Markdown 报告修改后旧登记不能继续冒充有效记录, 已用版本不被覆盖.
- 路线图现有视觉设计保留, 全屏弹窗, 返回/关闭, 专用模板和文档渲染实际可用; 不隐藏判据或执行不可信脚本.
