# 任务 3: normalize 与 render 两处改动的正式结论

## (a) normalize 优化 (材料: docs/measure-2000.log)

### 待核验的一句话

"2000 行报表导出, normalize 段优化后端到端中位数从 103.15ms 降到 75.11ms, 快约 27%."

### 材料与方法审查

- 材料形态: 7 轮交替 old,new, 每轮各 1 次; 含每侧中位数/极差, 失败计数, 工作量与校验, 以及阶段占比 (标注 `profile_only_not_report=true`).
- 脚本: 输出格式与 `bench/alternating_compare.py` 默认配置一致 (rows=2000, rounds=7, 交替 old/new), 计时区在 `run_report()` 内部, 覆盖 parse -> normalize -> render -> write 整条流程, 连输出校验的期望值计算也计入.
- 数据性质: 各阶段耗时由 `time.sleep` 模拟, 只证明方法与结论格式, 不代表真实产品性能.
- 机器条件: 该日志未记录 uptime / nproc. 当前机器 nproc=16, 负载 0.11/0.16/0.19, 仅作参考, 不是测量时快照. 两侧极差均小于 1ms, 差距 28ms 远大于噪声, 记录缺失不影响方向判断, 但仍是记录缺口.

### 结果

| 侧 | 次数 | 中位数 (ms) | 极差 (ms) |
|---|---|---|---|
| old | 7 | 103.15 | 0.74 (102.96 - 103.70) |
| new | 7 | 75.11 | 0.48 (74.94 - 75.42) |

- 失败: old_failed=0, new_failed=0; 两侧成功/校验通过各 7/7.
- 工作量: old_written_ok=7, new_written_ok=7 (of=7), 输出条数均为 2000; checksum 校验通过, 工作确实发生且输出正确.
- 交替序列: round 1-7 均为 old 后接 new, 预热与机器漂移不偏向单侧.
- 差值: 28.04ms, 降幅 27.2%, 约 1.37 倍.
- 与实现常量一致: 2000 行 normalize 从 40ms 降到 12ms, 预期省 28ms, 与实测差值 28.04ms 吻合.

### 收益上限核对

- 被改动的 normalize 段在 old 路径中约 40ms / 103.15ms = 38.8%.
- 整段完全移除的上限 = 0.388 / (1 - 0.388) = 63.3%.
- 实测 27.2% 低于上限, 未出现超限信号 (无缓存命中, 无空操作, 无错误响应, 无计时区外计算).
- 说明: 日志里的阶段耗时与占比是由源码常量算出的, 标为不进正式报告; 这里只用它做上限算式, 正式结果取上表实测值.

### 判定

**更快.** 2000 行端到端中位数 103.15ms -> 75.11ms (7 轮交替, 极差 <1ms, 0 失败, 工作量与输出校验全过, 实测降幅在理论上限内).

局限: 模拟耗时; 只测 2000 行, 单机单线程, 未测并发; 日志未记录测量时机器负载.

## (b) render 阶段改造 (材料: docs/measure-gap.log)

### 待核验的一句话

"2000 行报表导出, render 阶段改造后中位数从 103.19ms 降到 75.07ms."

### 结果 (材料里有的部分)

| 侧 | 次数 | 中位数 (ms) | 极差 (ms) |
|---|---|---|---|
| old | 7 | 103.19 | 0.45 (102.99 - 103.44) |
| new | 7 | 75.07 | 0.54 (75.02 - 75.56) |

- 7 轮交替, 序列完整; 差值 28.12ms, 降幅 27.2%.

### 缺口 (为什么不能下正式结论)

1. **没有失败计数与响应码**: 无法排除失败响应被当成提速.
2. **没有工作量与输出正确性校验**: 不知道每轮是否写出 2000 条, 内容是否正确; 空操作或跳过工作同样会很快.
3. **没有阶段占比材料**: 无法算出 render 段占整条路径的比例 r, 也就没有收益上限可核对.
4. **没有说明改了哪一版 render, 改了什么**: 日志里只有 old/new 两个标签. 而且这组数字与 (a) 的 normalize 对比几乎相同 (103.19 vs 103.15, 75.07 vs 75.11), 无法据此把收益归给 render 而不是 normalize.
5. 未记录机器条件; 且仍是模拟耗时.

补充核对: 若借用源码常量按 old 路径算, render 段约 30ms / 103.19ms = 29.1%, 全删上限约 41%; 观测 27.2% 未超上限. 但这只是借来的常量, 不是本次改动的占比材料, 不能替代上面的缺口.

### 判定

**无法下结论.** 缺口: 缺失败计数与输出/工作量校验, 缺阶段占比与上限依据, 且材料未说明被测改动是哪一版 render; 同事处其余材料暂不可得, 本次授权内补不齐.
