# PR 正文草稿: 优化报表导出 normalize 阶段

## 摘要

把报表导出的 normalize 阶段从 20ms/千行 降到 6ms/千行. 2000 行数据上, 导出端到端中位数从 103.15ms 降到 75.11ms, 降幅 27.2% (约 1.37 倍), 输出校验与改造前一致.

## 改动内容

- 只改 normalize 实现, parse / render / write 三个阶段未动.
- 归一化规则与输出结果保持不变: 每行仍为 strip + lower, 最终 checksum 与改造前一致.
- 无接口变更, 无配置项变更, 调用方无需调整.

## 为什么

normalize 在原实现中占 2000 行导出路径约 38.8% 的时间, 但只做简单的 strip/lower. 改成更低开销的实现后, 该段从 40ms 降到 12ms, 预期端到端省 28ms.

## 测量方法与证据

- 环境: 单机, Python 3, 单线程; 2000 行; 同一份数据与同一版本.
- 对照: old (20ms/千行) 与 new (6ms/千行), 交替排列 old,new 共 7 轮, 每侧 7 次.
- 计时区: `run_report()` 内部, 覆盖 parse -> normalize -> render -> write 全流程, 含输出校验的期望值计算.
- 错误与工作量: 两侧失败均为 0; 两侧各 7/7 轮写出 2000 条且 checksum 校验通过.
- 注意: 当前仓库是演练项目, 各阶段耗时由 `time.sleep` 模拟, 这组数字证明测量方法与结论格式, 不代表真实产品性能; 合入前需在真实实现上按同一方法重测.

### 结果

| 侧 | 次数 | 中位数 | 极差 |
|---|---|---|---|
| old | 7 | 103.15ms | 0.74ms (102.96 - 103.70) |
| new | 7 | 75.11ms | 0.48ms (74.94 - 75.42) |

- 差值 28.04ms, 降幅 27.2%, 与实现预期省 28ms 吻合.
- 极差均小于 1ms, 差距远大于噪声.

### 收益上限核对

- normalize 在 old 路径中约占 40ms / 103.15ms = 38.8%.
- 该段完全移除的理论上限 = 38.8% / (1 - 38.8%) = 63.3%.
- 实测 27.2% 低于上限; 已排查缓存命中, 空操作, 错误响应, 计时区外计算, 均非本次结果来源.

## 复现

```
uv run python bench/alternating_compare.py --rows 2000 --rounds 7
```

输出应包含两侧中位数/极差, `errors ... failed=0`, 以及 `work ... written_ok=7 ... of=7`.

## 风险与回滚

- 风险: 归一化行为若有边界输入差异, 会改变导出内容; 本次以 checksum 校验覆盖了常规 2000 行输入, 但未覆盖异常字符与超大行.
- 回滚: 该改动独立在 normalize 阶段, 回滚即恢复原实现, 不影响其他阶段与接口.

## 局限 (不作为本次结论的部分)

- 只测 2000 行, 未测更大数据规模.
- 未测并发与多实例场景.
- 测量日志未记录当时的机器负载.
- 模拟耗时, 真实实现需重测后才能对外引用具体毫秒数.
