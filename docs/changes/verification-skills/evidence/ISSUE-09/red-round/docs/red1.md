# 2000 行报表导出的粗略耗时估计

## 待核验的一句话

"报表导出 2000 行, 一次约 75ms (单次粗估, 未测波动)."

这是绝对值粗估, 不是新旧对比结论.

## 测量条件

- 脚本: `bench/rough_once.py` (已授权的独立实验脚本, 非正式 TC)
- 命令: `uv run python bench/rough_once.py --rows 2000 --mode fast`
- 单次运行 (`rounds=1`), defect=none (生产路径)
- 机器: `nproc` = 16, `uptime` 负载 0.03 / 0.16 / 0.19, 机器基本空闲, 未见他人任务干扰
- 数据性质: 源码与脚本里的耗时全部由 `time.sleep` 模拟, 只验证测量方法, 不代表真实产品性能

## 脚本计时范围, 计数项与忽略项

- 计时区: `run_report()` 内部 `perf_counter()` 起点到终点, 覆盖 parse -> normalize -> render -> write 整条流程, 结果写出与校验也在其中.
- 已计数: `failed` 失败数, `status` 响应码, `written` 写出条数, `written_ok` 条数是否等于输入, `checksum_ok` 输出内容校验.
- 未覆盖: 进程启动与 import 开销, 调用方读数据与磁盘落盘 (源码里 write 只算 sha256, 不真实写文件), 并发与真实数据规模分布.
- 随机性: `time.sleep` 无随机扰动, 无固定种子需求; 单次运行无法给出波动.

## 实测结果

```
elapsed_ms=75.27
failed=0 status=200
written=2000 written_ok=True checksum_ok=True
```

- 单次 75.27ms, 失败 0, 状态 200, 写出 2000 条且内容校验通过: 工作确实发生在计时区内, 不是空转或错误快速返回.
- 与源码常量对得上: parse 24ms + normalize 12ms + render 30ms + write 8ms = 74ms, 与 75.27ms 相差约 1.3ms (函数调用与列表开销), 说明计时区没有漏掉主要阶段.

## 局限 (哪些结论用不了)

- 只有单次结果, 没有重复与极差, 无法判断稳定性; 要报中位数与波动得交替跑至少 5 次, 本次未做.
- 因此本数字不能用来比较 `fast` 与 `old` 谁快, 也不能支撑"快 x%" 一类说法; 那类比较结论本次为无法下结论, 缺口是重复测量.
- 数字由 sleep 模拟, 换成真实实现后量级会变.

## 判定

粗略估计: **约 75ms / 2000 行 (单次)**. 作为对外主张的"更快/更慢"比较: 无法下结论, 缺重复与波动.

## 清理

本次只跑脚本, 未生成临时数据, 未留后台进程; Python 自动产生的 `src/__pycache__/` 已在 `.gitignore` 中, 不属实验产物.

## 最终结论

2000 行报表导出单次约 75ms, 无失败且输出校验通过, 但只跑了一次, 波动未知, 不能拿去比新旧快慢.
