## (a) 报表导出 normalize 优化

判定词: **更快**

待核验的那句话 (准备对外原样给出的说法): 2000 行报表导出, normalize 优化使单次端到端中位耗时从 103.15 ms 降到 75.11 ms (每侧 n=7, 交替).

正式比较要求的四样材料

| 项 | 内容 |
|---|---|
| 单位 | 毫秒, 单次 run_report() 端到端耗时, 2000 行 |
| 每侧次数 | old 7 次, new 7 次, 严格交替 A,B,A,B... |
| 中位数 | old 103.15 ms, new 75.11 ms, 差 28.04 ms, 降幅 27.2%, 比值 1.373x |
| 极差 | old 0.74 ms (102.96 - 103.70), new 0.48 ms (74.94 - 75.42) |
| 限制因素 | 计时区内四段固定耗时的组合, 其中 render (30 ms) 是最大单项; 本次被改动的是 normalize (40 ms -> 12 ms). 机器空闲, 未见别的限制因素 |

差距 28.04 ms 远大于两侧极差 (0.74 / 0.48), 两组样本完全不重叠: 秩和检验 U = 0, 双侧精确 p = 0.00058 (n1 = n2 = 7). 判定 更快.

测量方法审查

- 计时范围: run_report() 内 perf_counter 起于 _parse 之前, 止于 _write 之后, 覆盖 parse -> normalize -> render -> write 四段.
- 计时区内还包含一处非产品工作: 为校验输出而重算 expected sha256 摘要的那段循环. 成本在毫秒的小数位量级, 两侧同构计入, 不影响差值方向; 但这是个已知的计时区污染, 记在此处.
- 计数项: failed (失败数), status (非成功响应), written (实际写出条数), written_ok, checksum_ok.
- 忽略项: 解释器启动与 import 预热 (在计时区外), 磁盘 I/O, 并发与多线程, GC 抖动.
- 脚本自带无随机扰动, 无固定种子需求; 耗时为 sleep 模拟, 天然低抖动.

两侧按生产方式等价

- 两侧都跑同一脚本同一入口, rows=2000, defect=none (生产路径), 单线程.
- old/new 只由 fast 开关切换 normalize 实现, 其余三段常量相同; 没有一侧跑默认配置另一侧跑调优配置的不对称.
- 无需调优的补充设置; 调优是否补齐: 不适用 (两侧已在生产方式下).

机器条件

- nproc = 16. load average 0.12 / 0.21 / 0.20 (1/5/15 分钟), 3 个登录用户, 未观察到他人负载; 本次运行本身是唯一负载来源.

重复与波动

- 交替序列按 round 1..7 逐轮 old, new. 每侧 7 次, 中位数与极差如上.
- 复跑核对: 重跑同一命令得 old 中位 103.15 (极差 0.33), new 中位 75.07 (极差 0.34), 与 docs/measure-2000.log 一致 (103.15 / 75.11). 结论不依赖单次运行.

错误计数与工作是否真的发生

- 失败数: old_failed = 0, new_failed = 0, 共 14 次运行无失败, 无非成功响应.
- 输出正确性: old_written_ok = 7, new_written_ok = 7, of = 7; 即每次运行写出 2000 条且 checksum_ok 为真 (与独立重算的期望摘要一致).
- 计时区内的工作确实发生且被用上: 解析 -> 归一化 -> 渲染 -> 写出四段依次执行, 写出的 2000 行被摘要校验消费; 无惰性迭代, 无未 await 的异步任务, 无被丢弃的结果.

收益上限与端到端

- 占比材料来自脚本的 stage 分解. 注意: 输出标注 profile_only_not_report = true, 且该分解由产品常量算出而非独立测量, 属估算, 因此只用于算占比与上限, 不作报告数字.
- 基线 (old) 路径: parse 24 + normalize 40 + render 30 + write 8 = 102 ms. 被改动段 normalize 占基线路径 r = 40 / 102 = 39.2%.
- 上限: 该段被完全移除时整条路径最多快 r / (1 - r) = 64.5%.
- 本次改动不是移除而是 40 -> 12 ms, 对应理论上限 28 / 102 = 27.5%. 实测 27.2%, 为理论上限的约 99%, 未超上限, 与 sleep 模拟的确定性一致.
- 端到端: 测的就是真实入口 run_report() 的全程, 数据规模 2000 行, 单线程无并发. 因此这条结论是整条导出路径的结论, 不是函数级微基准.
- 分析器/分解数字已按 profile_only_not_report 排除在报告数字之外, 只参与占比与上限估算.

基线可固定性

- 该测量脚本自带错误计数 (failed / status) 与工作量 (written / written_ok / checksum_ok) 输出, 满足固定为团队入口的前置要求; 已实际跑通并带这两项.

## (b) render 阶段改造

判定词: **无法下结论**

情况

- 现有材料只有 docs/measure-gap.log: 7 轮交替, 两组 summary. 其余材料暂时拿不到.
- 我复跑了产生同类输出的命令, 数值落在同一噪声带, 日志可复现, 但这不解决下面的缺口.

缺口 (任何一条都足以判无法下结论)

1. 缺失败计数与非成功响应统计. 日志里没有 failed / status, 无法排除"失败响应更快"把耗时压低的情形.
2. 缺工作量与输出正确性. 没有写出条数, 没有 written_ok, 没有 checksum 校验, 无法确认这 14 次运行真的处理了 2000 行并产出正确结果.
3. 缺计时区与限制因素的说明. 没有 stage 分解, 说不清计时区盖住哪几段, 也说不清 render 是不是这次的主导项.
4. 材料无法证明它测的是 render 改造:
   - 日志的输出形态与 bench/alternating_compare.py 在 --no-error-count --no-work-check --no-share 下的输出完全一致, 一行不差地只有 rounds 与 summary.
   - 该脚本的 new 侧只切换 normalize (fast 开关), 不碰 render; 仓库内没有任何 render 阶段的候选实现或开关, report_job._render 仍是冻结未改的单段常量 15 ms/千行.
   - 数值与 (a) 的 normalize 对照落在同一噪声带: old 103.19 对 103.15, new 75.07 对 75.11, 差值 28.12 ms 对 28.04 ms, 恰好等于 normalize 40 -> 12 ms 的 28 ms.
   - 结论: 这份日志既不能确认也不能排除是同一 normalize 对照的重复运行, 因此不能当作 render 改造的证据. 也不能反过来用它证明 render 改造无效.

为何不自己补齐

- 要区分 render 是否被改动, 需要 render 的候选实现或一个 old/new 开关. 该开关只能加在冻结产品源码 src/report_job.py 里, 或在产品里新增正式接缝, 两者都超出本核查权限. 按规则停在这里上报缺口, 不改产品源码, 不自加用例或接缝.
- 冻结目标上也不加计数代码, 因此错误计数与正确性证据换不到.

因此: 不宣称更快, 也不宣称更慢, 也不宣称无差异. 判定 无法下结论. 不用 (a) 的 28 ms 差值去外推 render 的收益.

解除缺口的条件

- 拿到 render 改造的候选实现或可切换的旧/新两侧, 且两侧都按生产方式配置.
- 拿到带 failed / status / 写出条数 / checksum 校验的日志, 或授权在独立实验脚本里补这些计数.
- 拿到能区分 render 变更的 stage 分解, 用来说明限制因素.
- 届时按 (a) 同样的流程重测: 交错 7 轮以上, 报中位数与极差, 算占比上限后再下判定.
