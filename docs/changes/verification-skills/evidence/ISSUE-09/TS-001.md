## 红轮 (v0 技能, 无粗估与选型规则)

- `red-round/docs/red1.md` (`bm9-red` 任务 1, 单次粗估): 主动写了 "单次粗估", 给了单位, 同一轮查了 `failed`/`written`/`checksum` 与计时区工作. 该模型上 **没有跑红**.
- `red-round/docs/red2.md` (a) (500 异常): 做了复跑, 判 "无法下结论", 还发现给定 3.02ms 与源码路径矛盾. **没有跑红**.
- `red-round/docs/red2.md` (b) 与 `red-round/docs/red4.md` (a) (两库选型): 首轮未调优就声明 "这一轮比的是配置, 不用来选赢家", 补 `--tune-b` 后 5 轮交替再选. **没有跑红**.
- `red-round/docs/red4.md` (b) (错误输出): 判 "无法下结论", 缺口写作输出正确性. **没有跑红**.
- 结构性事实 (补充, 不作行为证据): v0 技能里没有粗估单次例外, 也没有选型边界的正文, 见 `git show 3c187b7:.agents/skills/benchmark-checklist/SKILL.md`; 本 ISSUE 的增量是这两处规则本身.
- 结论: 本模型在 v0 上未触发 AC-028 的失败表现, 如实记录, 不写成红轮通过. 绿轮的证据是 v1 规则下同一批场景的完整行为.

## 缺口与风险

- 全部数字来自 `time.sleep` 模拟, 只证明方法与判定流程, 不代表真实产品性能.
- 单模型单宿主 (16 核, pi 1.3.0, herdr 0.9.4); 其他模型是否会在 v0 上把单次数字当正式结论未验证, 所以本 ISSUE 的规则价值只能靠"规则已写入且可被点名加载"证明, 不能靠"必然跑红"证明.
- 选型轮里 fastidx 未调优的 7 轮被脚本记 `work_ok=0/7`, 那是脚本把 `per-row` 模式当不通过, 不是没干活; 会话已在 (c) 注明.
- 会话自己改过 `bench/two_libs.py` (补交替, 错误计数, 工作量校验), 属授权的独立实验脚本范围, 产品源码未动; 差异见 `red-round/bench/two_libs.py.diff`.
