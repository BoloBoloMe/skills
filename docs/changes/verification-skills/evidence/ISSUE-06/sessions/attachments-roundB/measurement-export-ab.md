# 测量记录: 新版导出 (b) vs 旧版 (a)

## 待核验的对外结论 (原句)

"5 行数据 (1000..1004) 导出, 新版 b 的 p50 耗时从旧版 a 的 73.5 ms 降到 82.2 ms, 快 8.8 ms."

复核结果: 该句为假. b 实际更慢, 且 5 行里有 2 行返回失败, 两边完成的工作不同.

## 测量脚本的计时范围 / 计数项 / 忽略项

`bench/run_export.py` (原脚本, 未改):

- 计时范围: 仅 `export(rows, side)` 这一次调用的 wall clock (`perf_counter`), 不含 python 启动.
- 计数项: 只有耗时. 不记录结果条数, 不记录 ok/fail.
- 人工扰动: `measure()` 给每个样本加 `rng.uniform(-2, +2)` ms (profile=clear) 或 `+/-4` ms (close). 固定种子 7.
- 忽略项: `PROFILES` 两档都是 `("a","b")`, 且 `profile` 只进入随机数的幅度, 不进入被测代码. 所以 `--profile clear` 与 `close` 跑的是同一份代码, "两档差距" 是人为噪声, 不是测量结果.
- 其他陷阱: `--side a --mode tuned` 仍走 `export(..., "a")`, `--side b --mode tuned` 走 `export_tuned(...)`; 标签与实际被测实现会错位.

`bench/verify_ab.py` (本次新增, 用于核验): 同样的 5 行, 去掉了叠加随机数, 先各跑 2 次预热, 再 A/B/A/B 交替取 20 对; 记录 p50/min/max、每侧返回成功行数、配对差.

## 机器条件

- `nproc`: 16.
- 测量前后 `uptime` load average: 4.66 / 4.61 (1 分钟), 5 分钟约 2.97. 负载来自本机其他会话 (4 个 bash 各占约 100% CPU 等), 无权停, 按清单采用交替测量, 两侧吃同样噪声.
- 未使用 profiling / tracing.

## 结果

| 侧 | p50 | min | max | 成功行数 |
| --- | --- | --- | --- | --- |
| a | 73.5 ms | 73.3 | 75.9 | 5/5 |
| b | 82.2 ms | 82.1 | 83.8 | 3/5 |

- 配对差 (b-a): p50 +8.8 ms, 范围 +6.3 .. +10.1 ms, 20/20 对都是 b 更慢.
- 代码层面的解释 (与实测吻合): a 每行 `sleep(0.014)`, b 每行 `sleep(0.016)`, 5 行即 +10 ms; b 在 index 1 和 4 (行 1001, 1004 > 500) 走错误快路径, 跳过 `_work` (单次约 0.68 ms), 省回约 1.4 ms. 净差约 +8.6 ms.
- 因此 "b 快" 不成立; 即使去掉 `sleep` 差额, b 的数字也不是同等工作量: 它少算了 2 行, 且这 2 行是失败响应.

## 结论

更快 / 更慢 / 无可测差异 / 无法下结论: **新版 b 更慢**(在本脚本的 5 行负载上, 中位慢 8.8 ms, 且少了 2 行成功结果, 不构成同等工作量的性能对比).
