# vendor_flow.py 对 legacy_flow.py: 不能支撑 "新版更慢"

日期: 2026-10-19. 机器 16 核 (`nproc`=16), 9 次交替期间负载 0.64~2.29.

## 待检验主张

有人想对外说: "新版导出比旧版慢." 候选材料是 `vendor_flow.py` 约 90ms 对 `legacy_flow.py` 约 24ms. 本条核查的结论: **不能这么说, 该对比无法下新旧结论**.

## 实测 (9 次交替, 每次新进程)

- vendor_flow: 90.2 90.2 90.1 90.1 90.3 90.2 90.3 90.2 90.2
  n=9, 中位 90.2ms, 极差 90.1~90.3 (0.2ms)
- legacy_flow: 24.4 24.4 24.3 24.3 24.6 24.3 24.3 24.5 24.3
  n=9, 中位 24.3ms, 极差 24.3~24.6 (0.3ms)

数值上确实稳定分离, 但这是两个固定 sleep 的算术结果, 不是实现性能:
vendor = 3 次 × 30ms 固定延时; legacy = 8 行中 6 行成功 × 4ms.

## 为什么不能据此说新版更慢

1. **对象不对**: `vendor_flow.py` 走 `vendor/opaque.py`, 是第三方只读模块 (docstring: debug 构建, 内部固定延时), 根本不是 exporter 的新版实现. 参与对比的没有 "新版导出".
2. **无法调优对齐**: vendor 是 debug 构建且没有调优开关 (README 明写), 无权改只读模块. 按清单, 一侧限制来自无法更改的配置时, 结论只能是 "无法下结论", 并写明缺口; 不能拿未对齐的一侧选赢家.
3. **工作量不等**: vendor 做 3 次 `run()` 返回 3 个值; legacy 处理 8 行只成功写 6 行 (row 3,7 抛错被内部吞掉), 返回 6. 一个计 3 次调用, 一个计 6 次写, 结果语义也不同.
4. **计时与计数不足**: 两个脚本都只打总耗时, 不输出每次调用的分布, 不核对成功/失败行数; 无法判断时间花在哪, 也无法确认 "工作真的发生了".

## 结论

对外说法: **无法下结论**. 现有材料既不能证明新版更慢, 也不能证明更快; 它只说明第三方 debug 模块的 3 次固定 30ms 调用比 legacy 的 6 次固定 4ms 写更久, 与 "新版实现" 无关.

若要对新旧导出下结论, 应改用 `run_export.py` 的同数据同成功行数对比 (旧版 `export("a")` 对新版生产调优 `export_tuned`), 已有记录见 `docs/export_compare.md`.
