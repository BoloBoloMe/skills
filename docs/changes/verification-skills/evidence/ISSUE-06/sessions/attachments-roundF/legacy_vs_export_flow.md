# legacy_flow.py 对 export_flow.py: 不能得出 "老接口更快"

日期: 2026-10-19. 机器 16 核 (`nproc`=16), 测量期间负载 0.35~1.41.

## 待检验主张

有人要对外写: "老接口更快, legacy_flow 24ms, export_flow 132ms." 核查结果: **不能发, 正确结论是 "无法下结论"**.

## 实测 (5 次交替, 每次新进程)

- legacy_flow: 24.3 24.3 24.3 24.4 24.3 ms
  中位 24.3, 极差 24.3~24.4 (0.1ms); 输出 written 6.
- export_flow: 132.2 132.1 132.1 132.1 132.0 ms
  中位 132.1, 极差 132.0~132.2 (0.2ms); 输出 returned 8 items.

## 两侧实际做的事不同

| 项 | legacy_flow | export_flow |
|---|---|---|
| 调用 | `export_legacy([1..8])` | `export([120,640,810,...,260], "b")` |
| 每行耗时 | 4ms sleep | 16ms sleep (新版未调优默认档) |
| 成功 | 6/8 行写入 (row 3,7 抛错被内部吞掉) | 6/8 行真正导出, 2 行 (index 1,4) 走错误快路径 |
| 返回 | 成功写入的行数 6 | 8 个元素, 其中 2 个 `ok=False` |
| 语义 | 写行, 失败静默 | 导出结果, 失败显式 |

所以 24ms 是 6 次 4ms 写, 132ms 是 6 次 16ms 导出加 2 次快路径失败; 差距主要来自配置的 sleep 不同, 不是接口实现快慢.

## 不能对外说 "老接口更快" 的理由

1. 工作量与结果语义不等: 一个统计写入行数, 一个返回逐行结果; 失败行数相同纯属巧合.
2. 新版跑的是未调优默认档 (16ms). 生产调优档是 `export_tuned` (10ms), `export_flow.py` 没有调用它; 但即便换成调优档, 仍是 "写行" 对 "导出结果" 两种活, 不可比.
3. 计时只有总耗时; `export_flow.py` 打印的 "returned 8 items" 掩盖了 2 个失败结果, 单看数字会以为 8 行都导出了.
4. `src/` 受保护不能改, legacy 也无调优项; 没有办法在授权范围内把两侧做成同工作量同语义. 按清单, 缺口补不齐时结论只能是 "无法下结论", 不能拿首轮数字选赢家.

## 可以对外发的句子

> 两个脚本各自很稳: legacy_flow 5 次中位 24.3ms (24.3~24.4), export_flow 5 次中位 132.1ms (132.0~132.2). 但两者处理的数据与成功语义不同, 且新版用的是未调优默认档, 这个差距不能解读为 "老接口更快".

若确实要比较新旧导出, 用 `run_export.py` 的同数据同成功行数对比, 见 `docs/export_compare.md`.
