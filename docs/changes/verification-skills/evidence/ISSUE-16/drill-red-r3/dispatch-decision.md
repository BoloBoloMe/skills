## 3. 分组, 人数与共用准备

### 3.1 场景组

只有一组:

- G1: AC-001-1 + AC-002-1 + BR-001.

计划派 1 名未参与本次实现与修复的非作者验收者.

### 3.2 只派一人的理由

- AC-001-1 和 AC-002-1 都假定同一个固定实例 `127.0.0.1:18231`; `NG-001` 明确不做多实例. 不为制造并行去加实例, 扩端口或放宽授权, 所以运行检查不能拆成两个同时开工的组.
- AC-002-1 已决定引用旧观察, 运行部分只剩 AC-001-1 的一次真实 `/health` 请求.
- BR-001 是小型只读静态检查, 不占用服务实例, 但工作量很小. 再开一个会话的启动和协调成本大于并行收益, 也不能缩短关键路径. 由同一名验收者在启动服务前后顺手完成即可.
- 因此只有一个不可再分的运行组. 当轮可用非作者验收者人数未知; 按最小必要派 1 名. 若实际可用人数为 0, 报告受阻并停下, 不让作者或参与过实现/修复的会话顶替.

### 3.3 共用准备与原始材料归属

- 共用准备只做一次: 由这名验收者从目标工作区启动一个 `127.0.0.1:18231` 实例, 供 AC-001-1 使用. 启动入口按项目 README: `python3 app.py 18231` (前台运行, 回环地址, Ctrl-C 停止). 这是被验产品的真实入口, 不用本地替身, 不换端口.
  - 启动入口以项目 README 为准. 本机全局的 uv 约定用于辅助脚本, 不用来替换被验产品文档里的入口; 报告要记录实际解释器路径和版本.
- 共用准备由 G1 验收者负责; 原始材料 (启动记录, curl 输出, 进程与端口状态, 清理记录) 也归 G1 验收者, 放到本轮证据目录.
- 作者日志只作为参考材料交给验收者. 产生者是作者, 版本与位置见第 2 节和第 7 节; 接收方必须自己核对覆盖范围, 版本和环境条件, 再独立给出结论, 不照抄作者的"通过".
- 没有写入片段争用: 本轮计划不写测试资源. 唯一共享资源是端口/实例, 只由一名验收者使用, 不需要先后排队.

### 3.4 执行顺序

1. 先做 BR-001 静态核对 (只读, 不需要服务).
2. 核对 `HEAD` 与工作区, 确认 `18231` 未被占用, 再启动服务.
3. 对 `/health` 发真实请求, 记录状态码, 响应体, curl 退出码, 时间, 进程和端口归属.
4. 停止服务, 验证进程消失, 端口释放, 没有留下 `runtime/` 或 `__pycache__/` 等临时对象.
5. 读取 `/version` 旧观察并核对适用条件; 适用就引用, 不适用就报告缺口或按规则改为本轮实跑.
6. 把原始记录和报告写入 `docs/changes/first-acceptance/round-1-65114d4/`.
