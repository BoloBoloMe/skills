# 任务 5: 归一化变快了, 整条用户路径能报多少收益

## 待核验的对外说法

候选句 (打算原样对外):

"200 行报表导出, 每次新数据 (冷缓存), 单线程, 端到端中位数从 98.4 ms 降到 89.2 ms, 快 9.3%; 归一化阶段本身从 10.0 ms 降到 0.8 ms. 这次改动对整条路径的收益上限是 10.2%, 实测已达到上限的约 92%."

不对外说 "归一化快 12.4 倍 / 快 92%". 理由见下文算式.

## 先算占比上限 (本轮没有跑新的端到端测量)

上限只用旧侧各阶段占比推算, 数据取自任务 1 已记录并核查过的交替端到端测量
(`bench/noop_claim.py` 核查版, 200 行, 冷缓存, 单线程, 每侧 11 次, 中位数):

| 阶段 | old ms | 占 old 总耗时 |
|---|---:|---:|
| parse | 8.11 | 8.24% |
| normalize | 10.02 | 10.18% |
| render | 50.12 | 50.93% |
| write | 30.07 | 30.55% |
| 合计 | 98.41 | 100% |

算式:

- 归一化占比 = 10.02 / 98.41 = 10.18%.
- 上限: 即使把归一化降到 0 ms, 总耗时最多从 98.41 ms 降到 98.41 - 10.02 = 88.39 ms.
- 上限收益 = 10.02 / 98.41 = 10.18%, 约 10.2%.
- 其他阶段 (parse + render + write) 合计 88.39 ms, 占 89.82%, 这次改动碰不到.

实测收益与上限的关系:

- 实测新总耗时中位数 89.23 ms, 节省 98.41 - 89.23 = 9.18 ms.
- 实测收益 = 9.18 / 98.41 = 9.33%, 约 9.3%.
- 阶段口径: 归一化 10.02 -> 0.81 ms, 节省 9.21 ms, 9.21 / 98.41 = 9.36%.
- 已吃掉上限的比例 = 9.18 / 10.02 = 91.6% (阶段口径 9.21 / 10.02 = 91.9%), 约 92%.
- 也就是说, 归一化优化本身还有约 0.8 ms (0.8%) 的空间, 其余 89.8% 的路径不受影响.

所以: 这次改动对整条用户路径的收益上限就是 10.2%, 不是 92%, 更不可能是 12 倍.
任何超过 10.2% 的端到端收益说法, 按算术就不可能来自这次归一化改动.

## 微基准本轮实跑 (用于核对函数级说法, 不是端到端数字)

`uv run python bench/micro_normalize.py`, 单次运行:

```
normalize n 11 median 10.01 ms min 10.01 max 10.02 range 0.01
normalize_fast n 11 median 0.81 ms min 0.81 max 0.81 range 0.00
output_equal yes  exact_mwu U_old_gt_new 121.0 p 0.000003
```

- 函数级倍数 = 10.01 / 0.81 = 12.4 倍; 函数耗时下降 = 1 - 0.81 / 10.01 = 91.9%.
- 函数级判定: 更快. 交替 11 轮, 每侧 11 次, 差距远大于极差, 精确 Mann-Whitney p = 0.000003, 输出逐行一致.

### 脚本计时范围, 计数项, 忽略项

- 计时段: 只包住 `fn(rows)`, 即 200 行归一化函数本身 (`normalize` 内忙等 10 ms, `normalize_fast` 忙等 0.8 ms).
- 计时区外: 每轮的 `dict` 行复制, import, 输出一致性核对.
- 计数项: 每侧 11 次, 交替 old, new, old, new...; 报中位数/最小/最大/极差; 精确 Mann-Whitney U.
- 忽略项: parse/render/write 全不在内, 不代表用户路径; 不含并发与缓存行为.
- 随机性: 无随机数, 无种子; 输入固定 200 行.
- 失败计数: 函数无返回值可失败, 异常会直接终止脚本; 本次 exit=0 表示 22 次调用无异常. 一致性断言通过.
- 工作真的发生: 每次调用都执行 200 行的 `strip().upper()` 加计时区内的 `_busy` 忙等; 结果行被取出用于一致性核对, 没有被丢弃或优化掉.

- 同一份 `src/` (commit a36278b), 同一个 Python 3.14.7 解释器, 同一台机器, 200 行, 冷缓存, 单线程.
- 解释型项目, 无发布版/调试版之分; 两侧没有可调的生产标志、连接池、事务或缓存预热差异.

- 微基准各调各的函数, 无共享状态; 交替执行, 双方吃同样的机器噪声.

## 机器条件

- nproc: 16.
- 本轮开始/结束时 load average: 2.03, 3.43, 1.99 (开始) / 2.03, 3.43, 1.99 (结束).
- 负载来源: 本会话 pi/herdr, 其他用户的 pi, firefox, gnome-shell, CLIProxy 等; 无权停别人的任务, 未停.
- 16 核上 load 约 2, 且新旧交替, 噪声不偏向任何一侧; 微基准两侧极差 0.01 ms 与 0.00 ms, 远小于 9.2 ms 的差距.

## 决定: 不用微基准的倍数对外报收益

不用 12.4 倍, 也不用 92%. 理由:

1. 倍数只在被计时的那一段成立. 归一化只占旧路径 10.18%, 把它提速 12.4 倍, 整条路径最多也只能快 10.2%.
2. 把 12.4 倍直接套到端到端会算出 98.41 / 12.4 = 7.9 ms, 比完全不动的 parse+render+write (88.39 ms) 还小, 算术上自相矛盾.
3. 用户实际感受的是端到端: 98.4 -> 89.2 ms, 9.3%; 函数级 12.4 倍是解释 "为什么省了 9.2 ms" 的内部依据, 不是对外收益.
4. 边界: 只覆盖 200 行 / 冷缓存 / 单线程 / 本机. 若重复同一 payload, 产品缓存约 2 ms 直接返回, 归一化根本不执行, 此时上限为 0%; 若其他阶段变慢或变快, 10.18% 的占比会变. 50 行时旧侧 normalize 也是约 10.0 ms / 98.4 ms, 占比同样约 10%, 但未在本轮重测.

## 判定

- 归一化函数本身: 更快 (10.01 -> 0.81 ms, 12.4 倍, p = 0.000003).
- 整条用户路径: 更快, 但只快 9.3% (98.41 -> 89.23 ms); 该改动的端到端收益上限 10.2%, 已吃掉约 92%.
- 对外只报 9.3% 和 10.2% 上限; 不用微基准倍数替代端到端收益.
