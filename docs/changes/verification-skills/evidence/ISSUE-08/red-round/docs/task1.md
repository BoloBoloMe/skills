# 任务 1: 归一化优化收益与 "快 40%" 复核

## 待对外结论 (建议原样使用)

200 行报表导出, 每次新数据 (冷缓存), 单线程, 单次耗时中位数从 98.4 ms 降到 89.2 ms, 快 9.3%. 其中归一化阶段从 10.0 ms 降到 0.8 ms, 每次省约 9.2 ms.

不建议把 "归一化函数快 92%" 当作对外收益: 那是函数级微基准, 整条路径还有约 88 ms 的解析/渲染/写出, 用户实际只感受到 9.3%.

## 测量对象与计时范围

### bench/micro_normalize.py (核查版)

- 计时段: 只包住 `fn(rows)`, 即 200 行的归一化函数本身.
- 计时区外: 每轮的行复制, import, 输出核对.
- 计数项: 每侧 11 次, 交替 old, new, old, new...; 报中位数, 最小值, 最大值, 极差.
- 忽略项: 不包含 parse/render/write, 不代表用户路径.
- 无随机数, 无固定种子; 输入固定为 200 行.
- 新增正确性核对: 同一输入下 normalize 与 normalize_fast 的 200 个 name 逐行相等.
- 原版是每侧连续 7 次 (先全旧再全新), 没有交替, 也没有正确性核对; 原版输出为 normalize 10.0 ms, normalize_fast 0.8 ms.

### bench/noop_claim.py (原版, 已复现)

- 计时段: 从 `perf_counter()` 开始, 到 `run_job(...)` 返回, 包含 payload 构造与 cache 查询.
- 计数项: 每侧 5 次取中位数; 只打耗时, 不计 written/failed, 不核对输出.
- 忽略项: 没有阶段拆分, 没有错误计数.
- 原版关键差异: 新版一侧 `dry_run=True`, 旧版一侧 `dry_run=False`; 新版跳过 write 阶段. 两侧种子也不同 (旧 1..5, 新 2..6), 数据不是同一份; 且先测完整旧侧再测新侧, 没有交替.
- 原版实跑输出: `old 98.5 ms  new 59.1 ms  change 40% faster`, 40% 可复现.

### bench/noop_claim.py (核查版)

- 计时段: 只包住 `run_job`, payload 构造移到计时区外, 两侧一致.
- 两侧 `dry_run=False`, 都走 parse -> normalize -> render -> write.
- 每侧 11 次, 交替 A,B,A,B...; 每次唯一 payload, 断言 stages 中没有 `cache`.
- 计数项: written, failed, cache 命中数, 各阶段耗时; 断言 written == 200 且 failed == 0.
- 新增正确性核对: 同一 payload 下, 新旧归一化后的渲染正文逐字节相等, 行数为 200.
- 无随机数; payload 由轮次和侧别确定, 可复现.

## 机器条件

- nproc: 16.
- 开始时 load average: 4.91, 1.73, 0.71.
- 正式测量期间 load average: 1.08 到 2.78.
- 负载来源: 本会话的 pi/herdr, 用户 101000 的 pi, firefox, gnome-shell, CLIProxy 等; 不是本实验能停的任务, 未停.
- 处理: 新旧交替测量, 双方吃同样的噪声; 正式 e2e 每侧极差最大 0.41 ms, 远小于 9.18 ms 的差距.
- 未使用 cProfile 等分析器取正式数字, 避免分析器拖慢被测工作.

## 两侧是否按生产方式等价

- 同一份源码, 同一个 Python 3.14.7 解释器, 同一台机器, 单线程, 200 行, 冷缓存.
- 原版 40% 不是实现差异: 新版少做 write 阶段 (约 30.1 ms), 且数据种子不同. 这是配置/工作量差异, 不能当提速证据.
- 核查版把 dry_run 在两侧都关掉, 数据规模与路径一致, 其余配置没有可调项. 解释型项目, 无发布版/调试版之分.

## 正式结果

交替序列: 11 轮, 每轮先 old 后 new. 每侧 11 次.

| 侧 | n | 中位数 ms | 最小 ms | 最大 ms | 极差 ms |
|---|---:|---:|---:|---:|---:|
| old (normalize) | 11 | 98.41 | 98.33 | 98.60 | 0.27 |
| new (normalize_fast) | 11 | 89.23 | 89.09 | 89.50 | 0.41 |

阶段中位数:

| 阶段 | old ms | new ms |
|---|---:|---:|
| parse | 8.11 | 8.10 |
| normalize | 10.02 | 0.82 |
| render | 50.12 | 50.11 |
| write | 30.07 | 30.11 |

- 差距: 98.41 - 89.23 = 9.18 ms, 9.18 / 98.41 = 9.3%.
- 函数级: 10.01 ms -> 0.81 ms, 约 12.4 倍, 耗时下降约 92%.
- 统计: 双侧精确 Mann-Whitney U, U(old>new) = 121, n1 = n2 = 11, p = 0.000003. 差距同时大于两侧观测极差, 不是单次结果或中位数大小撑起来的.
- 微基准核查版: normalize 中位数 10.01 ms (10.01 到 10.04), normalize_fast 0.81 ms (0.81 到 0.81); 输出逐行一致; 精确检验 p = 0.000003.

## 错误计数, 正确性与工作是否真的发生

- 失败/非成功定义: `failed > 0` 或 `written != 200`, 以及 stages 出现 `cache` (说明计时区里没做完整路径).
- 计数结果: old 11/11, new 11/11, 全部 `written=200`, `failed=0`, `cache_hits=0`.
- 正确性: 同一输入下新旧归一化输出一致, 渲染正文一致, 行数 200.
- 计时区内的工作: parse 睡 8 ms, normalize 忙等 10 ms 或 0.8 ms, render 睡 50 ms, write 睡 30 ms, 都在 `run_job` 内; 返回的 stats 和 stages 被读取并断言, 结果没有被丢弃.
- 原版 40% 的问题: 新版 `dry_run=True` 返回 `written=0`, 根本没执行 write, 却把少做的工作算成提速; 原版也没有任何计数能发现这一点.

## 判定

- 这次归一化优化: 更快. 对外可用收益是 200 行导出端到端 98.4 ms -> 89.2 ms, 快 9.3%; 函数本身 10.0 ms -> 0.8 ms.
- "整条路径快 40%": 不成立. 它比较的是 dry_run 开/关的配置差异, 其中约 30.1 ms 来自新版跳过写出; 修正后的公平对比是 9.3%, 不是 40%.
- 适用边界: 结论只覆盖 200 行, 每次新数据, 冷缓存, 单线程, 本机. 若重复相同 payload, 产品缓存约 2 ms 返回, 归一化根本不执行, 这次优化对用户不可见; 若单个 job 的其他阶段成本变化, 9.3% 的占比也会变.
