## 红轮 (v0 技能, 无本节规则)

- `red-round/docs/task2.md` (`bm-red` 任务 2): 没有新规则时也做了 baseline 审查 (复现 98.4 ms, 列出单次/构造计入/50 行/无版本), 也把 `team_entry.py` 补了工作量, 成功数与失败数, 并拒绝固定 `gate_measure.py` (报缺口, 未改 `src/`).
- 结论: AC-031 的三个分支红轮都没有跑红. 原因是 v0 已经带有 AC-027 的 "脚本没计数时在授权脚本内补计数" 规则, 该模型据此完成了大部分动作. 新节仍按 AC-031 写入, 因为: (a) 基线审查与固定入口的结论条件是 AC-031 的独立要求; (b) 绿轮把固定条件写成了可执行的接受条件 (exit 0 + correctness + 计数三项) 和自检反例, 强度高于红轮的自由发挥; (c) 后续 ISSUE-09 的结论规则依赖这里对 "固定入口" 的定义.

## 缺口与风险

- 自检反例在 lab 的 `/tmp` 复制件里做 (删 `.upper()`), 不在产品的 `src/` 上做; 复制件的耗时数字没有进入正式对比.
- `gate_measure.py` 的缺口只在本机模拟入口上验证; 真实项目里 "产品返回行级计数" 的形态可能不同.
- 演练只覆盖 50 行, 并发 1 的入口自检; 生产规模与并发未测, 记录里已写明边界.
- 只在单一宿主与 pi 1.3.0 + herdr 0.9.4 上做过.
