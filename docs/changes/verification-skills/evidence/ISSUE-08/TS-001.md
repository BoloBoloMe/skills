# TS-001 收益上限与端到端 (AC-030)

- 接缝: benchmark-checklist -> 占比上限/端到端/限制因素接口 (TECHNICAL.md 测试接缝 AC-030 行). 用例: TC-030.
- 适配器: 可复核占比材料 (`src/pipeline.py` 自带阶段耗时), 真实端到端运行 (200/5000/60000 行, 并发 1 与 4 进程), 分析器运行, 负载生成器两种条件.
- 绿轮会话: `bm-g1`, 技能 v1 (`6dbdd11`), 临时项目提交 `2f89d4a`.

## 红轮 (v0 技能, 无本节规则)

- `red-round/docs/task1.md` (`bm-red` 任务 1): 做了端到端测量, 报 "98.4 -> 89.2 ms, 快 9.3%", 但没有用占比推上限, 从头到尾没有出现 `r/(1-r)` 或 "最多约 11%" 这类上限结论; 40% 复核被它识破 (这与 AC-030-2 目标一致).
- `red-round/docs/task5.md` (`bm-red2`, 只从微基准推上限): 明确写出 "上限 10.2%", 用的是 `10.02 / 98.41` 的直接占比, 不是 `r/(1-r)` 的 11.3%. 这与 AC-030-1 要求的 "占 10% 的段全删最多约 11%" 有 1 个百分点以上的偏差.
- `red-round/docs/task4.md` (`bm-red` 任务 4-7): 分析器数字被排除, 限流对比被识破, 生成器饱和被识别, 这三条红轮没有失败.
- 结论: 红轮在 AC-030-1 的上限算法上跑红 (两轮都只给直接占比, 不给 `r/(1-r)`); AC-030-3 的并发在红轮第一次任务里缺失 (只跑了单并发), 补做的 4 进程并发出现在绿轮. AC-030-2/4/5/6 在该模型上未跑红, 如实记录.

## 缺口与风险

- 全部数字来自 `time.sleep` 与 CPU 忙等模拟的受控材料, 只证明方法, 不代表真实产品性能.
- 删除整段归一化的实测由 bench 内按 `run_job` 顺序复刻的路径给出 (产品源码冻结, 不能真删), 复刻件与真实入口校准差 <0.1% (`green1.md` 2.3 节); 对外宣布前仍应在真实产品分支复测.
- 线程并发 (原 `e2e_path.py` 方式) 在 200/5000 行出现 13.99%-17.10%, 超过单路径上限; 原因是 GIL 争用放大, 会话已标为无法下结论并改用独立进程重测 (`green1.md` 4.4 节). 这条是演练中出现的真实超限案例, 处理符合 AC-030-2.
- 只在单一宿主 (16 核) 与 pi 1.3.0 + herdr 0.9.4 上做过.
