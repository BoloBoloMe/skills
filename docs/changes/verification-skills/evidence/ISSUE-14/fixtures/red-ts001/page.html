01背景: 一个只会报错的壳

仓库最初只是一个骨架. 骨架里的 bin/wordcount 只有三行: 打印一句 not implemented 到标准错误 (也就是终端上那条错误信息走的通道, 而不是被管道接走的标准输出), 然后以退出码 1 结束. 退出码 0 表示成功, 非 0 表示失败, 这是命令行工具之间约定俗成的"结果信号". 

# cc48f65:bin/wordcount
#!/bin/sh
echo "not implemented" >&2
exit 1

骨架同时留下了三样东西, 后来都成了这次改动的硬约束:

  • tests/run.sh: 两条固定断言, 一条喂标准输入要 2, 一条用 --file 读 samples/notes.txt 要 2, 最后打印 ok.
  • samples/notes.txt: 内容就是 alpha beta 加一个换行, 两个词.
  • 产品标准里的 BR-001: 既有测试 tests/run.sh 不得被改动, 理由是审计.

BR-001 这条规则看起来只是"别动文件", 实际把改动的方向锁死了: 测试的期望值不能调, 样例文件不能改, 那么唯一能让测试通过的出口, 就是让 bin/wordcount 的行为去对齐测试里已经写死的期望. 改动前 sh tests/run.sh 必然失败: 断言取到的是空的标准输出, 与预期 "2" 不等; 加上脚本自身 set -eu, 脚本立即退出.

不改的后果很直接: 目标 G-001 (从标准输入统计) 和 G-002 (从文件统计) 都没有着落, 验收标准 AC-001, AC-002 都无法通过, tests/run.sh 永远红着. 这套骨架的存在意义就是"测试先红, 实现后绿".

注意: 仓库里没有留下改动前 sh tests/run.sh 的真实运行日志. 上面对失败方式的描述来自对 tests/run.sh 和旧脚本的代码阅读, 以及下面第 4 节"旧版对照"里我实际重放的结果. 那个重放是把旧脚本原样取出、在相同输入上运行, 不是真的在旧提交上跑过 tests/run.sh, 差别只在于脚本路径怎么被替换.

02思路: 一份计数算式, 两种输入来源

核心想法只有一句: 数词这件事和"词从哪里来"无关. 所以不要为两种来源写两套计数逻辑, 而是让同一段计数逻辑接受两种数据入口. 实现选了 awk, 因为 awk 天然是"逐行读记录, 按空白切字段"的模型, 数词几乎不用额外代码.

这段算式是 { n += NF } END { print n + 0 }. 拆开看三个部分:

  • { n += NF }: 对每条记录(这里一行就是一条记录)执行. NF 是当前行的字段个数, 也就是按空白切出来的词数. 于是 n 成为累计和.
  • END { ... }: 所有输入读完后执行一次, 用来输出总数.
  • print n + 0: n 在没有输入时根本没有被赋值过, 直接打印会是空字符串. 加 0 把它变成数字 0, 于是空输入输出 0 而不是空行.

同一个输入, 新旧做法对比

输入 printf 'alpha beta gamma\n' | bin/wordcount, 两条命令行都用真实运行结果填写, 详见第 4 节

两个细节值得留意, 因为它们决定了这个工具能不能被别的程序可靠地复用. 第一, 结果走标准输出, 告错走标准错误: 这样 $(bin/wordcount) 这种取值方式不会被噪声污染. 第二, 成败用退出码表达, 而不是靠人去读文字.

03代码讲解: 按执行顺序走一遍

不关心具体代码怎么写的读者, 可以直接跳到 第 4 节证据. 这里的每个折叠块独立展开, 键盘也能操作.

3.1 入口与参数分派: 为什么默认分支兜住一切 (第 1-3 行, 第 8-11 行)

脚本第二行 set -eu 定了两个基调: -e 是任何命令失败就退出, -u 是引用未定义变量就报错. 第三行 case "${1:-}" in 里的 :- 是给 -u 留的余地: 没传参数时取空字符串, 而不是触发"变量未定义". 

case "${1:-}" in
  --file) ... ;;     # 有且只认这一个选项
  *)      ... ;;     # 其余一切都当"没有选项"
esac

这里有一个明确的取舍: 没有做未知选项校验. 除 --file 之外任何第一个参数(比如 --help)都掉进 *) 分支, 被当作"没给选项", 于是去读标准输入. 我实测过 printf 'a b\n' | bin/wordcount --help, 输出 2, 退出码 0. 这在当前范围里可以接受, 因为产品标准只要求两种入口, 而且测试也不检查用法提示; 但如果以后要给人用, 这会是第一个该补的地方.

3.2 文件分支: 让 awk 自己打开文件, 而不是先 cat (第 4-7 行)

--file 分支做两件事: 先把第二个参数取到变量 file, 再把文件名作为参数交给 awk. 

  --file)
    file=${2:?缺文件路径}
    awk '{ n += NF } END { print n + 0 }' "$file"
    ;;

三个关键点:

  • ${2:?缺文件路径} 是"缺了就用这句话报错并退出"的写法. 没给路径时脚本直接停下, 不会掉进读标准输入的分支去默默等键盘输入. 实测这个错误信息长得有点拗口: bin/wordcount: 5: 2: 缺文件路径, 前面的 5: 2: 是所在 shell 加的行号和参数名. 信息能看懂, 但不好看.
  • 用 awk ... "$file" 而不是 cat "$file" | awk ...: 少一个进程, 而且文件打不开时错误信息直接来自 awk, 不会被管道遮住.
  • 文件名加了双引号. 这不是装饰: 没有引号时, 带空格或通配符的路径会被 shell 再解释一次, 变成多个参数甚至匹配到一串文件.

文件不存在时, awk 往标准错误打印 awk: cannot open "..." (No such file or directory), 因为 set -e, 脚本以非 0 退出. 我实测退出码是 2.

3.3 默认分支与"读标准输入"为什么不用 - 或 cat (第 8-10 行)

默认分支的 awk 没有给文件名. 没给文件名时 awk 就读标准输入, 这正是这里想要的效果: 于是管道左边的东西自然流进来. 

  *)
    awk '{ n += NF } END { print n + 0 }'
    ;;

这也是为什么两种来源共用的不只是一句算式, 而是同一句算式本身. 文件分支只是多给了一个文件名, 其余完全一致.

3.4 空输入的 n + 0: 一行代码换掉一种静默错误 (第 6, 9 行)

如果写成 END { print n }, 空输入时 n 从未被赋值, awk 会打印一个空行. 对脚本的调用方来说, 空行和"0"是两个不同的东西: [ "$(printf '' | bin/wordcount)" = "0" ] 这种判断会因为空串而不成立. 加 + 0 让"没有任何词"有唯一的表达方式.

这条不是产品标准里的显式要求, 是作者主动留下的一致性. 实测空输入和纯空白行输入都输出 0, 退出码 0.

3.5 跨模块约定: 这次改动为什么必须"只改一个文件"

参与这次变更的四个角色各有一条不能动的约定:

  • tests/run.sh: BR-001 禁止改动. 它的两条断言分别是"标准输入 alpha beta 要 2"和"--file samples/notes.txt 要 2".
  • samples/notes.txt: 内容是 alpha beta 加换行, 是 AC-002 场景里写明的假定. 改它等于偷换验收条件.
  • bin/wordcount: 这次唯一被改的文件, 也是唯一该改的地方.
  • PRODUCT.md: 验收标准的正文, 已确认, 不在范围内改动.

约定背后的含义是: 测试是"规格的可执行副本", 实现来适配它, 而不是反过来. 这条也解释了为什么两个分支输出格式必须完全一致, 都是裸整数, 不带文件名, 不带单位.

3.6 边界: 什么算"一个词", 以及中文的坑

NF 的口径是"按空白切出来的字段". 对空格和制表符分隔的西文, 这符合直觉; 对中日韩文本就不一定, 因为中文句子常常没有空格. 我实测: printf '你好 世界\n' 得到 2, printf '你好世界\n' 得到 1. 也就是说, 这个工具数的是"空白分隔的片段", 不是语言学意义上的"词". 当前产品标准没提中文分词, 所以这不算缺陷, 但属于使用者该知道的口径.

其他实测边界: 多空格与制表符会被正确压成一次切分; 文件末尾没有换行不影响计数(最后一行照样算一条记录); 一次只读一个文件, 多给的文件名被忽略; --file . 这种指向目录的调用会得到 awk: cannot open "." (Is a directory), 退出码 2. 不做递归目录统计正是非目标 NG-001.

05合并风险与回退

受影响面很小: 只有一个 11 行的 sh 脚本被改, 没有数据格式, 没有外部接口, 没有写入任何文件. 受影响的人是所有调用 bin/wordcount 的地方, 目前唯一的调用方是 tests/run.sh 和 README 里的两行示例.

可能出问题的地方, 按概率排:

  • 把"片段数"当成"词数". 没有空格的中文句子会被数成 1. 这不是回归, 是口径, 但如果有人拿它做字数统计就会觉得"少算了".
  • 未知选项静默走标准输入. 有人敲 bin/wordcount --help 会看到程序空等键盘输入, 或在他给了管道时输出一个数字. 排查时会困惑.
  • 只支持单文件. --file a b 里的 b 被丢弃, 不报错. 这符合 NG-001, 但静默忽略比报错更难发现.
  • 错误信息的可读性. 缺路径时的 5: 2: 前缀会让人以为是别处出错.

能否低成本回退

能, 而且很干净. 三选一: git revert 4187edb -m 1 回退整次合并, 或直接 git checkout cc48f65 -- bin/wordcount, 或把文件恢复成那三行桩. 这两种做法都不需要改测试, 因为测试本来就是红的; 回退后 tests/run.sh 会重新失败, 这是预期状态, 不是新问题.

回退条件是: 只要 bin/wordcount 之外的任何东西没被改, 回退就只影响这一个文件. 反过来, 如果将来有人为了迁就某个调用方去改 tests/run.sh 或 samples/notes.txt, 回退就不再是一个文件的动作, 而会连带丢掉审计线索, 那时回退成本明显上升.

没有外部副作用: 本次改动不写文件, 不写数据库, 不产生缓存, 不发请求. 所以"撤回代码"等于"完整撤回", 不存在代码退了而数据留在外面的情况.
