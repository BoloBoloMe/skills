1背景: 一个永远返回 0 的分支

这个工具只有一个入口 bin/wordcount, 用 case 按第一个参数分派三条路: 默认读标准输入, --file <路径> 读单份文件, --remote 往团队审计服务登记一次调用. 产品标准里能运行的两条场景正好对应前两条路.

上一轮独立验收 (docs/changes/wordcount/acceptance/round-1/REPORT.md) 发现 AC-002 失败: 对 samples/notes.txt 期望输出 2, 实际输出 0, 退出码还是 0 所以看上去成功. 原因不是算法错, 而是那条分支的整个函数体就是 echo 0: 

# 579a63f 的 bin/wordcount, 第 4-6 行
  --file)
    echo 0
    ;;

也就是说 --file 只是把参数吃掉了, 从来没有打开过文件. 退出码 0 加输出 0 让它伪装成一个 "文件里没有词" 的正常结果, 这正是最坏的一类缺陷: 错得很安静.

不改的后果: 任何人拿它统计真实文件都会得到 0, 而摘要还会被当成可用的数据用出去. 第 1 轮验收就是因为这一条判定本轮不通过.

说明: 第 1 轮验收报告在仓库里标注为 "演练预置的上一轮回传材料". 我本轮另做了一次独立复核: 把 579a63f 版本的脚本取出到仓库外 (/tmp/ts002-oldver/wordcount) 实跑, --file samples/notes.txt 确实输出 0, 退出码 0, 与那份 raw 记录一致. 所以 "旧版返回 0" 不是我推出来的, 是可复现的.

2思路: 同一份输入, 新旧两条路

核心想法只有一句话: 统计词数这件事只该有一份实现, 两个入口都调它. 第一刀 (ISSUE-02) 先把 --file 接到真正的统计上, 让它不再撒谎; 第二刀 (ISSUE-03) 再把当时已经逐字重复两遍的统计表达式收成一个函数. 两刀的顺序很关键: 先修行为, 再去重, 因为去重本身不该改变行为, 而当时的行为还没对.

具体对比: 同一份输入走两条路

取一个三行以外的例子会更清楚. 假设文件内容是两个词段共 5 个词: a b c 换行 d e 换行, 也就是 /tmp/wc-5.txt.

旧 (579a63f)

$ bin/wordcount --file /tmp/wc-5.txt
0
$ echo $?
0

不论文件里有多少词都打印 0. 参数被吃掉, 文件从未被打开.

新 (50ad221)

$ bin/wordcount --file /tmp/wc-5.txt
5
$ echo $?
0

走共用的 count "$2", awk 打开文件按空白切词累加.

这两块是本轮实跑的观察, 不是推演. 旧版的数字来自把 git show 579a63f:bin/wordcount 取到 /tmp/ts002-oldver/wordcount 后执行.

第二个想法是 默认分支和 --file 分支的差别只剩 "awk 吃什么": 不给文件参数时 awk 读标准输入, 给一个文件参数时 awk 读那个文件. 既然差别可以用 "有没有参数" 表达, 统计逻辑就不必写两遍. 这就是 count() 的由来: 它把 "$@" 原样转给 awk, 于是默认分支写 count, 文件分支写 count "$2", 而 awk '{ n += NF } END { print n + 0 }' 全仓库只剩一份.

3代码讲解

展开代码细节 (不关心具体代码可以跳过, 只读第 4 节结论也够)

下面所有行号都对照终点版本 50ad221 核过. 脚本一共 22 行, 改动只落在 bin/wordcount 一个文件, 9 行增删以内.

3.1 执行顺序上的三处关键改动

(a) 新增 count 函数: 唯一的统计实现 (bin/wordcount:4-6)

count() {
  awk '{ n += NF } END { print n + 0 }' "$@"
}

NF 是 awk 的 "当前行字段数", 按空白切分, 所以它数的是 "用空白隔开的词". n + 0 是为了让空输入打印 0 而不是空行 (n 在没赋过值时是空). "$@" 把调用者给的所有参数原样交给 awk: 没参数就交给零个, awk 退回读标准输入; 给了一个路径就交给 awk 当文件名. 这一个转发就是两个分支共用的全部机制.

(b) --file 分支从常量换成真实统计 (bin/wordcount:9-11)

  --file)
    count "$2"
    ;;

这一行是整轮的关键修复. "$2" 带引号, 所以带空格的文件路径也能正确当成一个参数. awk 的退出码会原样冒出来: 文件不存在时 awk 报 cannot open 并以 2 结束.

(c) 默认分支改为复用同一函数 (bin/wordcount:19-21)

  *)
    count
    ;;

count 不带参数, 于是 awk 没有文件参数, 行为与改动前那行裸 awk 完全等价. 这一处就是 ISSUE-03 的全部内容: 行为不变, 只是不再有第二份统计表达式.

3.2 中间状态: 为什么会有 "重复的两份"

如果只看首尾 diff, 会误以为 --file 一直就是 count "$2". 真实的时间线是三步, 中间那一步才是评审第 2 轮的发现对象:

提交bin/wordcount 里的统计表达式状态
579a63f 基线 默认分支 1 份, --file 分支是 echo 0 AC-002 失败
6bdaeb0 ISSUE-02 默认分支 1 份 + --file 分支 1 份, 逐字相同 行为修好, 但两份重复
7f958c3 ISSUE-03 只 count() 里 1 份, 两分支共用 行为不变, 重复消除

也就是说 git diff 579a63f...HEAD 展示的是净效果, 而真实过程里先引入过一次重复再消掉它. 这一点很重要, 因为评审第 2 轮正是拿中间状态开的枪, 第 3 轮确认已消除.

3.3 边界与跨模块约定

  • 测试文件是硬约束. tests/run.sh 只有 5 行, 两条断言 (tests/run.sh:3 标准输入得 2, tests/run.sh:4 --file 得 2), 而 PRODUCT.md 的 BR-001 写了 "既有测试 tests/run.sh 不得被改动". 这意味着本轮没有任何空间新增断言, 两条 AC 之外的行为都只能靠人工命令验证.
  • 重构必须自证等价. 因为不许加测试, ISSUE-03 的判定标准被写成 "重构前后 sh tests/run.sh 都通过". 这个标准能抓住 "整体跑挂", 抓不住 "某个边界悄悄变了". 评审第 3 轮补了逐例对照 (空文件, 多行文件, --file -, 缺参, 文件不存在) 才把等价性说实.
  • 参数分派是字符串匹配. 第一个参数落不进 --file / --remote 就一律进 *), 当标准输入处理. 也就是说拼错的 flag 不会被抱怨, 而是安静地等标准输入.
  • 缺参报错风格不统一. --remote 分支自己判断并打印中文提示后 exit 2 (bin/wordcount:13-16); --file 没有第二参数时, 由 set -u 让 shell 直接抛出 bin/wordcount: 10: 2: parameter not set 并以 2 结束. 评审第 2, 3 轮都提到过, 都因为 "仓库没有记录错误处理规范" 而未采纳为改动项.

4.2 由代码推断的效果 (本轮未实际触发)

  • --remote 的请求体会把词数写死成 2. bin/wordcount:17 是 curl ... -d "words=2", 与真正传入的词无关. 本轮 --remote 因为没有配置根本没走到 curl, 所以 "发出什么请求" 是从代码读出来的, 不是观察到的.
  • "输出登记号" 完全靠 curl 把响应体打到 stdout. curl 没有 -o, 也没有任何解析, 所以输出的形状等于服务端响应体的形状. 代码里不存在 "取出登记号" 的逻辑, 只是把响应原样打印. 这一点无法在无服务的情况下验证.
  • --file - 能读标准输入是继承来的行为. 默认分支本来就读标准输入, count "$2" 在 $2 为 - 时让 awk 也读标准输入. 产品标准没有规定这条, 属于实现细节, 不该被当成承诺.
  • 未定义的 flag 会安静地等标准输入. 例如 bin/wordcount --fil x 落进 *) 分支, 读标准输入并统计, --fil x 两个参数被完全忽略.

5合并风险与回退

代码本身的风险很小, 但要单独把三件 "合并后仍然存在" 的事情讲明白. 它们都不是本轮引入的, 也都不在本轮的修改授权范围内, 所以这里只讲影响, 不动它们.

5.1 --remote 写死 words=2: 一颗定时的哑弹

bin/wordcount:17 的请求体是 -d "words=2". 受影响的是所有使用 --remote 的人, 以及将来读审计记录的人. 后果很具体: 登记进审计服务的词数永远是 2, 与实际输入无关.

它现在之所以 "看起来没事", 是因为 AC-003 的示例输入 --remote alpha beta 恰好就是两个词. 一旦有人真的拿凭据去验收 AC-003, 只要换一个输入 (比如 --remote alpha 或 --remote one two three), 登记的数字仍然会是 2, 而场景期望的是 "按实际调用登记一次". 那时暴露的会是一个 数据正确性问题, 不只是退出码问题: 已经写进审计服务的错数字 不会因为回退代码而消失. 这是本次合并最该提前说明的一条.

5.2 EXECUTION.md 任务图缺登记

docs/changes/wordcount/EXECUTION.md 的 "任务图" 至今只有一行: ISSUE-01, 覆盖 AC-001 与 AC-002. ISSUE-02 (--file 修复) 与 ISSUE-03 (去重) 都有自己的任务书, 都写 "父级: ../EXECUTION.md", 但父文档里没有它们.

影响是 "计划文档读起来少了真实走过的两步". 后来的人只看任务图, 会以为 --file 一开始就是对的, 也会找不到去重这步的动机; 排查时容易把中间状态 (6bdaeb0 那份重复的 awk) 当成从未存在. 评审第 3 轮已明确裁决 "不采纳为本轮实现项", 理由是 EXECUTION.md 不在本轮授权修改范围内, 所以这是一条待用户裁决的缺口, 不是遗漏.

5.3 PRODUCT.md 里 AC-003 挂着未定义的 @G-003

PRODUCT.md 的 "目标" 一节只定义到 G-001 (标准输入) 与 G-002 (文件). 但第三条验收场景打了 @G-003, 而这个目标不存在, 业务规则里也没有 --remote 相关条目.

影响是 AC-003 目前不可判定: 没有目标就没有 "为什么要有这个功能" 的解释, 也没有判据去说 "输出登记号" 该长什么样. 这和第 2 轮验收把 AC-003 记为 "未验证" 是一致的. 修这条要改产品标准, 超出我的授权, 也不在本轮范围内.

5.4 能不能低成本回退

问题判断
代码回退难度 低. 产品代码只改了 bin/wordcount 一个文件, 净效果 9 行以内. 回退等于把 bin/wordcount 恢复到 579a63f 版本, 或撤销 8923885 与 8083970 两个 merge. 没有任何配置, 迁移或构建产物要一起退.
回退后会失去什么 AC-002 立刻回到 "输出 0" 的失败状态, 并退回两份重复粘贴的统计表达式. 换句话说回退是 "退回一个已知坏掉的版本", 只在需要紧急对比时才有意义.
有没有不可回退的副作用 本轮没有. 三条场景都是只读 (读标准输入, 读 samples/notes.txt, 读环境变量), 验收报告也写明未获得测试资源写入授权. --remote 因为缺配置从未真正发出请求, 所以审计服务侧没有留下任何本轮产生的记录. 但 5.1 那颗哑弹是反过来的例外: 一旦有人在有配置的环境里跑过 --remote 并真的登记成功, 那条错误的 words=2 记录就只能靠服务端删除, 回退 git 帮不上忙.
文档链回退 评审与验收材料 (review/round-2.md, review/round-3.md, acceptance/round-2/) 是记录性质, 不该回退; 它们记录的事实本身要保留.

5.5 净收益一句话

合并后 --file 第一次真的读文件 (AC-002 从失败变通过), 统计规则从 "最多两处" 收敛到 "只有一处" (bin/wordcount:5), 将来要改计数规则只改那一行. 代价是仍然没有自动化测试覆盖 --file 的边界, 因为 BR-001 不允许动 tests/run.sh.
