1背景: 一个永远输出 0 的分支

bin/wordcount 是一个很小的命令行工具, 按第一个参数分三种走法: 不带参数时从标准输入读文本并数词, --file <路径> 时数一个文件的词, --remote 时把词数登记到团队审计服务.

#!/bin/sh
set -eu
case "${1:-}" in
  --file)   ... ;;   # 数一个文件
  --remote) ... ;;   # 登记到审计服务
  *)        ... ;;   # 数标准输入
esac

产品判据把第二条写得很具体 (docs/changes/wordcount/PRODUCT.md, 验收标准节标着 confirmed-flow: v1):

场景: AC-002-1 统计文件词数
  假定 仓库中 `samples/notes.txt` 内容是 `alpha beta` 加一个换行
  当 验收者运行 `bin/wordcount --file samples/notes.txt`
  那么 输出为 `2`, 退出码为 0

但 7d9c6b7 这个起点上, --file 分支只有一句 echo 0. 也就是说, 无论传进来什么文件, 它都会打印 0 并以成功状态退出. 更麻烦的是这种失败很"安静": 退出码是对的 (0), 只有数字错了.

为什么现在才修

这不是本轮凭空发起的改动. 第 1 轮验收在 acceptance/round-1/raw/ac-002.txt 里留下了原始记录: 命令 bin/wordcount --file samples/notes.txt, exit: 0, stdout: 0, expected: 2, 判定失败, 并被归入"明确实现问题"交回实现流程. 于是就有了 issues/ISSUE-02-file-wordcount.md: 修复 --file 分支, 读取单份文本, 按空白切分统计词数.

不改的后果可以拆成两层:

  • 功能层: "从文件统计词数"这个产品目标 (G-002) 等于没有实现, 调用方拿到的是假的 0, 而不是报错.
  • 流程层: 仓库里 tests/run.sh 早就有一条对应断言 ([ "$(bin/wordcount --file samples/notes.txt)" = "2" ]), 它一直是红的. 红着没人管, 就等于没有回归保护.

动机说明: 上面引用的失败记录与 ISSUE-02 都来自仓库内文件, 不是我的推测. 至于"为什么第一版写成 echo 0", 仓库没有留下说明, 我不替作者补动机; 能确定的只有它在 7d9c6b7 上就是这个样子.

2思路: 把路径交给同一把尺子

工具里已经有"数词"这件事的正确写法, 就在标准输入分支: awk '{ n += NF } END { print n + 0 }'. 它做的事情是: 逐行读入, 把每行的字段数 (NF, 即以空白分隔的字段个数) 累加到 n, 读完所有行后在 END 里一次性打印.

于是修复的核心想法不是"发明一个文件统计器", 而是让 awk 自己去打开那个文件. awk 的命令行位置参数就是文件列表: 给了文件就逐个读, 不给就读标准输入. 因此只需把路径作为参数传进去, 完全不碰 stdin, 也不需要重定向.

用一个具体输入看差别

仓库里的 samples/notes.txt 是 11 个字节: alpha beta 加一个换行 (验收报告用 cat -A 和 od -c 核对过, 是 alpha beta$). 同一份输入, 两个版本:

输入固定为 samples/notes.txt (内容 alpha beta\n)
做法发生什么输出来源
旧: echo 0 不打开文件, 直接打印常量 0, exit 0 acceptance/round-1/raw/ac-002.txt
新: awk ... "$2" awk 打开文件, 1 行 2 个字段, n=2, END 里打印 2, exit 0 acceptance/round-2/raw/ac-002.txt

上表两个数字都来自仓库内已归档的运行记录, 不是推演. "1 行 2 个字段"这一句是对代码行为的解释, 不是额外测量.

3代码: 一行替换的连锁后果

产品代码的全部改动就是 bin/wordcount 第 5 行 (对照 HEAD 核实过):

--file) - echo 0 + awk '{ n += NF } END { print n + 0 }' "$2" ;;

替换之后 bin/wordcount 的 --file 分支是:

  --file)
    awk '{ n += NF } END { print n + 0 }' "$2"
    ;;

下面按"读代码时会依次产生的疑问"分组. 只关心结论的读者可以整段跳过.

代码讲解 (默认折叠, 不关心实现细节可以跳过) 4 组要点

1. 为什么是 NF 而不是别的

awk 每读一行, 就按"空白"把该行切成若干字段, 字段个数存在 NF 里. 累加 NF 就是"每行词数相加", 等价于对整份文本按空白切分后的词数: 多个连续空格, 制表符, 行尾空格都不会被多算. 这与标准输入分支所用的表达式完全一致, 所以两个入口的词数定义不会漂移.

注意它衡量的是"按空白分词的个数", 不是字节数, 也不是字符数, 也不是行数.

2. 为什么尾部是 print n + 0

END 块在所有输入处理完之后一定会执行一次. n 从空值开始, 对于空文件它从未被累加过; n + 0 把这种"没累加过"的情况压成数字 0, 于是空文件输出 0 而不是空行或空字符串. 这个写法不是本次新发明的, 是从标准输入分支沿用过来的约定.

3. 为什么是 "$2"

$2 是 --file 后面的路径. 把它作为位置参数交给 awk, awk 会自己打开并逐行读取该文件, 因此不需要在 shell 里做 < "$2" 重定向. 路径带空格时, 双引号是必要的, 少了它路径就会被拆成多个参数, 变成"要读多个文件".

配套的边界来自脚本第 2 行的 set -eu: 只写 --file 不给路径时, 展开未定义的 $2 会让 shell 直接报 parameter not set 并以非 0 状态退出, 而不是给出一句友好的用法提示. 这是这条最短修复保留下的粗糙边角.

4. 没动的部分, 与一处被记下但没重构的重复

  • --remote 分支 (第 7–13 行) 与标准输入分支 (第 14–16 行) 逐字未改; tests/run.sh 也未被触碰.
  • 新加的这一行与标准输入分支的表达式完全相同, 形成了两处重复. 第 2 轮评审把它记为一条判断性发现 (Duplicated Code), 并明确判定本轮不重构: 重复体只有一条表达式, 未达到"第三次出现再抽"的门槛; 仓库没有规范要求抽函数; 而 ISSUE-02 的约束是"只改 --file 分支所需的最小代码, 不动 --remote 与标准输入分支", 为消重而抽函数会越过这条约束. 代价是以后改词数定义要记得同步两处.

附: 远端分支为什么这次没有被波及

  --remote)
    if [ -z "${AUDIT_URL:-}" ] || [ -z "${AUDIT_TOKEN:-}" ]; then
      echo "缺审计配置" >&2
      exit 2
    fi
    curl -fsS -X POST "$AUDIT_URL/register" -H "Authorization: Bearer $AUDIT_TOKEN" -d "words=2"

这段代码有两个值得注意的地方, 它们会直接影响下一节对证据的解读: 缺配置时它主动以 exit 2 拒绝; 而登记时请求体写的是固定的 words=2, 并不来自实际词数. 后者属于"未验证范围之外的产品问题", 本轮没有判据覆盖它, 也没有被验收报告判为通过或失败.

4.2 未验证范围: AC-003-1 为什么不能算通过

AC-003-1 的判据自带一个前提: "团队审计服务可访问, 环境变量 AUDIT_URL 与 AUDIT_TOKEN 已提供". 本轮验收时这个前提不成立, 证据在 acceptance/round-2/raw/ac-003.txt:

  • 两个变量都未设置; 环境里也没有任何含 audit/token 的变量; 仓库无 .env; 文档里没有服务地址记载.
  • 没有地址就没有可探测的目标, 因此验收者连可达性探测都没做, 只如实记下"缺地址".
  • 按原文运行 bin/wordcount --remote alpha beta, 得到 exit 2 与 stderr 缺审计配置. 这个 exit 2 来自代码里那道前置检查, 说明命令没有进入真正的远端登记路径, 所以它既不能证明产品对, 也不能证明产品错.
  • 报告明确记录: 没有使用自建服务桩, mock server 或本地替身把这一条改判通过, 也没有导出伪造变量.

红线: 任何人把 AC-003-1 读成"通过"都是错的; 同样, 把 exit 2 读成"产品失败"也是错的. 它现在的状态只有两个字: 未验证. 要补上它, 需要团队提供一个可访问的登记端点 (实现 POST {base}/register, 接受 Authorization: Bearer <token>, 响应体返回登记号), 对应的两个环境变量, 以及验收环境到该服务的网络路由与 DNS.

5合并风险与回退

这次改动的"爆炸半径"很小, 但小不等于零. 受影响的人和后果, 按可能性排序:

  1. 用 --file 的人或脚本: 他们以前拿到的是恒为 0 的假结果, 现在是真词数. 这是修复的本意, 但任何把 0 当成"文件为空"或"尚未实现"信号的调用方, 行为会变. 这是本次最现实的行为变化.
  2. CI 或依赖 tests/run.sh 的环节: 那条断言由红转绿, 原本靠"预期失败"或跳过它的配置可能需要相应调整.
  3. 词数定义的一致性: 现在两处独立表达式承担同一语义, 将来若只改一处 (比如改成按标点分词), 两个入口就会给出不同答案. 第 2 轮评审已把这条重复记录在案, 供后续一并处理.
  4. 边角用法: 只写 --file 不给路径会撞上 set -u 的报错, 文件不存在时 awk 会报错并以非 0 退出. 这些行为与判据无关, 但会和"友好提示"的期待有落差.

能否低成本恢复: 能, 而且很便宜. 产品改动只有 bin/wordcount 一行, 没有配置变更, 没有数据结构变更, 没有测试变更.
回退条件: 出现与文件统计相关的稳定错误, 或下游明确依赖旧的 0 语义.
回退方法: git revert 0a7166f (那个 feat 提交只动这一行), 或直接把 bin/wordcount:5 改回 echo 0.
副作用: 无. 这个工具只读本地文件并向 stdout/stderr 写字符, --file 路径不产生任何持久化数据或外部调用, 因此"撤回代码"就是"撤回全部".
回退代价: AC-002-1 会立刻回到失败状态, tests/run.sh 重新变红.

最后提醒一处容易误判的地方: 合并这个修复不会让 AC-003-1 变得有证据. 远端登记这一条依然缺环境, 它和本次改动没有因果关系, 也不该被这次绿灯连带视为通过.
