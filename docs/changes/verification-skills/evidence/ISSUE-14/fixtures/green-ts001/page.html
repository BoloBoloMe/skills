01背景: 一个已被测试钉死的接口

产品规格 (docs/changes/wordcount/PRODUCT.md) 的背景很朴素: 团队需要一个命令行工具, 能从标准输入或单个文件统计词数, 供提交摘要复用. 目标两条: G-001 读标准输入, G-002 读文件. 非目标一条: NG-001 不做递归目录统计, 理由写在规格里, 是当前场景只处理单份文本.

起点提交 cc48f65 的产品实现是纯粹的占位: 

# git show cc48f65:bin/wordcount
#!/bin/sh
echo "not implemented" >&2
exit 1

关键在于: 同一次骨架提交里, 测试和样例已经按最终接口写好了. 

# tests/run.sh (cc48f65 引入, 到终点未变)
#!/bin/sh
set -eu
[ "$(printf 'alpha beta\n' | bin/wordcount)" = "2" ]
[ "$(bin/wordcount --file samples/notes.txt)" = "2" ]
echo ok

而产品规格的业务规则 BR-001 明确写着: 既有测试 tests/run.sh 不得被改动 (审计). 这两件事合起来决定了这次改动的边界: 接口不是实现者自由设计的, 已经被测试钉死成三件事.

  • 无参数时读标准输入, --file 路径 时读文件;
  • 标准输出只有裸数字 (命令替换 $(...) 取到的就是它, 多一个字都会让字符串比较失败);
  • 正常情况退出码为 0, 因为 set -eu 下断言失败会立即中断, 而脚本最后要打印 ok;

不动的后果也很直接: 两行断言拿到的都是空串加非零退出码, 与 "2" 不等, tests/run.sh 必然失败, 团队的摘要需求也没有工具可用.

动机材料的边界. 仓库里没有任何设计文档或提交信息解释"为什么选 awk". 下面关于选型的说法都是从最终代码反推的推断, 不是作者原话. 这一点在证据节单独标出.

02思路: 一个计数内核, 两条输入路径

新实现的核心想法可以一句话说完: 计数只写一次, 参数分发只决定这份数据从哪来. 没有子命令框架, 没有选项解析库, 没有外部依赖, 就一个 /bin/sh 脚本.

同一个输入, 新旧对比

输入 alpha beta gamma 加换行, 运行 printf 'alpha beta gamma\n' | bin/wordcount:

标准输出标准错误退出码
旧 (cc48f65)空not implemented1
新 (b519339)3 加一个换行空0

新的一列是已观察结果: 独立验收者实跑并用 od -c 逐字节核对过. 旧的一列是从 cc48f65 那三行源码读出来的, 本次没有运行旧版本, 不要当成实测.

至于为什么用 awk 而不是循环读行或别的计数工具: 代码里没写理由. 从结果看, 一行 awk '{ n += NF } END { print n + 0 }' 同时拿到两个需要的性质, 一是按空白分词计数, 二是零行输入也能打印 0 而不是空. 这属于推断.

03代码讲解 (可折叠)

只想知道为什么这么改, 不关心具体代码的话, 可以直接跳到 证据. 行号对应终点提交 b519339 的 bin/wordcount (共 11 行, 交付前已对照当前磁盘文件核过).

展开: 完整实现 (11 行, 大部分是新代码, 上下文不可省) 
 1  #!/bin/sh
 2  set -eu
 3  case "${1:-}" in
 4    --file)
 5      file=${2:?缺文件路径}
 6      awk '{ n += NF } END { print n + 0 }' "$file"
 7      ;;
 8    *)
 9      awk '{ n += NF } END { print n + 0 }'
10      ;;
11  esac

与起点相比只改这一个文件: 删掉 2 行占位, 加上这 9 行. tests/, samples/ 在范围内 0 变化.

A. 入口与参数分发 (第 1 到 4 行, 第 8 与 11 行)

#!/bin/sh 配 set -eu: 未定义变量和失败命令都立刻中止, 脚本不会带着半截状态继续跑. case "${1:-}" 里那个 :- 是必要的细节: 没有任何参数时用空串顶上, 否则在 set -u 下引用 $1 会直接报错. *) 是兜底分支: 除了精确的 --file, 任何参数都走标准输入. 于是 bin/wordcount foo.txt 不会报错, 也不读这个文件, 而是安静地等标准输入. 这是宽松的取舍: 不误伤, 但也不提示.

B. 计数内核 (第 6 与 9 行)

awk '{ n += NF } END { print n + 0 }' 里, NF 是 awk 的内置量: 当前这一行按空白切开后有几个字段, 也就是白话里的"这行几个词". 每读一行就把本行的字段数加到 n 上, 全部读完在 END 里打印总和. 末尾的 + 0 把空值强制成数字: 输入为空时打印 0, 而不是一个空行.

同一行代码在两个分支各写了一次, 重复了一行. 这换来脚本里没有函数, 没有中间变量, 也没有 awk 参数拼接, 读者从上到下就能读完. 对这个规模, 这个重复是划算的.

C. 错误处理与退出码 (第 5 行)

file=${2:?缺文件路径} 是 shell 的断言写法: 第二个参数缺失时, 打印冒号后那句提示到 stderr 并以非零码退出, 不会拿空路径去读. 文件本身不存在时不在这里检查, 而是由 awk 自己报错退出. 两个分支的最后一条命令都是 awk, 所以脚本退出码就是 awk 的退出码: 成功 0, 失败非 0.

跨模块的约定与边界

  • 输出契约. 标准输出必须只有数字加换行. tests/run.sh 用 "$(...)" = "2" 做字符串比较, 打印 2 words 或 count: 2 都会让断言失败. 这就是实现里不给任何提示文案的原因.
  • "词"的定义. 空白分隔的连续非空白片段, 一个算一个. 不做词形还原, 不区分语言. 中文如果不带空格, 一整行只算 1; 标点紧贴单词时算进同一个词. 这属于由代码推断的语义, 产品规格没有更细的定义.
  • 参数宽松. 只认第一个参数等于 --file 的字面形式; 多余的第三个参数被忽略; 用 - 表示标准输入这种习惯写法也不支持, 会落到兜底分支(结果仍是读标准输入).

由代码推断 没运行, 按语义必然如此

  • 空输入 printf '' | bin/wordcount 输出 0 加换行, 退出码 0 (来自 END 里的 print n + 0).

  • bin/wordcount foo.txt 忽略该参数, 等待标准输入 (来自兜底分支 *)).

05合并风险与回退

受影响的只有一类人: 调用 bin/wordcount 的脚本或人. 之前拿到的是"失败信号" (stderr 一句 + 退出码 1), 现在拿到的是数字与退出码 0. 如果有人用"它失败"来决定跳过某一步, 合并后这一步会开始真的执行. 这是本次最实际的行为差异.

  • 语义风险. "词"等于空白分隔的片段. 中英混排, 标点, 连字符都不特殊处理. 下游若要中文分词, 拿到的是一个看起来正常但含义不同的数字, 不会报错.
  • 参数宽松的代价. 把 --file 拼错 (比如 --fil) 会静默退化成读标准输入; 在管道里使用时可能"成功"地统计了另一份输入.
  • 结果稳定, 无副作用. 脚本不写文件, 不发网络请求, 不落状态, 所以行为可重复; 验收的复跑也印证了两次输出一致.
  • 非产品面. 范围里的 .agents/skills/* 是仓库级技能材料 (夹具装入), 与 bin/wordcount 的输入输出无关. 若这条历史要进以产品为主的仓库, 这些文件会一并进入仓库内容, 本身不改产品行为, 但是否保留要单独决定. 加上两个空提交, 会让历史的"看起来改了"和"实际改了"错位.

能否低成本恢复: 能. 产品面只有一个文件, 没有数据迁移, 也没有外部副作用. 回退办法二选一: 把 bin/wordcount 内容恢复成 git show cc48f65:bin/wordcount (三行占位), 或者对该文件做反向改动. tests/ 与 samples/ 从未被改, 所以不需要动测试. 回退后 tests/run.sh 会重新失败, 这不是回退出错, 而是回到了"已知未实现"的状态. 需要提醒的是: 如果下游已经把新数字写进提交摘要或报表, 回退代码不会把那些数字收回来.
