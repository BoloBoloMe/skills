# 夹具修正记录

演练过程中有两次夹具不满足 AC 前提, 修好后重跑. 原始产物保留在这里, 不删除也不当作通过证据.

## 1. 首版三组夹具工作量过小, 不能检验 AC-005-1 的 (3,2) 例子

- 夹具: `/tmp/orchestra-03/green-non-author`, 5 个场景 + 1 条审计 BR, 场景都是单条秒级命令.
- 结果: `i03-g1` 把 5 场景 + 审计划成 2 组后, 按"重复读同一份 PRODUCT, 同一份 prepare 准备的成本大于并行收益"只派 1 人 (原文见 `../drill-G1-non-author/REPORT.md` 的派工记录).
- 判断: AC-005-1 的前提要求"每组工作量足以独立承担且拆开各有明确并行收益". 该夹具每组只有几条秒级命令, 不满足这个前提, 所以不能用来判 (3 组, 2 人) -> 2 人.
- 处理: 保留该演练只作为 AC-004-1 的证据 (1 名非作者验收者, 未参与事实完整). 另建批量型夹具 `/tmp/orchestra-03/heavy/` (`../setup-heavy-drills.sh`), 每组含 200-250 条批量检查, 由 G3/G4 承接 AC-005-1 的 (3,3) 与 (3,2) 例子.

## 2. 首版微检查组夹具带审计 BR 且准备成本过低, 不能检验 AC-005-3

- 夹具: `/tmp/orchestra-03/green-micro-groups`, 3 个读 `dist/app.txt` 的场景 + 1 条审计 BR; `bash prepare.sh` 只跑一次清单生成, 约 1 秒.
- 结果: `i03-g5` 把共用的 3 个场景归成 1 组 (正确), 但把审计 BR 单独拆成第 2 组, 派了 2 人; 依据是"G2 只用 git 只读命令, 与 G1 资源不重叠, 有真实并行收益". 它的产物在 `micro-v1-plan2/` (PLAN 写计划 2 人, 报告见同目录).
- 判断: AC-005-3 的前提是"三组都只读同一份构建产物, 每次新开会话都要重复这项准备, 重复准备成本大于并行收益". 该夹具既多出一条不需要准备的审计项, 准备本身又只要 1 秒, 前提不成立.
- 处理: 另建 `/tmp/orchestra-03/micro2/micro-groups` (脚本 `../setup-micro-drill.sh`): 去掉审计 BR, 只留 3 个读同一产物的场景; `prepare.sh` 改成逐条跑 CLI 生成清单, 单次实测 22.26 秒. 重跑 `i03-g5b` 得 1 人, 见 `../drill-G6-micro-groups/`.

## 3. 目标提交号与实现提交号不同的原因

- 真实实现会话 `i03-author` 在 `/tmp/orchestra-03/author` 里提交 `04be7ddd9ca795eecbb4a5b2d5beba24617509ed`.
- 各夹具的 `PRODUCT.md` 不同, 所以不能直接共用同一个提交号; 每个夹具用 `git cherry-pick 04be7dd` 生成自己的目标提交.
- 核对方式与结果见 `../README.md` 的"实现基线与目标提交"一节: 各夹具目标提交的补丁与 `04be7dd` 的补丁 sha256 相同 (`8d161fe9ed5eee1b2fc5fb5822bc42a8126216a761f85d1cbc8bfa4d1ab2b34f`).
- `i03-g6` 在受阻报告里指出了清单写的提交号与本轮目标提交号不同, 并说明这不影响"实现会话不能当验收者"的结论; 这是它的如实记录, 不是错误.
