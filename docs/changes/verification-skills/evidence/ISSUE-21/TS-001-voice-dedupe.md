- 用例: 无独立 TC. 本 ISSUE 是写作面修订, 按 ISSUE 的验证入口做机械扫描与 diff 对照, 不新增行为用例, 也不开真会话演练.
- 工具: `check-issue21.py` (本 ISSUE 的任务专用审计脚本, 只做写作面机械审计, 不做行为断言).

## 判据

- 视角 (N1): 正文出现 "用户" 且不属固定术语即命中. 只用两个固定术语: "用户入口" 指产品的使用者入口, "用户调用" 指 BR-009 的调用方式. 需求方一律写 "我", 执行 agent 写 "你". 依据 `general/writing-for-llm/SKILL.md` 第 7 节 "叙述视角".
- 重复 (N3): 同一段正文 (去首尾空白后不少于 20 字符) 在两份正文各出现一次即命中. 阈值用来跳过 "完成标准:" 这类短标签; frontmatter 与代码块不计入. 依据同一文件 "剪枝" 节的单一真相源原则.
- 单一真相源与指针 (N3): 共用批准规则的两句只在其中一份正文出现一次; 另一份给出能解析到该文件的相对链接, 并点名所在小节; 两份文件各自保留自己的资源清单四项.
- 语义未改: 原有三条规则的约束全部还在读得到的位置.

## 改法 (diff 见 `diff-skills.log`)

1. 视角: create:22 与 maintain:35 的 "交用户批准" 改 "交我批准"; 两条派工单句的 "你转给用户决定" 改 "你转给我决定". 句子其余部分逐字不动, 约束强度不变.
2. 共用规则落到 create 一处: 原三段改为 `**共用批准规则.**` 标签加三条列表项, 并写明 "生成与维护配方共用, 只在这里维护, 维护配方按 `maintain-verification-skill` 的指针读回". 原 "生成配方的批准不覆盖运行期临时数据" 改成 "生成或修配方的批准都不覆盖运行期临时数据", 一句话覆盖两个技能, 约束没减.
3. maintain 只留自己的资源清单四项, 加一句写入前必读指针: 链接指向 `../create-verification-skill/SKILL.md` 的 "共用批准规则" 小节, 并列出该节管的四件事 (批准绑定到范围, 换范围先请新批准, 运行期临时数据单独批准, 派工单随批准范围下发), 再声明不重复原文. 指针点名四件事, 是为了让读者知道去原文核对什么, 而不是靠摘要当规则用.
4. 两份文件的 `完成标准` 句都保留, 分别写生成与维护自己的批准记录要求.

## 语义保持核对

- 批准绑定资源/对象/操作/清理这四样: 原文留在 create, 未被删改.
- 同范围后续写入与复跑直接执行, 换范围先请新批准, 旧批准不作新范围依据: 原文留在 create, 未被删改.
- 已信任项目, 容器工具免审批, 脚本自称自清理都不等于写入权限: 原文留在 create, 未被删改.
- 运行期临时数据要单独批准: 原文留在 create 并改为同时覆盖生成与维护, maintain 侧由指针与摘要项承接.
- 派工单原样带批准范围, 子会话记录写入与清理, 超范围停下由我决定: 原文留在 create, 视角改为 "我".
- 两份文件各自的资源清单 (资源与对象 / 操作 / 清理 / 验证办法) 与完成标准: 都在各自文件里, 未外移.

## 局限与风险

- 脚本只做写作面机械审计: 视角命中靠固定术语白名单, 重复命中只比逐字相同的整行. 近义改写造成的重复它查不到, 仍要靠人读.
- 指针是跨技能目录的相对链接. 两个技能在本仓库同级, 一起同步部署时成立; 若有人只部署 maintain 而不带 create, 指针会悬空. 这是为消除重复指令付出的代价, 已在本 ISSUE 的任务书允许范围内 ("共用规则只保留一处并用指针承接").
- 本切片不含真实会话演练: 批准语义与加载行为都没改, 行为层证据沿用 `../ISSUE-17/` 与 `../ISSUE-12/` 的既有演练结论; 本轮只声明写作面结论, 不扩大为行为已重验.
