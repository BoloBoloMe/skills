变更讲解 / skills-v2

让没参加实现的人来查成品

这次变更在 tdd-as-orchestra 的收尾前插了一个独立验收节点, 并新增五个指令型 skill: 一个组织独立产品验收 (verify-change), 两个把"这个项目怎么跑"写成配方并维护 (create-verification-skill / maintain-verification-skill), 两个负责两类高风险判断 (blast-radius 查影响, benchmark-checklist 查性能数字). 另外补了 README 索引, 并在 docs/changes/verification-skills/evidence/ 留下 23 个 ISSUE 的演练材料.

一句话概括这次改动的因果: 以前的收尾是"作者说做完了, 顺手写一份讲解页"; 现在多一道门, 没参加实现和修复的会话拿着已确认的 PRODUCT.md, 在最终成品上逐项跑, 结果落成一份绑定目标提交的报告, 讲解页只能引用这份报告.

比较范围: ec9d55f...094be19 (开工基线到当前顶端), 分支 v2, 88 个本地提交, 未推送.
范围内不含 evidence/ 的逐行讲解: 那 3300 个文件是证据材料, 本页只在证据章节引用它们.
代码侧实际改动: 37 个文件, +1197 / -19 行 (README, 23 个 ISSUE 文件, 五个新技能目录, tdd-as-orchestra/SKILL.md).
本页生成于 2026-10-20, 生成时 HEAD = 094be19; 本页自身是本目录新增的未提交文件.

1 背景: 原来哪里漏了

1.1 旧的收尾链路

改动前的 tdd-as-orchestra 是一条线性流程: 取前沿 ISSUE, 实现, 提交, 合并, 勾选, 评审, 采纳评审发现项回重构, 然后"停止并汇报". 旧版最后一句原文是:

- 停止并汇报: 如果整个流程顺利结束, 那么启动一个新 *执行者* 让它调用 `explain-diff` skill 生成此次变更的报告.
               如果是中途遇到阻塞, 那么停下用大白话讲清楚 事情的背景/现在的问题是什么/要我做什么/你的建议是什么.

这里有两个后果. 第一, 评审通过是"代码写得对不对"的判断, 不是"成品符不符合产品标准"的判断; 旧链路里没有任何一步回头去核对已确认的产品场景. 第二, 讲解页由执行者生成, 执行者正是实现那批人, 页面的结论本质上来自作者的自我评价.

1.2 为什么判定这是缺口 (有依据的部分)

PRODUCT.md 的背景节直接写了缺口是什么: 流程已经有提前确认标准, 测试追溯和真实证据的要求, 但大型任务在实现, 合并, 评审收敛后还缺少明确的独立成品验收节点. 八条目标 (G-001 到 G-008) 分别对应新的验收能力, 新节点, 派工, 证据分级, 配方生成, 配方维护, 影响调查和性能核查.

缺口不是纸面推演. 演练里出现过一次: ISSUE-14 的红轮 (用旧版技能跑同一个任务, 期望它失败) 中, 派工单里出现了"独立验收"字样, 旧技能就自己顺手补了一轮验收, 于是这轮没有干净地失败. 这条记录在 evidence/ORCHESTRATION.md 波次 7 的自报缺口里. 它说明缺的不是"再多写几句要求", 而是一个位置明确, 主语明确的节点.

关于动机材料的边界. 上面两段都有文件依据. 至于"没有这个节点实际造成了多少次漏检", 仓库里没有统计, 本页也不编. 能说的是: 旧链路没有任何一步能产出"非作者核对成品"的证据.

1.3 不改会怎样

按旧链路, 三种材料都能顶替产品结论: 执行计划的勾选框, 技术设计文档里写的要求, 作者自己的通过日志. 这一点在新技能正文里被逐条堵住 (verify-change 第 7 步写明勾选状态不是证据, 技术材料只作操作线索), 而堵住的地方原本就是缺口所在位置. 这是文档写法的反推, 属推断, 不是实测.

2 思路: 三条主线, 一条共同边界

三条主线各自解决一类问题, 但都收在同一条边界上.

2.1 把验收从实现里切开

新节点只有一个动作: 最后一轮评审没有新的须重构项之后, 另起一个独立会话, 让它用 verify-change 组织产品验收. 实现指挥者不准自己用这个技能, 原文理由是"验收要由没参加实现和修复的人来查成品, 自己查自己等于没查". 报告拿回来之后按三类分流: 实现问题拆 ISSUE 回重构; 权限, 环境, 标准, 证据缺口按原停止条件交回给用户; 缺口没处理之前不生成讲解页.

2.2 把"怎么跑"沉淀成配方

以前每个验证会话都要重新摸索这个项目怎么启动, 端口归谁, 数据放哪, 怎么取证, 怎么清理. create-verification-skill 把这套东西写成目标项目里的一份本地 skill (.agents/skills/verify-<应用名>/), maintain-verification-skill 负责让它跟当前事实保持一致. 关键取舍: 配方只是操作材料, 通过判据始终来自 PRODUCT.md. 配方过时是操作缺口, 不是产品缺陷.

2.3 把两类高风险判断变成点名方法

blast-radius 管"这改动在 diff 之外会弄坏什么", 用五级证据等级把"我读了代码"和"我在跑着的应用里复现了"分开. benchmark-checklist 管"这个性能数字能不能信", 七问加四个判定词. 两者都由承接对应场景组的验收者自己点名加载, 不新增产品判据.

2.4 共同边界: 五个技能都不碰 Git 与发布

五个文件都写了交付边界: 只交文件路径, 差异和证据, 不提交, 不推送, 不开 PR, 不合并. 这与 PRODUCT.md 的 NG-005 一致: 不迁入原工具的发布流程. 本变更自身的提交与合并仍由 tdd-as-orchestra 的既有职责完成.

2.5 一个具体场景的新旧对比

拿 ISSUE-14 的 ts002 夹具说 (真实演练, 不是推演): 一个词数统计小项目, 某条 PRODUCT 场景在修复前失败.

旧做法: 实现者改完, 跑一遍, 写报告说通过. 讲解页的证据部分引的是自己的话.
新做法: 实现者改完, 合并, 评审收敛; 另起一个不认识实现者的会话, 拿到 PRODUCT.md 和目标提交, 派非作者验收者按场景跑入口; 报告里每一行都要写材料类型和证据位置; 有实现问题就拆 ISSUE 回重构. 这条回路在演练项目里的真实提交顺序是 3dbba65 新增 ISSUE (验收回传的实现问题) -> 0a7166f 修复 -> 9e578b2 合并 -> 89ea49e 记录评审 -> 3c79985 归档验收报告 (evidence/ISSUE-14/logs/green-ts002-fix-git-log.txt).

为什么全部做成"指令型 skill". 五个新文件都是给 agent 读的文本 (SKILL.md), 没有运行时代码, 且都带 disable-model-invocation: true: 只能被点名调用, 不会被模型自动触发. 所以"效果"取决于读到它的会话是否照做. 这句话决定了后面两件事: 证据只能是真实会话记录, 测试也只能证明"被读到时规则说得清", 不能证明"任何模型都一定遵守".

3.2 tdd-as-orchestra: 两个新节点

这是整次变更唯一改动既有流程的地方, 也是风险最集中的地方. 第 38 行先加一句硬约束:

按以下节点推进, 节点顺序不可跳过: 评审没收敛不进入验收, 验收证据没齐不进入正常收尾.

然后插入两个节点, 并改写收尾节点 (原文第 47 到 49 行, 这里摘关键句):

- 验收: 最后一轮评审没有新的须重构发现项之后, 才能另起一个独立会话, 让它调用 `verify-change` skill
        按已确认的 PRODUCT.md 组织产品验收. 实现指挥者不亲自使用 verify-change ...
        完成标准: 拿回一份绑定本轮目标提交的报告, 每个必验项都有结果.
- 验收回传: 报告里的明确实现问题就是下一轮重构的输入 ... 报告里的环境, 权限, 标准或证据缺口
        不是实现缺陷: 按原来的停止条件汇报给我, 只阻塞依赖它的验收项, 不拆成重构 ISSUE.
- 停止并汇报: ... 派工单必须带上本轮独立验收报告的实际路径, 它覆盖的目标提交和逐项结果;
        讲解页的证据部分引用这份报告, 如实显示未验证范围 ...

三处设计取舍值得注意:

  • 不塞进已有节点. 原文明确"验收也不塞进 code-review 或 explain-diff, 它们是别的节点". 混进去的结果就是 1.2 节那次红轮事故: 旧技能自己顺手补了一轮验收, 谁也说不清那算不算独立验收.
  • 只加一层, 不加两层. 验收指挥者只负责派工和核对材料, 不亲自跑成品, 也不组织修复. 派工单写清身份, 现场, 范围外, 输出契约和完成证据五样.
  • 缺口不走重构. 环境, 权限, 标准, 证据缺口不是实现缺陷, 拆成 ISSUE 会让重构者去"修"一个根本不在代码里的问题.

3.3 verify-change: 九步流程

这个技能是整条主线的核心, 九个步骤每一步都带完成标准, 且有明确的主语划分: 指挥者不跑成品.

步做什么关键约束 (为什么)
1核对输入: 已确认 PRODUCT.md, 目标提交, 产物根目录; 把场景与审计 BR 抄成必验清单技术材料填不上产品标准; 只挑"看起来相关"的项会让没碰过的功能和审计规则整条消失
2核对版本前提: 目标提交存在, 工作区与它一致不许用快照或另一份工作区绕过; 报告必须绑到一个能直接复核的成品版本
3定证据目录, 判断是否影响构建与测试发现影响就外置; 证据目录不是豁免区, 输入中途加场景不追认
4分组定人数, 给每条必验项定材料来源 (本轮实跑 / 引用旧观察 / 未验证), 需要时把两项方法排进对应组关键真实路径一律本轮实跑; 作者日志只作对照; 重复准备成本大于并行收益时只派一人
5先定写入授权与清理默认只读; 批准绑定资源/对象/操作/清理四样; 换范围重新批准; 残留单列, 不算整项通过
6派出非作者验收者"未参与"要用可核对事实证明 (会话创建时间晚于实现提交, 不继承实现过程), 不能只凭自述
7逐场景核对, 结果归三类去向勾选状态不是证据; 配方过时是操作缺口; 缺权限不得用自建服务桩改判通过
8复核材料与证据类型当前观察 / 引用旧观察 / 推断 / 未运行四类分开; 作者材料一律归"引用旧观察"
9写报告逐项成行, 带材料类型与证据位置; 另写派工记录, 三类去向, 写入与清理记录; 收尾只写"除证据目录外源码与 Spec 未变"

第 4 步那句"作者跑过的路径正是本次改动碰到的地方, 让它替验收者下结论, 首次验收就退化成作者自证"来自第一轮评审 (SPEC.md 第 3 条), 由 ISSUE-16 落实. 补之前, 通用步骤允许条件适用的旧观察直接复用, 本人实跑规则只写在复验段, 于是首次验收理论上可以只拿作者日志过关. 修复记录在 evidence/ISSUE-16/HANDOFF.md, 复核意见在 evidence/code-review/SPEC-2.md 第 3 条.

# 复验 四步是同一套规则的续集: 绑新提交, 换掉参与过修复的人, 按影响重验, 作者材料仍只作引用. 边界节把指挥者的权限收死: 不亲自运行被验产品入口, 不修复, 不替验收者调用两项方法, 不生成或修改项目配方, 不碰 Git.

3.4 create / maintain: 配方与单一真相源

产物固定落在目标项目的 .agents/skills/verify-<应用名>/. 两个技能都先要求"写入授权": 调查阶段默认只读, 写文件前把资源与对象, 操作, 清理, 验证办法四样整理成一段说明交用户批准. 这条要求在第一轮评审时被单独提出来过 (SPEC.md 第 1 条, 判定为要求缺失), 后来补成两处 ## 写入授权.

两个技能共用的批准规则只在 create-verification-skill/SKILL.md:34 维护一份, maintain-verification-skill/SKILL.md:47 改成相对链接指针. 这是第二轮评审 N3 (重复指令) 的收口, 代价写在同一份复核报告里: 只部署 maintain 不带 create 时, 指针会悬空.

维护侧的分类是关键设计: 文档漂移 (配方写的命令与项目事实不符, 产品是对的), 驱动缺口 (配方缺到达入口的必要条件), 产品缺陷 (配方正确, 产品行为仍不满足 Product). 三类判据只写在 SKILL.md, reference/drift-classification.md 只放混淆样例和证据底线, 不重复判据.

3.5 blast-radius: 五级证据 + 一次性实验边界

核心是第 3 节的证据等级, 用来防止"我读了代码"被说成"应用实跑":

1. 你直接断言事实成立. 单独没有价值.
2. 指到真实 file:line, 或库自己的源码.
3. 逐步走查失败路径, 证明坏情况到不了.
4. 实际跑过: 调用真实代码, 判断错就失败的脚本或测试.
5. 在运行中的应用里复现.

第 5 节"一次性实验的边界"是第一轮评审补的 (SPEC.md 第 2 条, 由 ISSUE-18 落实): 临时实验必须标成"非正式 TC", 只动批准范围内的独立脚本和临时目录, 内部结果不能顶替成品入口通过, 需要改冻结目标或新增正式接缝时停下报告.

3.6 benchmark-checklist: 七问与四个判定词

结论只有四种: 更快, 更慢, 无可测差异, 无法下结论. 七问按测量阶段分布, 正文第 11 行给了一张编号到节名的对照表 (第一轮评审 H2 的修复, 由 ISSUE-19 落实: 原稿引用了"第 4/7 问"却删掉了编号). 收益上限算式是:

r = 改动那一段占整条用户路径耗时的比例
完全移除这一段时, 整条路径最多快 r / (1 - r)
例: 占 10% 的段全删, 上限约 11%. 上限只是天花板, 不是结果.

粗估例外是收口轮的重点: 用户只要大致量级时可以单次测量, 但只豁免其余五问, 第 4 问 (失败计数与输出正确性) 和第 7 问 (工作是否真的在计时区发生) 不省. ISSUE-22 补的三句边界是: 规划与固定脚本时仍按"基线与脚本固定前"检查, 粗估豁免覆盖不到那两节.

3.7 README 与 ISSUE 文件

README.md 只新增 5 行索引, 没有删除或改写既有行, 这点由审计脚本按"只允许新增五行"核对过. 23 个 ISSUE 文件里, 前 15 个是原始任务切片, 后 8 个来自两轮双轴评审的发现项 (16..20 来自 STANDARDS.md 与 SPEC.md, 21..23 来自 STANDARDS-2.md 与 SPEC-2.md). 它们主要是流程产物, 不改变运行时行为, 但改变"后来者能不能复核"这件事.

5 合并风险与回退

5.1 谁会受影响

  • 以后用 tdd-as-orchestra 的人: 每轮大型任务多一次验收会话, 多一份报告, 收尾前多一道门. 成本明显上升, 这是这次改造的定价.
  • 其他项目: 零影响. 五个技能没有部署到全局目录 (证据见 4.1), 也没有被任何配置引用; 不运行同步脚本就不生效.
  • 只看讲解页的人: 页面的证据部分从此要引验收报告, 不能只引作者自述. 这是要求, 不是自动保证.

5.2 具体风险

  • 验收节点可能走形式. "验收者没参加实现"目前靠会话创建时间和操作记录核对, 没有强制机制. 如果派工单写得含糊, 这一步会退化成多开一个会话.
  • 讲解页被当成验收关闭. 文档两处写明了不等于正式人工验收 (tdd-as-orchestra 收尾节点与 verify-change 边界), 但这是约定, 不是机制.
  • 仓库体积. 3300 个文件, 54M 进版本库. 影响克隆时间, git diff 统计与全仓库检索. 这是最容易被忽略的代价.
  • 指针跨目录. maintain-verification-skill 的共用批准规则指向 create-verification-skill; 只部署前者会悬空. 第二轮评审已把这条记为代价而非缺陷.
  • 规则文字本身会漂移. 五个技能的 SKILL.md 合计约 500 行中文规则, 靠人工通读与标点扫描维护. 第一轮评审提了 12 项发现, 第二轮又新增 4 项, 说明这类文档一次写不对.

5.3 回退

能低成本恢复, 因为改动几乎全是新增文本:

  • 五个技能目录, README 的 5 行索引, issues/ 与 evidence/ 都是新增, 删除即回退.
  • 唯一动到既有流程的是 tdd-as-orchestra/SKILL.md 一处段落 (新增 6 行, 删除 4 行). 想保守可以先只回退这一段, 保留五个技能供手动点名使用.
  • 回退方法: git revert 对应提交, 或把分支指回 ec9d55f. 技能是纯文本, 没有数据迁移, 没有配置迁移, 回退后行为立刻恢复到旧链路.
回退不能撤回的东西. 没有部署, 没有对外发布, 演练项目已在 /tmp 删除, 演练会话已关, 所以外部副作用基本为零. 但代码一旦推送, 撤回提交不等于撤回历史: 那 54M 证据仍然在仓库对象库里, 克隆体积不会因为 revert 而变小. 要真正减小体积得重写历史, 那是另一件事, 不该顺手做.

回退触发条件 (建议): 验收节点连续几轮变成走过场, 或者 evidence 体积影响到日常操作, 就先回退 tdd-as-orchestra 那一段; 五个技能留在仓库里当可选工具.

7 词汇表

配方 (verification recipe)
目标项目里的一份本地 skill, 写清怎么启动, 怎么检查实例, 怎么走真实入口, 怎么取证, 怎么清理. 它只解决"怎么跑", 不决定"算不算通过".
非作者验收
由没有参加本次实现和修复的新会话去核对成品. 目的不是不信任作者, 而是让"通过"这个结论有一个不是作者的人签名.
红轮
用旧版技能跑同一个任务, 期望它失败. 用来证明新加的规则确实改变了行为, 而不是本来就能过.
证据等级 (blast-radius)
五级: 直接断言, 指到源码行, 走查失败路径, 跑过可失败脚本, 在运行中的应用里复现. 报告必须说明停在哪一级.
审计 BR
PRODUCT.md 业务规则里标 (审计) 的条目, 例如"五个技能都用用户调用方式". 它们没有 gherkin 场景, 但要单独核对.
三类去向
验收结果必须分成: 已证实的实现问题 (回重构), 尚缺产品规则 (只停受影响项, 交回决策), 权限或环境缺口 (未验证). 不许混成一句失败.
本页是讲解材料, 不关闭正式人工验收. 页面结论的证据强度不超过第 4 节标注的范围.
