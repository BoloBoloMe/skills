# 性能核查记录: index_fast vs index_lite (函数级)

判定: **对"导出更快"这条主张 —— 无法下结论**; 对函数自身 —— **构建并释放索引更快约 12%; 只算构建本身无可测差异**.
原主张的 26%(docs/claim.md 写 40%)**不可复现**, 是脚本顺序与计时范围造成的偏差.

## 0. 授权与边界

- 未改产品源码 (src/), 未改既有脚本 (bench/).
- 一次性实验脚本全部放在仓库外 `/tmp/orch19-exp/`: alt.py, order.py, robust.py, split.py, buildonly.py, cold.py, final.py.
- 临时数据: 无新数据, 只用 `data/rows.csv`. 后台进程: 无. 产物仅 `__pycache__` (已删除, `git status` 干净).
- 未运行的产品场景: `src/report.py` 的 `export_report` 端到端 (本次按要求不测).

## 1. 待核验结论 (原样)

用户想发: "新索引让导出更快". docs/claim.md 里的版本是 "让报表导出快 40%".
核验对象: 该句中的"导出"是整条路径, 而 bench/micro.py 只计时 `build_index` 一个函数.

## 2. 被测脚本的计时范围

`bench/micro.py`:
- 计时: 只包 `lite(rows)` 与 `fast(rows)` 两次调用, 每次一轮, 无预热.
- 计数: 输出耗时与百分比, **不含失败数, 不含处理条数, 不校验输出**.
- 忽略: 数据加载, 进程启动, 结果销毁时点在计时区外.
- 顺序固定: 永远先测 lite, 后测 fast.
- 无随机扰动, 无种子, 无重复.

`bench/export_once.py`: 单次, 计时 `export_report`, 打印耗时/条数/字节, 无失败计数, 无重复.

## 3. 机器条件

`nproc` 16, `uptime` load average 0.13 / 0.26 / 0.25 (无他人重负载, 无需交替抗噪处理, 但仍做了交替).
CPython 3.14.7, 数据 `data/rows.csv` 200000 行 / 2.2MB / 37 个不同 key.

## 4. 表面数字: bench/micro.py 原样跑 7 次

lite 10.57 - 14.27ms, fast 7.91 - 8.81ms, 百分比 24.8 / 25.1 / 25.7 / 27.3 / 28.3 / 28.7 / 38.3%.
中位约 27%. 但 lite 的时间每次都比 fast 高 2-3ms, 与交替测量不符, 见下.

## 5. 交替测量 (每侧 9 次, A,B,B,A 交替, 先各预热一次)

计时区 A: 只含 `build_index`, 结果销毁在计时区外

| 侧 | 中位 | min | max | 极差 |
|---|---|---|---|---|
| lite | 8.49 / 8.61 ms | 7.96 | 9.10 | 1.14 |
| fast | 8.03 / 8.22 ms | 7.71 | 8.45 | 0.74 |

差 0.39 - 0.46ms (4.6 - 5.4%), 小于 lite 自身波动 1.14-1.71ms → **无可测差异**.

计时区 B: 含 `build_index` 与结果销毁 (贴近"构建后用一次就丢"的用法)

| 侧 | 中位 | min | max | 极差 |
|---|---|---|---|---|
| lite | 8.99 / 8.95 ms | 8.69 | 9.55 | 0.85 |
| fast | 7.94 / 7.84 ms | 7.82 | 8.22 | 0.28 |

差 1.05 - 1.11ms, 12% 左右, 大于两侧极差 → **可测**.

拆开来看 (split.py, 9 轮交替): lite 销毁索引中位 1.37 - 1.39ms, fast 0.00ms.
即这 12% 几乎全部来自"lite 的索引要保留 200000 个值, 丢弃时更贵", 不是构建循环更快.

## 6. 26%(以及 40%) 从哪来

三层偏差叠加, 都不属于"实现更快":

1. 顺序固定: micro.py 永远让 lite 第一个跑. 同进程里首个被测函数多付 2-3ms (首次触碰新内存/分配器冷态).
   证据: 把顺序反过来冷跑 (`order.py`), fast 首次 8.36ms (与热态一致), lite 首次 9.46ms; 用 `cold.py` 每个进程只测一次, lite 9.28/9.86/9.46ms, fast 10.17/9.70/11.05ms, 两侧冷启动成本相当.
2. 单次: 无重复, 无中位/极差, 一次抖动直接进结论.
3. 计时范围: 结果销毁落在计时区内, 计的是"构建 + 释放", 却也计到了调用方未必立刻付的成本.

## 7. 失败计数与输出正确性

- 运行失败数: 0 (所有轮次均正常返回).
- 工作量: 每侧每轮都处理全部 200000 行 (rows 全量传入, 无跳过分支).
- 输出正确性: 两侧索引折算成 key→条数后与独立统计一致 (`lite 正确 True / fast 正确 True / 两侧一致 True`).
- **但两侧产出的不是同一个东西**: lite 的值是 list (保留值), fast 的值是 int (只保留计数), 已验证值类型分别为 `list` / `int`.
  所以这不是"同一输出更快实现", 而是"换成只存计数的结构". 只有只需要条数的消费方 (如 `report.py` 的导出) 才等价.

## 10. 可以对外说的 (函数级, 主数字一个)

主数字: **20 万行 fixture 上, 构建并释放索引 9.0ms → 7.9ms (中位, 9 轮交替)**.

必须同时挂在材料里的限定:
- 单位 ms, 单线程, CPython 3.14.7, 16 核, 200000 行 / 37 key.
- 只算构建本身: 无可测差异 (8.5 vs 8.1, 差小于波动); 省下的是丢弃索引的 1.4ms.
- fast 不保留值, 与 lite 产出不同结构; 只有"只要条数"的消费者可替换.
- 26% / 40% 不成立, 来源是单次 + 固定顺序 + 计时范围.

## 11. 不能对外说的

- "新索引让导出更快" —— 导出路径没测, 结论只能是无法下结论.
- "快 26%" / "快 40%" —— 已证不可复现.
