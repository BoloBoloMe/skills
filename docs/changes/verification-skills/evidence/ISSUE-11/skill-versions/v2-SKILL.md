# 生成项目级验证 skill

把已确认的产品说明和项目里可观察的运行事实, 落成一份项目本地的操作配方, 让没做过这个项目的 agent 照着就能把功能真实跑一遍, 不用每次从零摸索启动方式和入口. 配方只解决"怎么跑, 看什么, 证据放哪", 通过判据始终来自 `PRODUCT.md`: 地图和代码现状与它冲突时以它为准.

## 输入

- 必需: 已确认的 `PRODUCT.md`. 它给出本轮覆盖哪些功能和入口, 以及各自怎么算通过. 找不到它, 或它的状态仍是草稿, 待确认时, 报告缺哪个文件, 哪一条没确认, 然后停下. 源码现状不能替代产品判据, 不会因为代码已经这样就去推断"应该怎么算通过".
- 可选: `TECHNICAL.md`, `EXECUTION.md`, 项目 README, 测试入口. 缺任何一份都继续做, 只在报告里写"未提供".
- 自己观察: 应用名与启动命令, 端口与数据目录, 用户入口, 前置数据, 现有测试入口.

完成标准: 能写出本轮入口清单, 每个入口都有三样事实: 怎么启动, 怎么操作, 观察到什么算这条判据满足. 观察不到的事实标成未确认, 不写成断言.

## 覆盖范围

只覆盖 `PRODUCT.md` 这一轮涉及的入口, 加这些入口共用的规则: 从空数据启动到真正可用, 只读的实例检查 (进程, 端口归属, 版本), 真实入口操作, 取证, 清理. 项目里其余功能不进配方, 也不为它们铺功能地图. 报告写明本次覆盖哪些功能和入口, 以及哪些功能被排除, 排除理由是什么.

完成标准: 功能地图里每一项都能追到 `PRODUCT.md` 的一条判据, 追不到的就删掉.

## 写什么

产物落在目标项目 `.agents/skills/verify-<应用名>/`:

- `SKILL.md`: frontmatter 里 `name` 与目录名一致, `description` 是一行人类摘要, `disable-model-invocation: true`; 正文先是共用规则, 再按功能分节写入口和操作.
- 需要辅助脚本时放在同目录, 调用方式写进正文, 不要求读者猜.

每条配方写到能照着敲: 前置 (数据, 工具链, 端口), 具体命令或交互步骤, 期望看到的结果, 证据留在哪个文件. 只写两类步骤: 你真跑过的, 或明确标了未验证和原因的.

完成标准: 一个没做过这个项目的人照某一节能一路敲到证据, 中途不需要回头问你.

## 改动边界

只新增或修改项目本地验证目录 `.agents/skills/verify-<应用名>/` 及它自带的辅助脚本. 产品代码, 项目配置, 既有测试, 全局部署副本保持字节不变: 配方是观察产品的工具, 一旦为了让它跑通而改产品, 它验的就不再是产品了. 应用构建或启动不了时, 报告现象与已尝试的路径, 把受影响的配方原样保留并标为未验证; 不装工具链绕过, 不用替身产物冒充构建结果, 不改产品, 配置或测试让配方看起来跑通.

完成标准: 交付前在目标项目跑一次范围对照 (`git status --porcelain`, `git diff --stat` 或等价), 结果里除验证目录外没有别的改动, 原始输出进证据.

## 交付前实跑

派一名没参与编写的会话去跑: 在目标项目里用 `/skill:verify-<应用名>` 加载这份配方, 按它跑完本次新增或修改的全部入口. 你自己敲一遍不算证明: 作者熟悉项目, 恰好绕过漏写的条件, 而配方是写给陌生人的.

- 派工单写清: 目标项目路径, 要跑的入口清单, 期望留下什么证据, 清理要求, 报告格式.
- 拿回记录后核对: 宿主报的 location 是否就是项目里这份文件, 展开的正文是否是当前内容, 每个入口是否都有操作, 取证, 清理记录. 手工粘贴正文不算按名加载.
- 加载失败, 同名冲突或来源不是这份文件时: 记下宿主原文和冲突诊断, 作为缺口报告, 不靠改项目配置或写全局部署来绕过.
- 跑不通或缺前置数据时: 配方原样保留并标未验证, 写明缺什么前置, 试过哪些路径; 不删步骤, 不降标准把它改到能跑.

完成标准: 每条新增或修改的配方, 要么有一条刚落盘的操作, 取证, 清理记录, 要么在报告的未验证清单里写明原因; 报告说明本次实跑覆盖了哪些入口.

## 交付报告

写清: 生成路径与文件清单, 本次覆盖的功能与入口, 排除的功能及理由, 实跑覆盖和加载 location, 未验证项与原因, 改动范围对照输出, 哪些可选输入没提供. 只交文件路径, 差异和证据; 不提交, 不推送, 不开 PR.
