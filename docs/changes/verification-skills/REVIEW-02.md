### C007 加载入口只验成功分支, 来源同一性的失败分支没有判据 (已证实问题, 中)

位置:

- `PRODUCT.md` AC-017-3 (第 425-430 行): 假定末尾写"宿主为 pi 1.3.0,项目已被信任且没有过滤或同名冲突"; 那么只描述"从目标项目当前的这个文件加载并给出其真实 location".
- `TECHNICAL.md` create 输出段: "同名冲突/过滤/信任不足时须核实实际加载来源并报缺口, 不绕过权限或用别处同名旧文件冒充新产物."

依据: F022 与 pi `docs/skills.md` 明确"Name collisions keep the first discovered skill and produce a warning"; `docs/security.md` 把项目 `.agents/skills` 列为受项目信任保护资源, 拒绝信任即跳过; 因此"实际加载了哪个文件"是本轮返工要解决的核心风险, 而不是边角条件.

后果: 验收标准把最容易误判的情形写进假定, 只保留顺利加载的一条分支. 演练若同名的旧部署副本存在 (例如后续 sync 过旧版本), 或项目未被信任, 技能被设置过滤, 场景在假定不成立时按规则应记"未验证", 而没有任何场景要求实际验收者报告"本次加载的是旧文件/未加载"并给缺口. 也就是说, 同一个证据缺口既能被当成"未验证"通过流程, 也能让演练悄悄跑在旧文件上却被判通过, 判据本身无法区分.

### C009 AC-003-1 与 AC-003-3 对"充分证据"的最低要求不一致 (疑点, 中低)

位置:

- `PRODUCT.md` AC-003-1 大纲第 1 行: 材料是"本轮对 /health 执行 curl 得到 200 响应且 ready=true", 引用信息是"命令,响应内容,执行时间", 判定"通过".
- `PRODUCT.md` AC-003-3: 只有"整理过的结论摘要", 没有可读取原始材料时不算充分证据, 须补交原始记录.
- `TECHNICAL.md` 证据段: 结论须有可读取的原始运行材料支撑; 同时"不一律复制完整日志或含秘密的原样输出".

后果: 同一份报告, 按 AC-003-1 可以"命令+响应内容+时间"判通过, 按 AC-003-3 可判"无原始材料, 不通过". 两处差别只在材料是否真实存在并留存, 而 AC-003-1 的引用信息栏不要求给材料位置, 读者无法从判据上区分"引用了留存材料"与"只是转写了一段输出". 这是本轮为补 O001 新增文本带来的判定歧义, 会让首轮争议的同一行为出现两种合法结论. 建议在 AC-003-1 的引用信息中要求给出材料位置, 或明确"引用信息"必须指向已留存的可读取材料.

### 主战场

P1 的生产等价性. 选择理由: v5 的主要修复正是"用同一入口验证", 但只把它用在了生成的项目配方上; 五个通用 skill 的生产入口仍是部署副本, 演练只能走源文路径. 这一环决定"验收通过"这句话能覆盖到多远, 拆它不影响 P2 与 P4, 但会让整个结论的可信范围缩水; 其余环节 (判据唯一, 证据分级, 低收益反例) 本轮已明显加固.

### O001 通用 skill 的演练入口与生产入口不对称, 结论会超出已验证范围

- 反驳: `TECHNICAL.md` 接缝段把生产侧写成"实际 skill 加载及项目/会话环境", 测试侧写成"通过目标运行时公开加载方式使用本仓库待测源文件的真实 agent". 对五个尚未部署的通用 skill, 不部署, 不改项目配置的公开加载方式实为 `pi --skill <路径>` (或临时项目里的 `.agents/skills` 副本), 而生产路线是 `sync-to-pi.py` 同步到 `~/.agents/skills/` 后, 由实现指挥者另开的子会话按名或按路径抵达. 两条路线在"谁提供名字/指针, 同名的旧副本是否先被发现, 项目信任与技能命令开关是否影响可达性"上完全不同. 于是: (1) 部署后若 `~/.agents/skills/` 已有旧版同名 skill, 演练无法暴露"实际加载旧文件"; (2) AC-014-1 要求"另开独立验收指挥会话组织产品验收", 演练只能证明该流程在源文加载下可行, 不能证明新节点部署后可用; (3) 收尾讲解页与"代理检查通过"没有义务标注这个边界, 读者容易把结论读成"五个 skill 已可用".
- 可观察后果: 一次全绿的 v5 验收之后, 部署当天用 `/skill:verify-change` 触发, 若同名旧文件先被发现或项目信任未决, 新节点静默失效, 而此前所有证据都合法地支持"验收通过".
- 反方立论: 在 PRODUCT/TECHNICAL 写清"生产可用性 (部署后按名加载) 不在本变更验收范围, 由部署后的独立冒烟项承担", 并要求验收报告与讲解页标注该覆盖边界; 或者只对 verify-change 做一次部署后 `/skill:name` 冒烟. 这不是要求本轮部署 (D039 已排除), 而是要求结论不宣称未验之事.
- 置信度: 中高.

### O002 验收节点"是否真的发生"没有可观察信号, 且新材料把负担压向指挥者

- 反驳: v5 把指挥者责任加重为"每个结论须有可读取原始材料支撑, 并要能发现记录与摘要冲突", 覆盖范围仍是 PRODUCT 全部场景加 3 条审计 BR. 而 tdd-as-orchestra 的收尾仍只靠流程文本要求"先验收再汇报", 交付物 (讲解页) 并不引用验收报告路径, 绑定提交或未验证项数. 结果: 压力下最可能的失败不是"验收不严", 而是"节点被跳过或草草收尾", 而这种跳过在产物上几乎无痕; AC-014-1 与 AC-014-3 都只描述代理人行为, 没有让"验收确实发生过"留下可检查痕迹.
- 可观察后果: 实现指挥者按原流程直接进入停止汇报并生成讲解页, 讲解页内容与实际验收报告无引用关系; 事后无法从交付物判断验收是否发生, 也无法判断报告覆盖的是哪个提交.
- 反方立论: 让 stop/汇报步骤以验收报告为输入 (报告路径 + 起始提交 + 逐项结果计数 + 未验证项数), 由讲解页或汇报正文引用. 这是一条调用关系约束, 不是 D039 已排除的固定 JSON 协议, 新平台, 硬预算或抽样规则; 它把"节点发生"从流程期望变成可核对事实.
- 置信度: 中.

### 自洽项

- C007: 不成立为既有判据允许错误加载也通过的设计矛盾. 正常场景明确要求实际来源是项目当前文件, 读到旧文件就不满足该结果; 未验证不能正常收尾也已明确. 技术接口已有冲突/过滤/信任不足时报缺口的错误模式, 由既有 to-execution 的接口错误模式 TC 承接. 可进一步显式指出这条承接, 但无需为每个运行时加载成因新增 Product 场景. 不认可未验证可以通过正常流程的推论.
