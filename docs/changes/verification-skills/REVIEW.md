## 自洽检查

### C001 项目级配方"按名抵达"没有判据承接, 且与三处既有约束互相拉扯 (已证实问题, 含一处待核实)

位置:

- `TECHNICAL.md` 第 32 行 (create-verification-skill 输出): "采用项目本地可发现位置, 不写全局部署副本或硬搬 .cursor 路径; 具体项目位置按现有约定和实际运行时核实."
- `TECHNICAL.md` 第 66 行 (接缝与适配器): "测试侧为显式读取本仓库待测源文件的真实 agent 与独立临时项目."
- `PRODUCT.md` BR-009 与 AC-018-1 (`PRODUCT.md` 第 406 行): 生成物 "新增与修改只出现在项目本地验证 skill 目录及其自带辅助脚本", 且 "项目配置 ... 未被改动".

依据:

- `general/writing-for-llm/SKILL-MECHANICS.md` 第 17 行: 用户调用 skill "对 agent 不可发现", 按名字抵达依赖环境里的路径指针 (本环境是 `AGENTS.md` 中指向 `~/.agents/skills/` 的一行), 并要求目录名与 `name` 一致; "没有指针的环境里, 用户调用 skill 只有我能抵达".
- `sync-to-pi.py` 第 467 行: 只同步到 `~/.agents/skills/`, 仓库内没有项目级 skill 目录的约定或指针写入机制.

后果:

- 生成的项目级配方按 BR-009 是用户调用, 又按 AC-018-1 不许改项目配置 (指针通常就得写进项目的 `AGENTS.md` 一类文件), 还要求"可发现". 三者同时成立的前提是"运行时自动扫描项目本地目录", 而本仓库没有任何文档或脚本支撑该前提. 若前提不成立, 验收者与配方实跑子会话都只能靠被注入文件文本才用得上配方.
- 测试侧适配器明确用"显式读取源文件"代替真实加载, 所以演练永远观察不到"陌生会话能否按名抵达配方". 对应后果: AC-010-1 (优先使用已有配方) 与 G-005/D006 "减少陌生 agent 重复探索" 的价值主张没有任何验收判据; 配方即便生成正确, 也可能没人能抵达.
- 待核实: 项目本地 skill 目录 (含 `disable-model-invocation: true`) 在 pi 运行时是否被扫描. 这需要运行时文档或一次只读实测, 本轮没有做.

### C002 `TECHNICAL.md` 的 BR-009 承接把已机械化的检查说成脚本未覆盖 (已证实问题)

位置: `TECHNICAL.md` 第 110 行 (BR-009 审计行): "复用 general/writing-for-llm/check_skill.py, 并实际核对 disable-model-invocation: true/name与目录/单行摘要等该脚本未完全覆盖的要求."

依据: `general/writing-for-llm/check_skill.py` 第 71-80 行实际检查三件事: `name` 小写 kebab-case 且与目录名一致; `description` 必须单行非空; `disable-model-invocation` 若出现只能是 `true`. `SKILL-MECHANICS.md` 的脚本说明也写"检查 name 是否 ... 与目录名一致", 并明确 "它不决定调用方式, 也不判断触发措辞或内容质量".

后果:

- 三项里有两项 (name 与目录一致, 单行摘要) 已被脚本完整覆盖, 说成"脚本未完全覆盖"与事实不符. 这会直接误导 BR-009 的取证: 要么重复人工核对已有机械证据 (浪费且削弱"机检结果为准"的纪律), 要么反过来以为"字段必须存在"也被脚本保证.
- 真正没被脚本强制的只有两点: 一是 `disable-model-invocation: true` 必须**存在** (脚本缺省按模型调用处理, 省略即静默通过), 二是 `description` 是否人类摘要而非触发词措辞 (语义判断). 建议把该行改成"脚本覆盖 name 与目录一致/单行 description/字段值; 需另核对字段存在性与摘要语义".

### C003 AC-005-1 的禁止项在假定成立时不可触发, 与自身例子也表面冲突 (已证实问题, 判据不可判定)

位置: `PRODUCT.md` 第 140-144 行 (AC-005-1 大纲): 假定已写明 "每组工作量足以独立承担且组间资源可隔离, 拆开后各有明确并行收益"; 而且 却要求 "不按组数机械地各分一人"; 例子是 2/2->2, 3/3->3, 3/2->2.

后果:

- 假定一旦成立, "每组一人"就是有依据的拆法, 禁止项永远触发不了; 3 组 3 人 的例子又恰好等于"按组数各分一人", 字面上正是被禁止的做法. 同一行为按两种读法可得出相反判定: 判"机械拆分"失败, 或判"收益充足所以拆三人"通过.
- 结果是该 AC 实际只验证了人数公式与"写了承接关系", 而 G-003 真正想要的分辨力 (何时不该拆) 没有可观察判据. AC-005-2 只覆盖"单组不拆", 不覆盖"多组但收益不足时不按组数拆".
- 建议: 增加一个"组间收益不足/必须串行"的分支 (例如 3 组中 2 组写同一实例同一记录, 预期合并或降为人少) 并给出对应人数, 或删除该禁止项.

### C004 D019 的"不每次先等用户审批分工计划"没有落进两份 Spec (待核实疑点, 低)

位置: `DECISIONS.md` 第 177 行 (D019) 明确 "指挥者自行评估后启动, 把分工依据留在报告中, 不每次先等用户审批分工计划". `PRODUCT.md` AC-005-1/AC-005-2 与 `TECHNICAL.md` verify-change 派工顺序段都没有这句话.

依据与后果: 相邻的写入规则 (BR-005, AC-011) 确实是"先批准再执行", 实施者很容易把同样的批准习惯套到派工计划上, 凭空多出一个用户关卡. 该行为外部可观察 (验收启动前是否停下来请示), 却没人验收. 承认的减损: `TECHNICAL.md` "然后启动" 与 AC-005-1 的"制定计划 -> 派出"流程顺序隐含了不设审批, 所以本条是表述缺口而非设计矛盾.

### C005 BR-010 的审计承接没有指定证据形式与存放位置 (待核实疑点, 低)

位置: `TECHNICAL.md` 第 111 行 (BR-010 审计行): "固定 SHA 原文/完整 MIT 版权与许可/明确行为差异记录/中文和 ASCII 标点审计, 按 translate-a-skill 完成语义对照".

依据: `general/translate-a-skill/SKILL.md` 第 33-52 行确实要求"每个差异记录: 源版位置, 目标版位置, 影响, 处理决定", 所以语义对照有流程依据; 但两份 Spec 都没说这份差异记录与 MIT 许可正文放在交付物的哪个文件, 也没说"ASCII 标点"用什么核对 (仓库内未找到现成的标点检查脚本, `check_skill.py` 不管标点).

后果: BR-010 是审计断言, 按 D033 必须有可复核结果; 现在承接只写了材料要求, 验收时可能只落一句"已对照源文", 无法复核差异清单是否覆盖核心步骤/强度/数量/例外/完成条件. 不构成设计错误, 属取证形式未定义.

### C006 `TECHNICAL.md` 安全策略里的义务没有声明下游承接去向 (待核实疑点, 低)

位置: `TECHNICAL.md` 第 118 行: "报告/页面/原始材料的交付片段先脱敏, 不写密钥/凭据正文/认证头或无关业务数据."

依据: 该义务有既有来源 (`workflow/use-sandbox-worktree/reference/task-conditions.md` 第 10 行 "不回显密钥或凭据正文"), 但 PRODUCT 没有对应场景或审计 BR; 按 BR-001 与 AC-002, 产品验收只覆盖 PRODUCT 的场景与审计 BR, 所以它在本变更的验收里不会被检查.

后果: 若期望它由下游 EXECUTION 的技术安全 TC 承接 (F003 的常规通道), 两份 Spec 都没写这个去向, 读者无法判断它究竟是"继承既有规则无需另测"还是"漏了承接". 同类还有 maintain 接口的"实例异常先核对健康/版本/归属"与 create 接口的"dry-run 副作用要查明". 建议在安全策略节补一行承接去向或继承来源即可, 不必新增 AC.

### 正方还原 (steelman)

- 定义: 用五个用户调用 skill 补上"最终成品由未参与实现的会话按已确认 PRODUCT.md 实跑验收"这一缺口, 只自动接入 tdd-as-orchestra 的收尾节点, 两个复刻提供影响调查与性能证据的方法, 验证方式用真实会话受控演练而不是新建评测平台.
- 前提: P1 指令型 skill 的行为差异可以通过真实会话执行被观察到, 并留下可复核证据; P2 产品判据只取 PRODUCT.md 就能避免出现第二套权威; P3 "非作者会话 + 独立判断"足以让结论可信到可以进入收尾; P4 成本可接受, 因为允许复用有效旧证据并按场景组决定人数.
- 论据: D031 (撤销技术验收) / D032 (动态人数) / D033 (全部场景与审计 BR) / D037 (真实会话演练); F005 (现有流程无强制非作者实跑) / F006 (既有真实证据与人工确认纪律) / F012 / F013 (复刻强度); 96 场景与 3 审计 BR 的逐项映射.
- 推理链: 缺口真实存在 -> 唯一产品判据 -> 非作者实跑 + 证据分级与复用 -> 用既有会话与既有入口演练 -> 得到可信的产品验收结论, 且不引入平台与第二套标准.

### 主战场

P1 与 P3 的结合部: 证据的独立性与可复核性. 选择理由: G-001/G-004 与 BR-003/BR-004 的全部价值都压在这一环; 拆掉它, 其余设计 (判据唯一, 复用规则, 不建平台) 仍然自洽, 但"独立验收比作者自验更可信"这个卖点落空. 拆 P1/P3 等于拆整个观点, 拆 P2 或 P4 只削弱局部.

### O001 证据链在系统内部自证, 没有独立于被验 agent 的锚点

- 反驳: `TECHNICAL.md` 第 66 行要求"观察实际会话/工具调用/文件/版本/报告, 不只采信 agent 自述已派发或已运行", 但观察者是同一类 agent, 报告里的"可复核位置"也由被验会话自己产生. 全文没有任何强制字段要求在报告里留下原始输出的原样副本 (命令回显, 退出码, 时间戳, 产生者会话 id) 并可由脚本核对存在性. 于是"当前观察"与"整理后的摘要"在判据上不可区分, 本变更想修的失败模式 (自证通过) 会在新的验收层内部复现, 只是从"作者自验"变成"验收者自证".
- 反例与可观察后果: 一次演练中, 验收者声称对 /health 实跑得到 200 并给出"可复核位置"; 若它实际只读了代码, 按 AC-003-1 的第 3 行它应当标"推断", 但没有任何机械检查能证伪它写"当前观察". 同理 AC-022-2 的"搜索无结果", AC-029-2 的"缺口无法补齐", 都能靠措辞满足.
- 反方立论: 每次验收输出必须附一份机检可读的证据索引 (场景 ID, 起始提交, 命令或操作, 原始输出文件路径, 时间, 产生者会话), 用一个小脚本核对字段齐全, 路径存在, 提交与报告一致; 原始输出原样落盘, 报告只引用路径. 这不建平台, 不解析行为, 也不新增产品判据, 属于 D037 允许的"证据整理".
- 置信度: 中.

### O002 派工质量与成本都没有可核对边界, 判据可被流利理由满足

- 反驳: AC-005 系列的判据是"给出人数 + 写明并行收益与承接关系". 任何有语言能力的 agent 都能为任一分配写出通顺理由, 所以"拆得对"与"事后合理化"不可区分; AC-005-2 只验"不拆", 不验"该拆时拆了". 另一侧, 全量覆盖 (D033/AC-002-1) 没有会话数或时间上界, 也没有抽样规则, 大型任务里验收层可能演变成几十个真实会话的机械清单, 而 G-003 想要的"减少互等与重复工作"无处体现.
- 可观察后果: 一份把 3 组派给 1 人并附"资源隔离成本高"理由的计划, 与一份 3 组派 3 人的计划, 在现有判据下都可能通过; 而 AC-002-1 只要求逐项列出结果 (允许"未验证"), 因此"形式齐全, 实质空转"的报告无法从判据上被排除 (收尾要求全部必验项通过, 但验收过程本身可以长期停在这个状态).
- 反方立论: 把"并行收益"从叙述降级为可机械核对的结构条件: 每个必验项恰好一个承接人, 同一资源的写操作区间不重叠, 组间无共享准备冲突; 三项由计划表直接核对, 叙述只留作补充. 同时给验收设会话数/时间上限与明确的抽样与降级规则 (超限即"部分未验证"), 让"成本"成为显式判据而不是默认无界.
- 置信度: 中高.

### 幸存与比较

- 正方仍成立的部分 (我不否认): 产品判据唯一 (BR-001 + AC-001 + AC-002) 这一条我没有反例, 它确实挡住了技术验收和"计划勾选当通过"的回潮; 缺口识别准确 (F005 说明现有流程确实没有强制非作者实跑最终应用); 证据复用规则 (BR-003 + AC-009) 避免了 SJR 式的全量重跑, 也回答了"改一行要不要全跑"; 拒绝建评测平台 (D037) 在成本与范围上是对的; AC-002-1 允许"未验证"作为结果, 使全量覆盖是报告义务而不是全量重跑义务, 这点削弱了我最初的成本攻击, 我据此收窄了 O002 的主张.
- 权重比较: O001 打击的是本变更的核心收益 (结论可信度), 发生概率我判中, 不可逆性中 (按自证结论收尾后错误进入交付, 事后难以复原现场); O002 打击效率与判据分辨率, 概率高, 代价中但可逆 (返工只改计划与报告格式). 即便承认正方最强的幸存论点 (唯一判据 + 证据复用 + 不建平台), O001 仍要求增加一个机械锚点, O002 仍要求把收益判断改成可核对条件, 所以反方占优, 但属于"显著约束", 不是推翻.
- 我没有采用的攻击 (免得虚张声势): "全量 PRODUCT 场景等于全项目巡检" 不成立, 因为 AC-002 只要求本变更 PRODUCT 的场景, NG-004 明确排除无关功能; "固定 SHA 不追 main 会让复刻腐化" 也不成立, 因为 D021/F008 已明确不追上游, 且 BR-010 用固定来源换取可复核性.
