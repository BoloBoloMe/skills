# 验证 skills 与独立产品验收 Product Spec

## 背景

现有流程已经提前确认产品标准, 建立测试追溯并要求真实证据和最终人工确认, 但大型任务在实现/合并/评审收敛后还缺少明确的独立成品验收节点. 用户希望借鉴 pstack 的实跑和操作配方机制, 让未参与实现的会话验证最终成品, 同时复用项目操作知识并提高影响判断与性能数字的可信度, 不替换既有工作流.

## 目标

- G-001: 调用者通过 verify-change 获得最终集成版本针对已确认 PRODUCT.md 的全部场景和审计 BR 的逐项结果与可复核证据, 不把技术设计评审或计划勾选当成产品验收.
- G-002: tdd-as-orchestra 在评审无新须重构发现项后, 于停止并汇报前委派独立会话组织产品验收; 明确实现问题回到原重构/实现/合并/评审循环, 产品检查通过才正常收尾.
- G-003: 验收指挥者在派工前按产品场景组评估人数/并行关系/共享资源/共同准备, 委派非作者实跑, 减少冲突/互等/重复工作, 不亲自验收或组织修复.
- G-004: 调用者能区分当前观察/可复用旧证据/推断/未验证, 明确结论覆盖的提交与条件; 证据输出不混淆验收输入, 阻塞和清理残留不伪装成产品通过.
- G-005: 配方生成者能按已确认 PRODUCT.md 的相关范围生成项目本地的启动/实例检查/真实入口操作/取证/清理规则及功能地图, 并由新子会话跑过本次全部新增或修改的功能配方后交付.
- G-006: 配方维护者能检查并修正当前 PRODUCT.md 相关范围内的文档或驱动问题, 委派新子会话实跑新增或修改内容, 将产品缺陷单独报告, 不通过修改配方掩盖产品与标准的差异.
- G-007: 调查者使用 blast-radius 识别变更安全所依赖的关键事实, 运行真实代码给出证明或明确未证实, 将已确认风险与已排除项分开, 大或宽变更采用多模型同题调查并合并答案.
- G-008: 性能检查者使用 benchmark-checklist 以实际运行证据审查测量方法和数字, 区分更快/更慢/无可测差异/无法下结论, 不从错误计数/未发生的工作/不公平配置/不足重复次数中选赢家.

## 非目标

- NG-001: 不让 verify-change 验收 TECHNICAL.md/EXECUTION.md 或代码库设计. 理由: 技术要求仍由既有执行验证和 code-review 承担, 新节点专注最终产品标准.
- NG-002: 不替换提前定义验收/TDD/双轴评审/合并后完整测试/最终人工确认, 不把代理检查通过当成正式人工交付. 理由: 这些能力已经存在.
- NG-003: 不自动给小任务 tdd 接入新节点, 不固定两个验收者/十路验证/每条 AC 一个会话. 理由: 先只接入大型编排, 分工须有实际收益.
- NG-004: 不全项目铺开或巡检无关功能地图, 不由生成/维护任务修产品代码/项目配置/既有测试, 不直接修改全局部署副本. 理由: 配方和本次范围各有明确职责.
- NG-005: 不让五个新 skill 自动提交/推送/开 PR/合并, 不改变调用方原有的本地提交和合并职责. 理由: 不迁入 pstack 的发布流程.
- NG-006: 不迁入 Cursor 生态或额外移植 why/how/arena/unslop/完整 poteto-mode 流程. 理由: 只提取本次实际依赖的规则, 保持五个通用 skill 的范围.
- NG-007: 不新增自动 agent 评测平台或公共流程回放框架. 理由: 复用现有会话能力进行真实受控演练, 只允许必要的任务专用夹具和证据整理.

## 业务规则

- BR-001: 已确认 PRODUCT.md 是产品验收判据来源; 操作地图/代码现状/技术材料/执行计划不得另立或弱化标准. verify-change/配方生成器/配方维护器都以 PRODUCT.md 为必需输入, TECHNICAL.md/EXECUTION.md 仅可选读.
- BR-002: 首次产品验收由未参与本次实现或修复的全新子会话执行; 原验收指挥者和验收者仅在未参与修复时可恢复复验. 实现指挥者/验收指挥者/实际验收者的职责不得合并为作者自验.
- BR-003: 验收者可共享有产生者/版本/位置的原始证据, 但须独立核对自己负责的标准, 不照抄他人的通过结论. 受影响的关键真实路径须由非作者实跑; 其他旧证据仅在覆盖和代码/依赖/配置/环境条件适用且无新失败线索时复用.
- BR-004: 未运行或缺乏充分证据的必验项不能算通过; 代码推断不冒充实际运行结果, 代理检查通过不替代最终人工确认.
- BR-005: 写入测试资源须先明确并批准本任务的资源/对象/操作/清理范围; 同范围可复查, 改范围再批准. 自清理不等于只读, 清理失败或残留必须独立报告, 不计为整项通过.
- BR-006: 产品验收从已提交且干净的最终集成版本开始, 结论绑定起始提交. 验收目标工作区内只允许约定独立证据目录新增验收记录; 该目录影响构建/测试发现/运行输入时外置, 其他源码或 Spec 变化不得借此忽略.
- BR-007: 明确实现缺陷与标准/权限/环境/证据缺口分开处理. 需要改变 Spec/范围/正式接缝或用例时停止并交回既有决策流程, 不即时发明要求或伪造缺陷.
- BR-008: 一次性实验可用于核实真实机制, 但不改产品源码/新增正式 TC/新增权威判据, 并受资源授权和清理约束; 内部实验不能代替成品真实入口验收.
- BR-009: 五个通用 skill 及生成的项目级 skill 都采用用户调用方式, name 与目录一致, disable-model-invocation 为 true; 其他流程可明确提名调用, 不增加常驻自动触发描述. (审计)
- BR-010: 两项复刻以 cursor/plugins 的 4382e687a50b8d2c5ce4d141d001186589cff8d5 为固定来源, 保留适用的 Lauren Tan 版权和完整 MIT 许可/免责段, 显式记录行为差异; 汉化保留核心步骤/强度/数量/例外/完成条件, 普通正文中文且使用 ASCII 标点. (审计)
- BR-011: 本变更只建设五个通用 skill 及必要参考材料/测试支持并接入 tdd-as-orchestra 的验收节点, 不替换既有 Spec/TDD/双轴评审规则, 不改部署副本, 不引入额外上游体系或自动 agent 评测平台. (审计)
