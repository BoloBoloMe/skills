# 工作流 skill 硬规则分类清单

用途: 作为「按验证重构工作流」的施工图. 每条硬规则标一个类别和一个动作, 由用户圈选异议项后动手.

## 分类定义

| 类 | 判定问题 | 默认动作 |
| --- | --- | --- |
| **验** | 没有它会出假通过或假完成吗? | 保留, 升为唯一权威 |
| **协作** | 它约束的是多 agent / 跨会话的产出位置, 命名, 顺序与交接吗? | 保留, 从主文件搬到单独参考页 |
| **安全** | 它防的是数据丢失, 越权, 不可逆操作吗? | 保留, 收拢到一处, 各 skill 只留指针 |
| **做** | 它只决定实现或调查的手段吗? | 降级为可选 (保留文件, 从强制链摘除) |

判定顺序: 先问「删掉它会不会有人假通过/假完成」, 会就是验; 再看是否只关协作; 再看是否只关安全; 都不沾才是做.

一条规则可拆成两条时拆开归类. 例如 `tdd` 的「先红后绿」拆为「做法 (红绿循环)」+「验 (红态必须真出现过)」.

## 分类定案的连带动作

`code-review` 的代码风格评审归「验」后, 需要补结论口径, 否则「验」名不副实.

- 现状: 基线规则明写「每个坏味道都是带标签的启发式判断, 绝不作硬性违规」, 即不产出通过/不通过.
- 补法: 保留「不作硬性违规」, 但要求 Standards 轴报告**完整列出全部发现, 不得省略或只给摘要**, 并把「已检查范围」写成可核对条目. 这样「好看与否」就成了可复查的验证结果, 而不是口味意见.
- 适用: 同理适用于任务内任何「主观判断类」验证项.
