# 重构前后的模拟对照任务

用途: 证明「按验证重构工作流」没有把工作流改坏. 同一个需求, 在改动前用旧说明书走一遍, 改动后用新说明书走一遍, 对比产物与证据.

## 需求 (造出来的, 但真实有用)

给 `tests/run` 增加 `--explain`:

- 打印本次改动面会跑哪些测试套件, 以及将要执行的命令, **不真的运行 pytest**.
- 退出码 0.
- 现有 `--fast` `--all` 与其他参数直通 pytest 的行为保持不变.

选择理由: 有真实命令行入口; 有可观察输出; 无网络与容器依赖; 改动小 (约 20 行); 现状下 `tests/run --explain` 会被当成 pytest 参数而报错, 天然构成前后对照.

## 对照记录

| 项 | 旧说明书 (baseline) | 新说明书 (after) |
| --- | --- | --- |
| issue 文件节数 / 其中「无」「不适用」的节数 | 待填 | 待填 |
| issue 是否声明变更类型与对应验证要求 | 待填 | 待填 |
| 是否被推向 TDD (红绿循环) | 待填 | 待填 |
| 验证入口是否事先写明可复跑操作与通过标准 | 待填 | 待填 |
| 证据是否来自真实运行 (含环境版本) | 待填 | 待填 |
| 未验证范围是否写明 | 待填 | 待填 |
| 产物总字数 | 待填 | 待填 |

## 判定标准

新流程算达标, 须同时满足:

1. 交付证据仍能证明需求逐项成立 (4 条行为各有一条真实运行记录).
2. 「未验证范围」没有因为模板变小而消失.
3. issue 不再包含与本次交付无关的空章节.
4. 强制项只剩验证相关的三节时, 执行者仍知道允许改哪些文件 (范围边界未丢).

## 执行方式

- 旧: 在 `sim/before` worktree 内, 按仓库当前 skill 文件逐条执行, 产物记入 `baseline/`.
- 新: 在 `sim/after` worktree 内, 按重构后的 skill 文件重跑同一需求, 产物记入 `after/`.
- 两个 worktree 均从同一提交切出, 需求文本不变.
