# 全程盘问对齐与编号汉化 Technical Spec

## 模块划分

- to-spec 流程文档: 编排领域感知, 设计核查, grilling 盘问, decision-ledger 入账, domain-modeling 按需维护, opposing-viewpoint 反方攻击, 主会话落笔, 独立检查与修文, 按需 handoff 接续; 不整体调用 deliberate.
- 规格格式与机检: PRODUCT/TECHNICAL 模板和 GHERKIN 纪律维持下游格式, check-ac.py/check-tech.py 检查格式与编号, 不冒充语义忠实检查.
- 预览与转正: ac-draft.py 保留工作区, 机械 HTML 阅读预览与产品原文转正; 移除 review_id 绑定, 保留确认标记及现有原子写入保护.
- 验证方案流程文档: verify-change 编排按方法盘问, 账本, 写前反方, 主会话成文与写后独立核对, 隐藏方案决定到覆盖表的转写与修订核对; 执行与复验保留既有独立验证职责. 复用既有流程模块, 不新增服务或记录工具.
- 调用说明与编号约定: navigate 承接盘问确认的规格语义, decision-ledger/to-execution 等现行编号约定与正文汉化一致, README 人工核对执行调用关系并经非作者复核.

原四块职责继续有效, 新增验证方案流程职责; 内部文件拆法可调整, 复用现有模块. 涉及目录为 workflow/to-spec, workflow/navigate, workflow/decision-ledger, workflow/to-execution, workflow/verify-change, general/ 内实际含编号规则的材料及 README; deliberate 独立流程保持既有语义, 历史快照不改.

## 模块接口

### 盘问与确认

- 输入为实际权威来源, 产物根目录和当前授权范围. 两份正式产物为根目录下 PRODUCT.md/TECHNICAL.md, feature 内编号稳定连续. 规格交付不扩大实施授权.
- 先感知领域并检查技术方向, 由两份模板展开范围树; 可查事实先查, 按当前能问的问题自然流动, 可跨产品/技术回补, 不按固定节序盘问.
- 产品判断和用户要固定的技术选择须亲答, 包括接口是否固定, 接缝与依赖, 兼容迁移承诺. 事实随所依赖的问题呈现, 用户拍板即确认依据事实, 标注随决策N确认; 无决策引用的纯背景事实不入账.
- 验收段按覆盖树中档: 每种非直译情况问一句主要刺激与可观察结果. 只有刺激/结果直接来自账本或用户答复中的已确认目标/规则, 且不新增前提/阈值/行为, 才免问; 拿不准就问. 同一实质刺激与结果只问一次, 多个落笔场景各自成条且引用同一依据.
- 主会话组织前提措辞和场景文字, 不得构造无依据的判定; 写稿缺判定先补问入账. 长期判定只用现有账本格式, 不新增过程记录文件/章节/格式, 免问情况不留痕. 领域语言与 ADR 按既有规则维护.
- 闭环前展示两模板逐节已问/未碰状态及未碰理由, 不要求逐节另附结论; 完成盲区扫描, 取得用户明确结束确认. 同时确认两份规格所需内容, 不再要求用户逐版审稿. 沉默/部分认可/要求继续不构成闭环.
- 反方与独立检查均不能替用户拍板, 规格确认不构成成品验收. navigate 的 acceptance 继续由用户按标准和证据逐项决定.

### 验证方案盘问与成文

- 输入沿用 verify-change 既有通用规则: 当前有效且已确认, 能定位全部必验项与例子, 产品入口/观察方式或审计对象/依据的权威材料. 不要求固定文件名或必须有两份规格. 先核实输入与 verification-contract, 设计会话只读权威输入, 不看实现, 不从实现或未落盘的口头要求反推产品判据.
- 盘问决定 LLM 如何验证某条或某类已有要求, 按验证方式归组讲清材料, 做法, 预期观察与证据. 不逐条重过已确认用例, 不把检查内容差别或操作小细节逐一交用户决定. 方法或适用条件有实质差别以及特殊情况里的新选择另问, 不因归组跳过新决定. 从已确认权威输入及本变更已有确认可直接推出的安排免问, 代理构造不算已有依据, 拿不准能否免问或是否同类就问.
- 沿用既有验证契约对方法和证据的要求, 不新增或改变产品判据. 原有按产品对外入口操作与观察, 行为与审计分开, 不用内部接口或测试桩顶替产品入口等约束保留. 输入不足/冲突, 方法或入口观察依据不足时报告具体缺口并停止提交完整方案, 交回输入维护或前置调查, 补齐并按原流程确认后继续. 不允许设计会话为补依据自行读实现或实验.
- 方法已知可行而执行环境未齐时, 可确认附条件方案并写明必备条件; 方法可行性未知不能以资源待准备代替调查. 执行时条件未满足的项记未验证, 不降低标准或用弱证据顶替, 写入和资源授权边界不变.
- 闭环前对照权威输入全部必验项和例子展示覆盖清单, 跳过理由和资源条件, 不以已问问题列表代替范围, 不要求用户逐行阅读成文步骤. 用户明确结束盘问即确认方案内容, 问完才写 VERIFICATION-PLAN.md, 成文后不再整份采纳. 沉默或部分认可不算确认. 已有两份规格时保持先规格后方案, 规格结束不能冒充未来方案的确认.
- 盘问决定进入现有 DECISIONS.md 决策/事实条目; 无账本时按 decision-ledger 新建通用账本. 分段续问与按需 handoff 沿用下述续问规则, 按验证方案实际范围保存进度, 不强加两份规格模板. 不新增盘问专用文件/章节/格式, 免问不留痕, 不以方案替代未确认决定或新增免问清单.
- 决定入账后由未参与相应决定的独立反方会话攻击, 主会话核实并按需补问入账, 收敛后主会话成文. 另一未参与相应决定或写稿的独立会话只查不改方案, 与反方分用会话. 检查忠实性, 全量覆盖和可执行性, 依据仅取已确认权威输入及盘问决定/用户答复, 不以方案自己自证. 初次全量核对; 修文复查受影响内容与引用, 有新证据需要时扩大.
- 主会话先复核发现, 误报给理由, 有据转述错误直接修文, 缺少或改变决定才补问并入账. 独立复查也核对转述错误的分类和当前版本与原确认是否相符, 不能由作者自标已确认免检. 纯修文不重新要求用户阅读或确认整份方案. 判据变更需求交回原权威输入维护或既有决策流程.
- 方案保留既有最低字段: 方案版本 vN, 确认状态, 来源引用及确认依据, 覆盖表, 必要前提/资源限制. 覆盖表按权威输入原有粒度逐项包含所有独立场景/要求与全部例子, 逐项写来源位置和原编号/标题, 验证类型, 产品入口或审计对象, 步骤, 预期观察, 证据与环境条件; 归组只改变提问方式, 不减成文覆盖行. 来源定位不自造版本或编号, 不复制整份输入.
- 内容修订递增方案版本, 保留变更和确认依据, 当前版本可追溯盘问确认及独立复查. 沿用现有来源引用与检查产物, 不新增专用记录格式. 用户明确闭环且成文检查无阻塞后才交付当前已确认方案, 状态和版本本身不作确认凭据. 执行/复验仍核对被引用内容与当前方案实际一致, 变化时先回设计方式更新, 只就新增或改变决定补问, 纯修文修正复查, 不恢复逐版整份审阅. 新一轮验证绑定实际方案修订号和明确目标提交, 仍由非作者操作并保留原件; 原轮不悄悄并入新输入.

### 独立会话与修正

- 落笔前由未参与盘问/落盘的独立反方会话攻击账本决定, 输入原始需求, 账本和必要代码入口. 主会话核实, 驳回给依据, 新增/改变决定交用户裁决, 收敛后主会话先产品后技术落笔.
- 落笔后另起未参与盘问/落笔的独立会话, 与反方分用会话, 只查不改两份正式规格. 通过现有任务输入和账本引用提供必要答复来源, GHERKIN 纪律与达标标准, 不新增盘问常设记录.
- 一次正式检查合并完成内容对账, 反向覆盖与达标检查. 首次覆盖所有场景刺激/结果, 目标/非目标/规则以及技术固定接口/接缝/约束; 叙述组织不逐句核. 按账本与用户答复重推应覆盖情况, 不以本次规格转写自证. 同时查可读性, 跨条目矛盾与产品到技术的承接.
- 发现需有位置, 来源依据与具体后果. 主会话先复核误报/真缺口: 误报驳回给理由; 有据但写错则改草稿; 缺决定或免问无据只补问该分支并入账. 不重问已定判定, 整盘重来仅由用户要求.
- 不在草稿和正式文件上重复整份独立检查. 修文后各类检查仍适用, 内容检查复查受影响内容与引用, 未变且未受影响部分沿用原结论. 检查会话说明影响范围, 主会话复核; 新证据或不能确认旧结论适用时扩大, 必要时全量, 保持最终整份规格有完整检查覆盖.

### 脚本与文件

- 固定保留产品正文暂存稿, 独立验收场景草稿与技术草稿三份临时材料. 内部文件名和私有函数形状可调整.
- check-ac.py 保留草稿/正式模式, 既有 Gherkin 子集/标签闭集/编号对账/正式标记要求及退出码0/1/2. 正文中文词加无前导零数字, 标签拉丁三位, 经既有归一化按数字对应, 重复/不存在编号仍失败. 现有输入容忍不构成允许写非规范正文的依据, 不额外引入未确认的产品拒绝判据.
- check-tech.py 保留固定节名, 必备节, 节序及既有退出码. 两份模板与 GHERKIN 的格式纪律保留, 逐版审稿说明改为盘问确认及忠实承接.
- ac-draft.py 保留 workspace/preview/promote 职责, stdout JSON 和 success/退出码约定. preview 从原文生成阅读卡片和草稿预览, 照常交付且可选看, 不作为确认入口. promote 接收产品暂存稿/验收草稿/正式输出路径, 删除 --review 必填与哈希审阅版本校验, 不保留旧参数兼容分支.
- 产品转正原样嵌入验收正文并加 confirmed-flow: v1, 机检通过才原子替换, 保留执行期间输入变化和正式目标变化检测. 正式机检仍拒绝缺标记. 标记v1表示流程格式, 不计修改次数, 不随修文升版, 不证明用户看过文件; 调用会话核实实际 chat 确认, 不另建确认状态文件.
- 技术稿经机检后机械复制为 TECHNICAL.md, 核实草稿与正式文件字节一致, 不由 LLM 复制重写. 可调整实现例为 cp 后 cmp. 产品转正失败保护既有 PRODUCT.md; 技术复制或任一检查失败则按关键流程保持整组未完成.
- 审计规则不进 Gherkin, 证据材料放账本事实来源, 对应决定引用事实号, 产品审计条目不承载证据路径.

### 分段续问

- 同会话未闭环继续当前能问的问题, 不因暂停提前写稿. 换会话前把已确认判定及依据事实入账, 再按 handoff 写交接文档, 新会话读取两者恢复.
- 交接含当前可问问题, 已否决分支及理由, 逐题进度, 逐节覆盖进度, 盲区扫描进度与待裁决项, 用户明确提出的暂停/节奏要求. 不推测疲劳或心理状态; 已入账内容只引用, 免问情况不留清单或锚点.
- 本会话闭环就不写交接. 落点沿用 handoff: 同机临时目录, 跨机仓库并推送, 位置不明先问. 不新增自动保存或跨容器恢复承诺; 原件缺失如实说明, 不猜未定判定.

## 接缝与依赖

- 文件接缝: 用户通过 to-spec 入口确认内容, 下游读取 PRODUCT.md/TECHNICAL.md, navigate 承接阶段状态与正式验收; verify-change 读取已确认权威输入, 输出 VERIFICATION-PLAN.md, 后续独立验证绑定其修订号. 方案的检查对象是候选流程条文和调用说明, 本次不要求用真实需求试跑. 文件生成和命令行输出是机械行为的观察入口.
- 命令行接缝: ac-draft.py 负责工作区/预览/产品转正, check-ac.py/check-tech.py 负责格式检查; 输入材料, stdout/退出码, 输出文件为可检查面. 独立会话以需求/账本/答复/正式稿为输入, 以只读报告为输出.
- 进程内依赖: 沿用 gherkin-official 解析与展开, 预览/转正复用 check-ac.py.
- 本地可替换依赖: 文件系统/临时目录, 现有技能与会话工具, 本机 present 展示服务; 使用隔离工作区核对实际产物.
- 远程但自有依赖: 既有模型网关及容器到宿主展示映射. 不新增服务是固定边界, 不新增外部数据服务.
- 流程场景从候选技能条文/调用说明核验, 机械场景从公开 CLI 实跑核验, 审计断言从限定范围差异及账本来源核查. 具体步骤和证据由 milestone-05 验证方案确定. 本次不要求真实需求试跑, 当前会话不证明已实现新版技能的实际表现.

## 安全策略

- 独立检查只接收与判定相关的必要材料并保留足够依据. 材料传递/展示按现有[安全底线的脱敏节](../../../workflow/verification-contract/SAFETY.md#脱敏)执行; 脱敏后不足以判断时报告缺口并交用户处理, 不猜, 不另定脱敏制度.
- 预览只挂专用目录, 内容与目录约束沿用 [present](../../../general/present/SKILL.md). 原始答复和无关材料不因核对需要而整份挂出.
- 本次不新增认证/权限/密钥机制, 未提出额外安全要求, 共用安全约束继续适用.

## 关键流程

1. 领域与输入核实 -> 范围树/事实查证 -> 按当前能问的问题盘问 -> 逐节清单/盲区扫描/用户明确闭环 -> 入账及按需领域维护 -> 独立反方 -> 主会话核实与必要补问入账 -> 先产品后技术落笔.
2. 三份临时材料 -> 草稿机检 -> 产品机械转正/技术机械复制并核实一致 -> 正式机检 -> 另一独立会话合并对账/反向覆盖/达标检查 -> 无阻塞交付两份规格, 照常交付机械预览供选看. 首次全量, 修文按影响范围复查.
3. 真缺口按已有依据修文或分支补问, 再经草稿机检和机械落正式; 不手改正式文件. 新判定入账, 已定判定不重问, 不要求整版审稿.
4. 失败处理跨产品转正/技术复制/检查, 在本节固定整组交付条件: 任一文件生成或检查失败, 整组仍未完成, 保留现场, 补齐失败步骤并检查两份后才交付. 会话及已有调用方状态记录未完成, 不新增确认状态文件. 不要求增加两文件同时替换机制, 未完整交付不向下游声明规格齐备.
5. 验证方案链路: 输入/验证契约核实 -> 按方法归组盘问与按需续问 -> 覆盖清单/跳过理由/资源条件/明确闭环 -> 入账及独立反方收敛 -> 主会话成文 -> 另一独立会话核对 -> 无阻塞交付已确认方案. 修文按决定是否变化分流, 版本递增, 当前内容可追溯确认和独立复查; 不整份重审. 独立检查不能替用户拍板, 附条件方案不提前取得通过结果.
6. navigate 的 spec 定义/完成标准/ACCEPTANCE-GUIDE 与 verification-plan 定义/完成标准改为对应的盘问确认语义, verify-change 执行入口/REVERIFY 的重新确认说明同步为只补问变化决定. README 与技能正文的执行调用人工对账并经非作者复核, deliberate 独立流程与历史文件保留.
