# 全程盘问对齐与编号汉化 Product Spec

## 背景

现有 to-spec 先起草验收用例和技术设计, 再请需求提出方逐版阅读采纳. 本变更让用户把精力用于拍板: 通过一场可分段继续的盘问确定两份规格的内容, 问完才落笔. 规格的忠实性由机检与独立核对承担. verify-change 的验证方案确认同样改为先盘问后成文, 用户决定 LLM 用什么方式验证已确认要求, 不逐条重过用例或阅读预写方案. 同时将 workflow/ 与 general/ 的正文编号统一为中文, 降低阅读负担.

用户已接受免问不留痕带来的静默漏检风险, 以及同机临时交接文档在容器删除后丢失的风险. 本变更落实既定核对流程, 不宣称能消除这两类风险. 验证方案同样保留免问不留痕, 仍有独立双方同时误判的残余风险; 不把旧范围的风险接受记录写成用户曾单独接受较弱验证证据, 验证契约及证据要求继续适用.

## 目标

- 目标1: 用户通过一场连续盘问确定 PRODUCT.md 和 TECHNICAL.md 所需判定, 确认盘问闭环即同时确认两份规格的内容, 无须阅读预写草稿或落笔后的 Gherkin.
- 目标2: 验收段按覆盖树讨论情况, 每种须问情况用一句话问主要刺激与可观察结果; 严格直译的情况免问, 同一判定只问一次, 不替用户作新判定.
- 目标3: 已确认决策与依据事实进入现有账本, 跨会话时通过账本和按需交接文档恢复盘问进度, 不引入盘问专用记录文件.
- 目标4: 决策先经独立反方攻击并收敛, 落笔后由另一独立会话对两份正式规格作内容对账, 反向覆盖和达标检查; 首次全量, 修文复查受影响内容, 发现问题只补缺失分支或按已有依据修文.
- 目标5: 两份权威规格的固定格式, 机检, HTML 预览和机械转正保留; 预览可选看, 转正不再依赖 review_id, 确认标记保留, 正式文件由通过检查的原文生成.
- 目标6: workflow/ 与 general/ 下现行编号约定统一为 决策1/事实1/验收1/规则1/目标1/非目标1/用例1, 保持 Gherkin 拉丁三位标签与 ISSUE-01 文件名前缀可用.
- 目标7: navigate 对规格整理, 验证方案确认和终点验收的说明及相关调用说明与新流程一致, 其余调用者仍可独立使用 deliberate.
- 目标8: verify-change 以验证方式为单位盘问, 用户确认盘问闭环即确认方案内容, 成文后不再要求阅读采纳整份方案; 必验项与例子仍全量覆盖并独立核对, 修订只补问新增或改变的验证决定.

## 非目标

- 非目标1: 不在本次改造中试跑真实需求, 不用样张问数承诺真实盘问规模; 真实使用后的粒度调整另起旅程.
- 非目标2: 不改 deliberate 的独立四步流程, 不把 to-spec 新流程反向替换其他调用者的决策盘问.
- 非目标3: 不兼容旧正文编号, 不迁移历史产物及指向历史条目的引用, 不改 milestone-01 这类里程碑 id 或目录名.
- 非目标4: 本里程碑交付规格, 下游实施范围不构成立即编码授权; 执行拆分, 成品实施与独立验证各由后续里程碑承接.

## 业务规则

- 规则1: 产品判断及用户要固定的技术选择必须由用户亲答; 可查事实由代理查证并随所依赖的决策一并确认, 纯背景事实不入账. 前提措辞和场景组织可以构造, 判定性内容必须有已确认依据.
- 规则2: 免问仅限刺激与结果能从已确认目标/规则直接推出, 且不新增前提, 阈值或行为的情况; 拿不准就问. 同一刺激与结果实质相同的判定只问一次, 不同落笔场景仍各自成条.
- 规则3: 闭环前向用户呈现两份模板的逐节清单, 标明已问/未碰及跳过理由, 不要求逐节另附结论, 并完成 grilling 的盲区扫描与结束确认. 沉默, 只认可部分内容或要求继续都不算闭环确认.
- 规则4: 反方攻击在决策入账后, 规格落笔前进行, 由未参与盘问与落盘的独立会话执行. 主会话核实发现, 需要新增或改变决策时交用户裁决.
- 规则5: 每次落笔和修订均须过机检, 判定性内容对账, 反向覆盖和独立达标检查. 首次独立检查覆盖两份正式规格全部判定; 修文复查受影响内容与引用, 未变且未受影响部分沿用既有结论, 有新证据时扩大范围. 对账和反向覆盖只依据账本条目与用户答复, 不以本次落笔的 PRODUCT.md/TECHNICAL.md 自证.
- 规则6: 主会话先复核检查发现; 误报说明理由, 有依据的转述错误先修草稿再机械转正, 缺判定或免问无依据则只补问受影响分支并入账. 已确认判定不重复问, 整盘重来只由用户要求.
- 规则7: 审计规则不进 Gherkin, 其证据材料写入账本事实条目的来源, 对应决策引用事实号; PRODUCT.md 的审计规则条目不承载证据路径.
- 规则8: 两份规格的盘问范围含产品与技术全部适用节, 允许自然跨话题回补. 反方与落笔后检查不得代替用户拍板, 机检通过不得宣称用户已验收.
- 规则9: to-spec 及其配套材料不规定盘问问题数上限, 不把样张估算或用户精力参考写成上限. (审计)
- 规则10: 盘问判定只用现有决策/事实账本格式持久记录, 不新增专用文件, 章节或格式, 免问情况不留痕; 领域语言/ADR 维护与按需 handoff 交接仍遵循各自技能. (审计)
- 规则11: 修改仅落本仓库, 不改已安装技能; 历史文件及历史引用原样保留, deliberate 独立流程保持既有语义. (审计)
- 规则12: 正文编号为中文词加无前导零数字, 标签仍用 @AC-001/@G-001/@BR-001 等既有拉丁三位形式, issue 文件名保留 ISSUE-01; 模板固定节名, 节序和现有机检约定继续有效. (审计)

- 规则13: 传给独立检查会话的原始答复只包含任务必要材料, 按既有共用规则脱敏; 展示只挂专用预览目录.
- 规则14: 两份正式规格共同构成交付单元, 任一文件生成或检查失败则整组未完成; 保留现场, 补齐失败步骤并检查两份文件后才交付.
- 规则15: 本次复用现有解析库, 会话工具与展示服务, 不新增服务. (审计)

- 规则16: 验证方案盘问按 LLM 验证某条或某类要求所用的方式归组, 讲清怎样验证, 预期观察与证据, 不逐条重过已确认用例或盘问检查动作的小细节; 方法或适用条件有实质差别及特殊情况中的新选择须另问. 已确认权威输入及本变更已有确认可直接推出的安排免问, 代理构造的新选择不算直接推导, 拿不准是否免问或同类就问.
- 规则17: 验证方案闭环前呈现覆盖清单, 跳过理由与资源条件, 清单对照全部权威必验项和例子, 不以已问问题清单代替完整范围, 不要求逐行阅读成文步骤. 用户明确结束即确认方案内容; 沉默或部分认可不足以确认. 规格与方案仍按既有阶段顺序分别确认, 确认方案不代替成品验收.
- 规则18: 验证方案落笔前由独立会话攻击已入账决定, 落笔后由另一未参与相应决定或写稿的独立会话检查忠实性, 全量覆盖与可执行性. 依据是已确认权威输入与盘问决定/用户答复, 不以方案自证. 首次全量核对, 修文复查受影响内容与引用, 新证据需要时扩大范围; 分组盘问不减少必验项与例子的成文覆盖行.
- 规则19: 主会话先复核方案检查发现, 误报说明理由, 有依据的转述错误直接修文并独立复查, 缺少或改变决定才补问入账. 内容修订递增方案版本并保留变更与确认依据, 当前版本须可追溯盘问确认及独立复查; 版本号和确认状态本身不证明获确认, 纯修文不重新要求用户整份采纳. 错误分类与当前版本是否忠实原确认内容同属独立检查范围.
- 规则20: 方法可行但执行条件未备齐时可确认附条件方案, 必备条件写明, 执行缺条件记未验证, 不降通过标准或用较弱证据顶替. 方法是否可行尚不明确时报告缺口, 交回权威输入维护或前置调查, 材料补齐并按原流程确认后再继续.
- 规则21: 验证方案设计只读当前有效且已确认的权威输入, 不看实现或从实现反推判据; 支持两份规格以外的权威输入. 判据或方法依据缺失/冲突时报告缺口并停止提交完整方案, 交回输入维护或既有决策流程, 不在方案中新增或修改产品判据. 验证契约约束方法与证据, 不新增产品判据.
- 规则22: 验证方案盘问与续问使用现有通用决策/事实账本和按需 handoff; 无账本时按 decision-ledger 既有规则新建 DECISIONS.md, 不另造盘问专用文件, 章节或格式, 免问情况不留痕. 同会话闭环无需交接, 换会话保存必要进度且已入账内容只引用; 成文方案不能替代尚未确认的决定或用来新增免问记录清单.
