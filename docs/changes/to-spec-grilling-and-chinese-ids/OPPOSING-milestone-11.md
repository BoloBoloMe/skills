## 正方还原

1. 定义: 调粗的是用户作决定时的提问单位. 从逐条讨论已确认用例及检查动作, 改为讨论验证某条或某类要求的方法. 每组须能说清材料, 做法, 预期观察和证据. 不减少要验的要求, 不把多个要求缩成一次抽样结论.
2. 前提: 已确认权威输入已经确定验什么; 相同验证方式可共同讨论, 内容不同不必重复问方法; 方法或适用条件有实质差别及特殊情况的新选择仍另问. 已有依据能直接推出的安排免问, 代理构造的新选择不算已有依据, 拿不准仍问. 以上来自决策32/39, 不是反方补出的授权.
3. 论据: 用户明确反对过细盘问, 认可主会话的归组复述并结束规格盘问. 决策39明示不替代31-38; 决策33/35仍要求全量覆盖与独立核对; 决策36/38仍保留可行性, 输入和验收边界. 成文对应见 PRODUCT.md:46-52及 TECHNICAL.md:27-36.
4. 推理链: 判据已定, 因而不再问一遍验什么; 归组讨论如何验, 消除相同方法的重复提问; 真正的新选择和适用条件差别仍交用户决定; 成文逐项展开并独立核对, 保住覆盖和证据要求; 后续另行确认具体方案, 本次规格确认不提前替它作决定.

四要素均可由任务输入和本地材料确定, 无须为还原正方补问. 真实使用能减少多少提问, 当前未知, 不作为正方成立的既有事实.

## 主战场

攻击最脆弱的前提: 代理能否把共享验证方式与实质不同的验证决定分开, 在少问的同时不替用户作新决定.

若一个笼统方法名就能吞掉入口, 观察依据或适用条件的差别, 用户确认的只是空泛类别, 成文细节会变成未经确认的决定. 相反, 若每处不确定都拆成一个动作问题, 调粗又会失效. 必须检验规则是否给出两端之间可执行的界线, 不能只以用户喜欢少问来证明归组可靠.

## 反方反驳

以下后果均为条件成立时的失败路径, 不是本轮已观察到的违规事实. 确定缺口为0项, 待验证的执行疑点为3项.

### 攻击1: 归组可能只剩一个笼统方法名, 把证据差别藏进细节

- 来源: 决策39的 "按验证方式归组" 与 "不问检查动作里的小细节"; 决策32/33关于新选择和全量覆盖的约束. TECHNICAL.md:28-30要求讲清材料, 做法, 观察和证据, 并保留行为与审计分开等约束.
- 最强反驳: 若仅说 "由 LLM 检查", 就可能把查看候选流程条文和运行公开 CLI 混成同一种方式. 用户无法知道哪些要求会实跑, 哪些只核对文字. 两者确实有不同验证对象和证据, 不是措辞差别; 本次这种区分可直接见 TECHNICAL.md:64-69.
- 实际后果: 若按上述错误归组执行, 可能拿文字核对顶替应有的运行结果. 即使覆盖表每行都有内容, 仍未证明相应机械行为满足要求.
- 对正方剩余约束的检验: 决策39要求讲清怎么验及证据, 并保留特殊情况的新选择另问. 决策32还要求验证契约合规, 禁止把代理新选择当直接推导. 决策36不允许弱证据顶替. TECHNICAL.md:29/69已明确入口和证据层面的区别. 上述错误无法在同时遵守这些规则时获得放行依据.
- 性质: 执行误判疑点, 不是已证实规则缺口. 对证据或可行性有影响的差别不能仅靠同名归组免问, 这一约束已存在. 不需要用户重新裁决静态核对与实际运行是否有区别.
- 置信度: 现有规则足以拒绝上述误用 = 高; 未来会否误判 = 未知.

### 攻击2: "拿不准仍问" 可能把调粗拉回逐动作盘问

- 来源: 决策32的保守口径与决策39的调粗要求, PRODUCT.md:46及 TECHNICAL.md:28同时保留二者.
- 最强反驳: "实质差别" 没有穷举定义. 代理可以对每个检查动作都声称拿不准, 再逐条追问. 形式上保留了保守原则, 实际仍让用户承担本应由代理完成的操作设计. 调粗的收益可能归零.
- 实际后果: 若发生, 用户仍反复确认用例内容或操作细节, 方法决定淹没在细节中, 再次出现本轮明确反对的使用负担.
- 对正方剩余约束的检验: 决策39明确约束提问内容, 不仅减少问数. 要解释的是方法或适用条件的实质差别, 不是每个动作怎么写. 决策32的拿不准针对能否免问和方法同一性, 不能扩成所有实现细节都问. 现行 verify-change:25本已不要求按钮点击序列, 产品/技术规格又明确不逐项盘问操作小细节. 代理应指出尚未决定的验证做法或适用条件, 并按方法组织问题; 不能用一句拿不准取消新确认的粒度要求.
- 性质: 执行尺度疑点, 不是必须新增裁决的冲突. 无法事先穷举所有实质差别, 不等于已有边界不可执行. 若具体问题确有难以归类的新选择, 现有拿不准就问已提供处理路径.
- 置信度: 不存在必须二选一的规则冲突 = 高; 实际能否稳定少问 = 未知.

### 攻击3: 不逐条重过用例, 可能连闭环覆盖清单也被缩成方法列表

- 来源: 决策39的不逐条重过用例, 决策33的成文逐项覆盖, 决策35的闭环清单; 对应 PRODUCT.md:47-48及 TECHNICAL.md:31/35.
- 最强反驳: 只展示几个方法组, 不能证明每个必验项都有方法. 若闭环只报 "文字核对/CLI实跑", 用户看不到被整个遗漏的要求. 独立检查若只对照这些组, 也可能重复遗漏.
- 实际后果: 若覆盖范围缩成已问方法列表, 某些必验项会在没有被决定跳过的情况下消失. 后续结束确认缺少完整范围依据, 不能据此声称方案闭环完成.
- 对正方剩余约束的检验: 决策35明确清单对照全部权威必验项与例子, 不以已问问题清单代替完整范围. 决策33/39禁止因归组减少成文覆盖, 独立核对须从权威输入和决定出发. 展示完整覆盖范围不等于逐项重新提问或要求用户逐行读步骤, 两条要求可同时执行.
- 性质: 已有明文禁止的误用风险, 不是新增规则缺口. 要求再次裁决清单是否完整, 会无据重开上轮已收敛的 F1.
- 置信度: 规则已覆盖 = 高; 将来清单是否真正完整 = 未知, 留待具体方案检查.

## 反方立论

反方可独立成立的主张是: 方法是否相同, 应看它能否以已经讲清的做法和证据验证相应要求, 不能只看方法名称. 覆盖行数完整也不自动证明方法有效. 这来自验证需要建立要求与可复查证据的对应关系, 不依赖正方错误才成立.

据此, 如果同组中的某项必须改走入口, 改变观察依据或采用不同强度的证据, 就应按现有规则检查是否存在方法或适用条件的实质差别. 涉及新选择则补问该决定, 不能把它藏成动作细节; 若已有权威依据可直接推出, 仍按免问规则处理, 不机械地每处差异都问.

这一立论能否替代正方? 不能. 决策32/33/36/39及成文规格已经容纳这些限制. 它约束的是把调粗误读成无条件合并, 没有证明用户已确认的调粗原则缺少新取舍. 本轮不提出固定方法分类表, 问题数门槛, 免问记录或逐项重新确认等新要求.

## 幸存与比较

正方最强的幸存点是提问粒度与成文覆盖明确分开. 用户减少重复作决定, 代理仍须逐项完成方案, 独立会话仍须从外部依据检查. 这不是只靠写后检查兜底: 提问阶段已有新选择另问和拿不准就问, 方法阶段还有验证契约及可行性约束.

反方所指误用一旦发生, 影响可涉及整组证据效力, 不能因每行都有文字就忽略. 但本轮没有找到一种同时遵守现有规则仍必然漏掉必要用户决定的具体路径. 三项攻击的发生概率均未知, 没有实跑数据支持把风险说成已发生或高概率. 发现后可按决策33/34补问受影响决定或按已有依据修文并独立复查, 无须整盘重开.

决策39也未破坏其余衔接: 决策31继续确定改造范围, 决策34继续按决定变化处理修订, 决策36继续区分方法未知与资源未齐, 决策37继续规定账本与交接, 决策38继续支持通用输入并保留用户验收权. 本次两份 spec 是事实, 不是新增的固定输入门槛.

另有两条不能作为攻击成立的捷径: 本次规格结束确认未确认未来验证方案, 来源见 DECISIONS.md:315及 TECHNICAL.md:31; 本报告发生于规格成文之后, 只如实保留该时序限制, 不伪称写前攻击, 也不以形式重写冒充实质修复.

权重结论: 反方未占优. 未找到强反方, 无新增必须裁决项. 三项疑点应由后续具体方案的盘问和独立检查按已有规则检验, 不构成本轮继续细问用户的理由.
