它是怎么操作容器的

先说本质: sandcastle 操作本地容器的方式, 是最朴素的一种 — 拼 CLI 命令起子进程。podman.ts 与 docker.ts 里没有任何容器 daemon API 或 SDK 调用, 全部是 child_process 的 execFile / spawn, argv 一个参数一个参数地拼。反差在于云端 provider (Vercel / Daytona) 恰好相反, 走官方 SDK。

podman.ts (bind-mount 最完整) docker.ts 云端 SDK

所有动作汇合于一个类型契约 — SandboxProvider.ts (纯类型文件, ~450 行, 零实现)。Provider 是三种形态的 tagged union:

// src/SandboxProvider.ts — 三种形态
BindMountSandboxProvider  // tag: "bind-mount" — worktree 直接挂进容器
IsolatedSandboxProvider   // tag: "isolated"   — 无共享 FS, 靠文件搬运 (bundle 进, patch 出)
NoSandboxProvider         // tag: "none"       — 裸奔宿主机 ("opt in at your own risk")

// handle 契约 (bind-mount 形态)
exec(command, { onLine?, cwd?, sudo?, stdin? })  // 强制支持逐行流式
interactiveExec?(args, options)                   // 可选, TTY
copyFileIn(hostPath, sandboxPath)
copyFileOut(sandboxPath, hostPath)
close()
细节两枚 exec 契约强制逐行流式 (onLine) — 这是空闲超时检测与实时反馈的地基; prompt 走 stdin 而非 argv, 规避 Linux 单参数 128KB 上限。
微妙差异 podman.ts 显式传 --entrypoint sleep infinity; docker.ts 的 startContainer 不传 entrypoint, 依赖镜像自带的 ENTRYPOINT ["sleep","infinity"] — 同一意图, 两个 provider 各写一遍, 一处显式一处隐式。

出处: src/sandboxes/podman.ts (create / checkImageExists / 注册清理), src/DockerLifecycle.ts:99, src/SandboxProvider.ts, src/shutdownRegistry.ts:72

它定义自己的镜像吗

答案有点出乎意料: 既不用现成镜像, 也不发布镜像。仓库里找不到独立的 Dockerfile — 镜像定义以字符串常量内嵌在 InitService.ts 里 (按 agent 各一份: CLAUDE_CODE / PI / CODEX / CURSOR / OPENCODE / COPILOT), sandcastle init 时写入用户仓库的 .sandcastle/ 目录, 用户本地执行 build-image 构建。

为什么生成而非发布 UID/GID 必须与宿主用户一致 (build-image 命令自动传 id -u / id -g 作 build-args), 镜像天然因机器而异; 加上 agent 选择是用户决策, 干脆把 Dockerfile 当作 init 的生成物 而非制品。
未知点 云端 provider (vercel/daytona) 无自建镜像, 源码走 git bundle 注入; 但 isolated 形态下 agent CLI 如何在云端沙箱就位, 已读代码中找不到路径 (grep "npm install" 无命中) — 推测依赖平台 runtime 或用户 hooks, 未经确认。

出处: src/InitService.ts (DOCKERFILE 常量区段, :502, :589), src/mountUtils.ts:39 (defaultImageName), src/cli.ts:545,618 (build-image), src/sandboxes/podman.ts:462 (inspect 预检)

代码库模块设计

整体是一块四层蛋糕 — 依赖严格自上而下。贯穿的两条设计事实: 边界外是纯 Promise, 内部是 Effect-ts (桥在 SandboxFactory.makeSandboxFromHandle); 契约前置 — 扩展点全部先写成纯类型文件, 新 provider 只需 200–500 行实现。每层 ▸ 可展开。

L1 编排 / 入口层 run · interactive · createSandbox · createWorktree · cli

run.ts 是主 API: 多轮 agent 循环 (maxIterations, completion signal 提前结束), 校验组合合法性 (head + isolated 不兼容等), env 三方合并, 组装 Effect Layer。interactive.ts 是宿主 TUI 会话。createSandbox.ts 返回长驻 Sandbox 对象 (含 Symbol.asyncDispose, 支持 resume)。templates/ 是 init 脚手架: simple-loop, sequential-reviewer, parallel-planner(-with-review), blank — 每套 template.json + main.mts + prompt 文件。

L2 沙箱生命周期层 SandboxFactory · SandboxLifecycle · syncIn/syncOut · WorktreeManager

SandboxFactory.ts:290 的 WorktreeDockerSandboxFactory 用 Effect.acquireUseRelease 把 worktree 修剪/创建 → copyToWorktree → host hooks → startSandbox → 业务 → close → worktree 清理包成一次事务。isolated 分支的代码搬运: syncIn.ts:80 = git bundle create --all → copyIn → 沙箱内 git clone → 校验 HEAD; syncOut.ts:219 = 以自有 ref refs/sandcastle/sync-base 为 base 做 format-patch → 宿主 git am。SandboxLifecycle.ts 负责 hooks 与 merge-to-head, 用 git rev-list baseHead..HEAD --reverse 收集 agent 提交。

L3 agent 适配层 AgentProvider · 六个实现 · SessionStore

AgentProvider.ts:264 定义 agent 契约: name / env / captureSessions / sessionStorage / buildPrintCommand / parseStreamLine 等。六个内置实现 (claudeCode, codex, copilot, cursor, opencode, pi), 各自负责 print 命令拼接与 stream-json 行解析。SessionStore.ts 把 claude/codex/pi 的会话 JSONL 在宿主与沙箱间搬运, 支持 resume / fork (ADR-0018)。

L4 基础设施层 EnvResolver · errors · shutdownRegistry · terminalCleanup · …

碎而稳的一层: EnvResolver + mergeProviderEnv (.env 与 provider env 三方合并); errors.ts / ErrorHandler / RecoveryMessage (失败步骤的可恢复提示); shutdownRegistry (共享退出钩子, 解决并发沙箱 MaxListenersExceededWarning); terminalCleanup (异常退出时恢复光标 \x1b[?25h); boundedTail (流式输出尾部限长 64KiB); Output.ts (结构化输出 <tag> 提取); PromptResolver / PromptPreprocessor / PromptArgumentSubstitution (prompt 文件, !command 上下文注入, {{arg}} 替换)。

文档滞后两处 README provider 表未列 Daytona (package.json exports 已有 ./sandboxes/daytona); "two kinds" 漏了第三种 none。读代码比读 README 可靠。

出处: src/index.ts, package.json (exports / bin), src/SandboxFactory.ts:99,290, src/AgentProvider.ts:264, docs/adr/

对照我们的 use-sandbox 方案

研究它的真实目的, 是给容器试验场方案找参照系。共性先摆出来: 长驻容器 (它 sleep infinity, 我们 sshd), fat 镜像 + 秒级启动, UID 对齐 (它 --userns=keep-id, 我们 rootless 天然同 uid), host 仓库进容器。分岔在于: 它是程序化编排的无人车间 (库代码 exec 注入, 用完即毁), 我们是ssh 可入的长住工坊 (我本人在里面干活, 有展示需求)。

维度sandcastleuse-sandbox (我们)
进入方式podman exec 程序注入, 无交互登录ssh 登录, 容器即工作区
端口映射本地 provider 零端口 (全仓无 -p), 仅 vercel 有核心需求: 2222 / 8800 / 6080
镜像策略init 按 agent 生成 Dockerfile, 本地构建一份全量 fat 镜像, 手工维护
代码回流format-patch → git am (补丁信使)容器内 commit, 经 remote 回流
git bundlesyncIn: bundle --all → 容器内 clone, 免网络已列为备选 (强隔离需求时)
image inspect 预检运行前检查镜像存在, 失败提示 build可纳入 use-sandbox 流程
会话搬运SessionStore 跨界搬运 JSONL, resume/fork暂无对应物 (我们的会话在 host)
agent 面六家 agent, provider 可插拔就我一个, 无需抽象层
清理兜底handle.close + shutdownRegistry 双保险试验场长驻, 语义不同 (可不管)
一句话结论 它证明 "拼 CLI 命令 + sleep infinity 长驻容器" 这条最朴素的路线足够支撑严肃的沙箱编排 — 这正是我们方案的地基; 而它没有的东西 (端口, 登录, 展示链) 恰好是我们方案真正的增量, 不是重复造轮子。
