# M03 脚本封装反方审查

## 正方还原

### 定义

正方主张: host llm 操作容器的动作约八成是可预先写死的机械序列, 因而应立即把生命周期操作封装成 5 个场景脚本: 诞生, 恢复, 查询, 终结, 换母体, 并把这作为 M03 的明确要求. 这里的"脚本"应理解为 host 侧编排入口, 不是把容器内 agent 的工作过程自动化.

### 前提假设

1. 五个场景的主要命令序列已经足够确定, 只有镜像依赖件推导, 白名单盘点, 脏检查放行, 镜像换版重建 4 类判断点.
2. 已实测的 git 拓扑, Podman 端口行为, nft 注入点可以直接组合成稳定的生命周期实现; 剩余问题只是集成咬合.
3. 脚本边界与 `use-sandbox-worktree` skill 文档边界已经清楚, 五个脚本不会重新定义生命周期语义.
4. 把 D008 config 模板和 D011 fail-closed 顺序写入脚本, 能显著降低 host llm 即兴漏项或乱序的风险.
5. M03 应同时承载"首次完整跑通"和"五场景 API 固化", 而不是只承载一个最小可验证切片.

其中有三项不能由当前判断确定, 记为未知: 五个脚本各自的输入/输出/幂等性契约, "查询"要证明的状态集合, 以及 M03 所谓"编排脚本雏形"是否明确要求 5 个独立用户入口. 不能用正方的机械步骤清单替代这些接口定义.

### 论据

1. 正方给出诞生 9 步, 恢复 4 步, 存续查询, 终结 3 步, 换母体 4 步, 认为这些都是确定性命令.
2. M03 确实列出一个编排脚本雏形, 其主链为建 worktree 作母体, 起容器, ssh 入, 容器内 clone/干活, ff-push 回流, 拆容器 [roadmap/MILESTONE-03.md:7-15].
3. 路线 A 确实选择垂直切片先行, 并以单项机制已实测, 只剩集成咬合作为理由 [roadmap/ROADMAP.md:19-23].
4. D008 的 config 模板确实承载了 ref 隐藏, ff-only, 禁删和 `updateInstead` 等硬约束 [DECISIONS.md:61-76].

### 推理链

既然底层机制已逐项验证, 且生命周期命令大部分可重复, 先把命令序列脚本化就能把硬约束变成可执行代码. 五个场景覆盖完整生命周期, 既减少人工操作, 又为英文原生报错译解和用户交互提供统一入口. 因此脚本化不应等待完整流程实跑, 反而应成为 M03 首次实跑的载体和产物.

## 主战场

**严重: 尚未有一次完整流程事实, 却要把五个场景及其边界冻结为 host 侧操作契约.**

这不是"是否值得省几条命令"的问题, 而是"哪些状态转换已经被证明可由代码承担"的问题. M03 的完成判据是用 `podman exec`/`ssh` 实际跑通一次建 -> 干 -> 回流 -> 拆, 并把结果记入产物 [roadmap/MILESTONE-03.md:13-15]. 当前路线 A 的"只剩集成咬合"仍是路线选择理由, 不是集成已通过的事实 [roadmap/ROADMAP.md:19-23].

如果集成失败, 五个脚本会把错误的状态假设,恢复顺序,清理范围和提示语变成后续调用者依赖的接口. 由于其中至少两个操作会改变主仓全局状态, 这不是可忽略的文档迭代成本: D008 明确说 config 常驻主仓, 并提醒它可能拒绝用户手动向主仓 push [DECISIONS.md:74]; D010 又要求换母体停止旧母体全部容器/守护进程, 校验后才改全局例外分支 [DECISIONS.md:85-90].

拆掉这个前提, 正方仍可保留"先写一条最瘦 E2E 编排器来实跑", 但不能推出"立即承诺五个稳定场景脚本".

## 反方反驳

### 1. "八成机械"没有可审计的分母, 且隐藏判断远多于 4 个

"八成"按命令数量计算没有意义: 一个错误的全局 config 写入或一个错误的清理决定, 风险和实现成本可能超过若干正常命令. 按理想路径的 shell 命令数计算, 也会遗漏失败路径和状态发现.

至少有以下隐含分支已经在决策账本中明写, 不属于正方列出的 4 类:

- **母体身份与复用**: 需要判断当前目录是否 worktree, 是否已有同目录容器, 是新建母体还是复用母体, 是否触犯同一主仓至多一个活动母体的不变量. D010 还允许旧母体跨时复用, 允许同母体多容器, 但禁止同仓不同母体同时活跃 [DECISIONS.md:85-90]. 这会直接改变诞生和换母体路径.
- **恢复的状态机**: D011 要求先确认用户是否重启, 注入 nft, 拉起并校验 daemon, 最后才 start 容器; 规则未就绪时容器工作负载不得运行 [DECISIONS.md:92-97]. 这不是四个命令的线性序列, 还包括已有实例探测, stale daemon 处理, readiness 校验, 中途失败后的可重入状态.
- **终结的数据保护**: D012 要求通过 ssh 检查未 commit 改动和未 push commit, 脏时阻塞, 只有用户明示才强拆, 且母体保留 [DECISIONS.md:99-103]. 容器已停或 ssh 不可达时如何判断, "未 push"相对哪个 ref 判断, 强拆确认如何避免误删, 均未被 3 步清单定义.
- **共享母体的并发冲突**: D009 允许多容器共推同一母体, non-ff 后要容器内 fetch, 解冲突, 重推 [DECISIONS.md:78-83]. 因此存续查询和终结不能只看一个容器的本地状态.
- **全局 config 的版本和恢复**: D008 明确 `!` 否定例外依赖 Git 版本, 部署时须重验, 且 `receive.*` 是主仓全局接收策略 [DECISIONS.md:74]. 脚本要处理已有配置, 失败回滚, 主仓作为发送方的既有行为, 以及结束后策略是否保留, 这些都不是模板复制.
- **镜像版本提示**: D013 要求诞生时比对 digest, 有新版时提示是否终结重建, 不自动拆存活容器 [DECISIONS.md:105-110]. 这又是一个用户决策和状态分支.

因此"4 个判断点"至少是低估, "约八成机械"至多是未经定义的直觉比例, 不能作为冻结五个接口的依据. 该反驳的置信度为高.

### 2. 单项实测不能证明组合后的时序和失败语义

D008 的模板曾对拓扑做过单项实测, 但它同时暴露了组合风险: `receive.hideRefs` 才是有效键, `uploadpack.hideRefs` 只影响读广告而不防 push, HEAD 广告仍可能暴露 main 对象 [DECISIONS.md:69-74,144-147]. 脚本若只检查命令 exit code, 可能把"clone 成功但 clone 到了 HEAD 对象"误当作正确母体分支, 或把读面检查误当成写面检查.

同样, D011 的 nft 规则在 stop/start 后会丢失, 所以顺序必须是规则注入/daemon 拉起/校验/start 容器. 这个顺序的设计已拍板, 但当前材料只给出规则和容器行为事实, 没有完整编排器在部分失败,重复调用,stale 进程时的验证结果. 脚本化可以帮助验证, 却不能先验地把验证结果当作已成立的脚本契约.

M03 还明确允许全通网络的中间态, 但要求真远端永不暴露, 且 receive config 收敛后才能拉起 daemon [roadmap/MILESTONE-03.md:9-13]. 如果"五场景脚本"把最终白名单,所有镜像能力,恢复和换母体都作为 M03 必须完成的行为, 它就超出当前瘦闭环的最小验收面; 如果不把这些做完, 则更不能声称五场景已经完整封装.

### 3. 脚本职责与 skill 文档职责尚未划界

Roadmap 把 agent 放在容器内, ssh 入容器的是用户, `use-sandbox-worktree` 会话只管理生命周期 [roadmap/ROADMAP.md:11-15]. 这至少要求区分:

- host 脚本: 状态探测, 资源创建/停止, config 和 daemon 顺序, 可验证的清理.
- skill 文档: 用户确认点, 共享母体和冲突语义, 原生报错译解, 不支持的并发边界.
- 容器内流程: clone 分支, commit, fetch/解冲突/ff-push.

正方没有给出这三层的输入/输出和错误责任. 尤其"原生英文报错译解表可挂脚本输出"不是脚本化理由: D008 已把原生报错透明化降级为 skill 文档附译解表, 并要求明示主仓手动 push 可能被拒 [DECISIONS.md:74-76]. 将译解复制到五个脚本会产生重复和漂移, 还可能掩盖需要保留原始错误的诊断信息. 该项为中高置信度风险.

### 4. 防错价值真实, 但不推出五脚本立即落地

正方最强的点是成立的: D011 的 fail-closed 次序和 D008 的模板不应长期依赖 llm 现场记忆. 纯 checklist 对"先启动容器还是先装规则"这种硬顺序的保护弱于可执行检查.

但在首次 E2E 之前, 更轻且更适合发现未知的约束方式是:

1. 用一个固定测试仓和单一母体写一个带阶段日志的 `e2e-smoke` 编排器, 只覆盖 M03 明列的建 -> 干 -> 回流 -> 拆.
2. 每个阶段都做反向断言, 例如 clone 必须检出母体分支, push 后母体文件必须变化, 真远端不得出现在容器 remote, 拆后母体仍在.
3. 用 checklist 记录尚未固化的用户决策和失败处理: 母体复用, 镜像 digest 提示, 黑/白模式, 脏检查放行, 端口冲突, daemon/netns 残留.
4. 实跑并记录事实后, 从已通过的阶段抽取共享 host 原语, 再决定哪些场景值得成为公开脚本入口.

这保留了脚本的防错价值, 同时不把未知的恢复/查询/换母体语义伪装成确定性 API. checklist 不是最终替代品, 而是第一次集成期间的决策登记和缺口清单.

### 5. 五个入口会放大未决问题的实现成本

ROADMAP 仍把多 sandbox-worktree 并发, rootless netns 清理失败兜底, 镜像 GC 和镜像复用边界列为未决迷雾 [roadmap/ROADMAP.md:44-50]. M03 还把镜像制备与依赖推导留在 M06, 并明确镜像内容不钉死 [roadmap/ROADMAP.md:25-30,39-42].

如果现在分别实现诞生/恢复/查询/终结/换母体, 每个入口都要复制或依赖一套尚未稳定的身份发现, 进程归属, 清理, 镜像和并发规则. 后续真实 E2E 暴露接缝时, 修复会变成五个入口的行为兼容问题. 这是典型的不可逆性不对称: 推迟入口抽取只增加一次手工或临时编排成本, 错误入口一旦被 M03 文档或调用者依赖, 修改会带来状态残留和兼容负担.

## 反方立论

反方主张: M03 应要求"一个可观测,可清理,可反复运行的瘦 E2E 编排器雏形 + 结果事实", 不应要求"五个场景脚本"作为先验冻结的交付边界.

建议的 M03 边界如下:

1. **先固定一个授权域和一条成功路径**: 单主仓, 单活动母体, 最简镜像, 一个容器, 采用 D008 config, 明确沿 D011 的顺序. 多容器冲突, 镜像换版, 同仓不同母体并发暂不成为首次脚本的公开承诺.
2. **把脚本当实验编排器而非稳定 API**: 它可以拥有 birth/smoke/cleanup 等内部阶段, 但输入,输出,幂等性和失败后状态必须记录. 不要在尚未实跑前承诺 query/switch 的完整语义.
3. **硬约束由可执行断言承担**: config 写入后验证关键键和值, daemon 仅在 config 就绪后启动, clone 验证分支, push 验证母体文件变化, terminate 验证母体留存. 对 nft 暂不上最终白名单时, 明确记录为中间态, 不能把"命令执行成功"当作安全验收.
4. **先用 checklist 管理用户决定和未知状态**: 记录复用/新建, 脏检查放行, 镜像 digest, 黑/白模式, 端口发现/冲突, 失败清理. 这些决定成熟后再进入脚本的显式交互.
5. **实跑后再抽取五场景**: 只有当一条链路和至少必要的负向断言通过, 才把已验证的生命周期阶段提取为 birth/recover/query/terminate/switch 等入口. 每个入口都应有状态前置条件, 成功后状态, 失败清理责任和禁止操作.

这不是反对脚本化, 而是反对在验证前把"脚本雏形"扩张成五个尚无契约的场景产品. 反方替代方案独立依赖 M03 的既定完成判据和可观测验证, 不依赖正方命令比例成立.

## 幸存与比较

### 正方仍成立的部分

- M03 确实需要编排脚本雏形, 因为完成判据要求用 `podman exec`/`ssh` 实际走完整链路, 而 ROADMAP 也把"镜像 + 母体 config 拓扑 + 编排脚本雏形"列为 M03 产物 [roadmap/MILESTONE-03.md:7-15, roadmap/ROADMAP.md:39-42].
- 把 D008 模板和 D011 的 fail-closed 顺序编码, 比依赖 host llm 临场记忆更可靠. 这是需要保留的工程方向.
- 查询,端口发现,错误保留原文等确实适合工具化, 但前提是先定义输出和失败语义.
- 垂直切片先行的方向本身合理, 只是"垂直切片"应以一条真实闭环为切片, 不应等同于五个生命周期入口一次性冻结.

### 权重比较

正方的收益是减少重复命令和遗漏固定顺序, 主要是可逆的工程效率收益. 反方指出的风险涉及主仓全局 config 持久化, 活动母体切换, 容器内未 push 工作的丢失, 以及恢复期间网络边界; 这些是高影响状态错误. D008 的 config 常驻主仓和 D012 的强拆数据损失说明, 一次错误自动化不只是多打印一条错误, 可能影响正常 push 或丢失未回流工作 [DECISIONS.md:74,99-103].

风险发生概率不能精确量化, 因为完整链路尚未运行过; 但正是这个证据缺口使"立即冻结五脚本"无法获得高置信度. 推迟五入口抽取的代价是 M03 初次实跑需要一个较窄的临时编排器和 checklist, 可在一次验证后回收. 相比之下, 错误脚本边界会把未决状态传播到五个入口. 按影响范围和不可逆性衡量, 反方占优.

## 置信度

- "M03 需要某种可执行编排器": 高. M03 文字直接列出编排脚本雏形和端到端完成判据 [roadmap/MILESTONE-03.md:7-15].
- "五个场景脚本必须立即成为 M03 明确要求": 高置信度反驳. 现有 M03 只要求编排脚本雏形和一次完整演练, 没有五个入口的契约或验收定义 [roadmap/MILESTONE-03.md:7-15].
- "八成机械, 只有 4 个判断点": 低置信度支持, 高置信度认为证据不足/明显低估. D008-D013 已列出多个额外状态和用户决定 [DECISIONS.md:74-110].
- "提前脚本能固化硬约束": 中高. 对固定顺序和模板有价值, 但只有加入状态探测, 负向断言, 幂等/失败清理后才真正防错; 仅复制命令序列可能把错误假设固化.
- "应先做单一 E2E 编排器, 再抽取五场景": 高. 这直接符合"首次实际跑通"的 M03 目的, 且把不可逆的全局状态操作留在已验证边界内.

总结: 反方找到了足以显著约束原观点的承重缺陷. 编排代码应立即开始, 但交付边界应是单授权域的可观测瘦闭环, 不是未经完整实跑就冻结五个场景脚本. "八成机械"和"四个判断点"没有足够证据, 且忽略了母体复用, 全局 config, 失败恢复, 脏数据保护和并发语义. 首次闭环及负向断言通过后, 再把稳定阶段提取为五个场景入口更可逆, 风险更低.
