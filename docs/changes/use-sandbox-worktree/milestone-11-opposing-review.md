正方还原

### 定义

正方决定把 host 侧 sandbox-worktree 生命周期收进一个 `swt.py` module, 对外提供五个子命令:

- `birth`: 建立或复用母体, 配置主仓, 注入网络规则, 拉起 daemon, 创建并校验容器.
- `resume`: 按 fail-closed 顺序恢复已有容器.
- `status`: 只读盘点母体, 全部容器, daemon, config, 镜像和网络状态.
- `terminate`: 按容器做脏检查后删除容器及其专属资源, 母体保留.
- `switch`: 停下旧母体的全部容器并改换主仓全局授权分支.

五个入口共享探测, D008 config 模板, runtime 状态文件和 `DECIDE`/`STATE` 输出协议. 危险动作保持显式: `switch` 独立, 强拆使用 `terminate --force`. `--repo` 是主定位, 不再使用 M03 的跨命令注册表.

### 前提假设

1. D008 的 config 模板,D010 的单活动母体,D011 的 fail-closed 恢复顺序,D012 的脏检查都应由实现代码固定, 以减少 host llm 漏步骤或乱序.
2. M03 已实跑的阶段函数可以作为生产实现的直接前身, M03 的测试可以改为 CLI 黑盒测试而不再保留原脚本.
3. host llm 是稳定的调用方: 它能读 exit code 和 `DECIDE` 行, 把用户答案转成 flag, 再重跑同一命令. 一次调用可以列出全部当前待决问题, 重入时重新探测.
4. D009 允许同一母体存在多个容器, 因此 status, terminate, resume 和网络资源必须区分母体级资源与容器级资源.
5. birth/resume/switch 的部分失败可以由 runtime 状态和同一命令重跑收敛, 即使 v1 不公开 config/daemon 修复原语.

第 3 至第 5 项的具体机制仍是未知: 设计没有定义跨 `DECIDE` 两次进程调用的锁生命周期, 是否有不可复用的决策 token, 多容器实例的唯一命名规则, nft 表的归属/引用计数, 以及 switch 后旧容器是否允许 resume. 这里不替正方补全这些缺口.

### 论据

- M03 的完成判据确实要求建、干、回流、拆的真实链路, 现有 `e2e-smoke.py` 已有阶段日志, D008 config 校验, clone 分支校验, push 回流, 拒绝矩阵, 脏树阻塞和清理记录.
- D010 明确禁止同仓不同母体同时活跃, 但允许同一母体多容器.
- D011 要求恢复时先注入 nft, 再拉起并校验 daemon, 最后 start 容器.
- D012 要求终结前检查未提交和未 push 工作, 不可达或已停视同脏, 用户明确同意后才强拆.
- `net-firewall.py` 已有 `apply/show/clear` interface, `image-prep.py` 已有匹配和构建流程, 所以正方认为 swt 可组合既有模块而不新增 provider 抽象.

### 推理链

生命周期的固定机械部分已经有单项实测和 M03 的完整链路证据. 将这些步骤收进一个共享 module, 用统一状态探测和退出协议暴露, 可以把硬约束从 llm 的记忆搬进代码. 通过把危险操作单独命名, 把用户决定留在 `DECIDE`/flag, 再用 runtime 文件支撑重入, 正方认为五个场景既能覆盖 MILESTONE-11 的状态分支, 又能把调用方压缩为敲命令, 转述决定, 重跑命令.

主张最强的部分是: 不应再让 host llm 手写 D008 和 D011 的关键顺序, 也不应为五个入口复制五套探测和协议.

主战场

**主战场是跨调用的决策协议和资源身份绑定.** `birth`,`terminate`,`switch` 都会改动主仓全局 config, 容器, daemon 或网络规则. 它们把一次调用的观察结果变成用户决定, 再把 flag 带到另一次调用执行. 如果这个决定没有绑定同一个 repo, 母体, 容器实例, image digest 和网络资源, 那么 `exit 1` 只是一段给 llm 看的文字, 不是可靠的确认协议. 这会同时击穿 D010 的单活动母体,D012 的用户明示强拆和 D011 的确认后恢复.

共享母体和 e2e 覆盖是两个独立的硬伤. 即使把 `DECIDE` 协议修好, 现有网络资源 interface 仍不能直接支持正方声明的多容器语义, 而“下沉后退役”也不能自动继承 M03 的负向覆盖.

反方反驳

### 1. `DECIDE` 的“重新探测”与“决定不过期”互相冲突

设计要求 exit 1 后用户回答, 调用方带 flag 重跑, 重跑时重新探测, 但又说决定不过期. 这三件事不能同时成立:

- 如果 flag 代表第一次探测的答案, 重跑必须验证资源仍是同一对象. 否则用户确认的是容器 A 脏, 代码可能强拆同名重建的容器 B.
- 如果 flag 代表“对当前状态都适用”, 那它不是用户对第一次问题的确认, 而是一次无范围的授权. 在 `--repo` 缺省唯一容器时, 第一次看到 A, 等用户回答期间 A 被删且 B 被创建, 同一命令可能把 force 施加给 B.
- 如果状态改变就重新 DECIDE, 那决定会过期, 与设计文字相反. 这不是措辞问题, 而是需要一个可检查的状态绑定规则.

设计没有 decision id, 资源 UUID, observed fingerprint, config digest 或原子 apply 前的 compare-and-swap. runtime 文件也只是记录状态, 没有被定义为不可复用的确认票据. 因此“重探测”不是安全性, 只是把旧答案重新套到新观测上.

最危险的是 `switch --force` 和 `terminate --force`: 它们的后果涉及停止或删除容器. 用户确认应绑定容器 ID, 母体分支 tip, dirty counts 和目标 config, 而不是只绑定一组命令行 flag.

### 2. “一次列全”与设计自己的调用示例矛盾

正方明确要求一次 invocation 列出全部待决问题, 不挤牙膏. 但设计示例实际是:

1. 第一次 `birth` 只得到网络模式的 `DECIDE`.
2. 用户重跑带 `--mode`.
3. 第二次才得到母体新建/复用和 `BUILD-NEW` 的 `DECIDE`.

母体探测和 image match 都可以在第一次调用中完成, 没有材料说明它们必须等待网络模式. 这个示例证明协议目前不是“一次列全”, 而是分阶段执行到下一个问题才停. 分阶段本身可以接受, 但就必须承认后续决策依赖新状态, 引入 plan/token 或明确“前面没有任何副作用”. 当前设计两者都没有:

- 若第一次 exit 1 前已创建母体, 写入 config 或分配资源, 后续问题失败时就不满足 exit 1 的纯决定语义.
- 若第一次完全不改状态, 就应该一次完成所有可知的预检并输出稳定的 decision manifest, 而不是依赖调用方多次试错.
- “一次列全”也无法覆盖中途才出现的问题, 例如 daemon 已拉起后容器 start 失败, 或恢复时发现旧 daemon PID 与 runtime 不一致. 这类新问题必须有 PARTIAL 语义和明确的后续操作, 不能继续假装是第一次的 pending decision.

### 3. 同主仓文件锁无法保护两次调用之间的空窗

决策写的是第二个调用者拿同一主仓锁就 exit 2 不排队. 但第一个调用在 exit 1 时已经结束进程, 普通文件锁随之释放. 用户思考和回答期间, 第二个调用者可以修改 config, 删除容器, 推进母体 ref 或切换母体. 第一个调用随后带 flag 重跑时没有锁可以证明状态仍是原来的状态.

若要让锁跨过用户思考, 就不能只靠进程持有的文件锁, 而要落一个有 owner, lease, 资源指纹和失效处理的持久计划. 设计没有这套协议. 因此“第二者不排队”与“同一命令重入收敛”不能共同提供事务边界, 只提供了单次进程内的互斥.

此外, status 是否要取得同一锁也没有定义. 不锁会看到 birth/switch 的半状态, 加锁则只读查询可能频繁 exit 2. 这会影响调用方用 status 诊断 PARTIAL 的可靠性.

### 4. exit 2 的“状态未变”与端口失败事实冲突

设计把端口被占列为 exit 2, 并说状态未变. 但 F006 的实测是 start 时端口被占会失败, 容器留下 exited 状态. birth/resume 在执行到 `podman start` 后已经改变了容器状态, 还可能已经创建了母体, 写过 config, 注入过规则或拉起过 daemon. 它不能同时属于“前置不满足, 状态未变”.

端口预检也不能解决 TOCTOU: 检查通过和实际 start 之间仍可被别的进程占用. 正确分类至少应是: 尚未创建资源的明确预检失败才可 exit 2, 已创建或改变状态后的端口失败必须 exit 3, 并带出精确的回收/恢复动作. 否则调用方按协议“不要重试”会留下需要重跑才能收敛的半套资源.

### 5. resume 无 gate 违背 D011 的 fail-closed 语义

D011 不是单纯的提示习惯. 它规定已有容器时先问用户是否重启, 用户确认后才按 nft、daemon 校验、容器 start 的顺序恢复. 正方把这句“经确认”移到 skill 文档, 让 CLI 的 `resume` 永不 DECIDE.

这使关键安全条件重新依赖 llm 是否遵守文档, 正好退回本次脚本化要消除的漏项风险. `resume` 会重新打开容器工作负载和网络, 还会杀掉 stale daemon, 绝非无副作用的查询. 用户可能只让 llm 查看状态, 或 llm 在处理 PARTIAL 时直接尝试 resume, CLI 却没有代码级确认门.

“resume 无破坏性”也不成立: 它会改变容器运行状态, 重建网络规则, 杀掉进程并使 agent 重新运行. 即便不丢数据, 这仍是 D011 所要求由用户确认的动作. 最低限度应有一次由 CLI 产生并绑定目标容器的确认票据, 而不是把 D011 的一半留给文档.

### 6. 多容器共享母体与现有 nft interface 直接不兼容

这是一条不依赖 llm 可靠性的确定性反例.

`workflow/use-sandbox-worktree/scripts/net-firewall.py` 的表名固定为 `inet swt`, 表位于共享 rootless netns. `apply` 明确检查表中是否有其它容器源地址, 发现后返回 `APPLY-CONFLICT`, 不合并规则. `clear` 没有容器 IP 参数, 直接删除整个 `inet swt` 表.

而 D009/D010 又允许多个容器共享同一母体. 按当前 design:

- 容器 A 和 B 同时活动时, `terminate --name A` 的“清 nft 表”会删除 B 的网络保护, 使 B 变成无规则状态.
- B 恢复时, `resume --name B` 按单容器调用 `apply`, 会因为表中存在其它容器规则而冲突; 若实现先 clear 再 apply, 又会在窗口内清掉 A 的规则.
- `status` 的 `table-present=true` 只能表示表存在, 不能证明每个剩余容器都有自己的规则.

所以“按容器终结”并不等于“按容器拥有资源”. daemon 可以按容器归属, 但 nft 表是共享资源. 设计没有资源引用计数, 全量重渲染所有剩余容器的规则, 或只删一个源地址的实现. 这足以推翻“D009 多容器已被五入口覆盖”的说法.

### 7. 多容器身份模型本身没有落地

D009 允许多个容器共享一条母体分支, 但 D007 的“一名贯穿”又把母体分支, worktree 目录和容器名绑定. design 的 `birth` 没有容器实例 ID 或唯一 name 参数, 默认例子是 `swt-<slug>`. 同一母体第二次 birth 会得到同一个 Podman name, 无法创建第二个容器.

如果 M12 私自追加序号, 就会破坏当前“容器名主体等于母体名”的身份假设, 也会影响 `--name` 定位, runtime 文件名, label 和 status 输出. 如果不追加, D009 的多容器语义根本不可用. 正确模型应把 `mother-id` 和 `container-id` 分成两个标识, 当前决定没有给出这一接口.

### 8. switch 后旧容器的恢复路径会穿过新的全局授权

switch 的步骤是停旧母体的全部容器和 daemon, 改主仓全局 `hideRefs` 例外到新分支, 但设计只明确“不删旧母体”, 没有明确删除或永久封存旧容器. 若旧容器保留为 stopped, 它的 runtime 仍存在.

之后调用 `resume --repo ... --name <旧容器>` 时, design 只检查 runtime 存在, 没有检查 runtime 中的母体分支是否仍是当前全局授权分支. 它可能用旧容器的 clone 和旧 daemon 地址启动, 但 daemon 读取的主仓 config 已经只允许新母体分支. 结果可能是:

- 旧容器恢复失败并进入 PARTIAL.
- 旧容器连到新授权域, 看到或尝试操作错误分支.
- 为恢复旧容器而切回 config, 影响当前新母体的所有容器.

这不是一个普通报错, 而是共享主仓 config 下旧资源的归属丢失. switch 必须在前置阶段决定旧容器是删除, 标记 retired 且禁止 resume, 还是先切回旧授权域; 当前方案没有这个状态.

### 9. 脏检查没有解决共享母体和并发写入

按容器检查 `git status` 加上 HEAD 对比主仓 `refs/heads/<母体分支>` 是必要的, 但不充分:

- B 的本地 HEAD 可能落后于 A 刚推到母体的 ref. 这不是 B 的“未 push”, 需要区分 ahead, behind 和 diverged, 不能用一个 HEAD/ref 不相等计数.
- A 可能在 SSH 检查之后继续写文件或提交, terminate 随后才 rm 容器. 这是 TOCTOU: 检查时干净不代表删除时干净.
- 多容器同推一条 ref 时, `git fetch`/冲突处理和终结检查必须有明确定点. 主仓 ref 的当前值不能自动告诉 host 某个 commit 是谁推的, 也不能代替容器内工作树审计.

设计只给出“参照 ref 是主仓 ref”这一选取, 没有给出 ahead/behind/diverged 算法和检查到删除之间的冻结协议. 因此 D012 的“宁可阻塞也不误删”仍未被代码语义保证.

### 10. 下沉 e2e 阶段不等于继承 e2e 覆盖

M03 的证据是一个特定瘦闭环: 单主仓, 单母体, 单容器, 全通网络中间态, 容器内 clone/push, host 侧负向断言和 cleanup. 它证明了该链路, 没有证明五个公开入口之间的状态机组合, 也没有证明 D009 的多容器资源归属.

把阶段函数直接下沉到 swt 后, 再用“swt 调用成功”作为测试依据有循环证明风险: 测试可能只验证 production code 按自己的预期返回 `STATE`, 而没有独立观察 config, ref, Podman 状态, netns 规则和容器内 git 事实. 原有 M03 测试还包含拒绝矩阵, 脏树拒绝, hooks 未改, daemon 不带 `--export-all`, 中途清理和重复 birth 等具体断言. design 的新测试列表没有逐项给出这些用例到五个子命令的映射, 也没有给出多容器 resume/terminate/switch 和 crash window 的新断言.

因此“原脚本退役, 测试替换不叠加”目前是覆盖证据的削弱, 不是简单重构. 在 CLI 黑盒测试达到逐项等价之前退役 M03 基准, 会让之后的实现同时失去独立回归基线和多入口覆盖矩阵.

反方立论

反方主张: 可以保留一个共享 `swt` module 和显式危险入口, 但不能按当前契约冻结五个场景为“已经覆盖且可重入”的安全 API. v1 应先把跨调用事务, 资源所有权和黑盒证据补齐.

### 1. 把用户决定变成有边界的计划

每次需要用户决定时先完成无副作用预检, 生成不可复用的 plan, 至少绑定:

- repo 绝对路径和主仓 identity.
- 母体分支, worktree 路径和当前 ref.
- 容器 ID/Podman ID, 不只用可复用 name.
- image digest, config fingerprint, network mode 和规则输入.
- 脏检查计数, 目标分支和所有将受影响的容器.

exit 1 输出 decision id 和这份观察摘要. 重跑时在拿锁后做 compare-and-swap. 任何绑定字段改变都不能静默沿用 flag, 应返回新的 DECIDE 或无副作用的 FAIL. 这不是把用户确认变成脆弱的时间过期, 而是防止答案跨对象漂移.

“一次列全”应定义为: 在第一次改变任何资源前, 列出当前所有可知问题. 若后续才发现新的状态问题, 必须是无副作用的 PARTIAL/FAIL, 并说明已完成阶段, 不能把新问题伪装成原决定的延续.

### 2. 让 D011 真正落在代码里

`resume` 至少需要显式的 confirmation token 或一次 CLI `DECIDE`. token 要绑定容器 ID, 当前母体授权分支和待执行的 fail-closed plan. skill 可以负责向用户提问, 但 CLI 必须验证确认没有被拿去启动另一个对象.

同时重新划分退出码:

- 资源尚未创建且预检失败: exit 2.
- 已创建/已停止/已写 config 后失败: exit 3.
- 环境能力不足: exit 4.

每个阶段创建资源后立即原子登记, 身份不一致或登记损坏时 fail-closed, 不能仅靠 PID 字符串和过期 runtime 文件猜测归属.

### 3. 分离母体身份和容器实例身份

母体应由 repo identity + branch/worktree identity 表示, 容器应有独立 instance ID/name. birth 必须能表达“在同一母体再起一个容器”, status/terminate/resume 按 instance ID 处理. 所有 label 和 runtime 记录同时保存两种 identity.

共享资源的归属应显式定义:

- 主仓 config 和母体 worktree是母体级资源, 只有 switch 或最后一个实例的生命周期可以改变它们.
- daemon, SSH key, Podman 容器是实例级资源.
- nft `inet swt` 是当前 netns 的共享资源, 不能用现有 `clear` 当实例级删除. 需要实现按源地址删除, 或每次变更时在锁内根据所有剩余实例全量重渲染, 最后一个实例才删表.
- resume 必须在共享表场景下保存其它实例的规则, 不能把 `apply` 的 `APPLY-CONFLICT` 当作正常恢复路径.

switch 前先验证目标母体存在且干净, 再审计所有旧实例, 之后要么显式终结/封存旧实例, 要么为旧实例写入 retired 状态并让 resume 拒绝. 不能让 stopped old container 在新全局 config 下成为可恢复对象.

### 4. 先保留独立的 M03 黑盒基线

新 CLI 测试应逐项覆盖 M03 已有证据, 至少包括:

- D008 多值 config 的既有值, 错值和幂等重跑.
- daemon 只在 config 验证后启动, clone 分支和 read face.
- 容器内 push 回流, new branch/tag/non-ff/delete 拒绝, 母体脏树拒收.
- SSH 不可达和已停容器视同脏, 强拆登记, 中途资源回收和重复 birth.
- M03 负向断言的真实外部状态, 而非只断言 swt 自己的 `STATE`.
- 两个容器共享母体时分别 resume/terminate, 同时保留其它容器的 nft 规则和 daemon.
- switch 中途失败, 旧实例封存, 新实例恢复和全局 config 回滚.

在这张矩阵全部通过前, `e2e-smoke.py` 可以改为兼容适配层, 但不应直接删除独立回归证据. 等价测试稳定后再退役, 才能证明是替换而不是覆盖缩水.

### 5. 对 v1 范围诚实分类

如果上述多容器和恢复事务暂时做不到, 应明确把 v1 限定为单母体单容器实验编排器, 禁止对外宣称 D009 的多容器终结和完整 resume. 同理, 如果不提供 repair 原语, exit 3 必须明确列出每种半状态的唯一人工恢复步骤, 不能同时承诺“重跑同一命令必然幂等收敛”.

这样仍保留正方最有价值的方向: 共享探测和 config 实现, 显式 switch/force, status 只读, 以及用代码固定 fail-closed 顺序. 反方反对的是未经状态归属和独立证据验证就把它们包装成完整五场景协议.

幸存与比较

### 正方仍成立的部分

- 一个 module 比五份复制探测, config 和输出协议更容易保持一致.
- `status` 独立且只读是合理的. 查询不应被藏进 birth 或 terminate.
- `switch` 独立命名, `terminate --force` 显式, 不自动构建镜像, `--repo` 明确定位, 都降低了误触和隐式副作用.
- D008 模板,D011 顺序,D012 脏检查确实适合进入可执行实现. 只靠 skill 文档会让 llm 漏掉关键步骤.
- M03 的真实运行记录是很好的实现起点. 反方不否认单容器瘦闭环已经有相当证据.
- 共享 runtime 状态比 M03 的全局注册表更接近实际资源生命周期, 但它必须有身份和原子更新语义, 不能只当作“重跑提示”.

### 权重比较

正方的主要收益是减少重复命令和减少固定顺序遗漏, 这是可逆的效率收益. 反方指出的两个问题不是风格偏好:

1. `resume` 把 D011 的确认放回 llm, 会让本应代码强制的安全条件失去强制性. `DECIDE` 无身份绑定时, 强拆或切换的用户答案可能落到不同资源上. 这些错误的影响是停止错误容器, 删除未 push 工作, 改写主仓全局授权或重新开放错误的网络面.
2. 多容器场景下, 现有 `net-firewall.py clear` 删除共享整表, `apply` 又拒绝存在其它容器规则. 只要按 D009 真正运行两个容器, 终结一个或恢复一个就可能影响另一个. 这是实现接口和目标状态模型的确定性冲突, 不是低概率的 llm 误操作.
3. M03 单容器 happy path 的证据不能证明五个入口的边界. 退役原脚本而不保留覆盖等价证明, 会降低发现上述问题的概率.

即使接受正方最强的幸存点, 当前决定仍不能原样进入 M12. 替代方案的成本是增加 plan/token, 两层身份, nft 重渲染/按地址删除, switch 的 retired 状态和一张黑盒覆盖矩阵. 这些成本是可审计且可回退的; 目前方案把成本转移给 llm, 用户确认和发生故障后的人工救场, 而故障后可能不可逆.

结论: 反方找到足以显著约束并部分推翻原决定的论证. 可以保留“一个 module + 显式场景”的骨架, 但必须先修正跨调用确认协议, D011 resume gate, 多容器资源所有权和 M03 覆盖迁移. 在这些条件未满足前, “五入口已覆盖 MILESTONE-11 且可重入收敛”不成立.

置信度

- `DECIDE` 的一次列全与设计示例自相矛盾: 高.
- 没有 decision token/资源 fingerprint 就无法保证重跑答案仍指向原对象: 高. M12 尚未实现, 具体补救机制未知.
- `resume` 无 CLI gate 不符合 D011 的“经确认”约束: 高.
- 现有 `net-firewall.py clear` 删除共享 `inet swt`, 与多容器按容器终结冲突: 高. 结论基于仓库现有实现和正方声明继续组合该 interface.
- 多容器身份没有唯一实例名: 高. D009 允许多容器, design 默认 name 与母体 slug 绑定, 两者无法同时成立.
- switch 后旧 stopped container 的 resume 归属错误: 中高. 设计未声明旧容器删除/封存规则, 实际行为取决于 M12 未给出的 runtime 校验.
- 脏检查的 ahead/behind/diverged 和检查到删除之间的竞态: 中高. 风险由 D009 的共享推送和 design 的检查后直接 rm 推出, 具体实现未知.
- M03 测试覆盖不会因阶段函数下沉自动继承: 高. M03 证据范围明确是单容器瘦闭环, 五入口和多容器测试映射未提供.
- 反方替代方案所需实现量和是否能在 v1 完成: 未知.

结果不是“未找到强反方”. 当前方案的主骨架有价值, 但其安全承重部分仍依赖未定义的跨调用事务和共享资源所有权, 不能按现状冻结为 M12 的完整实现契约.
