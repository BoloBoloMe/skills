①目的地

use-sandbox-worktree skill 落地并经端到端演练验证可用 — 它管理 sandbox-worktree (host git worktree + 容器的绑定对) 的完整生命周期.

  • 诞生: 用 use-worktree 在 host 建工作树分支目录 + 拉起容器 (镜像由 host llm 按项目推导制备, 内含 pi CLI + skill 库 + 部分扩展)
  • 存续: 用户 ssh 入容器, 驱动容器内的 pi 干活; 产物经 gate 门禁 (sandbox/work ff-push + updateInstead) 回流 host; 展示链与登录墙容器内可用
  • 终结: 删容器 + 删 host worktree
完成判据: 端到端演练跑通整个周期 (建 → 干 → 回流 → 拆). 交付物是一个可工作的 skill, 不是又一份设计文档.

②地图: 依赖树与迷雾

箭头即阻塞关系, 右为下游. 红实心结点须用户在场 (HITL), 蓝灰空心结点由代理独立驱动 (AFK). M03 瘦闭环是全局咽喉; 关键路径沿 M01/M02 → M03 → M07 → M09 → M10 走, 登录墙支线最长.

③Milestone 详表

MILESTONE-01 · gate 设计 deliberate · HITL

读通道 (真远端是否对容器暴露, 读全走 gate 镜像?) / gate 服务形态 (git daemon vs ssh) / gate 工作树干净保障 (who/when).

阻塞于: 无

MILESTONE-02 · sandbox-worktree 生命周期语义 deliberate · HITL

一个 sandbox-worktree 从生到灭的状态机, 两个资源面一起拍:

  • worktree 面: 分支生灭 / reset 策略 / 与 use-worktree 的交互
  • 容器面: 容器生灭与分支的同步关系 / stop 还是只许 rm / 镜像换版时存活容器处置 / 孤儿容器清理
  • 终结面: 拆的顺序 / 脏状态检查 (未 push 的工作怎么办)
  • 端口分配结果算不算 sandbox-worktree 的身份信息 (容器 restart 后宿主端口会变)

阻塞于: 无

MILESTONE-03 · 瘦闭环端到端 task · AFK

最简镜像 (git+pi+ssh) + gate 工作树仓 + 编排脚本, 跑通 建 → 干 → ff-push 回流 → 拆. 全通网络中间态须守 T7b 拓扑铁律: real 仓永不入任何可写端点路径.

阻塞于: MILESTONE-01, MILESTONE-02

MILESTONE-04 · 网络访问控制 (双模式) task · AFK

黑名单 (默认放行+拒清单) 与白名单 (默认拒+放行清单) 两种模式并存; host llm 创建容器前询问用户选定; 白名单模式含创建时盘点确认环节; 运行期不切换. 静态 IP 子网 + nft 注入 + 启动后重注入.

阻塞于: MILESTONE-03

MILESTONE-05 · podman 镜像元数据能力调研 research · AFK

labels / inspect / 命名与 tag 策略 / 按 label 查询过滤 — "镜像属于哪个项目, 内容物有什么, 版本号" 记录到哪的事实基础.

阻塞于: 无

MILESTONE-06 · 镜像制备策略 + 约定降级 deliberate · HITL

镜像内容不钉死, 由 host llm 按项目推导: 依赖件分析流程 (运行环境/构建工具/harness/浏览器/系统工具) / 版本号语义 / 记录位置 (借 M05 结论, 优先 podman 原生) / "最合适" 匹配规则 / 失配重建触发. 约定降级 (~/docs, ~/Workspace) 归入本簇: 约定文档也是 harness 内容物, 由 host llm 制备时推导, 不落项目 git.

阻塞于: MILESTONE-05

MILESTONE-07 · 镜像制备实现 task · AFK

host llm 分析 → 查已有镜像 → 选最适版本或 build 新版 → 记录元数据. 端口动态分配 (-p 6080 省宿主侧) + podman port 事后发现, 容器内端口固定, 宿主端口不钉.

阻塞于: MILESTONE-03, MILESTONE-06

MILESTONE-08 · 展示链接线 task · AFK

容器内 present web_server bind 0.0.0.0, 经端口映射交付 URL. 考察点: 此路径不经 host 常驻展示服务, add-dir/stop 缺失是否真有影响 (预期无 — stop 随容器灭, add-dir 可绕过).

阻塞于: MILESTONE-03

MILESTONE-09 · 登录墙闭环 task · AFK

Xvfb :99 + x11vnc + websockify/noVNC 接入编排, DISPLAY=:99 BROWSER_HEADED=true 切换约定, 浏览器 profile volume 持久化; 底层通道已实测 (2026-09-01 vnc-demo).

阻塞于: MILESTONE-07

MILESTONE-10 · SKILL.md 定稿 + 全链演练 task · HITL

按实证现实写 SKILL.md (非设计虚构); 用户 ssh 实操验收: 建 → ssh 干活 → 过门禁回流 → 展示 → 登录墙 → 拆.

阻塞于: MILESTONE-04, MILESTONE-07, MILESTONE-08, MILESTONE-09

④未决迷雾

在范围内, 但问题形状还不够清晰, 尚不能写成 Milestone. 前沿推进到那里时再回访:

  • ☁ 运行期新站点需求的处理流程形态 (回父会话确认 → 更新容器的具体动作)
  • ☁ 多 sandbox-worktree 并发 (动态端口分配后可能缩水为资源限额问题)
  • ☁ rootless netns 清理偶发失败的编排兜底是否够用 (M04 后回访)
  • ☁ 镜像版本积累后的 GC 策略
  • ☁ 镜像复用的项目边界 (严格按项目隔离, 还是允许跨项目匹配)
  • ☁ 容器崩溃 / host 重启后的恢复语义 (可能与孤儿清理同解, M02 后回访)

⑤范围外

  • subagent 工具容器化 / sandcastle 集成落地 — 已否定方向 (调研 §6)
  • pi 整进程容器化 (gondolin / whole-process-docker / OpenShell) — 隔离对象不同, 形态不同
  • present web_server ISSUE-02/04 实现本体 — present-web-server 会话跟踪中, 本路线只消费其结果
  • 云端 provider (vercel / daytona) — 本地 rootless podman 已够

⑥笔记: 路线与拍板

路线 A「垂直切片先行」(已选定): 最瘦闭环先跑通, 再逐层加固. 理由: 单项机制已被调研全部实测, 仅存不确定性是集成咬合, 垂直切片最早兑现它; 切片骨架与完成判据同形; SKILL.md 最后写 = 记录实证现实.
  • 路线 B「契约先行」排除理由: 先写 SKILL.md 有写出不可执行文档的真实风险, 集中在集成缝; 其 "规格逼决策" 的收益已由前置 deliberate Milestone 获得, 不需要拿文档当赌注.
  • 路线 C「自底向上组件先行」排除理由: 组件各自验收但集成期才暴露接缝 (容器内 pi 真跑通 / 展示链 / ufw), 谨慎买不到新信息.
本次会话拍板与修正:
  • 改名 use-sandbox → use-sandbox-worktree; 新概念 sandbox-worktree 入领域语言 (worktree + 容器绑定对)
  • agent 的位置修正: agent 就在容器内, ssh 入容器的是用户; use-sandbox-worktree 会话只管理生命周期
  • 调研 §4.1 "白名单单模式" 修正为 黑/白双模式, 创建时询问用户选定
  • 镜像内容不钉死: host llm 按项目推导依赖件, 镜像=带元数据的缓存制品, 优先 podman 原生记录; 镜像/容器是环境信息, 不落项目 git
  • 端口动态分配: 宿主端口不钉死, podman port 事后发现; 容器内端口固定
  • 白名单盘点确认是 sandbox-worktree 诞生步骤的固定环节, 非可选
