# 1. 复杂度结论

- **总体判断**：可用但需关注
- **置信度**：中
- **审查范围**：本次审查覆盖当前工作区中 HILP 相关未提交 diff：`human-in-loop-planning/SKILL.md`、`references/blueprint.md`、`references/handoff-contracts.md`、`references/routing-matrix.md`、`references/execution-handoff.md`、`references/reapproval.md`、`references/event-action-rules.md`。
- **结论说明**：这次变更把大范围修改的蓝图组织从单体文档扩展为“主蓝图 / manifest + 子蓝图 + 覆盖矩阵”的分层蓝图包，方向是支持持续变更的：它没有牺牲确定性，而是把审查视角和局部细节拆开，能降低大蓝图的阅读与审批成本。但新的包语义、版本绑定、审批传播和执行交接规则被分散写入多个 reference 文件，后续只要调整蓝图包语义，就需要同步修改多处规则；如果缺少一个集中契约或示例，长期有规则漂移风险。

# 2. 最高风险点

- **主风险**：分层蓝图包的核心契约没有单一权威定义，导致未来规则演进容易在多文件之间漂移。

当前表现是：`blueprint.md` 定义蓝图规模、manifest、子蓝图、覆盖矩阵和审批纪律；`handoff-contracts.md` 又定义 manifest 引用、输入输出契约和禁止交接；`event-action-rules.md` 定义批准事件和未确定项事件；`execution-handoff.md` 定义执行范围；`reapproval.md` 定义局部重审传播；`routing-matrix.md` 定义何时启用 package。这个拆分符合阶段职责，但“什么是一个合法的分层蓝图包”这一核心接口被多处描述，缺少一个最小 schema 或规范锚点。

它会抬高未来修改成本：后续如果要调整包成员状态、允许局部批准、增加波次资产、或改变 coverage matrix 字段，维护者必须记得同步所有 reference 文件。任何一处遗漏，都可能让 agent 在蓝图、审批、交接或重审阶段产生不一致行为，例如 manifest 认为包可交接，但执行交接发现 `execution_scope` 或包成员状态不满足条件。

次级风险：当前规则要求分层蓝图包批准时同步 manifest 和全部成员状态，但没有明确“成员在提交审批前应处于什么状态、是否允许成员单独 ready-for-approval、包级批准如何落盘成多个 approved 文件”的完整流程样例。这个风险尚未导致结构失控，但会影响 agent 执行一致性。

# 3. 建议的重构动作

1. **抽出“分层蓝图包最小契约”小节或独立 reference** —— 在 `blueprint.md` 或新增专门 reference 中集中定义 `blueprint_form`、`package_members`、成员状态、版本绑定、覆盖矩阵字段、审批传播和交接入口。
   - 收益：把“合法蓝图包”的接口收敛为单一权威来源，其他文件只引用它，降低规则漂移。
   - 代价：需要小幅整理现有重复描述，避免 reference 之间互相覆盖。

2. **把蓝图包字段补入全局资产元数据扩展规则** —— 在 `handoff-contracts.md` 的资产元数据附近增加“蓝图包扩展元数据”，明确 `blueprint_form`、`package_members`、`approval_scope`、`determinism_check` 等字段何时必须出现。
   - 收益：agent 生成资产时不必从多个段落拼字段，接口更稳定。
   - 代价：会让元数据章节略长，但这是集中复杂度的合理代价。

3. **补一个完整 package 生命周期样例** —— 覆盖 ready-for-approval、Human Approval Granted、approved manifest、按 Wave 交接、子蓝图失效重审五个节点。
   - 收益：最低成本地暴露规则冲突，提升人类和 agent 的执行一致性。
   - 代价：需要维护样例随规则变化更新。

4. **收窄重复描述为引用式表述** —— 例如 `execution-handoff.md` 只声明“按 handoff-contracts 的蓝图包入口检查执行”，不要再次完整复述全部成员状态规则。
   - 收益：后续改动更局部，减少多处文字略有差异造成的歧义。
   - 代价：阅读单个文件时需要跳转 reference，但这是协议型文档可接受的依赖。

# 4. 验证建议

1. **最低成本验证**：用 3 个手工压力场景走读当前规则：小范围单体蓝图、大范围分层蓝图包、子蓝图失效后局部重审。每个场景只检查资产状态、版本绑定、确定性检查和下一跳是否唯一。
2. **契约检查**：为分层蓝图包列一份字段 checklist，验证主蓝图 / manifest、子蓝图、覆盖矩阵、执行交接是否都能填满且没有待定项。
3. **窄集成验证**：让 agent 根据一个模拟 Stage 3 approved 设计生成 package 蓝图，再要求批准、执行交接、局部重审，观察是否会遗漏 `package_members`、`approval_scope` 或 `execution_scope`。
4. **优先补的检查**：优先补“分层蓝图包 lifecycle 样例”和“manifest 字段完整性检查”，比继续扩展规则文字更能降低不确定性。

- **缺失证据**：目前缺少真实的大范围 HILP 任务样例、分层蓝图包实际产物、以及 agent 端执行回放记录。拿到这些材料后，可以把置信度从“中”提升到“高”。
