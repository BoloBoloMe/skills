# Spec 编写标准操作流程 (SOP)

## 1. 目的与适用范围

本 SOP 旨在为团队提供一套清晰、可复用的规范编写指南，确保从产品需求到技术实现的全链路信息无损传递。它同时面向人类开发者与 AI Coding Agent，通过分层关注点分离，让每个角色都能高效获取所需信息，降低认知负荷和维护成本。

**适用范围**：所有中大型特性、重构或技术改进。对于微小变更（如修 Bug），可裁剪使用。

## 2. 核心原则

- **分层关注点分离**：严格区分“为什么做（Why）”、“怎么做设计（How）”、“如何落地执行（Execution）”，不同角色只需聚焦对应层。
- **引用而非复制**：层与层之间通过引用锚点（章节号或文档链接）关联，避免信息冗余。
- **显式化隐含上下文**：将开发必须了解的目录结构、约束、文件变更范围等隐性知识显式写进规范，尤其提升 AI 执行效率。
- **可验证、可执行**：所有需求都要能转化为验收标准或自动化测试用例。

## 3. Spec 三层结构定义

一套完整的 Spec 由以下三层文档构成，物理上推荐独立文件，逻辑上强关联。

| 层次 | 文档名 | 回答的核心问题 | 主要受众 |
||--|-|-|
| **产品规范** | `product.md` | 为什么做？要达成什么业务目标？ | PM、产品负责人、业务方、设计 |
| **技术规范** | `technical.md` | 怎么做技术设计？契约与约束是什么？ | 前后端开发、架构师、QA、SRE |
| **执行规范** | `execution.md` | 如何一步步落地？给 AI 的工作单 | 执行开发的工程师、AI Coding Agent |

### 3.1 产品规范 (Product Spec)

**目标**：描述业务问题、用户价值、核心规则与成功标准，完全避免实现细节。

**必含内容（检查清单）**：
- [ ] 背景：当前痛点、需求来源、为何现在做
- [ ] 目标：可衡量的业务/产品目标
- [ ] 非目标：明确本次不做什么，防止范围蔓延
- [ ] 用户故事：标准格式（As a... I want...），可辅以流程图
- [ ] 核心业务规则：如“密码错误5次锁定账户”
- [ ] 验收标准：可验证的结果列表（用于判断是否交付完成）
- [ ] 成功指标：上线后如何衡量效果（可选，但强烈推荐）

**注意**：不应出现技术选型（如 JWT、Redis）、API 细节、数据库表名。

### 3.2 技术规范 (Technical Spec)

**目标**：定义完整的技术契约，所有开发者据此独立完成开发与自测。

**必含内容（检查清单）**：
- [ ] 架构与组件图：服务模块、交互方式
- [ ] API 契约：端点、请求/响应、状态码、错误码（优先使用 OpenAPI/Protobuf 等机器可读格式）
- [ ] 数据模型：逻辑模型、物理表结构、状态机（如有）
- [ ] 关键流程与时序：复杂逻辑的流程图或伪代码
- [ ] 安全策略：认证授权方式、加密要求、数据脱敏
- [ ] 非功能需求：
  - 性能（P95 延迟、QPS）
  - 可观测性（日志、指标、追踪）
  - 可用性（降级、容错、SLA）
- [ ] 边界情况与异常处理：依赖超时、并发冲突、非法输入等
- [ ] 假设、依赖与风险：外部系统依赖、关键假设、已知技术风险
- [ ] 开放问题：待确认的技术决策点

**重要原则**：它是唯一的技术真相来源，API 和数据模型部分必须精确到可直接生成桩代码。

### 3.3 执行规范 (Execution Spec)

**目标**：为实际的编码执行提供确定性的工作指令，消除猜测。**AI 时代的核心创新层**。

**必含内容（检查清单）**：
- [ ] 仓库上下文：项目顶级目录结构，标注哪些目录/模块可修改
- [ ] 实施计划：按依赖拆解的有序步骤（Step 1 → Step 2 → …）
- [ ] 文件变更清单：每个步骤预计新增/修改的文件名
- [ ] 约束条件：明确的技术禁令（如“不能引入新依赖”、“禁止修改公共库”）
- [ ] 完成定义 (DoD)：代码提交前的自检项（lint、测试覆盖率、基准测试等）
- [ ] 测试策略指引：引用 Technical Spec 的验收场景，指定需编写的测试类型

**任务化增强**（推荐）：将步骤进一步转为带依赖关系的任务列表，如：
```
Task-001: 新增 JWT Service (依赖: 无) → 产出 jwt.go
Task-002: 修改登录 API (依赖: Task-001) → 修改 login.go
...
```
此方式让 AI 能够按拓扑顺序执行，失败时可精准恢复。

## 4. 编写与评审流程

采用自顶向下、分层编写的瀑布式评审，避免过早陷入实现细节。

1.  **启动**：PM/需求方发起，明确需求性质，决定是否需出全三层 Spec（微小变更可简化为单文件内含三层）。
2.  **编写 Product Spec**：由 PM 或产品负责人起草。
3.  **评审 Product Spec**：架构师、Tech Lead、开发代表参与，确保业务目标清晰、无实现歧义。评审通过后锁定作为后续依据。
4.  **编写 Technical Spec**：Tech Lead 或主力开发基于已锁定的 Product Spec 进行设计，需涵盖 3.2 检查清单所有项。
5.  **评审 Technical Spec**：相关开发、QA、SRE 共同评审技术契约与约束。此阶段可调整 API 设计，但不得违背 Product Spec 的业务规则。评审通过后，API 契约定为基线。
6.  **编写 Execution Spec**：负责执行的开发者（或 AI Agent 使用者）编写，将 Technical Spec 翻译为具体执行步骤。若主要面向 AI 执行，此步必须高度细致。
7.  **评审 Execution Spec**（可选，视团队实践）：快速同步执行步骤，确保无遗漏。若 AI 执行中频繁卡住，则需改进本层。
8.  **进入实现阶段**：开发者或 AI 严格按照 Execution Spec 执行，并以 Product Spec 验收标准作为交付确认。

## 5. 文档组织规范

推荐在代码仓库中按功能模块存放 Spec，实现代码与规范的共置，方便维护和发现。

```
项目根目录/
└── docs/
    └── specs/
        └── <feature-name>/
            ├── product.md          # 产品规范
            ├── technical.md        # 技术规范
            ├── execution.md        # 执行规范 (可含 tasks.md)
            ├── openapi.yaml        # API 契约 (机器可读)
            ├── schema.sql          # 数据库变更 (可选)
            └── decisions/          # 技术决策记录 (ADR)
                ├── adr-001-why-jwt.md
                └── adr-002-token-storage.md
```

各层之间需要引用时，使用相对路径或章节锚点链接，例如：`详见 technical.md#api-design`。

## 6. 与 AI Coding Agent 的协作

- **AI 的入口点是 Execution Spec**。不要直接把 Product 或 Technical Spec 丢给 AI，那样会消耗大量 token 用于搜索和理解上下文。
- Execution Spec 中必须明示**可修改范围**和**禁令**，大幅减少 AI 的自由发挥。
- 利用任务化（Task List + 依赖）让 AI 逐步执行，每一步的产出可验证，出错时可重新从当前任务继续，而不会全盘重来。
- 若 AI 在执行中反复误解某项约束，说明 Execution Spec 不够明确，应迭代补充。

## 7. 规模裁剪指南

| 项目/特性规模 | 实践方式 |
||-|
| **个人小项目 / 修复简单 Bug** | 单文件 `spec.md`，用 `## Why`、`## How`、`## Execute` 标题分隔，内部按需节选检查清单项。 |
| **中等特性 / 2-3 人协作** | 推荐完整三层独立文件，但 Execution Spec 可以精简为实施步骤列表和约束。 |
| **大型特性 / 跨团队** | 严格执行本 SOP 的所有分层、评审、任务化要求，特别是 Technical Spec 必须包含完整 API 契约和 ADR。 |

## 8. 维护与更新

- **Spec 随代码变更**：当实现与 Spec 产生偏差时，必须回写对应的 Spec 层，保持 Spec 始终是系统的实时文档。
- **版本管理**：每一层文档均使用 Git 跟踪，修改记录在提交信息中体现。重大变更需走评审流程。
- **引用层不变原则**：当 Technical Spec 的 API 变动时，只需修改该层，Execution Spec 因引用了具体章节会自动关联新内容，避免同步改三处。



以上即为一套融合了最佳实践的 Spec 编写 SOP。团队可根据自身情况裁剪和落地，但核心的分层思想和为 AI 设计的执行层，将是未来规范驱动开发保持高效的关键所在。
