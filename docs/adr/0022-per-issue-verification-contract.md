# 按 issue 类型选验证契约, 不要求每个 issue 走 TDD

每个实施 issue 在 `to-execution` 拆分时, 按交付结果选择行为变更, 结构变更, 缺陷修复, 性能改进, 非行为改动中的一种或多种类型. 各类型注明对应范围, 验证要求全部满足; 同一检查可覆盖多种类型, 共用结果和材料. 不同的证明要求不必排主次, 也不为分类拆 issue; 配置或依赖改动若改变外部行为, 也按结果归类. 只负责人工核验或整合验证的任务没有实施改动, 单独写明验证入口和证据. 验证入口事先写做法和通过标准, 交付证据事后记录实际结果. 这样评审能分清打算检查什么和实际检查了什么. 契约不指定工具, 也不按"是否写测试"区分.

TDD 不再是每个 issue 的必经步骤, 采用自动化测试也不等于采用 TDD; 仅在决定用测试驱动开发时进入红绿循环. 结构变更是先观察既有行为再改, 检查在动手前就应通过; 类型检查与 lint 无法单独证明行为未变. 硬套红绿会诱发绑定实现的测试: 行为没变, 重构却弄坏测试.

编排节点按 issue 声明派活, 执行者不现场换契约; `code-review` 的 Spec 轴核对交付证据是否覆盖声明的全部变更类型并符合契约, 例如标结构变更却没有任何能观察既有行为的检查, 标行为变更却只有测试通过而没在真东西上验过. 最终独立验收 (`verify-change`) 不受契约影响, 仍按已确认的 PRODUCT.md 复核, 契约只承担执行者自证, 不构成验收结论. 完整规则见 [verification-contract](../../workflow/verification-contract/SKILL.md).
