# 按 issue 类型选验证契约, 不要求每个 issue 走 TDD

每个 issue 在 `to-execution` 拆分时声明五类验证契约之一: 行为变更, 结构变更, 缺陷修复, 性能改进, 非行为改动. 每类绑定各自的完成证据 — 真面命令与输出, 动手前的钉住物与动手后同基线复跑一致, 先红后绿的复现, 基线与改后数字, 构建加 lint 加入口真跑一次. 契约只界定证据类型, 不指定工具, 也不按"是否写测试"区分.

TDD 从"每个 issue 的必经步骤"降为两处: 缺陷修复里接缝便宜的回归测试, 行为变更里需要锁住的复杂逻辑. 结构变更是先钉住后改, 钉住物在动手前就该是绿的, 不造红态; 类型检查与 lint 不算钉住. 理由是硬套红绿的代价不是变慢, 而是逼出绑定实现的测试: 行为没变, 重构却弄坏测试, 正是测试反模式里最贵的一种.

编排节点按 issue 声明派活, 执行者不现场换契约; `code-review` 的 Spec 轴核对交付证据与声明契约是否一致, 例如标结构变更却没有任何行为钉住物, 标行为变更却只有测试通过而没在真东西上验过. 最终独立验收 (`verify-change`) 不受契约影响, 仍按已确认的 PRODUCT.md 复核, 契约只承担执行者自证, 不构成验收结论. 完整规则见 [verification-contract](../../workflow/verification-contract/SKILL.md).
