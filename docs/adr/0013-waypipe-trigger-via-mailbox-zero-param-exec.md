# waypipe 窗口直飞经信箱零参数 exec 指令触发, 排除常驻隧道与容器出向

Status: accepted

swt 容器内 AI 需要把 headed 浏览器窗口投到设备侧桌面时, 触发链路定为: AI 投信到信箱 (swt-base-server), 设备侧取信会话收到 exec 指令后执行 `waypipe ssh` 拉起窗口. exec 白名单首个成员是该拉窗指令, 且被加严为**零参数** (只带容器标识, 窗口导航由容器内 AI 事后经 CDP 自己完成), 执行器幂等 (同容器已有会话则 no-op) 并加限频. 排除的两个看起来更"直接"的方案: 设备侧常驻 ssh -R 隧道 + 容器内按需起 waypipe server (新增常驻运维负担, 隧道断后残留 socket, 而反馈黑洞已由 "投信后轮询容器内会话 socket 文件事实" 堵上, 隧道买不到新价值); 容器拨出直连设备 (要求容器持设备凭证 + 出向白名单放行, 与 "容器不可信" 的沙箱立身前提正面冲突).

零参数 + 幂等 + 限频的由来: 反方攻击指出, 带 URL 参数的直批指令会让容器控制的数据进入设备侧命令拼接路径 (转义失误 = 注入借白名单还魂), 且无限频的直批在容器被提示注入操纵时可窗口轰炸. 能力收窄到 "只能拉起一条预定义命令" 之后, 直批不问人才不与信箱 exec 白名单 (ADR 0011) 的安全立场矛盾.

详细决策与事实见 `docs/changes/swt-cross-host-access/milestone-06/DECISIONS.md` (D001/D007/D008).
