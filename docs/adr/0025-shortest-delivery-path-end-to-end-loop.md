# 执行哲学: 最短交付路径 + 端到端验证闭环

背景: 现行流程仍按旧式"先规定做法再验"阅读. ADR 0022 保留了 tdd 作为可选红绿循环, ADR 0023 把 tdd 缩成缺陷修复专用, 但 verification-contract 的行为变更证据只说"一条真实运行记录"不限入口层级, 结构变更仍写"先建立检查再改"的做法, 共用底线的"边开发边实跑"笼统到无法落地. 结果是可以拿单元级测试冒充端到端证据, 也可以把过程顺序当成通过条件.

决策: 实现走最短交付路径, 不规定过程 — 不强制先写测试, 不规定红绿顺序. 先把能跑的可验证版本做出来, 再从真实入口对它跑端到端, 发现问题修复后对同一端到端重跑, 既确认修复也暴露新问题, 循环到闭环. 拆任务按垂直切片, 每片本身能端到端交付并可演示. 判据重心在交付物经真实运行确实达到要求, 不在过程是否按规定走. mock 不禁用但要谨慎: 过度 mock 会在真实实现之外攒出脆弱测试并掩盖真实行为. 环境不可得时报未验证缺口, 不用弱证据充抵.

修 bug 另有一条统一链条, 不分 bug 大小: 复现 → 定位原因 → 制定修复方案 → 执行修复 → 验证修好且没改坏. `diagnosing-bugs` 改名为 `fix-bugs`, 定位为这条链在难 bug 上的详细手法 (阶段可省, 链不可省), 并补上原缺的"制定修复方案"与"验证没改坏"两环; 调用它的会话按调度方加诊断者/修复者/复核者三角色分工, 复核者不可省. 取证与复验手段优先用代码库自身技术栈与既有入口, 不新增专用脚本; 一次性脚本不提交进仓库. 修复方案的审核尺度: 只有"纯修错, 不动对外行为, 不超边界, 不碰安全"才由代理自行修.

后果: `workflow/tdd/` 删除, 其中好/坏测试细节迁入 `workflow/verification-contract/reference/tests.md` 作按需查阅; mock 边界清单只在 verification-contract 共用底线维护一处, 不再迁入第二份. 闭环机制唯一维护在 verification-contract 共用底线, drive-execution 只写作者自跑材料只作对照、不作任何必验项通过依据, 终局由 verify-change 独立判定. 本文取代 ADR 0022 关于 TDD 的表述, 取代 ADR 0023 中"tdd 重写为缺陷修复专用"的具体动作 (tdd 已不存在) 以及同段末尾"退回新增功能默认写测试的旧口径"半句 (与现行 skill 和本次裁决相反, 按笔误处理); 两篇旧文与历史变更文档原文不改. 完整决策见 [milestone-10 账本](../changes/workflow-stack-review/milestone-10/DECISIONS.md).
