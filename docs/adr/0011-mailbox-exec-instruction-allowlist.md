# 信箱 exec: 服务端最小指令集白名单, 集合外降级 request

Status: accepted

信箱 exec 类消息 (容器请求设备执行动作) 不做任意 shell 直批. 消息体是结构化指令 (调哪个工具+参数), 属于预定义的最小指令集 (首个成员: 直通 GUI 窗口的 waypipe 拉起命令); 服务端按白名单校验, 命中才允许设备直批执行, 集合外一律降级为 request, 由设备侧 LLM 走 pi 既有权限流程 (默认问用户). 白名单存服务端 (host 可信持久), 不住容器.

理由: 反方攻击确认 — HMAC 签名防外人伪造但不约束持钥者, 容器被提示注入操纵时任意命令直批等于设备远程代码执行无人过目, 而"容器不可信"正是沙箱出向白名单的立身前提; 且取信会话全部手动首启 (人在场), 直批的收益仅是省一次确认键. 同一批不可信容器, llm-proxy 限模型/限额/限时可吊销, 信箱却放行任意命令, 授权粒度自相矛盾.

备选方案: 任意命令直批靠设备侧 pi 门禁 hooks 兜底 (用户原判, 被反方攻击推翻 — hooks 对 bash 任意命令覆盖范围未验证, 且注入文本直达执行者); 砍掉 exec 全走 request (反方主张, 用户未选 — 自动化价值保留给白名单内指令).

后果: 扩大指令集前须先实测门禁 hooks 对 bash 的覆盖 (F005, 见 docs/changes/swt-cross-host-access/milestone-01/DECISIONS.md); 指令集成员变动即安全策略变动, 须过 e2e 测试门禁.
