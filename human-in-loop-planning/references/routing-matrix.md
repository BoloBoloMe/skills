# 路由矩阵

本文件给出“人在回路”skill 包的最小路由矩阵，用于统一：
- 规划原型（Planning Archetype）判定
- 治理模式（Governance Mode）判定
- 规格策略（Spec Strategy）映射
- 验证策略（Validation Strategy）映射
- 升级 / 降级触发器

---

## 零、参考文件优先级

当 references 之间出现冲突时，按以下顺序裁决：

1. `event-action-rules.md`：最高优先级。凡涉及阻断事件、失效、必须人工裁决的决策、状态变化和 允许状态转移，优先服从事件动作规则。
2. `handoff-contracts.md`：第二优先级。凡涉及内部模块间是否允许交接、最小输入 / 输出契约、禁止交接，优先服从交接契约。
3. `routing-matrix.md`：第三优先级。用于初始路由、默认映射和治理模式建议；不得覆盖事件阻断或交接禁令。

若 `routing-matrix.md` 建议前推，但 `event-action-rules.md` 命中阻断事件，必须停止前推并进入重审或补证据。

---

## 一、规划原型判定表

### 行为变化型（Behavior Change）
适用于：
- 功能需求（feature）
- 以改变用户可见行为为目标的 缺陷修复（bug fix）
- 一部分 API 行为变化

优先信号：
- 用户想要新的行为结果
- 成功标准以新的外部表现来定义

默认规格策略：
- 行为规格（Behavior Spec）
- 如核心变化发生在接口边界，可叠加 契约规格（Contract Spec）

默认验证策略：
- 验收验证（Acceptance Validation）
- 回归测试（Regression Tests）

---

### 行为保持型（Behavior Preserve）
适用于：
- 重构（refactor）
- 清理（cleanup）
- 外部行为不变的结构优化

优先信号：
- 外部行为必须保持不变
- 目标是结构收敛、模块边界优化、重复逻辑消除

默认规格策略：
- 特征刻画规格（Characterization Spec）

默认验证策略：
- 特征刻画测试（Characterization Tests）
- 回归测试（Regression Tests）

---

### 兼容性过渡型（Compatibility Transition）
适用于：
- 迁移（migration）
- 依赖升级（dependency upgrade）
- schema 演进
- 协议变更
- 带兼容窗口的跨模块改动

优先信号：
- 存在兼容窗口
- 需要双读 / 双写 / 双协议共存
- 存在切换窗口
- 回滚是核心安全条件
- 新旧接口 / 模式 / 依赖必须并存一段时间

默认规格策略：
- 迁移规格（Migration Spec）
- 必要时叠加 契约规格（Contract Spec）

默认验证策略：
- 集成验证（Integration Validation）
- 回滚验证（Rollback Validation）
- 人工验证清单（Manual Validation Checklist）

---

### 不确定性收缩型（Uncertainty Reduction）
适用于：
- investigation
- spike
- 根因未明的缺陷
- 设计空间尚未收敛的问题

优先信号：
- 目前还不能形成绑定性设计承诺
- 关键事实缺失是核心问题
- 需要先缩小不确定性

默认规格策略：
- 调查简报（Investigation Brief）

默认验证策略：
- 初期以证据充分性作为退出标准
- 转入实现导向后再选择相应验证策略

---

## 二、升格规则

### 升格为 Compatibility Transition
若满足以下任一条件，应优先升格：
- 存在显式兼容期
- 需要双读 / 双写 / 双协议共存
- 存在切换窗口
- 回滚是核心安全条件
- 新旧接口 / 模式 / 依赖必须并存一段时间

### 优先进入 Uncertainty Reduction
若满足以下任一条件，应优先进入调查导向路径：
- 根因不明
- 当前行为未建立
- 影响面未知
- 设计空间过宽
- 当前建议无法脱离核心猜测

---

## 三、治理模式判定表

### lean
默认模式。适用于：
- 局部问题
- 低耦合
- 低回滚成本
- 无兼容窗口
- 无跨模块联动
- 无 必须人工裁决阻断

最低保留：
- stage gating
- 范围 / 目标说明
- 精简事实确认
- 精简实施说明
- 最小验证说明

允许：
- Stage 1 + Stage 2 合并，但合并资产必须包含“初始分流摘要”和“事实求证摘要”两个小节，文件名可使用 `00-初始分流阶段_no-approval_router-and-facts@vN.md`，且 asset_ref 摘要必须说明该资产同时承载事实基础。
- 不跳过 Stage 3；无设计分叉时由 Stage 3 输出极简单路径设计选择
- Stage 4/5 蓝图可在满足完整性检查、确定性检查且无 必须人工裁决的决策时进入 `ready-for-approval`（待审批）
- 进入执行交接的蓝图仍必须为 `approved`（已批准）且通过确定性检查；lean 模式下 批准可以是显式轻量批准，例如“确认按此蓝图执行”
- Stage 4 + Stage 5 合并

### standard
适用于：
- 行为保持型重构
- 中等复杂度的行为变化
- 存在关键设计取舍但尚未达到高风险迁移级别
- 需要显式保留关键判断

增加：
- 决策日志（Decision Log）
- 假设日志（Assumption Log）
- 基础关键追溯
- 更明确的变更重审

### strict
适用于：
- 高风险迁移
- 长兼容窗口
- 高回滚成本
- 多模块联动
- 切换顺序敏感
- 需要更强审计和回退能力

增加：
- 兼容 / 回滚检查点
- 扩展关键追溯
- 更显式的影响登记
- 更强的阶段间重审纪律

strict 模式最小控制件清单：
- 兼容窗口：说明新旧行为、协议、schema 或依赖的共存边界。
- 回滚条件与回滚边界：说明何时回滚、回滚到哪里、哪些数据或接口不可逆。
- 影响登记：列出受影响模块、调用方、数据路径和人工操作点。
- 切换顺序或发布顺序：说明上线、切换、清理和停止旧路径的顺序。
- 验证清单：覆盖集成验证、回滚验证和必要人工验证。
- 仍影响后续判断的未决问题：Stage 3 及以前可以保留会改变方案的开放问题；进入 Stage 4/5 前必须全部关闭，不得带入蓝图或执行交接。

升级到 strict 后，以上控制件未补齐时，不得将相关设计或蓝图推进到 `ready-for-approval`（待审批）。从 Stage 4/5 开始，确定性检查未通过时同样不得推进。

### 蓝图规格策略

实施蓝图阶段必须先判定蓝图组织形式：

- `single`（单体蓝图）：适用于局部、低耦合、切片较少、依赖关系可线性表达的修改。
- `package`（分层蓝图包）：适用于大范围修改；以主蓝图 / manifest 组织跨切片拓扑，以子蓝图承载局部确定性，以覆盖矩阵证明设计决策、切片、验证项和风险检查点没有遗漏。

命中以下任一条件时，默认使用 `package`（分层蓝图包）：
- 涉及多个子系统、模块族或调用链层级。
- 改动切片数量较多，平铺后会显著降低审查可读性。
- 文件范围庞大，主文档列出完整文件级细节会掩盖关键拓扑。
- 依赖关系需要按 DAG、波次或阶段表达，而不是单一线性顺序。
- 存在多阶段发布、兼容窗口、迁移路径、回滚边界或人工操作点。
- 治理模式为 `strict`，且蓝图细节足以形成多个独立审查域。
- 审批者需要按领域、波次或风险等级分开审查。

分层蓝图包不属于治理降级，也不得减少 Stage 4/5 的确定性检查项。无法判定时，选择更利于完整审查且不会隐藏细节的组织形式。

---

## 四、治理升级触发器

命中以下任一条件，优先考虑升级：
- 原本局部问题暴露出跨模块联动
- 新发现兼容窗口
- 发现双读 / 双写 / 双协议共存
- 出现切换窗口
- rollback 成为核心安全条件
- 影响面已无法由局部修订安全控制
- 已批准关键前提被推翻，需要多资产联动修订

---

## 五、治理降级条件

满足以下任一条件，可考虑降级：
- 不确定性显著收缩为局部问题
- 兼容窗口被排除
- 风险边界回落到单点或低耦合修订
- 原为谨慎而启用的控制件不再影响判断

降级动作：
- 停止活跃维护多余控制件
- 将其转为 `archived`（已归档）
- 不删除历史依据

---

## 六、路由优先级

默认按以下顺序判断：
1. 是否存在阻断性安全 / 失效 / 必须人工裁决的决策事件
2. 当前主要问题是“要做什么”还是“现在真实是什么”
3. 主规划原型是什么
4. 治理模式是什么
5. 主 / 辅规格策略是什么
6. 主 / 辅验证策略是什么
7. 下一跳应该进入哪个内部模块

---

## 七、用户可见阶段名称

路由内部仍使用模块标识，普通用户可见输出默认使用中文阶段名称：

- `hilp-router` → 初始分流阶段
- `hilp-requirements-facts` → 需求对齐与事实求证阶段
- `hilp-design-approval` → 方案设计与审批阶段
- `hilp-blueprint` → 实施蓝图阶段
- `hilp-reapproval` → 变更重审阶段
- `hilp-execution-handoff` → 执行交接阶段
- `hilp-archive` → 规划资产归档阶段
- `hilp-skill-pressure-test` → 协议压力测试阶段

## 八、下一跳默认映射

- 需求不稳 / 事实不足 → `hilp-requirements-facts`（需求对齐与事实求证阶段）
- 设计需要比较与拍板 → `hilp-design-approval`（方案设计与审批阶段）
- 存在 `approved`（已批准）的 Stage 3 design asset，且无 必须人工裁决的决策、上游失效事件或会影响蓝图的未确定项 → `hilp-blueprint`（实施蓝图阶段）
- 上游资产失效 / 模式升级 / 需要回退 / 蓝图确定性检查未通过 → `hilp-reapproval`（变更重审阶段）
- 存在 `approved`（已批准）且通过确定性检查的蓝图资产或分层蓝图包，上游批准资产仍有效，执行模式和执行范围已确定，需要交接执行 → `hilp-execution-handoff`（执行交接阶段）
- 执行交接成功落盘且入口检查为“无阻断项”，或用户要求基于有效执行交接资产重新生成归档索引且无重审触发 → `hilp-archive`（规划资产归档阶段）
- 需要验证整个 skill 包行为 → `hilp-skill-pressure-test`（协议压力测试阶段）
