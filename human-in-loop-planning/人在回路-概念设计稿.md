# 人在回路 Planning Protocol（规划协议）

## 一、文档目的（Document Purpose）

本文是一份**完全不依赖前文**的完整信息版概念稿。读者无需阅读更早版本，也无需了解此前讨论过程，即可独立理解以下内容：

- 这套协议（protocol）是什么
- 它为什么存在、要解决什么问题
- 它不是什么，边界在哪里
- 它的核心原则、运行方式、分层结构与阶段结构
- 为什么采用“一个统一主协议 + 条件分支”，而不是多个独立工作流（workflow）
- 它如何通过规划原型（planning archetype）、规格策略（spec strategy）、验证策略（validation strategy）与治理模式（governance mode）完成路由
- 它如何通过事件-动作规则（event-action rules）实现程序化裁决
- 它如何控制成本，避免制度膨胀
- 它在轻量、中等、严格三种运行姿态下分别长什么样
- 它在真实任务中最小会触发哪些规则、产生哪些资产（artifacts）
- 它在冲突态（conflict state）下如何处理多事件并发、阶段回退、治理升级与资产失效

本文的目标不是给出最终技能（skill）实现文件，而是给出一份**完整、自洽、可继续规格化（specification）和可落成 skill 的上位协议定义**。

---

## 二、最小术语表（Minimal Glossary）

为控制术语密度，本文约束如下：

- 每个核心概念只保留**一个正式名字**
- 中英文并列仅用于首次定义，后文尽量固定使用同一组词
- 模板层与实现层应复用本文术语，不再局部发明近义词

本文只保留以下最小核心术语：

1. **Planning Archetype（规划原型）**  
   决定任务主路径的类型抽象。

2. **Spec Strategy（规格策略）**  
   决定上游约束文档应采用什么表达形态。

3. **Validation Strategy（验证策略）**  
   决定如何验证规格与实施承诺。

4. **Governance Mode（治理模式）**  
   决定当前允许消耗多少规划预算（planning budget）。

5. **Artifact（资产）**  
   协议在运行中留下的可审阅产物，如阶段文档、日志、检查点。

6. **Artifact State（资产状态）**  
   资产当前所处的状态，如 `draft`、`approved`、`needs-revision`。

7. **Event-Action Rule（事件-动作规则）**  
   用 `trigger -> required action -> blocked transitions -> artifact state change` 表达的裁决规则。

8. **Human Decision Point（人类决策点）**  
   需要人介入裁决的节点，分为 `required` 与 `recommended` 两类。

9. **Conflict Walkthrough（冲突走查）**  
   用于验证协议在多事件并发与回退情形下是否仍可用的示例。

除以上概念外，其他词都应视为说明性词汇，而不是新增正式术语。

## 三、这是什么（What This Is）

这不是一个通用“需求分析”技能，也不是一个单纯生成代码计划的模板集合。  
它是一套面向 AI 编码代理（AI coding agent）的**人在回路 Planning Protocol（规划协议）**。

它约束的对象不是“代码生成”本身，而是**进入编码（coding）之前的规划过程（planning process）**。  
也就是说，它主要治理的是：

- 需求如何澄清
- 事实如何建立
- 方案如何比较与选择
- 改动如何拆解
- 实现约束如何明确
- 哪些地方必须由人拍板
- 哪些变化会让先前批准失效
- 哪些文档该保留，哪些控制件该折叠或归档

这套协议的目标不是让代理（agent）写更多文档，而是让代理在真正写代码之前，先以**受约束、可审阅、可裁决、可按预算运行**的方式完成规划（planning）。

一句话定义：

**它是一套面向 AI coding agent 的、由统一主协议驱动、按条件分支路由、按规划预算运行、按事件-动作规则裁决、并把人放在关键取舍环节中的规划协议。**

---

## 四、它要解决什么问题（Problem Statement）

没有协议约束时，AI coding agent 在规划阶段常见的失控方式包括：

- 需求未澄清就直接设计或直接编码
- 把假设当事实，把推断当结论
- 不区分“用户说的”“代码里观察到的”“仍待确认的”
- 根因未明就给出看似完整的方案
- 设计、执行计划、实现细节混在一起
- 给出方案但不说明 trade-off（取舍）
- 一边写规划，一边悄悄扩大范围（scope expansion）
- 上游需求或事实改变后，下游计划却默认仍然有效
- 在信息不足时继续合理发挥
- 把“人在回路”做成形式审批，而不是真正的关键决策介入

因此，这套协议要解决的核心问题不是“代理会不会写代码”，而是：

**代理在进入编码前，能否用一种受控方式，与人对齐目标、边界、事实、方案、改动路径与实现约束。**

## 五、它不是什么（Non-Goals）

### 1. 它不是一个总代码生成器（code generator）

它的终点可以是足够细的实施蓝图（implementation blueprint），但它本身不等于自动写最终代码。

### 2. 它不是“所有任务都先写 formal spec（正式规格），再做 TDD（测试驱动开发）”

某些任务适合强规格 + 强测试驱动；另一些任务更适合先调查、先刻画现状、先明确兼容窗口或先做回归验证。  
因此它追求的是**按任务选择合适的规格策略与验证策略**，而不是统一方法论。

### 3. 它不是一套默认满配的治理制度

它默认是轻量运行，只有在风险、不确定性、耦合范围、兼容窗口或回滚成本升高时，才升级治理强度。

### 4. 它不是多个完全独立的 skill（技能）或 workflow（工作流）

它采用的是**一个统一主协议 + 条件分支**，不是按 bug、feature、migration、refactor 各做一套互不相干的流程。

### 5. 它不是为了“文档完整”而文档完整

它只保留真正决定推进方式的规则与资产。其余内容应下沉到模板（template）、检查表（checklist）或案例（walkthrough）。

## 六、为什么采用“一个统一主协议 + 条件分支”（Why One Unified Protocol with Conditional Branches）

这套协议明确采用**一个统一主协议（unified master protocol）+ 条件分支（conditional branches）**的设计，而不是多个独立协议，原因有四个。

### 1. 公共治理规则高度共享

无论是 bug fix（缺陷修复）、feature（功能开发）、refactor（重构）、migration（迁移）还是 investigation（调查），都有一些共同规则：

- 先规划后编码
- 上游变化触发下游重审
- 关键地方要有人拍板
- 证据不足时不能把推断写成事实
- 阶段之间不得越界

如果拆成多套独立协议，这些公共规则会重复定义、重复维护，并很快漂移。

### 2. 真实任务经常是混合型

真实世界里常见的并不是“纯净的单类任务”，而是：

- bug fix 中夹带局部重构
- feature 伴随接口演化
- refactor 同时触发兼容性要求
- migration 中间必须先做 investigation

如果用多套互斥 skill，很容易在边界交界处发生切换困难或规则冲突。

### 3. 统一协议更适合做成本控制

统一主协议可以把“轻量默认、按条件升级”的预算逻辑写成共同规则。  
如果拆成多套协议，每一套都容易自带自己的“完整版流程”，反而更容易制度膨胀。

### 4. 统一协议更适合以后封装成一个可维护的 skill

最终要做成 skill 时，最稳定的结构不是“多个相互重叠的长 prompt（提示词）”，而是：

- 一套主协议定义
- 一套路由逻辑
- 一组模板与检查表
- 一组事件-动作裁决规则
- 一组案例与资源文件

这比维护多份相近但不完全相同的 skill 更可控。

## 七、顶层原则（Top-Level Principles）

### 1. Lean First（轻量优先）

默认以最小必要成本运行。  
Lean（轻量模式）是常态，非 Lean（非轻量）需要理由。

### 2. Evidence First（证据优先）

根因不明、现状行为未知、影响面不明、兼容窗口不清时，必须先建立事实，再讨论绑定性的设计与实施承诺。

### 3. Stage-Bounded Progression（阶段有界推进）

协议保留六阶段，但每阶段只回答一个主问题，并有明确不得越界清单。  
阶段化不是为了形式感，而是为了防止范围（scope）、证据（evidence）、设计（design）、执行（execution）和实现约束（implementation constraints）互相污染。

### 4. Human in the Loop（人在回路）不仅是审批在回路

人不是只在最后说一句“继续”。  
人要在关键取舍处真正拥有裁决权。

### 5. Key Decision Traceability（关键决策追溯）

只要求关键需求、关键约束、关键设计选择与关键验证承诺之间可追溯。  
目标不是全量编号化，而是关键判断不会失忆。

### 6. Change-Triggered Re-review（变更触发重审）

一旦上游范围、约束、成功标准、关键事实或所选设计发生变化，下游不能默认仍有效。

### 7. Governance Proportionality（治理与风险成比例）

风险越高、耦合越强、兼容期越长、回滚越难，治理越应显式。  
反之，局部任务默认局部处理。

### 8. Artifact Economy（资产经济性）

协议不仅会生成资产，也必须会淘汰资产。  
任何日志、矩阵、台账，只要不再改变后续判断，就应折叠或归档。

## 八、四层结构（Four-Layer Structure）

### 第一层：Protocol Definition（协议定义层）

只回答：**这套协议是什么，目标是什么，最小运行原则是什么。**

### 第二层：Routing Logic（路由逻辑层）

只回答：**面对不同任务，应该走什么规划路径。**

负责：

- Planning Archetype（规划原型）判定
- Governance Mode（治理模式）判定
- Spec Strategy（规格策略）判定
- Validation Strategy（验证策略）判定
- 是否先进入 Uncertainty Reduction（不确定性收缩）或 Characterization（特征刻画）

### 第三层：Artifacts（产物层）

只回答：**每一步需要留下什么可审阅资产。**

包括：

- 阶段文档
- Decision Log（决策日志）
- Assumption Log（假设日志）
- Open Questions Log（开放问题日志）
- Blueprint Artifacts（蓝图资产）
- 必要的 Traceability Artifacts（追溯资产）

### 第四层：Governance Rules（治理规则层）

只回答：**什么时候禁止推进，什么时候必须重审，什么时候升级或降级治理，什么时候资产应被折叠或归档。**

只保留四类上位规则：

- Progression Rules（推进规则）
- Invalidation Rules（失效规则）
- Governance Switching Rules（治理切换规则）
- Artifact Lifecycle Rules（资产生命周期规则）

---

## 九、三类路由轴（Three Routing Axes）

协议不是只靠 task type（任务类型）路由，而是同时看三类轴：

### 1. Planning Archetype（规划原型）

决定**主流程关注点**。

### 2. Spec Strategy（规格策略）

决定**上游约束文档应采用什么表达形态**。

### 3. Validation Strategy（验证策略）

决定**如何验证规格与实现承诺**。

再加一层：

### 4. Governance Mode（治理模式）

决定**当前允许消耗多少 planning budget（规划预算）**。

这四者的关系是：

- **Planning Archetype** 决定主路径
- **Spec Strategy** 决定约束表达方式
- **Validation Strategy** 决定验证哲学和主要验证机制
- **Governance Mode** 决定这套东西跑得多轻或多重

## 十、Planning Archetype（规划原型）

### 1. Behavior Change（行为变化型）

适用于：

- feature（功能开发）
- 一部分 bug fix（缺陷修复）
- 一部分 API change（接口变更）

关注重点：

- 行为边界
- 验收标准
- 回归验证 / 验收验证

### 2. Behavior Preserve（行为保持型）

适用于：

- refactor（重构）
- cleanup（清理）
- 保持外部行为不变的结构优化

关注重点：

- Characterization（特征刻画）
- Non-Regression（非回归）
- 行为保持边界

### 3. Compatibility Transition（兼容性过渡型）

适用于：

- migration（迁移）
- dependency upgrade（依赖升级）
- schema evolution（模式演化）
- 接口切换
- 带兼容窗口的跨模块改动

关注重点：

- compatibility window（兼容窗口）
- phased rollout（分阶段发布）
- rollback（回滚）
- 切换顺序

#### 升格条件（Promotion Criteria）

满足以下任一条件，应升格为 Compatibility Transition：

- 存在显式兼容期
- 需要双读 / 双写 / 双协议共存
- 存在切换窗口
- rollback 是核心安全条件
- 新旧接口 / 模式 / 依赖必须并存一段时间

### 4. Uncertainty Reduction（不确定性收缩型）

适用于：

- investigation（调查）
- spike（探索）
- 根因不明的缺陷
- 设计空间尚未收敛的问题

关注重点：

- 证据收集
- 选项分析
- 缩小不确定性
- 暂缓实现承诺

#### 退出条件（Exit Criteria）

满足以下至少一项，才算完成不确定性收缩：

- 已识别足以进入实现规划的主问题边界
- 已缩小为有限可比较方案集
- 已明确当前无法推进的阻断条件
- 已得出“应终止 / 暂缓 / 不值得继续”的建议

## 十一、Spec Strategy（规格策略）

### 1. Behavior Spec（行为规格）

定义：

- 目标行为
- 边界条件
- 验收标准
- 非目标

适合：

- feature
- 业务规则明确的行为变化
- 用户体验目标相对清楚的需求

### 2. Contract Spec（契约规格）

定义：

- 接口
- 数据结构
- 字段语义
- 输入输出约束
- 调用前提和兼容要求

适合：

- API change
- schema change
- 跨服务或跨模块边界变化

### 3. Design Spec（设计规格）

定义：

- 架构目标
- 职责划分
- 模块边界
- 方案候选
- 设计取舍

适合：

- 中大型 feature
- cross-module change（跨模块改动）
- greenfield design（从零设计）

### 4. Migration Spec（迁移规格）

定义：

- 迁移顺序
- 兼容期
- 双读 / 双写策略
- 切换条件
- rollback conditions（回滚条件）

适合：

- migration
- dependency upgrade
- protocol / schema transition（协议 / 模式过渡）

### 5. Investigation Brief（调查简报）

定义：

- 当前问题
- 已知事实
- 未知项
- 调查范围
- 可能选项
- 建议下一步

适合：

- investigation
- spike
- 根因未明的问题

### 6. Characterization Spec（特征刻画规格）

定义：

- 当前行为
- 不可破坏的外部表现
- 已观察到的输入输出特征
- 保持不变的边界

适合：

- refactor
- legacy modernization（遗留系统现代化）
- behavior-preserving change（行为保持型改动）

### 选择原则（Selection Principles）

- **Behavior Change** 默认优先考虑 Behavior Spec；若边界变化发生在接口，则可转 Contract Spec。
- **Behavior Preserve** 默认优先考虑 Characterization Spec。
- **Compatibility Transition** 默认优先考虑 Migration Spec；若核心在接口边界，也可叠加 Contract Spec。
- **Uncertainty Reduction** 默认优先考虑 Investigation Brief。

一个任务可以有主规格策略与辅规格策略，但**不应把所有规格都堆在一起**。

---

## 十二、Validation Strategy（验证策略）

### 1. Acceptance Validation（验收验证）

关注：

- 是否满足预期业务行为
- 是否满足用户可感知目标

### 2. Contract Tests（契约测试）

关注：

- 接口输入输出
- 字段语义
- 调用约束
- 向后兼容性

### 3. Regression Tests（回归测试）

关注：

- 既有行为未被意外破坏
- 缺陷修复未引入新破坏

### 4. Characterization Tests（特征刻画测试）

关注：

- 当前系统外部行为被刻画并固定
- 重构后这些外部行为保持一致

### 5. Integration Validation / Integration Tests（集成验证 / 集成测试）

关注：

- 多模块联动
- 真实依赖关系
- 迁移与切换路径
- 兼容窗口下的系统级行为

### 6. Manual Validation Checklist（人工验证清单）

关注：

- 不易完全自动化的交互行为
- 高体验导向的前端问题
- 依赖人工观察的切换过程
- 风险点确认

### 选择原则（Selection Principles）

- **Behavior Change** 往往采用 Acceptance Validation + Regression Tests。
- **Behavior Preserve** 往往采用 Characterization Tests + Regression Tests。
- **Compatibility Transition** 往往采用 Integration Validation + Rollback Validation（回滚验证）+ Manual Validation Checklist。
- **Uncertainty Reduction** 初期可能不绑定测试，而以“证据充分性”作为退出标准；一旦转入实现导向流程，再选择相应验证策略。

### 一个重要澄清（Important Clarification）

这套协议不把“测试”视为唯一验证机制，也不把 TDD 视为所有任务的默认驱动力。  
更准确的表述是：

**先为任务选择合适的规格策略，再为该规格策略匹配合适的验证策略。**

## 十三、Governance Mode（治理模式）：把分级写成规划预算

### 1. Lean（轻量模式）

**预算哲学：局部问题局部处理，默认不扩张控制面。**

意味着：

- 更少的显式资产
- 更少的状态维护
- 更少的强制重审传播
- 更强的默认局部修订，而不是制度化回看

最低保留：

- stage gating（阶段门控）
- 范围 / 目标说明
- 精简事实确认
- 精简实施说明
- 最小验证说明

### 2. Standard（标准模式）

**预算哲学：把关键判断显式化，但避免全局治理。**

增加内容：

- Decision Log
- Assumption Log
- 基础关键追溯
- 更明确的变更重审

### 3. Strict（严格模式）

**预算哲学：为高风险演化保留审计与回退能力。**

增加内容：

- 扩展关键追溯
- Compatibility / Rollback Checkpoints
- 更显式的影响登记
- 更强的阶段间重审纪律

### 4. 动态升降级（Dynamic Escalation / De-escalation）

治理模式不是在 Stage 0 一次性定死，而是随证据动态调整。

#### 升级触发器（Escalation Triggers）

- 原本局部问题暴露出跨模块联动
- 新发现兼容窗口、双写 / 双读、切换窗口或回滚要求
- 影响面无法再由局部修订安全控制
- 已批准关键前提被推翻，需要多资产联动修订

#### 降级条件（De-escalation Conditions）

- 不确定性已显著收缩为局部问题
- 兼容窗口被排除
- 风险边界回落到单点或低耦合修订
- 先前为谨慎而启用的控制件已不再影响判断

#### 补偿规则（Compensation Rules）

- 升级时：当前阶段即时生效；新增必需资产必须补齐后，才允许继续审批
- 降级时：不删除历史依据；仅停止活跃维护，并把不再必要的资产转为 `archived`

### 5. Lean 下的文档实体合并规则（Document Merge Rules under Lean）

为了避免 Lean 只是“轻量版完整流程”，Lean 模式下允许以下合并：

- **Stage 1 + Stage 2** 可合并为一个简短的 scope-and-facts note（范围与事实说明）
- 若无设计分叉，**Stage 3** 可显式跳过
- **Stage 4 + Stage 5** 可合并为一个 implementation note（实施说明）

这意味着：

- 阶段逻辑仍然存在
- 但文档实体不必一阶段一文件
- Lean 的最小路径可以非常短，不应保留“穿着正装修水龙头”的形式负担

## 十四、六阶段（Six Stages）：每阶段只回答一个问题

### Stage 0：Task Intake and Routing（任务受理与路由）

**只回答：这是什么任务，走哪条规划路径，用多少预算跑。**

输出应包括：

- 原始任务摘要
- 主 / 次 Planning Archetype
- Governance Mode
- 主 / 辅 Spec Strategy
- 主 / 辅 Validation Strategy
- 是否先做 evidence collection（证据收集）或 characterization
- 当前是否存在 Human Decision Point

不得越界：

- 不承诺设计方案
- 不承诺文件级实现

### Stage 1：Requirements Alignment（需求对齐）

**只回答：要解决什么，不解决什么，成功长什么样。**

输出应包括：

- 目标
- 范围 / 非目标
- 成功标准 / 验收标准
- 显式约束
- 待确认项

不得越界：

- 不假装根因已知
- 不把设计取舍写成需求事实

### Stage 2：Current-State Analysis（现状分析）

**只回答：现在真实情况是什么，哪些是事实，哪些只是解释。**

输出应包括：

- 观察到的事实
- 证据来源
- 关键未知项
- 初步影响面判断

不得越界：

- 不把推断伪装成事实
- 不在证据不足时形成可审批设计结论

### Stage 3：Design Choice（设计选择）

**只回答：在架构、职责与接口策略层，应该选哪条路线，以及为什么。**

允许处理：

- 架构方向
- 职责划分
- 接口策略
- 关键取舍
- 需要人拍板的问题
- 高层验证承诺（只写承诺验证什么）

不得越界：

- 不写模块 / 文件级改动切片
- 不写局部算法骨架
- 不写测试点颗粒度
- 不展开协商过程，只列需要裁决的问题

#### Stage 3 进入 `ready-for-approval` 的硬门槛（Approval Gate for Stage 3）

Stage 3 只有同时满足以下条件时，才能进入 `ready-for-approval`：

1. **已建立与当前设计选择直接相关的关键事实**  
   也就是说，设计结论不再依赖“可能如此”的核心前提。

2. **未决问题不会改变主设计路径，或已被标记为 `human_decision_required`**  
   允许存在未决问题，但这些未决问题不能处于“可能推翻整条设计路线”的灰区。

3. **当前推荐路径不再依赖未经验证的核心假设**  
   可以存在次要假设，但不能靠未经验证的核心假设支撑主设计结论。

若不满足以上三条之一，Stage 3 只能停留在 `draft`，不得进入 `ready-for-approval`。

### Stage 4：Change Topology（改动拓扑）

**只回答：改动范围与依赖顺序如何切片，怎样安全推进。**

只定义：

- change slices（改动切片）
- dependency order（依赖顺序）
- risk checkpoints（风险检查点）
- rollout / verification checkpoints（发布 / 验证检查点）
- 模块 / 子系统 / 文件范围

不得越界：

- 不定义局部实现细节
- 不定义类型 / 数据结构细节
- 不写关键伪代码

### Stage 5：Implementation Constraints（实现约束）

**只回答：编码时哪些局部实现不能乱写。**

只定义：

- data shape（数据形状）
- interface constraints（接口约束）
- local algorithm skeleton（局部算法骨架）
- error handling requirements（错误处理要求）
- test commitments（测试承诺）
- 必要的 code sketch（代码示意）

不得越界：

- 不重新发明执行顺序
- 不重写范围定义
- 不把设计层重新展开成新的方案讨论

## 十五、人类决策点（Human Decision Points）

### 1. `human_decision_required`（必须拍板）

典型触发场景：

- 范围与非目标存在不可兼得冲突
- 设计取舍涉及性能、兼容性、可维护性的高影响冲突
- 需要扩大改动范围才能换来结构正确性
- rollback cost（回滚成本）高但收益不确定
- 多个合理方向都无法由证据排除，且会显著改变后续投入

对推进的影响：

- 可以形成 recommendation（建议）
- 可以进入 `ready-for-approval`
- **不得进入依赖该决策的绑定性后续推进**

### 2. `human_decision_recommended`（建议拍板）

典型触发场景：

- 多个方向都合理，但差异主要是风格或局部成本
- 结构更优雅但改动面稍大
- 长期演进性更好，但短期收益有限
- 两种方案都满足安全边界，只是局部体验不同

对推进的影响：

- 必须显式写出默认路径
- 可以继续推进
- 不得把“建议优先选项”写成“人已拍板的既定结论”

#### 默认路径约束（Default Path Constraints）

当 `human_decision_recommended` 未获得人工裁决而继续推进时，默认路径必须同时满足：

1. **满足安全边界且额外承诺最少**  
2. **不得预先占用明显更高的未来成本**  
3. **必须可被后续人工裁决覆盖而无需大幅返工**

因此，默认路径不是“代理最喜欢的路径”，而是**最保守、最可覆盖、最少额外承诺的路径**。

## 十六、资产状态（Artifact States）

只保留五种状态：

- `draft`
- `ready-for-approval`
- `approved`
- `needs-revision`
- `archived`

说明：

- 不单列 `stale`。凡上游变化导致不能直接继续依赖的资产，一律归入 `needs-revision`
- 凡不再参与活跃判断但仍保留历史价值的资产，一律归入 `archived`

## 十七、最小裁决核心（Minimal Adjudication Core）：事件-动作语义

协议把裁决逻辑压成一个最小事件-动作模型：

`trigger -> required action -> blocked transitions -> artifact state change`

### 上位优先级（Rule Precedence，规则优先级）

只保留三条决定裁决顺序的上位规则。

#### 规则 A：Safety over Efficiency（安全性优先于效率）

凡命中以下触发器，均优先于 Lean 默认、节奏连续性与“先往下写一点”：

- evidence trigger（证据触发器）
- invalidation trigger（失效触发器）
- rollback / compatibility safety requirement（回滚 / 兼容性安全要求）
- `human_decision_required`

#### 规则 B：New Facts over Prior Approval（新事实优先于旧批准）

只要 Stage 2 或后续阶段出现足以推翻此前边界、假设或设计前提的新证据：

- 原批准可以失效
- 相关下游资产进入 `needs-revision`
- 不允许以“已经批准过”为由跳过回看

#### 规则 C：Primary Archetype Owns the Flow（主原型决定主流程）

- 主 Planning Archetype 决定主路线
- 次原型只追加检查项、验证要求与风险控制
- 不允许通过原型叠加生成新的阶段体系

### 并发处理总规则（Concurrent Event Resolution Rule，多事件并发处理规则）

**当多个事件同时处于活跃状态时，先按优先级顺序处理阻断性事件（blocking events），再评估非阻断性事件（non-blocking events），然后重新计算当前阶段允许的状态转移（allowed transitions）与资产状态。**

这意味着：

- 先处理 evidence / invalidation / required decision / safety 类事件
- 再处理 recommended decision、降级、折叠等非阻断性事件
- 每轮事件处理后，都必须重新判断当前阶段还能否进入 `ready-for-approval`、`approved` 或后续阶段

### 最小事件-动作表（Event-Action Table，事件-动作表）

#### 事件 1：Evidence Trigger Hit（命中证据触发器）

| Trigger（触发条件） | Required Action（必须动作） | Blocked Transitions（阻断的状态转移） | Artifact State Change（资产状态变化） |
|---|---|---|---|
| 根因不明、现状行为未建立、影响面未知、兼容窗口不清 | 先补 Stage 2，并暂停基于未证实前提形成的新设计结论 | 禁止进入 Stage 3 的可审批设计结论；禁止把未证实结论写入 Stage 4/5 | 基于未证实前提写出的 Stage 3/4/5 内容改为 `needs-revision` |

#### 事件 2：Human Decision Required Hit（命中必须拍板）

| Trigger | Required Action | Blocked Transitions | Artifact State Change |
|---|---|---|---|
| 范围冲突、关键取舍不可兼得、高回滚成本高不确定收益、多合理方向无法由证据排除 | 显式列出待裁决问题、选项与建议；暂停相关分支推进 | 禁止把相关结论标记为 `approved`；禁止依赖该决策继续产出绑定性 Stage 4/5 内容 | 当前阶段保持 `ready-for-approval`；未决项不进入 `approved` |

#### 事件 3：Human Decision Recommended Hit（命中建议拍板）

| Trigger | Required Action | Blocked Transitions | Artifact State Change |
|---|---|---|---|
| 多个方向都合理但差异不大、结构更优雅但改动面变大、收益存在但不影响安全边界 | 显式说明建议裁决点，并标注默认路径 | 不阻断当前阶段进入 `ready-for-approval`；仅阻断将“人未选的优先选项”写成既定事实 | 资产可进入 `ready-for-approval` |

#### 事件 4：Approved Upstream Invalidated（已批准上游被新事实推翻）

| Trigger | Required Action | Blocked Transitions | Artifact State Change |
|---|---|---|---|
| 已批准的需求边界、关键假设或设计前提被新证据推翻 | 回到最近受影响的上游阶段修订；登记影响范围 | 禁止继续依赖旧版本进入后续审批 | 被影响的下游资产全部变为 `needs-revision` |

#### 事件 5：Governance Escalation（治理升级）

| Trigger | Required Action | Blocked Transitions | Artifact State Change |
|---|---|---|---|
| 耦合范围扩大、回退成本上升、发现兼容窗口、从单点问题变为多模块联动 | 当前阶段即时生效更高治理模式；补齐新增必需资产 | 禁止跳过升级后必需控制件直接向后审批 | 已有资产保持原状态；新增资产以 `draft` 创建 |

#### 事件 6：Governance De-escalation（治理降级）

| Trigger | Required Action | Blocked Transitions | Artifact State Change |
|---|---|---|---|
| 风险收缩、不确定性下降、兼容窗口被排除、范围回落为局部变更 | 显式确认可降级；折叠不再必要的活跃控制件 | 不阻断推进；但不得丢失仍有判断价值的历史依据 | 不再活跃维护的控制件改为 `archived` |

## 十八、控制件（Control Assets）：只保留最小活跃集

### Lean 默认活跃集

- 阶段文档或合并后的简短说明
- 必要时的少量待确认项

### Standard 按需增加

- Decision Log
- Assumption Log
- 最小 Open Questions Log

### Strict 增加

- Compatibility / Rollback Checkpoints
- 扩展关键追溯记录
- 更显式的影响登记

### 统一清理纪律（Sunset / Pruning Discipline，过期清理纪律）

#### 必须保留到结束的内容

- 已批准的需求边界
- 已批准的关键设计选择
- 仍影响编码或验证的未决问题
- Strict 模式下仍影响回滚 / 兼容判断的检查点

#### 进入下一阶段后可折叠的内容

- 已关闭且不再影响判断的开放问题
- 已确认并已吸收入主文档的假设
- 仅服务于原型判定、后续已无价值的路由说明

#### 治理降级后应归档的内容

- 原为高风险预防而创建、现已不再影响判断的扩展控制件
- 不再参与活跃重审传播的影响登记

规则：

**活跃集只保留仍会改变后续判断的东西；其他内容进入 `archived`。**

## 十九、默认启发排序（Positive Heuristics Ordering，正向启发排序）

为了防止“听起来都对，执行时很玄学”，协议给正向启发规定默认排序：

1. correctness / safety（正确性 / 安全性）
2. reversibility（可回退性）
3. locality of change（改动局部性）
4. implementation cost（实施成本）
5. elegance / future extensibility（优雅性 / 未来扩展性）

含义：

- 更优雅不能压过更安全
- 更可扩展不能压过更容易回退
- 一次做漂亮不能天然压过局部安全落地

## 二十、最小执行路径（Minimal Walkthroughs，最小走查示例）

这一部分不是为了展示制度完整，而是为了证明：

**这套协议对 agent 来说不会天然太贵。**

### 示例 A：Lean 的单点 bug fix（单点缺陷修复）

#### 场景

某个输入边界条件导致函数返回错误结果。问题可稳定复现，影响范围初看局限于单模块单函数。

#### 实际触发的规则

- Stage 0 路由到 Behavior Change
- Governance Mode 为 Lean
- 因复现条件明确，不触发强证据补充
- 无必须拍板的人类决策
- 允许 Stage 1 + Stage 2 合并
- 无设计分叉，Stage 3 显式跳过
- Stage 4 + Stage 5 合并为一个 implementation note

#### 实际生成的资产

- Stage 0 路由摘要
- 一个合并后的 scope-and-facts note
- 一个 implementation note
- 最小回归验证说明

#### 没必要出场的规则 / 资产

- 不需要 Decision Log
- 不需要 Assumption Log
- 不需要扩展关键追溯
- 不需要 Compatibility / Rollback Checkpoints
- 不需要治理升级

#### 经济性结论

这是一个真正轻量的最小路径案例。协议保留阶段逻辑，但没有把文档实体做重。

### 示例 B：Standard 的 behavior-preserving refactor（行为保持型重构）

#### 场景

要把分散在多个文件中的重复逻辑收敛到一个公共模块，外部行为必须保持不变，但调用链较多。

#### 实际触发的规则

- Stage 0 路由到 Behavior Preserve
- Governance Mode 为 Standard
- 命中 Characterization 要求
- 存在建议拍板的人类决策：是先做最小抽取，还是顺手统一命名与接口风格

#### 实际生成的资产

- Stage 0 路由摘要
- Stage 1 行为保持边界与非目标
- Stage 2 现状行为与调用点分析
- Stage 3 结构选择与取舍
- Stage 4 改动切片与依赖顺序
- Stage 5 接口约束与非回归验证承诺
- Decision Log
- 少量 Assumption Log

#### 没必要出场的规则 / 资产

- 不需要 Strict
- 不需要 compatibility window 控制
- 不需要 rollback checkpoint 体系
- 不需要扩展影响登记

#### 经济性结论

这里比 Lean 多出的，是关键判断显式化，而不是全局治理化。

### 示例 C：Strict 的 compatibility transition（兼容性过渡）

#### 场景

服务接口从旧字段协议迁移到新字段协议，需要双读一段时间，之后再切流并保留回滚能力。

#### 实际触发的规则

- Stage 0 路由到 Compatibility Transition
- 初始 Governance Mode 即为 Strict
- 命中兼容窗口、双协议共存、回滚为核心安全条件
- 命中必须拍板：切换窗口与回滚阈值
- 若 Stage 2 发现调用方比预期更多，则触发即时治理升级补偿动作

#### 实际生成的资产

- 全部六阶段文档
- Decision Log
- Assumption Log
- Open Questions Log
- 扩展关键追溯
- Compatibility / Rollback Checkpoints
- 更显式的影响登记

#### 没必要出场的规则 / 资产

- 不需要额外发明新的治理档位
- 不需要把所有局部实现细节都追溯到每条需求
- 不需要让所有历史中间稿长期活跃维护

#### 经济性结论

Strict 更重，不是因为协议偏爱制度，而是因为任务本身天然需要审计与回退能力。

## 二十一、冲突走查（Conflict Walkthrough）

这一示例专门用来证明：这套协议不只会跑“顺风局”。

### 场景

起初是一个 Lean 的单点 bug fix：  
某接口在特定参数下返回错误值。最初看起来像局部行为修复。

但推进过程中发生以下变化：

1. Stage 2 发现该接口实际上同时服务旧客户端与新客户端  
2. 新旧客户端对字段解释并不完全一致，存在兼容窗口  
3. 代理在 Stage 3 形成了一个推荐方案  
4. 随后又发现旧客户端的调用量远高于预期，导致原推荐方案的切换风险显著升高  
5. 同时出现一个必须拍板的问题：是否接受更大改动面以换取更稳妥的兼容路径

### 事件序列

#### 第一步：初始路由

- Stage 0 将任务路由为 Behavior Change
- Governance Mode 为 Lean

#### 第二步：命中 Evidence Trigger

Stage 2 发现存在双客户端并行与字段语义差异，说明影响面与兼容条件此前并未建立。

触发：

- Evidence Trigger Hit

动作：

- 补强 Stage 2
- 暂停基于“局部修复”前提的设计结论

结果：

- 任何基于局部单点修复前提写出的设计草稿保持在 `draft` 或转为 `needs-revision`

#### 第三步：触发治理升级与原型升格

由于发现存在兼容窗口、新旧解释并存、潜在切换路径，任务不再适合继续以普通 Behavior Change 处理。

触发：

- Governance Escalation
- Planning Archetype 升格为 Compatibility Transition

动作：

- Governance Mode 从 Lean 即时升级到 Strict
- 必需新增 Compatibility / Rollback Checkpoints
- 路由说明更新

结果：

- 已有文档保留
- 新增控制件以 `draft` 创建
- Allowed transitions（允许的状态转移）需要重新计算

#### 第四步：形成 Stage 3 推荐方案

补强后的 Stage 2 支持形成一个推荐设计：  
通过双读过渡 + 延后切流解决兼容问题。

但此时它只有在满足 Stage 3 的硬门槛时，才能进入 `ready-for-approval`。

#### 第五步：新事实推翻原推荐路径的风险评估

新的流量分析表明，旧客户端调用量远高于预期，原推荐切流窗口的风险被低估。

触发：

- Approved Upstream Invalidated 或至少 New Facts over Prior Approval

动作：

- 回到最近受影响的上游阶段重新修订
- Stage 3 推荐方案进入 `needs-revision`

结果：

- 不允许继续依赖旧推荐方案写绑定性 Stage 4 / Stage 5
- Allowed transitions 重新计算

#### 第六步：命中 `human_decision_required`

此时出现一个关键取舍：

- 方案 A：扩大改动范围，增加兼容层，换取更稳妥切换
- 方案 B：保持小改动，但切换风险更高

这不是代理可以自行决定的 advisory 问题，而是 required decision。

触发：

- `human_decision_required`

动作：

- 列出两个方案、各自收益与代价
- 将当前阶段置于 `ready-for-approval`
- 暂停依赖该决策的绑定性后续推进

结果：

- 局部冻结，但不是全局中止
- 不依赖该决策的背景整理、事实补充仍可继续
- 依赖该决策的 Stage 4 / Stage 5 不得进入可审批状态

### 这个案例证明了什么

它证明这套协议不仅能处理“普通路径”，还能处理：

- 从 Lean 到 Strict 的即时升级
- 主原型的中途升格
- 新事实推翻已形成的推荐方案
- `required` 决策触发的局部冻结
- 多事件并发下按优先级串行处理，然后重算允许状态转移与资产状态

这正是事件-动作规则存在的价值：  
不是让顺风局更正式，而是让冲突态不靠代理临场发挥。

## 二十三、这套协议最终想守住什么（What This Protocol Ultimately Protects）

这套协议最终想守住的，不是“把所有风险都各立一法”，也不是“让代理显得更严肃”。

它想守住的是六件事：

- 普通任务默认轻量，不被制度拖重
- 高风险任务能够被明确升级，而不是靠经验硬扛
- 规格策略与验证策略按任务匹配，而不是统一套法
- 规则相撞时有程序化裁决，而不是靠代理临场发挥
- 人真正介入关键取舍，而不是只在阶段末尾形式审批
- Lean、Standard、Strict 都能在真实任务里跑得动，而不只是概念上成立

所以，这套协议追求的不是一棵枝繁叶茂的制度盆景，而是一个更克制、更可执行的最小骨架：

**统一主协议、条件分支路由、按预算运行、事件动作裁决、关键判断追溯、活跃资产最小化。**

这就是它真正的“人在回路”含义。
