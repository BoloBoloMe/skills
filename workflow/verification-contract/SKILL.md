# 验证契约

每个 issue 先定契约, 再动手. 契约只界定**交付什么证据**, 不指定工具, 也不靠"是否写测试"来区分. 五类之外不自由发挥; 套不进任何一类时停下报缺口.

## 行为变更

- 用: 成品出现新行为, 或外部可观察的行为被改.
- 做法: 做完去真东西上验. 浏览器点, 命令行跑, HTTP 打.
- 完成证据: 一条任何人能重跑的命令, 加观察到的输出 (脱敏后), 写进 issue 的 `验证入口` 节.
- 可以完全不写测试. 本 issue 内分支多, 边界多或计算密集的逻辑可额外补测试锁住行为, 但测试不替代真面证据.
- 禁止: 拿"测试通过"当唯一证据; 拿 mock 出来的世界证明联动成功.

## 结构变更

- 用: 行为不变, 只改结构, 位置, 命名, 类型.
- 做法: 动手前先钉住. 钉住物可以是描述当前行为的测试, 快照, 等价脚本或录制输出. 钉住物在动手前就该是**绿的**; 造红态说明走错了契约. 然后小步改, 每步都让钉住物保持绿.
- 完成证据: 钉住物路径, 加动手前后同一基线复跑的两次输出, 且两者一致.
- 禁止: 顺手改行为. 发现行为必须变, 拆成新 issue 走行为变更契约. 类型检查与 lint 不算钉住.

## 缺陷修复

- 用: 有明确失败现象要修.
- 做法: 走 `diagnosing-bugs` 找根因. 找到根因后, 先把复现落成红态, 再修.
- 完成证据: 红态 (命令与输出, 且复现提交落在修复提交之前), 绿态 (同一循环通过), 原始未最小化场景复跑通过.
- 没有正确接缝时: 用最接近的可执行检查 (定向脚本, 命令, trace 重放), 并把它落成仓库里可复跑的脚本, 不是只在报告里贴一次输出; 同时记下"这块代码缺接缝"这个发现.
- 禁止: 没复现就改代码; 拿猜测式的双保险防护当修复.

## 性能改进

- 用: 有可测指标要改善.
- 做法: 先量基线, 再改, 再同法量. 输入, 采样方式和命令全程不改.
- 完成证据: 基线数字与改后数字, 附命令与原始输出, 并按 `benchmark-checklist` 核过.
- 禁止: 没基线就报收益; 前后两侧用不同方法量.

## 非行为改动

- 用: 配置, 接线, 依赖升级, 注释, 文档.
- 完成证据: 构建通过, lint 通过, 相关入口真跑一次的输出.
- 禁止: 为凑数造测试.

## 派发与边界

- 契约在 `to-execution` 拆 issue 时定, 落到 issue 的 `验证契约` 节. 执行者按契约干活.
- 契约定错时停下报缺口, 不现场换契约. 一个 issue 只标一个主契约; 两类活混在一起就拆 issue.
- 契约是执行者自证. 最终独立验收 (`verify-change`) 不受契约影响, 仍按已确认的 PRODUCT.md 复核.

## 与其他 skill 的关系

- 行为变更里需要锁住的复杂逻辑: 用 `tdd` 的接缝与用例设计, 红绿循环也在其中.
- 结构变更的钉住物: 用例设计参考 `tdd`, 但检查从改前就绿, 不走红绿循环.
- 缺陷修复: `diagnosing-bugs` 负责找根因, 本 skill 负责交付证据.
- 性能改进: `benchmark-checklist` 核数字.
