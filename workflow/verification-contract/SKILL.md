# 验证契约

按这次变更要达到的结果, 从下面五类中选择验证方式, 再决定是否需要编写测试.
验证应随开发进行: 每完成一部分, 就在隔离测试环境运行实际代码, 检查这一部分是否符合要求, 不必等整个功能完成.

## 共用底线

- **边开发边实跑.** 通过当前可用的接口或命令运行实际代码和所需依赖的真实测试实例, 不要求启动整个系统. 只对实际跑过的范围下结论, 未接入的部分明确标为未验证.
- **依据已确认要求.** 用例优先取自 PRODUCT.md 已确认的 [Gherkin 场景](../to-spec/GHERKIN.md), 没有时用其他已确认要求. 同时核对技术/审计要求和受影响的旧行为. 要求不清先澄清, 不凭猜测添加用例.
- **按需自动化.** 实跑足以取证时不另写测试; 需要反复检查或保护复杂行为时, 才写最少的自动化测试, 通过公开接口调用实际代码. 不以 mock 内部组件后的测试结果代替实际运行. 已有测试照常运行, 不因此删改. 只有决定采用测试驱动开发时才调用 `tdd` skill.
- **安全环境.** 只在隔离测试环境运行, 不使用生产环境, 生产服务或真实客户数据. 缺环境先搭建, 搭不起来就报告未验证; 涉及费用, 共享资源或不可逆操作先获我批准. 第三方无法安全调用时可在对接处使用替代实现, 但须说明未真实验证的范围; 关键依赖未验证不能报通过. 静态文档检查不必启动实例.
- **保留原始数据.** 实跑数据优先放仓库外, 记录位置, 版本, 操作和占用. 默认保留, 不自动清理或过期, 停止实例也要保留数据. 复跑优先隔离; 必须清理旧数据时, 先保留可查看的原数据副本, 留不了就停下问我. 其他删除须经我批准, 截图/日志不能替代原始数据.

## 行为变更

- 适用情况: 新增或改变外部可观察行为.
- 做法: 按实现进度, 从当前可用入口逐项实跑已确认的用例. 本次变更完成时, 核对承诺的全部行为, 受影响的旧行为及技术/审计要求.
- 完成证据: 已实现及未验证的范围, 测试环境和数据位置, 入口操作与输入, 对应要求, 预期与实际结果 (脱敏输出或截图).

## 结构变更

- 适用情况: 对外行为不变, 只改结构, 位置, 命名或类型.
- 做法: 改前确定受影响的公开接口和旧行为, 建立可重复运行的行为检查, 可用已有测试, 命令或脚本. 确认改前通过后才重构, 改后用相同用例, 输入和条件复跑, 检查标准不随内部结构改变. 无法运行或观察结果就停下报告缺口; 类型检查/lint 不能单独证明行为未变.
- 完成证据: 检查入口, 改前版本, 相同输入/条件及前后结果. 同时改变行为时, 补交对应的验证证据.

## 缺陷修复

- 适用情况: 消除已知失败现象.
- 做法: 调用 `diagnosing-bugs` skill, 修复前实际复现原症状, 修复后用同一检查及原始场景确认消失. 检查确实能抓住故障且需要反复运行时, 才保留为自动化回归测试; 否则留下可复跑命令/脚本, 并记录检查缺口.
- 完成证据: 修复前后的检查命令与脱敏结果, 原始场景复跑结果, 留下的回归检查或可复跑步骤及检查缺口; 有复现提交时注明它先于修复提交.

## 性能改进

- 适用情况: 改善可测的性能指标.
- 做法: 在实际受影响的代码路径上先量基线再改, 在可比条件下复测; 调用 `benchmark-checklist` skill 核对公平性和结论边界.
- 完成证据: 前后数字, 运行条件, 测量方法, 原始输出和清单核查结论.

## 非行为改动

- 适用情况: 不改变外部行为的注释, 文档, 配置, 接线或依赖维护. skill/提示词若改变实际操作, 按行为变更验证.
- 做法: 选与改动直接相关的检查, 不为凑数量写测试.
- 完成证据: 如引用/渲染检查, 构建, lint 或相关入口的结果; 无适用检查则写明核对内容及原因, 不声称未运行的检查已通过.

## 交付边界

拆 issue 时, `验证契约` 写主要交付结果所属类别及附带验证, `验证入口` 写预定操作和通过标准; 执行后, `交付证据` 写实际操作, 结果, 未验证范围及可复查材料. 无 issue 时同样留证, 分类有误先交拆分方修正后再执行.
本 skill 用于开发者验证当前实现及评审核对, 不代替最终验收. 最终独立验收仍由 `verify-change` 按已确认的 PRODUCT.md 复核.
