# 验证契约

按这次变更要达到的结果, 从下面五类中选择一种或多种类型, 再决定如何验证及是否需要编写测试.

**本 skill 只规定验证.** 实现手段由你按现场决定, 不在此约束. 约束的是结论: 通过与否只能来自真实运行.

## 共用底线

- **类型对应结果.** 每种类型须对应明确的交付结果和改动范围, 并满足各自的验证要求. 不为分类拆 issue.
- **尽早完成真实验证闭环.** 涉及运行行为时, 实现走最短交付路径, 先产出能跑的可验证版本; 在隔离测试环境从真实入口对该版本做端到端验证, 使用必要的真实依赖. 发现问题后修复, 再跑同一端到端路径, 既确认修复也暴露新问题, 循环到当前要求闭环. 不强制先写测试或红绿顺序, 不必等全部实现完成或启动无关部分, 只对实际跑过的范围下结论.
- **入口可复跑.** 实现必须留下能从外部入口重复执行的路径, 并把它写进 issue 的 `验证入口`. 只存在于内部的实现无从验证, 遇到时报缺口, 不把 "验不了" 当成通过.
- **依据已确认要求.** 用例优先取自 PRODUCT.md 已确认的 [Gherkin 场景](../to-spec/GHERKIN.md), 没有时用其他已确认要求. 同时核对技术/审计要求和受影响的旧行为. 要求不清先澄清, 不凭猜测添加用例.
- **按需自动化.** 只有需要长期重复检查或保护复杂行为时, 才新增最少的自动化测试. 已有测试照常运行, 不因此删改. 编写或修改测试/手动验证代码前, 先读 [测试编写规范与抽查验收](reference/tests.md). 验证代码沿用项目已有技术栈; 手动验证代码不混作功能测试或计入其通过数.
- **测试只看行为.** 自动化测试通过公开接缝验证行为, 不检查实现细节; 代码内部改变时用例仍应成立. 预期值须来自独立真相源 (字面量, 手算例子, 规格), 不用与代码相同的方式重算.
- **持久层不得替换.** 禁止 mock 持久层, 也禁止用 Map/列表等内存假实现, stub 或预设返回值冒充真实 Repository/DAO/数据库. 测持久层接口或调用它的上层行为, 都用项目真实持久层实现与隔离测试存储; 不能只证明假实现符合接口. 环境不可得时报未验证, 不用替身补成通过. 具体边界见 [测试编写规范](reference/tests.md#持久层不得用替身).
- **其他替身只在系统边界.** 外部 API, 时间与随机性, 有时文件系统可按验证目标在系统对接处替换. 自己的模块, 内部协作者和任何你控制的东西都算实现, 用真实实现跑. 文件系统本身是持久化对象时也遵守上一条. 外部服务无法安全调用时须说明未真实验证的范围; 关键依赖未验证不能报通过.
- **安全环境.** 不使用生产环境, 生产服务或真实客户数据. 需要实例而缺少时先搭建, 搭不起来就报告未验证; 涉及费用, 共享资源或不可逆操作先获我批准.
- **记录证据.** 记录对应要求, 入口操作与输入, 预期与实际结果, 未验证范围及可复查的脱敏原始材料. 实跑还须记录环境和版本; 有原始数据时另记位置和占用. 同一检查满足多种类型的要求时, 共用结果和材料, 不重复执行.

数据保留, 实例停启, 删除与写入授权等安全要求集中见 [SAFETY.md](SAFETY.md).

## 行为变更

- 适用情况: 新增或改变外部可观察行为.
- 做法: 逐项验证本次承诺的全部行为.
- 完成证据: 每条承诺行为一条真实运行记录, 含命令/操作, 输入, 实际输出与预期对比. 优先从真实使用入口端到端验证, 分层测试与自动化测试作补充, 不用它们代替端到端结论; 环境不可得时报未验证缺口, 不用弱证据充抵.

## 结构变更

- 适用情况: 对应改动只调整结构, 位置, 命名或类型, 不改变对外行为.
- 完成证据: 须含改前与改后同一检查在相同输入/条件下的结果及改前版本, 改前就应通过. 只给改后结果不算完成. 类型检查与 lint 不能单独证明行为未变.

## 缺陷修复

- 适用情况: 消除已知失败现象.
- 做法: 调用 `fix-bugs` skill 执行统一链条: 复现 → 定位原因 → 制定修复方案 → 执行修复 → 验证修好且没改坏. 链条对所有 bug 一样, 不分大小. 取证与复验手段优先用代码库自身的既有测试, 开发命令或 CLI 入口, 其次真实入口操作, 必要时才用一次性临时脚本 (不提交, 跑完清理), 不为此新增专用脚本.
- 取证选择: 能用低成本可靠测试就用测试; 需要新建测试设施, 只能靠脆弱 mock, 环境耗时过长, 只在生产特殊状态出现, 复现条件不清或要改大量无关测试数据时, 在安全环境改用非测试手段取证, 并在交付证据写明为什么没用测试. 无法安全复现则报缺口. 失败须来自目标问题而非环境或测试代码自身; 检查意外通过时先怀疑它没覆盖症状.
- 完成证据: 红态真实出现过的记录 (命令与失败输出), 修复后同一检查通过, 原始场景复跑结果, 留下的可复跑方式及检查缺口; 有关联的复现或修复提交时, 记录提交号. 另留受影响范围的复验结果与独立复核记录, 写明检查范围, 手段和未覆盖的缺口, 不把有限检查说成全部没改坏.

## 性能改进

- 适用情况: 改善可测的性能指标.
- 做法: 在可比条件下测量, 调用 `benchmark-checklist` skill 核对公平性和结论边界.
- 完成证据: 基线与改后数字, 可比条件, 测量方法和清单核查结论.

## 非行为改动

- 适用情况: 不改变外部行为的注释, 文档, 配置, 接线或依赖维护. 改变实际操作的 skill/提示词不属此类.
- 做法: 选与改动直接相关的检查; 无适用检查时, 说明核对内容及原因.

## 测试代码验收

正式交付前执行 [测试代码人工抽查验收](reference/tests.md#测试代码人工抽查验收). 是否需要我选样及何时完成, 统一按该节的分支与完成标准判定; 无 issue/无 Roadmap 时同样执行.

## 交付边界

拆 issue 时, `验证契约` 写变更类型, 对应范围及验证要求/证据, `验证入口` 写预定检查和通过标准; 执行后, 按上述证据要求将结果记入 `交付证据`. 无 issue 时同样留证. 已有 issue 的分类有误时, 交拆分方修正后再执行.

**方法 skill 与完成标准.** 给做法的方法 skill 可选, 不构成完成标准; 通过与否只看本 skill 的完成证据. 方法 skill 用 "本 skill 是方法 skill" 自称, 其完成标准指向本 skill.

本 skill 用于我验证当前实现, 以及评审核对, 不代替最终验收. 最终独立验收仍由 `verify-change` 按已确认的 PRODUCT.md 复核.
