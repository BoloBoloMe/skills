# 验证契约

拆实施 issue 时按本次交付的主要结果选一类, 写明如何验证和交付什么证据. 不按是否写测试分类, 也不按文件形式分类: 会改变 agent 实际操作的 skill, 提示词或规范文档, 按它实际改变的行为归类, 不因是 `.md` 就归非行为改动. 五项之间没有固定的高低顺序. 无法归类时报告缺口.

修复已知故障归缺陷修复, 改善可测指标归性能改进; 两者有交集时按本次承诺解决的结果选: 承诺消除具体故障走缺陷修复, 交原症状复现证据; 承诺提升指标走性能改进, 交前后测量; 另一侧的证据作为补充仍须交付. 其余按是否改变外部可观察行为区分, 包括调用方可见的接口. 配置或依赖改动若改变运行结果, 也按结果归类.

一个垂直切片可以同时带两类结果. 主类按该切片最主要的交付结果选, 负责组织该 issue 的验证; 附带结果不免证, 仍须交付所属类别要求的验证证据. 只有确实可以独立交付时, 才拆成不同 issue. 已知故障修复优先说明原症状如何复现和消失; 承诺性能改善仍须前后测量; 新功能伴随重构时, 新行为和受影响的旧行为都要核对.

只负责人工核验或整合验证, 不修改成品的任务不套改动契约, 按 `to-execution` 的纯核验模板写明验证入口, 通过标准和完成证据.
`验证入口` 预先写操作和通过标准; 执行后把实际操作, 结果及可复查的材料写进 issue 的 `交付证据` 节. 两者分开, 评审才能区分计划和已验证的事实.

## 行为变更

- 用: 新增或改变外部可观察行为.
- 做法: 从受影响的真实入口运行成品, 观察预期行为. 多分支, 多边界或计算密集的逻辑可另外调用 `tdd` skill 锁住行为.
- 完成证据: 可复跑的环境, 输入与操作步骤 (命令或界面操作), 预期与实际结果 (脱敏后的输出或截图). 单有测试通过或模拟环境的结果, 无法证明真实入口已生效.

## 结构变更

- 用: 外部行为不变, 只改结构, 位置, 命名或类型.
- 做法: 改前选能观察既有行为的检查, 如测试, 快照或可执行脚本. 它改前就应通过; 改动期间保持通过. 类型检查和 lint 只能检查代码形状, 不能单独证明行为保持不变.
- 完成证据: 检查的路径, 改前版本, 相同输入与运行条件, 改前与改后的结果; 两次观察到的行为一致. 需要改变行为时, 按主类归类并交附带验证; 确实可独立交付才另拆 issue.

## 缺陷修复

- 用: 修复已知的失败现象.
- 做法: 调用 `diagnosing-bugs` 找根因, 在修复前得到能暴露原症状的失败检查, 修复后用同一检查和原始场景复跑. 没有合适的测试接缝时, 保留仓库内可复跑的检查脚本, 并记录接缝缺口.
- 完成证据: 修复前跑出原症状的命令与输出 (复现提交先于修复提交落地), 修复后用同一检查与原始场景复跑的通过结果, 以及随修复一起留在仓库的复现检查.

## 性能改进

- 用: 改善可测的性能指标.
- 做法: 先量基线再改, 在可比条件下复测; 按 `benchmark-checklist` 核对公平性和结论边界.
- 完成证据: 前后数字, 运行条件, 测量方法和原始输出, 以及该清单的核查结论.

## 非行为改动

- 用: 注释, 文档或不改变外部行为的配置, 接线和依赖维护. 会改变 agent 实际操作的文档不属本节, 按实际改变的行为归类.
- 完成证据: 与改动直接相关的检查及结果, 如文档引用/渲染检查, 构建, lint 或相关入口运行. 没有适用的检查时, 写明核对过的具体内容以及无法运行检查的原因. 不为凑数造测试或宣称不存在的构建已通过.

## 派发与边界

- 契约在 `to-execution` 拆 issue 时写入 `验证契约` 节; 执行者发现分类错误时报告缺口, 由拆分方修正 issue 后再执行.
- 结构变更的检查可参考 `tdd` skill 的接缝与好测试两节, 但从改前就通过, 无须制造失败.
- 这些证据供执行者自证和评审核对; 最终独立验收仍按已确认的 PRODUCT.md 由 `verify-change` 复核.
