# 验证契约

按这次变更要达到的结果, 从下面五类中选择验证方式, 再决定是否需要编写测试.

## 共用底线

- **边开发边实跑.** 涉及运行行为时, 在隔离测试环境随开发进度运行当前已实现的部分和必要的真实依赖, 从当前可用入口验证. 不必等整个功能完成或启动无关部分, 只对实际跑过的范围下结论.
- **依据已确认要求.** 用例优先取自 PRODUCT.md 已确认的 [Gherkin 场景](../to-spec/GHERKIN.md), 没有时用其他已确认要求. 同时核对技术/审计要求和受影响的旧行为. 要求不清先澄清, 不凭猜测添加用例.
- **按需自动化.** 只有需要长期重复检查或保护复杂行为时, 才新增最少的自动化测试, 通过公开接口验证实际行为. 不以 mock 内部组件后的结果代替真实运行. 已有测试照常运行, 不因此删改. 决定采用测试驱动开发时, 调用 `tdd` skill.
- **安全环境.** 不使用生产环境, 生产服务或真实客户数据. 需要实例而缺少时先搭建, 搭不起来就报告未验证; 涉及费用, 共享资源或不可逆操作先获我批准. 外部服务无法安全调用时可在对接处使用替代实现, 但须说明未真实验证的范围; 关键依赖未验证不能报通过.
- **保留原始数据.** 实跑产生原始数据时, 优先放仓库外并默认保留, 不自动清理或过期; 停止实例也要保留数据. 复跑优先隔离; 必须清理旧数据时先保留可查看的副本, 留不了就停下问我. 其他删除须经我批准, 截图/日志不能替代原始数据.
- **记录证据.** 记录对应要求, 入口操作与输入, 预期与实际结果, 未验证范围及可复查的脱敏原始材料. 实跑还须记录环境和版本; 有原始数据时另记位置和占用.

## 行为变更

- 适用情况: 新增或改变外部可观察行为.
- 做法: 逐项验证本次承诺的全部行为.

## 结构变更

- 适用情况: 对外行为不变, 只改结构, 位置, 命名或类型.
- 做法: 改前确定受影响的公开接口和旧行为, 建立可重复运行的行为检查, 可用已有测试, 命令或脚本. 确认改前通过后才重构, 改后用相同用例, 输入和条件复跑, 检查标准不随内部结构改变. 无法运行或观察结果就停下报告缺口; 类型检查/lint 不能单独证明行为未变.
- 完成证据: 改前版本及相同输入/条件下的前后结果. 同时改变行为时, 补交对应的验证证据.

## 缺陷修复

- 适用情况: 消除已知失败现象.
- 做法: 调用 `diagnosing-bugs` skill.
- 完成证据: 原症状的修复前后对比, 原始场景复跑结果, 留下的可复跑方式及检查缺口; 有复现提交时注明它先于修复提交.

## 性能改进

- 适用情况: 改善可测的性能指标.
- 做法: 先量基线再改, 在可比条件下复测; 调用 `benchmark-checklist` skill 核对公平性和结论边界.
- 完成证据: 基线与改后数字, 可比条件, 测量方法和清单核查结论.

## 非行为改动

- 适用情况: 不改变外部行为的注释, 文档, 配置, 接线或依赖维护. skill/提示词若改变实际操作, 按行为变更验证.
- 做法: 选与改动直接相关的检查; 无适用检查时, 说明核对内容及原因.

## 交付边界

拆 issue 时, `验证契约` 写主要交付结果所属类别及附带验证, `验证入口` 写预定检查和通过标准; 执行后, 按上述证据要求将结果记入 `交付证据`. 无 issue 时同样留证, 分类有误先交拆分方修正后再执行.
本 skill 用于开发者验证当前实现及评审核对, 不代替最终验收. 最终独立验收仍由 `verify-change` 按已确认的 PRODUCT.md 复核.
