# 测试编写规范与抽查验收

## 先区分代码用途

- **功能测试**: 验证系统真实功能是否满足已确认要求, 用来长期防止行为退化. 自动化功能测试接入项目既有测试入口, 有独立预期和能因目标行为错误而失败的断言. 手动执行本身不改变功能测试的身份.
- **手动验证代码**: 为调查环境, 核实外部行为, 验证技术假设或辅助取证而写的代码, 不是验证系统功能的测试. 即使使用 JUnit/pytest 或放在 `test/` 下, 也不能因此算功能测试. 应保留时放项目既有测试目录的手动区域 (如 `test/manual/`, Java 项目沿用自身目录结构), 写清目的, 执行命令, 环境, 判断标准与结论边界; 不接入默认测试发现或 CI, 不混入功能测试用例/通过数量. 不能自动排除时用项目现有分组/标签机制显式隔离.
- **沿用现有技术栈**: 两类代码都优先用项目既有语言, 框架和测试设施. Java 后端已有 Java/JUnit 能完成的验证, 不另写 Bash/Python 验证程序; 使用 shell 启动现有构建/测试命令不算新增验证技术栈. 已有独立测试平台照常复用. 确有能力缺口时先说明现有工具为何做不到, 新技术栈的必要性及维护成本, 经我确认再引入.
- **不为取证造长期负担**: 一次性临时代码不因适合放测试目录就必须提交. 缺陷取证的临时脚本仍按验证契约不提交, 跑完清理. 要长期保留的手动验证代码须有明确复用目的, 不能用来绕过该限制.

## 持久层不得用替身

- 禁止 mock 持久层. 不论测试叫单元测试还是集成测试, 不论直接测 Repository/DAO 接口还是上层服务, 都不能换成 mock/stub, 自写内存假实现或预设结果. `FakeRepository` 用 Map 存取后再读回, 只证明 Fake 正确, 没测项目真实持久层.
- 使用项目真实持久层代码连接隔离测试存储, 加载实际 schema/迁移和必要配置. 优先使用与实际部署相同的存储引擎; 读写, 约束, 事务, 查询及重连后的持久性按本次已确认要求选择验证, 不为此凭空加需求.
- 真正的内存数据库不是自写假 Repository, 但也不能自动等同于部署存储. 例如 H2 不能证明 PostgreSQL 的方言, 锁或事务行为; 内存模式不能证明重启后数据仍在. 只有目标行为不依赖这些差异, 且证据边界写清时才可使用, 不能替代涉及真实存储差异的验证.
- 缺数据库/权限/环境就报未验证和所缺条件, 不降级成假持久层后宣布通过. 使用测试存储仍须遵守 [安全底线](../SAFETY.md), 不触碰生产数据.

## 好测试

**集成式**: 通过真实接口测试. 不 mock 内部部件.

```typescript
// 好: 测试可观察行为
test("有效购物车可以结账", async () => {
  const cart = createCart();
  cart.add(product);
  const result = await checkout(cart, paymentMethod);
  expect(result.status).toBe("confirmed");
});
```

特征:

- 测试用户或调用方关心的行为
- 只使用公开 API
- 能扛住内部重构
- 描述做什么, 不描述怎么做
- 每个测试只有一个逻辑断言
- 数据和状态彼此隔离, 不依赖执行顺序或其他测试残留; 安全保留与清理按安全底线执行
- 失败能指向目标行为; 不靠吞异常, 跳过用例或删除断言把失败变绿

## 坏测试

**实现细节测试**: 绑定内部结构.

```typescript
// 坏: 测试实现细节
test("checkout 调用 paymentService.process", async () => {
  const mockPayment = jest.mock(paymentService);
  await checkout(cart, payment);
  expect(mockPayment.process).toHaveBeenCalledWith(cart.total);
});
```

警示信号:

- mock 内部协作者
- 测试私有方法
- 断言调用次数或调用顺序
- 行为没变, 重构却弄坏测试
- 测试名称描述怎么做, 不描述做什么
- 绕过接口验证

```typescript
// 坏: 绕过接口验证
test("createUser 保存到数据库", async () => {
  await createUser({ name: "Alice" });
  const row = await db.query("SELECT * FROM users WHERE name = ?", ["Alice"]);
  expect(row).toBeDefined();
});

// 好: 通过接口验证
test("createUser 让调用方能读取用户", async () => {
  const user = await createUser({ name: "Alice" });
  const retrieved = await getUser(user.id);
  expect(retrieved.name).toBe("Alice");
});
```

**同义反复测试**: 预期值重述实现. 所以测试按构造通过.

```typescript
// 坏: 用实现同法重算预期值
test("calculateTotal 汇总行项目", () => {
  const items = [{ price: 10 }, { price: 5 }];
  const expected = items.reduce((sum, i) => sum + i.price, 0);
  expect(calculateTotal(items)).toBe(expected);
});

// 好: 预期值是已知字面量
test("calculateTotal 汇总行项目", () => {
  expect(calculateTotal([{ price: 10 }, { price: 5 }])).toBe(15);
});
```

## 测试代码人工抽查验收

这是正式交付前的必做环节, 与产品功能验收分开, 不把测试代码规范塞进 PRODUCT.md 或交给 `verify-change` 代验. 可与正式人工验收同场进行, 但须单列结论; 完成本项不代替逐项产品功能验收.
先核实并记录比较基线与目标提交. 已有评审起点时沿用; 没有 issue/Roadmap 或尚无评审起点时, 核实本次改动前的提交, 无法核实先报缺口. 比较范围覆盖功能测试, 手动验证代码及其夹具, 替身和运行配置的新增/修改/删除/移动, 不只搜索 `test/` 目录. 据实际差异选择分支:

- **无相关变更**: 在验收记录中写明比较范围, 目标提交和无相关变更的依据, 状态记为 "无相关变更". 这些记录齐备即完成本项, 无需我选样或接受, 不执行下列抽查步骤.
- **有相关变更**: 执行下列步骤, 由我选样并核对规范; 完成条件见第 5 步.

1. **准备完整清单.** 作者先按本文件自检全部本轮相关变更. 每项写路径与用例/代码用途, 对应要求或待核实问题, 真实依赖与替换点, 执行入口及实际运行结果/未运行原因. 删除项说明失去的验证及替代位置. 清单与原始证据绑定目标提交, 供我直接选样本, 不只展示作者推荐的好例子. 完成标准: 全部相关变更均已列出, 每项信息齐全且可追溯到目标提交.
2. **由我选样本.** 展示完整清单, 可以建议优先看持久层, 外部依赖, 手动验证代码, 技术栈例外和共用夹具, 但抽哪些及抽多少由我决定, 不硬设比例, 不要求我全看. 完成标准: 我的选样已有记录; 我未在场或尚未选样本时保持待验收, 停在此步.
3. **逐个核对样本.** 展示实际代码, 必要的被测实现/夹具和对应运行记录, 按本文件核对: 测到真实行为和真实持久层没有, 预期是否独立, 断言是否有效, 技术栈是否沿用, 手动验证是否分类隔离. 静态看过不等于运行通过, 全绿也不等于测试写对. 完成标准: 每个样本都有可复查的核对结果, 未抽查范围已标明且未扩大结论.
4. **发现问题就返工.** 我抽到违规后, 作者检查整份清单中同类写法及共用夹具的全部使用处, 不只修样本. 修复并复跑受影响检查, 给出新提交, 清单与结果, 再由我决定复抽范围. 改动使原样本或其依据失效时重新确认, 未影响的已确认结果可注明依据后沿用. 完成标准: 无待处理问题; 发生返工时已有同类排查及修复/复跑证据, 并已回到选样和核对步骤.
5. **记录结论.** 沿用正式验收记录及其产物目录, 单列测试代码验收. 无既有验收记录时才在调用方指定的产物根目录单独留档, 后续验收引用原件, 不另写一份. 写比较范围与目标提交, 完整清单位置, 我选的样本, 发现与同类排查/修复/复跑证据, 未抽查范围及我明确给出的接受/返工结论. 完成标准: 我的明确接受记录与本轮版本对应; 未获接受时保持待验收, 不正式交付或自动关闭.
