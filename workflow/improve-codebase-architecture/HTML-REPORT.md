# HTML 报告格式

## 内容结构

头部给出仓库名称, 日期和本次检查范围. 每个候选使用独立章节, 标题概括拟议变化, 包含:

- **定位与证据**: 相关文件/代码位置, 调用者或测试, 摩擦与删除测试结论.
- **方案与前后对比**: 什么责任会被收进模块, 调用者可以少关心哪些细节, 测试会通过哪里覆盖行为. 涉及依赖时给出依赖类别与测试方式, 分类沿用 `codebase-design` 的深化参考材料.
- **收益与代价**: 预期改善及其依据, 迁移范围, 兼容约束和可能损失的能力.
- **待验证问题**: 缺少的证据, 验证方式及执行情况.
- **建议强度**: 按下方标准给出标签及理由.
- **ADR 关系**: 如适用, 附 ADR 编号或位置, 指出冲突及值得重新审视的理由.

末尾给出首选建议, 链接到对应候选, 说明为何优先于其他候选. 证据不足时, 首选可以是先补证据, 而非立即重构.

## 建议强度

- **强**: 现状摩擦与预期收益有充分依据, 主要代价已查明, 关键未知不影响优先推进该项的判断.
- **值得探索**: 摩擦已证实, 深化方向合理, 收益或可行性仍需验证.
- **推测**: 已有局部证据, 但问题范围或因果仍不明确, 必须指出缺少什么证据.

## 前后对比

每个候选都有前后对比图, 标清"现状"与"设想", 展示调用关系, 责任归属或调用者所需知识的变化, 让图表回答为什么这次深化有用. 同类关系使用一致含义的标记, 所需图例就近给出.
调用次数等数值注明代码或测量依据; 估算标明估算, 未来效果标明预期, 缺乏依据时使用定性描述. 图形大小不充当未经证实的复杂度度量.

## 输出语言

报告全文使用朴素中文; 文件名/路径, 代码标识符和 ADR 编号保持原样. 仅有英文的领域术语首次给出中文译名并括注原文, 后续使用同一译名.
