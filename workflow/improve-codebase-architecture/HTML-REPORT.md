# HTML 报告格式

架构审查报告由 `adaptive-presentation` skill 生成与展示: 自包含 HTML, 临时目录, 视觉风格, 浏览器展示均遵循其规则. 本文件只携带架构报告的内容结构与图表模式增量.

## 头部

仓库名称, 日期, 和简洁图例: 实线框 = 模块, 虚线 = 接缝, 红色箭头 = 泄漏, 粗深框 = 深模块. 不写介绍段落 - 直奔候选.

## 候选卡片

图表承担重量. 文字稀少, 通俗, 使用术语表术语 (来自 `codebase-design` skill) 而不做任何仪式.

每个候选是一个 `<article>`:

- **标题** - 短, 命名这次深化 (例如 "合并订单接入流水线").
- **徽章行** - 建议强度 (`强` / `值得探索` / `推测`), 加上依赖类别标签 (`进程内`, `本地可替代`, `端口与适配器`, `模拟`).
- **文件** - 等宽字体列表.
- **前后对比图** - 核心内容. 两列, 并排. 见下方模式.
- **问题** - 一句话. 什么痛苦.
- **方案** - 一句话. 什么改变.
- **收益** - 条目, 每条 <= 10 个汉字或短语. 例如 "测试命中一个接口", "定价不再泄漏", "删除 4 个浅包装器".
- **ADR 提示框** (如适用) - 警告色提示框中的一行.

没有解释段落. 如果一个图表需要一段文字才能理解, 重画图表.

## 图表模式

全部用内联 SVG 和 HTML+CSS 手工绘制. 混合使用. 不要让每个图表看起来一样 - 多样性是部分目的.

### 流程与依赖图 (主力)

当要点是 "X 调用 Y 调用 Z, 看这一团糟" 时, 用手工方框箭头图: 模块作为带边框和标签的 `<div>` 或 SVG `<rect>`, 箭头作为相对定位容器内绝对定位的内联 SVG `<line>`/`<path>`. 虚线描边表示接缝, 红色边表示泄漏, 深色实心框表示深模块. 往返次数标注在边上 ("之前: 6 次往返; 之后: 1 次").

### 横截面图 (适合分层浅模块)

堆叠水平条带来展示一次调用穿过的层. 之前: 6 个薄层每个什么都不做. 之后: 1 个厚条带标注着合并的责任.

### 体量对比图 (适合 "接口与实现一样宽")

每个模块两个矩形 - 一个表示接口表面面积, 一个表示实现. 之前: 接口矩形几乎与实现矩形一样高 (浅). 之后: 接口矩形短, 实现矩形高 (深).

### 调用图折叠

之前: 一棵函数调用树渲染为嵌套框. 之后: 同一棵树坍缩为一个框, 现在内部的调用在其内部以淡色显示.

## 增量样式

视觉风格遵循 `adaptive-presentation`; 报告只追加:

- 前后对比图并排, 高度约 320px, 不需滚动即可同屏对比.
- 图表内模块标签用小号字加宽字距 (英文标签用大写), 读作示意图, 不是界面.
- 颜色纪律: 红 = 泄漏, 警告色 = ADR 冲突, 一个强调色渲染建议强度徽章; 其余用低饱和自然色.

## 首选建议部分

一个更大的卡片. 候选名称, 一句话说为什么, 锚点链接到其卡片. 就这样.

## 输出语言

报告全文使用中文: prose, 徽章, 图例, 图表标注一律中文, 不允许整句或整段英文. 三类例外保持原样: 文件名/路径, 代码标识符, ADR 编号.

上游 `codebase-design` skill 的术语仍以英文定义, 进入产物时必须按下表翻译:

| 英文 (上游定义) | 产物中写作 |
| --- | --- |
| module | 模块 |
| interface | 接口 |
| implementation | 实现 |
| deep / shallow | 深 / 浅 |
| depth | 深度 |
| seam | 接缝 |
| adapter | 适配器 |
| leverage | 杠杆 |
| locality | 局部性 |
| mock | 模拟 |

领域术语表中的英文术语同样翻译成中文, 首次出现时括注英文原文 (如 "订单 (Order)"), 后续只用中文.

## 语气

朴素中文, 简洁 - 架构名词和动词使用上表的中文译法, 与 `codebase-design` skill 一一对应. 简洁不是漂移的借口.

**精确使用:** 模块, 接口, 实现, 深度, 深, 浅, 接缝, 适配器, 杠杆, 局部性.

**绝不替换:** 组件, 服务, 单元 (指模块) * API, 签名 (指接口) * 边界 (指接缝) * 层, 包装器 (指模块, 当你意指模块).

**符合风格的表述:**

- "订单接入模块是浅的 - 接口几乎与实现匹配."
- "定价在接缝上泄漏."
- "深化: 一个接口, 一个测试的地方."
- "两个适配器证明接缝: 生产中 HTTP, 测试中内存."

**收益条目** 用术语表术语命名收益: *"局部性: bug 集中在一个模块中"*, *"杠杆: 一个接口, N 个调用点"*, *"接口缩小; 实现吸收包装器"*. 不写 *"更容易维护"* 或 *"更干净的代码"* - 这些术语不在术语表中, 没有挣到它们的位置.

不做含糊其辞, 不做开场铺垫, 不写 "值得注意的是...". 如果一句话可以成为条目, 让它成为条目. 如果一个条目可以削减, 削减它. 如果一个术语不在 `codebase-design` skill 术语表中, 在发明新术语之前寻找一个已存在的.
