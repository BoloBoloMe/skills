# 改进代码库架构

发现架构摩擦并提出 **深化机会** - 将浅模块重构为深模块的变更. 目标是可测试性和 AI 可导航性.

本 skill 受项目领域模型启发, 并建立在共享设计词汇之上:

- 调用 `codebase-design` skill 获取架构词汇 (**模块**, **接口**, **深度**, **接缝**, **适配器**, **杠杆**, **局部性**) 及其原则 (删除测试, "接口是测试表面", "一个适配器 = 假想接缝, 两个 = 真实"). 在每个建议中精确使用这些术语 - 不要混用 "组件", "服务", "API" 或 "边界".
- `docs/language/UBIQUITOUS_LANGUAGE.md` 中的领域语言为好的接缝赋名. 多上下文项目先读取 `docs/language/UBIQUITOUS_LANGUAGE_MAP.md`. `docs/adr/` 中的 ADR 记录了本 skill 不应重新审视的决策.

## 流程

### 1. 探索

首先阅读项目的领域术语表: 单上下文项目读取 `docs/language/UBIQUITOUS_LANGUAGE.md`; 多上下文项目先读取 `docs/language/UBIQUITOUS_LANGUAGE_MAP.md`, 再读取相关 `docs/language/contexts/*.md`. 同时阅读你正在触及区域的 ADR.

然后直接探索代码库. 如需分派只读探查子代理压缩上下文, 若当前运行时明确支持只读委派, 可委派探查子代理; 否则当前会话直接探索并产出同样结果. 不遵循死板启发式 - 自然探索, 注意经历摩擦的地方:

- 理解一个概念需要在许多小模块之间跳转?
- 模块是 **浅** 的 - 接口几乎与实现一样复杂?
- 纯函数仅为可测试性而被提取, 但真正的 bug 藏在它们的调用方式里 (没有 **局部性**)?
- 紧密耦合的模块跨它们的接缝泄漏?
- 代码库哪些部分未经测试, 或难以通过当前接口测试?

对你怀疑是浅模块的任何东西应用 **删除测试**: 删除它会集中复杂性, 还是只是移动它? 回答"是, 集中了"才是你想要的信号.

### 2. 将候选呈现为 HTML 报告

调用 `adaptive-presentation` skill 呈现报告: 自包含 HTML, 临时目录, 视觉风格和浏览器展示都由它负责, 不会有任何东西落入仓库.

每个候选获得一个 **前后对比可视化**. 强调可视化.

对每个候选渲染一个卡片, 包含:

- **文件** - 涉及哪些文件/模块
- **问题** - 当前架构为什么产生摩擦
- **方案** - 用通俗语言描述什么会变化
- **收益** - 以局部性和杠杆解释, 以及测试会如何改善
- **前后对比图** - 并排, 自定义绘制, 展示浅模块和深化
- **建议强度** - `强`, `值得探索`, `推测` 之一, 渲染为徽章

报告末尾以 **首选建议** 章节收尾: 你会先处理哪个候选以及原因.

**使用 `docs/language/UBIQUITOUS_LANGUAGE.md` 或相关 `docs/language/contexts/*.md` 词汇指代领域, `codebase-design` skill 词汇指代架构.** 如果词汇表定义了 "订单", 说 "订单接入模块" - 不是 `FooBarHandler`, 也不是 "订单服务".

**ADR 冲突**: 候选与现有 ADR 矛盾时, 仅在摩擦足以值得重新审视该 ADR 时才展示. 在卡片中清楚标记 (例如警告提示: _"与 ADR-0007 矛盾 - 但值得重新打开, 因为..."_). 不要列出 ADR 禁止的每一个理论重构.

内容结构与图表模式见 [HTML-REPORT.md](HTML-REPORT.md); 样式与展示规则以 `adaptive-presentation` 为准.

**报告全文使用中文.** 英文术语 (含 `codebase-design` 词汇和领域术语表中的术语) 进入产物时译为中文, 对照表和例外见 [HTML-REPORT.md](HTML-REPORT.md) 的输出语言节.

**不要** 此时提出接口. 报告展示后, 询问我: "你想探索哪一个?"

### 3. 盘问循环

我选定一个候选后, 调用 `grilling` skill 与我一起走设计树 - 约束, 依赖, 深化后模块的形状, 接缝背后是什么, 哪些测试保留.

副作用在决策结晶时内联发生 - 调用 `domain-modeling` skill 保持领域模型随行更新:

- **用不在领域语言文件中的概念命名一个深化后的模块?** 调用 `domain-modeling` skill, 将术语添加到 `docs/language/UBIQUITOUS_LANGUAGE.md` 或相关 `docs/language/contexts/*.md`. 文件不存在则惰性创建.
- **在对话中打磨了一个模糊术语?** 调用 `domain-modeling` skill, 在对应领域语言文件中更新.
- **我以有力理由拒绝了候选?** 提议 ADR, 表述为: _"记为 ADR 吗? 这样未来架构审查不会再建议它."_ 仅当该理由确实需要让未来探索者避免重复建议同一方案时才提议 - 跳过短暂理由 ("目前不值得") 和不言自明的理由.
- **想为深化后的模块探索替代接口?** 调用 `codebase-design` skill 及其 "设计两次" 并行子代理模式.
