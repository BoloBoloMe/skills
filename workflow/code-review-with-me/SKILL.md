# 带我评审代码

交互式代码走读的操作规范. 核心目标: 协助我对代码建立充分了解.

## 回复风格

电报文: 短,准,密. 删客套/铺垫/修饰/转折/比喻/语气词. 保留结论/原因/动作/风险/必要连接成分 (了/的/是/会/要/把/被/但/而/再/先/后/因/故). 仅压缩表达, 不省略思考.

## 阶段 1 - 明确边界与模式推断

1. 根据会话内容推断需要 review 的代码范围和模式 (全量/diff/PR), 向我确认.
2. **委派子代理**完成代码库探索, 主会话只收结构化摘要. 子代理产出物必须写入产出物目录下的 `subagent/` 子目录:
   - 全量: 目录扫描, 入口识别, import 依赖图, 层级定位 → 输出模块关系简图 + 文件清单
   - diff: 解析 diff, 对每个变更文件查看变更点所在完整函数/方法体及调用者和被调用者, 识别是否触及接口/契约层 → 输出变更文件清单 + 每文件变更摘要
   - PR: 读 PR 描述/title/关联 issue + diff 解析 + 按文件性质分类 (新增文件→全量, 变更文件→diff) + PR 额外检查 (描述一致性/遗漏文件测试/commit 粒度)
3. 向我展示模块关系简图和 review 计划, 确认后你将 review 计划写入产出物目录 (`review-plan.md`). 画图规则:
   - 默认用 ASCII box 图, 可混用纯文本箭头链补充细节
   - 交叉密集的局部生成落盘 Mermaid 文件 (路径: 产出物目录/`模块关系图.mermaid`), 主会话用 box 图展示骨架并指引我查看 Mermaid 文件
   - 子模块过多时分层输出, 先顶层后展开
4. 确定产出物目录: `docs/reviews/YYYY-MM-DD-<简短标识>/` (无 `docs/` 时创建). 见 [REFERENCE.md](REFERENCE.md) 中的模板.

## 阶段 2 - 逐段走读

从执行入口开始, 沿调用链深度优先, 一次 ~50 行. PR 模式按文件分流: 新文件走全量, 变更文件走 diff.

### 片段选取策略

- 全量: 调用链优先, 自上而下
- diff: 变更影响优先, 从变更点向外扩散
- 我指定入口时从指定位置开始

### 文件引用规范

格式: `[文件名:开始行号 ~结束行号](相对路径:开始行号 ~结束行号)`, 行号用 `:` 分隔 (禁用 `#L`). 路径以 cwd 为基准, 不能含空格或特殊字符. 不用 inline code (`path`) 代替链接.

示例: `[Foo.java:32 ~51](src/main/java/com/example/Foo.java:32 ~51)`

### 交互循环

每个片段:
1. 按文件引用规范指引我去看代码位置, 不要复述代码内容. 一次只指引一处. 然后给出要点提炼 (风险/权衡/隐患/错误/参考资料, 省略次要信息)
2. diff 模式额外关注: 变更是否安全, 是否对原逻辑造成破坏性修改, 是否超出声明边界
3. 询问我的评价, 给出选项. 以下是选项的参考, 不要机械模仿, 按实际情况组织. 在问题的前面之前显示当前进度: `已审片段数/计划总片段数`
   - A. 赞成, 看下一段
   - B. 反对, 补充评论
   - C. 仍有疑问
   - D. 跳过, 这段不重要
   - E. 展开更多细节
4. 将审查结果追加到 `<代码评审日志.md>` (模板见 [REFERENCE.md](REFERENCE.md)). 若我的结论是要改实现且讨论过较复杂方案, 方案记录要具体 (目标/改动点/取舍/遗留问题)

### 中断恢复

你启动时先检查产出物目录是否存在未完成的日志. 若有, 你读取日志从最近未审片段继续.

## 阶段 3 - 人审报告

所有片段走完后编写 `<人审报告.md>` (模板见 [REFERENCE.md](REFERENCE.md)), 包含:
- 风险评级 (高/中/低) + 一句话结论
- 发现汇总表 (文件/行号/类型/严重度/描述)
- 建议行动项 (编号列表)
- 评审过程统计 (总片段数/已审/跳过/待定)
