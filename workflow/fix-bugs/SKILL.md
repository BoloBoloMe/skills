# 修复 bug

修 bug 的统一链条对所有 bug 一样, 不分大小: 复现 → 定位原因 → 制定修复方案 → 执行修复 → 验证修好且没改坏. 完成证据见 skill `verification-contract` 缺陷修复节: 红态真出现过, 修复后同一检查通过, 原始场景复跑.

本 skill 是这条链在难 bug 上的详细手法: 阶段 3, 4 在循环足够锐利时可按需跳过, 其余阶段只有理由明确时才允许跳过; 复现与验证没改坏的复核不可省.

探索代码库时, 调用 `domain-awareness` skill 感知当前工作目录的领域模型, 并查阅所触及区域的 ADR. 开始复现前若尚未读过 `verification-contract` skill, 调用它; 已读则复用其共用底线及缺陷修复证据要求, 不重复调用.

## 分工

调用本 skill 的会话是调度方: 只分派与收口, 不亲自复现, 不写代码. 下设三个角色:

- **诊断者**: 在真实路径上复现并最小化, 定位根因. 交付根因报告, 可复跑的复现命令或步骤, 以及复现环境的真实程度 (哪些是真实依赖, 哪些是替身, 有无缺口). 不修.
- **修复者**: 按根因定方案 (阶段 5) 并修 (阶段 6), 按方案审核条件决定是否先给我审, 修后跑复现命令, 原始场景与受影响基线.
- **复核者**: 未参与前两步, 独立执行阶段 7, 核对替身没越界, 出复核报告.

简单 bug 允许把诊断者与修复者合成一人; 复核者不可省.

## 阶段 1: 构建反馈循环

**这是本 skill 的核心**, 其余都是机械动作. 有一个 *紧凑 (tight)* 的判红信号 (能在这个 bug 上变 *红 (red)* 的 pass/fail 信号), 就找得到原因: 二分, 假设检验, 插桩都只是在消费它. 没有它, 盯多久代码都没用.
在这里投入不成比例的精力. **激进, 有创造力, 拒绝放弃.**

### 选择构建方式

按能否抓住真实症状和运行成本选择, 以下方式没有固定优先顺序:

- **curl / HTTP 脚本**, 打向运行中的 dev server.
- **CLI 调用**, 喂 fixture 输入, 把 stdout 与已知正确的快照 diff.
- **无头浏览器脚本**, 驱动 UI 并断言 DOM/console/network.
- **重放捕获的 trace**: 把真实网络请求/payload/事件日志存盘, 隔离地重放经过代码路径.
- **已有测试或针对性检查**, 通过能抓住故障的公开接口触发实际代码.
- **一次性 harness**: 拉起能保留真实故障链路的最小子系统, 用一次调用触发症状.
- **属性/fuzz 循环**: bug 是 "输出有时错" 时, 跑 1000 个随机输入找失败模式.
- **二分 harness**: bug 出现在两个已知状态 (commit, 数据集, 版本) 之间时, 自动化 "在状态 X 启动, 检查, 重复", 供 `git bisect run` 消费.
- **差分循环**: 同一输入分别跑旧版本与新版本 (或两套配置), diff 输出.
- **HITL 脚本**, 最后手段: 必须人来点时, 用 `scripts/hitl-loop.template.py` 驱动人, 循环仍保持结构化, 捕获的输出回流给你.

构建出对的反馈循环, bug 就修好了九成.

### 收紧循环

把循环当产品打磨. 有了一个循环之后, **收紧 (tighten)** 它:
- 能更快吗? 缓存 setup, 跳过无关初始化, 收窄测试范围.
- 信号能更锐利吗? 断言具体症状, 而不是 "没崩".
- 能更确定吗? 固定时间, 固定随机种子, 隔离文件系统, 冻结网络.

30 秒还 flaky 的循环比没有循环好不了多少; 2 秒确定的循环才是 *紧凑* 的, 是调试超能力.

### 非确定性 bug

目标不是干净的复现, 而是**更高的复现率**. 把触发循环 100 次, 并行, 加压, 收窄时序窗口, 注入 sleep. 50% 抖动的 bug 可调试, 1% 不行. 持续提高复现率, 直到可调试.

### 确实建不出循环时

停下并明说, 列出试过的方法. 向我要: (a) 能复现的环境的访问权, (b) 脱敏后的捕获工件 (HAR, 日志转储, core dump, 带时间戳的录屏), 或 (c) 添加临时生产插桩的许可.

### 完成标准: 一个能变红的紧凑循环

循环 *紧凑* 且 *可变红 (red-capable)*: 你能指出**一条命令** (脚本路径, 测试调用, curl), 它**已至少跑过一次** (展示调用与脱敏后的输出), 且满足:
- [ ] **可变红**: 驱动真实的 bug 代码路径, 断言**我描述的确切症状**, 因此能在这个 bug 上变红, 修好后变绿. 不是 "跑完没报错"; 必须能抓住这个具体的 bug.
- [ ] **确定**: 每次运行同一结论. flaky bug 按上文要求, 固定的高复现率.
- [ ] **快**: 秒级, 不是分钟级.
- [ ] **agent 可运行**: 你能无人值守地跑; 需要人时只通过 `scripts/hitl-loop.template.py`.

如果你发现自己在命令存在之前就读代码建理论, **停**: 直接跳假设正是本 skill 要防的失败. 没有可变红命令, 不进阶段 2.

## 阶段 2: 复现 + 最小化

跑循环, 看它随 bug 出现而变红. 确认:
- [ ] 循环产出的是**我描述的**失败模式, 不是恰好相邻的另一个失败. 诊断错 bug = 修错 bug.
- [ ] 失败多次运行可复现; 非确定性 bug 复现率达阶段 1 要求.
- [ ] 已捕获确切症状, 供后续阶段验证修复真的对症.

### 最小化

变红后, 把复现缩减到**仍然变红的最小场景**. 输入, 调用方, 配置, 数据, 步骤, **一次只砍一个**, 每砍一刀重跑循环, 只留对失败起支撑作用 (load-bearing) 的部分.
为什么值得: 最小复现收窄阶段 3 的假设空间 (可疑的活动部件更少), 并为阶段 6 提供修复前后对照的检查.
完成标准: **每个剩余元素都是 load-bearing**: 删掉任何一个, 循环变绿.
未复现且未最小化, 不继续.

## 阶段 3: 假设

先产出 **3-5 个排序过的假设**, 再测试其中任何一个. 只产一个假设会锚定在第一个看似合理的想法上.
每个假设必须**可证伪 (falsifiable)**: 说出它的预测.
> 格式: "若 <X> 是原因, 则 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更严重."
说不出预测的假设是直觉, 丢弃或磨利它.
**测试前把排序列表给我看.** 我常有领域知识能瞬间重排 ("我们刚部署了对 #3 的改动"), 或知道哪些已排除. 便宜的检查点, 省大量时间. 不必阻塞: 我不在时按你的排序继续.
完成标准: 每个假设都可证伪并带有预测; 排序列表已给我看过.

## 阶段 4: 插桩

每个探针必须对应阶段 3 的某个具体预测. **一次只改一个变量.**
工具偏好:
1. **调试器 / REPL 检查**, 环境支持就用. 一个断点胜过十条日志.
2. **定向日志**, 只打在能区分假设的边界上.

**每条调试日志打唯一前缀**, 如 `[DEBUG-a4f2]`. 收尾清理就是一次 grep: 没标签的日志会存活, 有标签的会死.

**性能分支.** 性能回归时日志通常是错的工具. 改为: 先建立基线测量 (计时 harness, `performance.now()`, profiler, 查询计划), 再二分. 先测量, 后修复.
完成标准: 每个假设已被证实或排除; 幸存假设指向根因, 且证据来自一次只改一个变量的探针.

## 阶段 5: 制定修复方案

根因确定后先写清方案再动手. 方案含: 改动点, 影响范围, 备份与回滚考虑.

以下任一条成立, 先把方案给我看, 得到答复再修:

- 改变对外可观察行为或既有约定 (接口, 数据格式, 配置项, 错误语义, 默认值).
- 要动共享接口, 跨模块路径或数据迁移.
- 有多条可行路线且取舍靠产品判断, 或要放弃现有功能.
- 触碰安全, 权限, 删除与数据保留语义.
- 隔离环境造不出复现, 需要生产数据, 生产插桩或新权限.
- 与已确认 spec 或决策冲突, 需要改标准.

一句话判据: 只有 "纯修错, 不动对外行为, 不超边界, 不碰安全" 才由你自行修.
完成标准: 方案已写出改动点, 影响范围与回滚考虑; 命中上述任一条时已给我看过并拿到答复.

## 阶段 6: 执行修复与复验

沿用已建立的复现检查: 改前已抓住原症状, 应用修复后同一检查通过, 再用原始 (未最小化的) 场景重跑阶段 1 的反馈循环.
诊断时反复运行检查, 不等于必须新增一份长期测试. 是否将复现长期保留为自动化回归测试, 按已调用的 `verification-contract` 共用底线判断. 不新增测试时, 保留可复跑命令或步骤.
回归测试须以故障真实发生的方式覆盖同一故障, 确认它能抓住修复前的症状并在修复后通过. 没有能覆盖故障的接口时记录缺口, 保留原复跑方式, 不用抓不住故障的测试顶替.
完成标准: 修复后同一检查通过, 原始 (未最小化) 场景复跑通过; 回归测试已保留, 或接口缺口与可复跑方式已记录.

## 阶段 7: 验证没改坏

由复核者 (未参与诊断与修复) 独立审查本次修复的影响面:

- 核对修复差异, 按复现指向的路径追调用方与合作方.
- 必要时跑项目既有检查或真实入口; 不强制跑自动化测试.
- 涉及共享接口, 数据格式或跨模块路径时, 调用 `blast-radius` skill 深查.

报告中写明检查了什么, 用了什么手段, 覆盖不到哪里. 覆盖不到的写缺口, 不宣称 "没改坏".
完成标准: 复核报告含差异核对, 受影响面, 所用手段与缺口; 在阶段 8 清理前完成.

## 阶段 8: 清理

宣布完成前必须:
- [ ] 原始复现不再复现 (重跑阶段 1 循环).
- [ ] 阶段 7 复核报告已出, 缺口已写明.
- [ ] 已保留可复跑命令或步骤; 新增的回归测试已通过, 接口缺口已记录.
- [ ] 所有 `[DEBUG-...]` 插桩已移除 (grep 前缀验证).
- [ ] 无关的一次性调试代码已删除, 或移到明确标记的调试位置; 可复跑检查及实跑产生的数据和证据仍保留.
- [ ] 被证实正确的假设写进了 commit / PR 信息, 让下一个调试者受益.
