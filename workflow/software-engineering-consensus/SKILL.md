# 软件工程共识

## 验证与验收

**验证**是按已确认标准, 在明确的版本, 环境, 输入和入口下检查结果, 并留下可复查证据. 结论只适用于实际检查的范围, 可记为通过, 失败或未验证.

**验收**是需求提出方依据已确认标准和验证证据决定是否接受交付. 在本工作流中, 只有我能验收. LLM 可验证并报告结果, 但报告不等于验收, 不能代我决定. 未验证或未达标的交付不能判为验收通过.

以终为始是需要贯彻的原则: 动手写代码前先通过 `verification-contract` skill 明确如何验证成品.

## MVP

MVP 是能让目标用户实际使用, 检验核心价值的最小产品. 每版交付可实际使用的软件, 以及本版验证通过的可复查证据.
最小表示本版范围小, 本版已确认的功能, 权限, 数据或性能等要求仍须全部满足. 通过当前全部标准才算交付; 未通过时继续修正当前版本, 不把补齐工作称为下一次迭代.
验证按已确认的当前标准从真实使用入口进行: 功能看实际操作结果, 性能看实测数字, 数据要求看实际数据. 自动化测试或人工检查按标准选择, 测试全绿本身不等于可交付.

## PoC

PoC 验证某个技术方案能否做成. 交付明确方案在明确条件和判断标准下可行/不可行的实测结论, 以及真实实验依据.
依据须能复查所测方案, 待回答的问题, 实验条件和判据, 实际操作与结果, 结论的适用范围. 实验代码是支撑结论的材料, 不承诺可直接成为产品.
验证须用能区分可行与不可行的真实实验. 设计推断或演示效果不能代替技术实测; 方案 A 在条件 X 下达不到要求, 不等于所有方案都做不到.
环境或权限等原因导致实测未完成时, 记为未证实并保持未完成, 不能报不可行. 换成方案 B 是验证另一个方案, 不叫同一个 PoC 的下一次迭代.

## demo

demo 是演示用途: 让人看清指定的样子, 行为或过程, 支撑讨论和决策. 可以展示已交付的 MVP, PoC 结果或专门制作的样品.
检查它是否准确呈现要讨论的内容, 足以让我判断. 可用假数据或简化实现, 同时说明真实行为与演示部分.
演示活动不新增产品交付承诺, 不改变被演示软件原有的交付身份. 演示成功不自动证明技术可行或产品达到交付标准.
可以保留演示文件和必要说明供回看, 这些材料不作产品交付. 调整演示不叫迭代.

## 迭代

迭代只属于 MVP: 当前版本通过当前全部标准并交付后, 要求/判据变化才产生下一次迭代; 下一版也须通过对应的新标准才算交付.
需求变更导致标准变化是一个例子. 同一标准下的修错, 返工或补齐未完成要求仍是当前版本的修正. 只换验证方法也不触发新迭代: 要求从响应 100ms 改为 50ms 是标准变化, 仍要求 100ms 而换工具或增加测量次数是方法变化.
PoC 换方案是验证另一个方案, demo 修改是调整演示. 版本编号本身不表示交付已达标.

## 垂直切片

tracer bullet. 一次交付的工作切片, 本身端到端走通, 能从真实入口独立验证, 完成时即可演示. 切片穿过哪些层不构成判据.
_避免_: 水平切片 (按层或按模块分期, 单期完成时演示不出任何完整结果), 任务分解

## 权威输入

产物编写必须依据的上级输入文档集, 典型成员: PRODUCT.md / TECHNICAL.md / DECISIONS.md. 优先级: spec 优先于决策账本 (spec 是决策的提炼产物, 直接读账本费 token). 冲突时停止并盘问我, 不自行改写权威方.
_避免_: 把会话中的口头指示当权威输入 (未落盘者不是); 绕过优先级直接读账本 (有 spec 时)

## 交付单元

共用同一组已确认要求和验证依据的一次交付工作. 可以跨多个不同类型的里程碑, 这些里程碑共用一个产物根目录; 不同交付单元可用不同目录.
_避免_: 单个里程碑 (交付单元可以包含多个里程碑), 单次会话 (会话不是交付边界)

## 产物根目录

本变更所有产物的落盘根目录, 默认 `docs/changes/<feature-slug>/`, 调用方可指定其他; navigate 使用里程碑的 `output_dir`, 同一交付单元的多个里程碑共用一个根目录, 不按里程碑编号强制分目录. 本变更产物 (**权威输入**, 执行拆分) 间的相对引用都基于它解析; 外部信源与上游决策账本按实际位置解析.
_避免_: 假设信源/账本一定在根目录内; 把 `issues/` 等子目录产物当根目录直属文件
