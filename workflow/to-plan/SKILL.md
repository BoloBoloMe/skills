# To Plan

为 prd 下的所有议题生成合并源码级执行计划并写入落盘文档, 人类审核通过后, AFK agent 按计划执行.

## 流程

### 1.读取输入

基于对话上下文中已有的任何内容开展工作.如果用户传入了议题引用(议题编号/URL 或路径)作为参数,请从议题跟踪器获取该议题,并阅读其完整正文和评论.

### 2. 聚焦代码探索

基于议题描述中的领域术语和模块名, 在代码库中做聚焦搜索, 确定每个议题的代码修改边界. 以议题为维度组织探索结果, 不要求全局代码扫描.

对于修改边界不确定的情况, 标注到 PLAN.md 对应议题的风险点中.

### 4. 生成 PLAN.md

按下方模板生成 PLAN.md

输出后向用户展示 PLAN.md 路径和内容摘要 (涉及文件总数, 风险概览).

## PLAN.md 模板

```markdown
# 执行计划

> 基于 PRD: `path/to/PRD.md`

## 交叉风险概览

<!-- 列出被多个议题共享的文件, 标注重叠/相邻修改区域 -->

| 文件 | 涉及议题| 重叠级别 |
|------|-----------|---------|
| `path/to/file` | issue-a, issue-b | 同一函数 / 相邻区域 / 同文件不同区域 |

<!-- 若不存在共享文件冲突, 写 "无交叉风险." -->

## 议题执行计划

<!-- 按议题依赖关系和推荐执行顺序正序排列. 每个议题一个 section. -->

### <issue 标题>
> 基于议题: `path/to/issue`

#### 变更列表

<!-- 采用用双层列表结构: 外层为需要变更的代码层, 内层为代码层内需要变更的文件列表 -->
<!-- 按项目实际架构动态命名层名, 只写涉及变更的层, 如 Controller / Service / Dao -->
<!-- 文件变更类型分四类: 修改 / 新增 / 删除 / 只读参考 -->

##### <层名>

**修改** (路径 + 关键符号 + 关键行号):

- `path/to/file` -- `ClassName.methodName()` (L45~L72): <概要变更意图>
- `path/to/file` -- `functionName()` (L100~L130): <概要变更意图>

**新增** (路径 + 职责概要):

- `path/to/new/file` -- <该文件的预期职责>

**删除** (路径):

- `path/to/old/file`

**只读参考** (路径, 实现时需理解但不修改):

- `path/to/reference/file`

#### 议题测试用例清单

<!-- 针对议题功能边界 (深模块) 的测试用例清单, 不要深入边界内部的具体的代码细节 (浅模块) -->

#### 风险点

<!-- 高/中/低 三档 + 缓解建议 -->

- **[高/中/低]** <风险描述>. 缓解: <建议措施>
```
