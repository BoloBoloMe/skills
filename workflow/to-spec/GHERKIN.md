# Gherkin 书写规范参考

本文件是 `to-spec` skill 的补充参考, 管 PRODUCT.md 验收标准 Gherkin 块的书写细节; 模板形态与机检触发时机见 `SKILL.md`. 全部检查遵守本 skill 的[达标标准与检查边界](SKILL.md#达标标准与检查边界), 现有机检要求不变.

## 1. 语法子集

`验收标准` 节为单个 ```gherkin 代码块: 首行 `# language: zh-CN`, 次行 `功能: <变更标题>`, 其后为全部场景. 单块自身即完整可解析单元, 未来抽出即为合法 .feature 文件.

### 允许的关键字与最小示例

关键字使用官方 zh-CN 集:

| 关键字 | 用途 |
|---|---|
| `功能:` | 块头, 次行, 值为变更标题 |
| `背景:` | 全部场景共享的公共前提 |
| `场景:` | 单个场景 |
| `场景大纲:` | 参数化场景, 配 `例子:` |
| `例子:` | 场景大纲的参数表 |
| `假定` | Given 步骤 |
| `当` | When 步骤 |
| `那么` | Then 步骤 |
| `而且` | And 连接步骤 |
| `但是` | But 连接步骤 |

```gherkin
# language: zh-CN
功能: 补发优惠券

背景:
假定 客服已获得补券权限

@AC-001 @normal @G-001
场景: 客服为订单首次补券
假定 订单 A100 尚未补发过优惠券
当 客服为订单 A100 申请补券
那么 系统发放优惠券, 订单 A100 的累计补发次数为 1

@AC-002 @edge @G-001 @BR-002
场景大纲: 单笔订单的补券次数限制
假定 订单 A100 已补发 <次数> 次优惠券
当 客服为订单 A100 再次申请补券
那么 <结果>

例子:
| 次数 | 结果 |
| 2 | 系统发放优惠券, 订单 A100 的累计补发次数为 3 |
| 3 | 系统拒绝申请, 订单 A100 的累计补发次数仍为 3 |
```

### 关键字只认一种写法

关键字只认上表写法. 官方 zh-CN 集里的同义词与非官方写法都由 `check-ac.py` 的白名单拒绝, 报错后按上表改写; `规则:` 与英文关键字同样只由该白名单拦截. 业务规则归属只靠 `@BR-NNN` 标签表达.

## 2. 标签约定

标签集封闭, 只允许以下三类, 禁止自由标签. 反模式根源见旧格式实例: 自由散文 AC 无标签面, 机检无从下手.

| 标签 | 含义 | 基数约束 |
|---|---|---|
| `@AC-NNN` | 场景所属验收标准 | 每场景恰好一个; 同一 AC 的状态分支场景共用同一标签 |
| `@G-NNN` `@BR-NNN` | 覆盖关系 (目标/业务规则) | 每场景至少一个; AC 的覆盖关系取其全部场景标签的并集 |
| `@normal` `@failure` `@edge` | 区分正常/失败/边界场景 | 建议按行为标注; 机检不强制基数, 不单为数量返工 |

`@G-NNN`/`@BR-NNN` 引用的编号必须在 PRODUCT.md 的 `目标`/`业务规则` 节真实存在, 且 `@BR-NNN` 只能引用领域规则条目, 不得指向标 `(审计)` 的审计式断言; 两条均由机检对账.

1 AC = 1..N 场景: 同一 AC 下的状态分支场景共用同一 `@AC-NNN`; 场景大纲计为一个场景. 不在落盘时拆 AC: 拆分等于在用户确认之外做语义切分.

常见标签错误 (均被机检拒绝):

```gherkin
# 反例: 伪标签, 自由标签, 一景多 AC 标签
@AC-001 @AC-002 @例子 @smoke
场景: 错误示范
```

- `@例子`: 伪标签, 不是封闭集成员.
- `@smoke`: 自由标签, 开放标签是腐烂起点.
- 同时挂 `@AC-001 @AC-002`: 违反每场景恰好一个 AC 标签; 若确属两条 AC 的行为, 应拆成两个场景, 各归其 AC.

## 3. 书写纪律

- 正文直接用我能读懂的大白话: 不查实现代码也能判断已有情况, 做什么及应该看到什么. 领域用词保持准确, 陌生词首次出现时就地解释. 阅读卡片只换排版, 可读性必须在原文中解决.
- 角色和指代明确: 优先用领域角色名词, 让场景自包含并与项目 ubiquitous language 对齐; 仅在指代会造成误解时改写.
- 优先用声明式步骤表达行为结果, 不为描述交互而补内部实现细节; 已确认要求涉及具体 UI 操作时如实表达.
- 每个场景表达清楚刺激与响应的对应关系, 优先单个 `当`; 多个独立行为导致结果归属不清时拆成多场景, 共用 AC 标签, 不单为步骤数量拆分.
- `那么` 只写外部可观察结果: 可被产品层观察的行为/状态, 不写实现细节 (如内部函数返回值).
- 影响通过与否的数据须确定: 已确认的范围, 阈值和预期值写全, 不用"超时后"代替已确认的 `24h`. 不影响行为判断的测试数据可在执行时准备, 不为填数值新增产品决策. 多组数据可用场景大纲 + `例子:` 表.
- 分支条件与预期结果一一对应: 条件逻辑使适用前提或结果不清时拆分场景, 可用 `@failure`/`@edge` 区分类型; 不为等价表达反复重组场景.
- `背景:` 仅用于真正公共前提: 只有全部场景都需要的公共前提才进 `背景:`; 部分场景需要的前提写在各自场景的 `假定` 中.
- 写不成刺激-响应行为的审计式断言 (如"未引入认证") 不进场景, 归入 PRODUCT.md 的 `业务规则` 节并在末尾标 `(审计)`; 转得了行为的断言必须写成场景.

主会话按本 skill 的[达标标准与检查边界](SKILL.md#达标标准与检查边界)检查上述内容; 脚本通过不代表语义正确, 偏离推荐写法本身也不构成返工理由.

## 4. 校验方法

草稿/正式校验及 `ac-draft.py` 均复用同目录 `check-ac.py` 的验收规则; 预览另检查能否完整展开, 不代替正式校验. 路径按当前 skill 目录解析:

```bash
uv run <skill 目录>/check-ac.py <PRODUCT暂存稿> --draft <验收草稿>
uv run <skill 目录>/check-ac.py <PRODUCT.md 路径>
```

草稿仅含一个完整 Gherkin 代码块及首尾空白, 不含节标题, 确认标记或其他正文. 暂存稿提供真实的 `目标`/`业务规则`, 并保留唯一的 `验收标准` 节作为嵌入位置. 草稿模式在内存中组合两者, 只豁免确认标记, 不写入正式文件.

校验项:

1. Gherkin parser 解析.
2. 标签封闭集与 `@AC` 唯一性.
3. 覆盖完整性: 每个 AC 至少一个场景, 每个场景至少一个覆盖标签.
4. 关键字白名单: 禁 `规则:`, 禁同义变体, 只认 §1 选定的唯一写法.
5. 标签位置限定: 标签只允许出现在场景/场景大纲行.
6. 编号对账: 目标/业务规则编号不重复, 场景引用的 @G-NNN/@BR-NNN 在对应节真实存在, 且 @BR 不指向 (审计) 条目.
7. 确认标记: 正式模式的 `验收标准` 节必须在 Gherkin 块前含 `<!-- confirmed-flow: vN -->`, 缺失判为输入错误 (退出码 2). 草稿模式仅豁免此项, 确认后由转正脚本添加标记.

退出码: 0 通过 / 1 解析或规则校验失败 / 2 输入或文件错误. 失败时按报错修正后重跑, 机检结果不由目检替代. 已展示版本的任何修改都回到主会话检查, 重新预览并取得我的采纳; 不在正式文件上尝试修复.
