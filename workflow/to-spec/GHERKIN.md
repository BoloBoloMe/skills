# Gherkin 书写规范参考

本文件是 `to-product-spec` skill 的补充参考, 管 PRODUCT.md 验收标准 Gherkin 块的书写细节; 模板形态与机检触发时机见 `SKILL.md`.

## 1. 语法子集

`验收标准` 节为单个 ```gherkin 代码块: 首行 `# language: zh-CN`, 次行 `功能: <变更标题>`, 其后为全部场景. 单块自身即完整可解析单元, 未来抽出即为合法 .feature 文件.

### 允许的关键字与最小示例

关键字使用官方 zh-CN 集:

| 关键字 | 用途 |
|---|---|
| `功能:` | 块头, 次行, 值为变更标题 |
| `背景:` | 全部场景共享的公共前提 |
| `场景:` | 单个场景 |
| `场景大纲:` | 参数化场景, 配 `例子:` |
| `例子:` | 场景大纲的参数表 |
| `假定` | Given 步骤 |
| `当` | When 步骤 |
| `那么` | Then 步骤 |
| `而且` | And 连接步骤 |
| `但是` | But 连接步骤 |

```gherkin
# language: zh-CN
功能: 示例变更

背景:
假定 服务以单例模式运行

@AC-001 @normal @G-001 @US-001
场景: 远程会话首次交付展示
假定 主机上无存活服务实例
当 agent 执行 start 并交付 URL
那么 远程用户在自己设备的浏览器打开 URL 看到展示内容

@AC-002 @edge @G-001 @BR-001
场景大纲: 端口冲突重试
假定 服务未启动
当 agent 选取端口 <端口>
那么 <结果>

例子:
| 端口 | 结果 |
| 49152 | 服务就绪 |
| 65534 | 报 port_in_use 并换端口 |
```

### 显式禁令

- `给定` / `则`: 非官方关键字, Gherkin parser 不识别, 解析即失败.
- `规则:` (Rule): Rule 强制场景分组排序, 收益不抵约束; 业务规则归属仅靠 `@BR-NNN` 标签表达, 该禁令由机检脚本的关键字白名单强制.
- 英文关键字: 文档与步骤皆中文, 英文关键字造成语义断裂.
- `假如` / `假设` / `剧本` / `剧本大纲` / `并且` / `同时`: 虽属官方集, 但与本规范选定的唯一写法不一致, 统一用 `假定` / `场景` / `场景大纲` / `而且`.

## 2. 标签约定

标签集封闭, 只允许以下三类, 禁止自由标签. 反模式根源见旧格式实例: 自由散文 AC 无标签面, 机检无从下手.

| 标签 | 含义 | 基数约束 |
|---|---|---|
| `@AC-NNN` | 场景所属验收标准 | 每场景恰好一个; 同一 AC 的状态分支场景共用同一标签 |
| `@G-NNN` `@US-NNN` `@BR-NNN` | 覆盖关系 (目标/用户故事/业务规则) | 每场景至少一个; AC 的覆盖关系取其全部场景标签的并集 |
| `@normal` `@failure` `@edge` | 场景类型 (正常/失败/边界), 承接盘问的确认粒度 | 每场景标一个, 书写纪律, 机检不强制基数 |

1 AC = 1..N 场景: 一个 AC 打包多个状态分支时, 每条分支各写一个场景, 共用同一 `@AC-NNN`; 场景大纲计为一个场景. 不在落盘时拆 AC — 拆分等于在用户确认之外做语义切分.

常见标签错误 (均被机检拒绝):

```gherkin
# 反例: 伪标签, 自由标签, 一景多 AC 标签
@AC-001 @AC-002 @例子 @smoke
场景: 错误示范
```

- `@例子`: 伪标签, 不是封闭集成员.
- `@smoke`: 自由标签, 开放标签是腐烂起点.
- 同时挂 `@AC-001 @AC-002`: 违反每场景恰好一个 AC 标签; 若确属两条 AC 的行为, 应拆成两个场景, 各归其 AC.

## 3. 书写纪律

- 步骤主语强制领域角色名词 (如 远程用户/agent/攻击者), 禁用代词 `我`: 场景须自包含, 不依赖叙述视角, 并与项目 ubiquitous language 对齐.
- 声明式步骤, 禁 UI 操作细节: 写"远程用户打开 URL 看到内容", 不写"点击按钮/滚动页面/在输入框键入".
- 每场景单个 `当`: 一个场景验证一个刺激; 多个刺激拆多场景, 共用 AC 标签.
- `那么` 只写外部可观察结果: 可被产品层观察的行为/状态, 不写实现细节 (如内部函数返回值).
- 步骤含具体数据: 端口写 `49152-65534`, 不写"某端口"; 超时写 `24h`, 不写"超时后". 多组数据用场景大纲 + `例子:` 表.
- 步骤内禁条件逻辑: 不写"如果 X 则 Y, 否则 Z"; 每个分支一个场景, 由 `@failure`/`@edge` 区分类型. 旧格式 AC-002 把存活/进程死/文件缺失三条分支挤在一条散文里, 新格式应拆为三个场景.
- `背景:` 仅用于真正公共前提: 只有全部场景都需要的公共前提才进 `背景:`; 部分场景需要的前提写在各自场景的 `假定` 中.
- 写不成刺激-响应行为的审计式断言 (如"未引入认证") 不进场景, 归入 PRODUCT.md 的 `非行为验收` 小节; 转得了行为的断言必须写成场景.

### 边界声明

本节纪律无法机械化, 属 LLM 判断; 机检只覆盖解析/标签/覆盖/关键字子集. 两类规则本性不同, 不算漏洞 — 机检保证形态正确, 书写纪律保证语义质量, 后者由 spec 编写方对照本节自检.

## 4. 校验方法

唯一机检入口 (check-ac.py 与本 skill 同目录, 路径相对 skill 目录解析):

```bash
uv run <skill 目录>/check-ac.py <PRODUCT.md 路径>
```

校验项:

1. Gherkin parser 解析 (依赖 gherkin-official, 支持官方 zh-CN 关键字).
2. 标签封闭集与 `@AC` 唯一性.
3. 覆盖完整性: 每个 AC 至少一个场景, 每个场景至少一个覆盖标签.
4. 关键字白名单: 禁 Rule, 禁同义变体 (`假如`/`假设`/`剧本`/`剧本大纲`/`并且`/`同时`), 只认 §1 选定的唯一写法.
5. 标签位置限定: 标签只允许出现在场景/场景大纲行.

失败处理: 按报错定位到具体场景/标签/关键字修正后重跑, 直至退出码 0. 五项校验一律以脚本结果为准, 禁止目检替代脚本.
