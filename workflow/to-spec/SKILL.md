# 编写产品与技术规格

`PRODUCT.md` 定义产品结果, `TECHNICAL.md` 定义技术设计, 两份共同构成下游权威输入. 开始时说明本会话交付物与不做事项. 产物根目录按 `software-engineering-consensus` 的约定确定, 调用方指定时从其指定. 两份规格都写在该目录, 各类编号在本变更内稳定且连续. 规格交付不扩大实施授权; 催收口或中断后的"继续"不单独构成阶段切换或确认. 我收窄范围时同步更新仍在执行的协作任务.

## 规格约束与停止条件

必须遵守的内容包括已确认的产品结果, 范围与验收, 业务与安全约束, 对外兼容承诺, 必要的跨切片接口约定, 以及我明确固定的技术选择. 按 `decision-ledger` 的 `必须遵守` / `可调整` 区分, 不自行降级约束. 内部做法只留理解方向必需的说明, 标 `可调整`, 由实施者在不改变约束的前提下选择并验证. 不因模板有栏目就强行裁决内部做法. 例如, "终止后到款不得恢复权益"是结果约束, 用哪种锁不是, 除非我明确固定它. 改变账本决策的内容, 状态或约束性时按账本规则确认.

## 1. 核实输入, 盘问并确认

先调用 `domain-awareness` 感知领域和术语, 调用 `codebase-design` 核查技术方向. 核实权威输入与授权; 影响当前承诺的事实先调查, 关键前提尚未证实则调查或实验, 不拿猜测开问. 按两份[模板](TEMPLATES.md)的全部适用节展开范围树, 再调用 `grilling`. 按当前能问的问题分轮推进, 话题自然流动, 可随时跨产品/技术回补, 不按固定节序问. 本流程组合现有技能, 不整体调用 `deliberate`.

- **须亲答.** 产品判断 (目标取舍, 非目标, 业务规则, 覆盖情况增删, 阈值, 安全约束) 和我要固定的技术选择 (接口是否固定, 接缝与依赖, 兼容与迁移承诺) 必须由我亲答. 可查事实由你先查, 随所依赖的问题呈现; 我拍板即同时确认其依据事实.
- **验收情况.** 按覆盖树逐种过正常/失败/边界. 每种须问情况用一句话问主要刺激与可观察结果; 我的答复写成账本决策条目. 只有刺激和结果均能从账本或我答复中的已确认目标/规则直接推出, 且不新增前提, 阈值或行为, 才免问, 落笔时直接从该依据写成 Gherkin. 原文没有的判定不能自行填; 拿不准是否直译就问. 同一实质刺激与结果只问一次, 多个落笔场景各自成条, 引用同一决策. 已定判定直接引用账本, 不重问.
- **续问.** 同会话暂停后继续当前能问的问题, 不提前写规格; 本会话闭环不写交接. 需要换会话时先按下条入账, 再调用 `handoff`. 交接写当前可问问题, 已否决分支及理由, 逐题和逐节覆盖进度, 盲区扫描进度与待裁决项; 只记我明确提出的暂停或节奏要求, 不推测疲劳或心理状态. 已入账内容只引用, 不补免问清单或锚点. 同机用系统临时目录, 跨机按 `handoff` 落仓库并推送, 位置不明先问. 新会话读账本与交接恢复进度, 原件缺失就说明缺口, 不猜未定判定.
- **入账.** 调用 `decision-ledger`, 没有账本时按其模板建立 `DECISIONS.md`. 已确认判定和依据事实在闭环后或换会话前入账; 决策引用所依赖的事实号, 事实条目标明"随决策N确认". 无决策引用的纯背景事实不入账. 判定的持久记录只用现有决策/事实格式, 不增盘问专用文件/章节/格式, 免问不留痕. 领域术语或 ADR 需要维护时另按 `domain-modeling` 既有规则处理.
- **闭环.** 向我展示两份模板每一节的已问/未碰状态, 未碰节附理由, 不要求逐节另附已定结论. 清单呈现和 `grilling` 盲区扫描完成, 所有待裁决项关闭后, 才问我是否明确结束. 沉默, 部分认可或要求继续都不算, 不得开始写稿. 明确结束即同时确认两份规格所需内容, 不要求我读预写稿, 成文后的 Gherkin 或逐版采纳.

完成标准: 两份模板每节的已问/未碰状态及理由, 盲区扫描结果和全部待裁决项都已呈现并关闭, 我在 chat 明确结束, 决定与依据事实已入账; 仍在续问或有待裁决项时停在盘问, 不写稿.

## 2. 写前反方与主会话落笔

闭环且决策/事实入账后, 委派未参与盘问或落盘的独立会话调用 `opposing-viewpoint` 攻击账本决策. 给原始需求出处, 账本和必要代码入口. 主会话逐项核实, 驳回给依据; 新增或改变决策由我裁决并更新账本. 无未收敛发现后才由主会话先写产品, 后写技术. 组织措辞与前提可以, 不能构造未经确认的判定; 落笔发现缺依据时先补问该分支并入账再写. 审计式断言只写在产品业务规则节, 末尾标 `(审计)`, 不进 Gherkin. 把证据材料路径写进账本事实的来源字段, 决策引用事实号, 产品审计条目不携带证据路径.

先读 [GHERKIN.md](GHERKIN.md), 用 `uv run <skill 目录>/ac-draft.py workspace` 建专用工作区, 从 JSON 取 `dir` 与 `review` 路径. 下列 `<skill 目录>` 指当前 SKILL.md 所在目录, 不依赖工作目录. 保留三份临时原件:

- 产品正文暂存稿放 `dir` 内, 按 Product 模板写, 验收标准正文留空.
- 独立验收草稿放 `review` 内, 只含完整 Gherkin 代码块及首尾空白, 不带节名或确认标记. 草稿名含专用目录名, 避免展示服务的同名遮蔽.
- 技术草稿放 `dir` 内, 按 Technical 模板写, 不把不适用的条件节留在稿内.

完成标准: 写前反方的发现已逐项核实收敛, 三份临时原件按上述位置与内容约束就位; 反方留有未决发现或落笔处缺依据时停在该处, 补问入账后才继续, 不进入机检.

## 3. 机检与机械落正式

用当前盘问范围和依据核实 chat 的明确闭环确认, 包括后来有变动的分支是否已获答复并入账. 没有可核实的依据就停在缺口, 不凭文件标记或预览放行, 不另建确认状态文件. 草稿机检过后转正产品, 复制技术稿, 检查字节一致, 再机检两份正式稿:

```bash
uv run <skill 目录>/check-ac.py <产品暂存稿> --draft <验收草稿>
uv run <skill 目录>/check-tech.py <技术草稿>
uv run <skill 目录>/ac-draft.py promote <产品暂存稿> <验收草稿> <产物根目录>/PRODUCT.md
cp -- <技术草稿> <产物根目录>/TECHNICAL.md
cmp -- <技术草稿> <产物根目录>/TECHNICAL.md
uv run <skill 目录>/check-ac.py <产物根目录>/PRODUCT.md
uv run <skill 目录>/check-tech.py <产物根目录>/TECHNICAL.md
```

按顺序执行, 转正须退出 0 且 JSON `success` 为 true, 其余命令须退出 0. 转正脚本把验收原文字节嵌入临时产品副本, 在代码块前加固定 `<!-- confirmed-flow: v1 -->`, 正式机检通过才原子替换产品文件. 标记是流程格式, 不随修文升版, 不证明我看过文件. 转正发现本次输入或正式目标变化时停止替换, 保留现场, 核对当前输入与确认依据后处理. 技术稿机械复制, 不由模型重写. 两份正式稿不是同时替换的事务: 任一生成或检查失败, 会话及已有调用方状态记整组未完成, 保留现场, 补齐失败步骤并复查两份后才交付. 不向下游宣称规格齐备.

完成标准: chat 的闭环确认已核实到本次范围, 转正退出 0 且 JSON `success` 为 true, 技术稿 `cmp` 与两份正式稿机检均退出 0; 任一命令失败或发现输入/正式目标变化时按整组未完成保留现场处理.

## 4. 写后独立检查与修正

正式机检通过后, 另起未参与盘问/落笔的独立会话, 与写前反方分用会话. 只查不改两份正式稿, 不在草稿和正式稿上重复整份独立检查. 给检查会话账本, 必要答复出处, GHERKIN 纪律和下节达标标准. 原始答复只传与任务有关的必要材料, 按[共用脱敏要求](../verification-contract/SAFETY.md#脱敏)保留足够上下文; 脱敏后不足以判断则报告缺口, 交我处理, 不猜.

一次检查合并三项: **对账**逐项核实是否忠实, **反向覆盖**从账本和我的答复重推应覆盖情况再比对, **达标检查**按下节核查下游能否使用. 前两项的判定依据只用账本和我的答复, 不以待查的两份规格自证. 首次覆盖每个场景的刺激和结果, 全部目标/非目标/规则, 技术固定接口/接缝/约束; 叙述组织不逐句核. 每个发现给位置, 来源依据和具体后果.

主会话先复核并分流:

- 误报: 当场驳回并记录理由, 不交我裁决.
- 有依据但转述错或漏写: 修产品暂存稿/验收草稿中受影响部分, 或修技术草稿, 重走相关机检和机械落正式, 技术复制后仍核实字节一致. 不手改正式稿, 不请我重审整版.
- 缺判定/缺决策, 包括免问场景找不到原文依据: 只补问受影响分支, 入账后修文. 已定判定不重问, 整盘重来仅由我明确要求.

每次修订仍适用机检和三项独立检查. 检查会话说明影响范围, 主会话复核; 独立复查受影响内容及引用, 沿用未变且未受影响部分的结论. 有新证据或不能确认旧结论仍适用时扩大, 必要时全量. 确保最终整份规格均有检查覆盖.

完成标准: 对账, 反向覆盖, 达标检查三项都有结论, 每个发现已分流为驳回(记理由), 修文(重走机检与机械落正式)或补问入账, 最终整份规格都在检查覆盖内; 尚有未关闭的发现时不进入预览.

## 达标标准与检查边界

达标指足以支撑下游验证设计和执行拆分. 适用于主会话写稿自查和正式独立检查:

- 问题, 目标, 范围和非目标明确; 已确认约束完整, 无矛盾或无依据新增, 可调整做法未被写成硬要求.
- 场景前提, 输入和可观察结果明确; 审计断言有观察入口; 产品结果有技术设计承接, 模块职责, 接口与依赖清楚, 下游不用猜契约.
- 技术方向与关键前提有事实依据. 实施验证项写清待确认事实, 验证入口与通过标准, 未实测不写已验证.
- 现有机检通过, 固定节名/节序及下游引用的编号/路径满足约定. 机检只查格式和编号, 不证明语义忠实.

只报告会影响后续理解, 决策, 执行或验证的发现; 不因存在更好写法返工. 机检失败或引用失效仍须解决.

## 5. 预览与整组交付

无阻塞后, 从当前机检通过的暂存稿和验收草稿照常生成机械预览, JSON `success` 为 true 才用返回的 `preview` 和 `draft` 路径:

```bash
uv run <skill 目录>/ac-draft.py preview <产品暂存稿> <验收草稿>
```

调用 `present` 交付照原文生成的阅读卡片页面与草稿原文件链接, 仅供选看, 不等待确认. 只挂本次专用 `review` 目录, 不挂工作区整根, 不挂原始答复或无关材料. 不用模型改写页面; 预览生成失败按报错修正并重检受影响内容, 展示服务失败按 `present` 的失败出口交付文件.

汇报两份正式规格路径, 机检结果与独立检查结论, 不复述全文. 只有两份均生成并通过检查才交付. 反方与检查不能替我拍板; 盘问结束和检查通过均不是成品验收, `navigate` 的终点验收仍由我按标准与证据逐项决定.

完成标准: 预览 JSON `success` 为 true 且只挂本次 `review` 目录, 两份正式规格路径, 机检结果与独立检查结论已汇报; 预览或展示失败时按失败出口只交文件, 不声称整组已交付或成品已验收.
