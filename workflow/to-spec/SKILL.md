开始前, 调用 `domain-awareness` skill 只读感知当前工作目录的领域模型.

目标: 编写当前变更的两份 spec: 产品写 `PRODUCT.md`, 技术写 `TECHNICAL.md`. spec 是下游执行的权威输入, 缺一份执行链就缺信源. ID 在 feature 内稳定且连续.
输出为 `<产物根目录>/PRODUCT.md` 与 `<产物根目录>/TECHNICAL.md`; 产物根目录默认 `docs/changes/<feature-slug>/`, 调用方可指定其他根目录.

写作前, 逐项检查已确认决策与事实是否已包含编写 spec 所需的全部内容. 标准是: 仅通过转述已定决策和事实便可将 spec 中的每一项内容都填出来, 填不出就是有缺口.
存在缺口或冲突 → 调用 `deliberate` skill 敲定并固化, 把下方缺口盘问要求作为盘问重点传达; deliberate 固化产物后, 以更新后的决策与事实继续.

缺口盘问要求:
先敲定 Product Spec, 再敲定 Technical Spec.
`PRODUCT.md` 验收标准的每条 Gherkin 场景, 必须在盘问会话中逐条与我沟通并经我采纳; 未经我逐条确认的场景禁止写入文档.

# Product Spec: PRODUCT.md

使用下方模板写 `PRODUCT.md`. 书写 `验收标准` 节前, 必读同目录 `GHERKIN.md`.

````markdown
# <变更标题> Product Spec

## 背景

用一段大白话解释清楚需求的背景是什么, 要解决的问题是什么, 提出方是谁, 真实受益者有谁.

## 目标

写 "变更之后会有什么不同", 而不是写 "我们要做什么". 是 "做完了" 的判定标准. 编号格式: G-<编号>

eg:
- G-001: "客服可以在后台直接为用户补发优惠券，无需再转交技术支持"

## 非目标

一些不写出来容易让人误以为是目标之一的事情, 在此列出以澄清. 提前杀死那些 "我以为这个也包含在内" 的争论.
每条非目标写下来之前问一句: "如果不写这条, 会不会有合理的角色默认它包含在本次变更里? 会 -> 写；不会 -> 删.  编号格式: NG-<编号>

eg:
- NG-001: 不做批量补券, 一次只处理一单. (理由：当前补券工单 95% 是单笔, 批量场景量太小.)

## 业务规则

此节写两类内容, 共用 BR-<编号> 连续编号:
第一类: 独立于变更也成立的领域规则, 供 Gherkin 场景以 @BR-<编号> 标签引用, 真实存在领域规则时保留, 没有就不写; 
第二类: 写不成 刺激-响应行为 的审计式断言, 禁止进 Gherkin, 末尾标 (审计) 与第一类区分, 由覆盖矩阵承接. 没有就不写.

eg:
- BR-001: 补发优惠券的面额不得超过原订单的实付金额. (财务)
- BR-002: 同一订单的累计补发次数不超过 3 次. (运营/风控)
- BR-003: 本变更不新增第三方依赖. (审计)

## 验收标准

全部验收场景写在单个 ```gherkin 代码块中.

eg:
```gherkin
此处省略
```

## 决策引用
- <账本路径>: D001, D002. 多账本时每份账本一行. 无则写"无".
````

完成编写后, 执行本 skill 同目录的 check-ac.py (`uv run <skill 目录>/check-ac.py <PRODUCT.md 路径>`), 退出码 0; 机检六项校验一律以脚本结果为准, 禁止目检替代脚本.

# Technical Spec: TECHNICAL.md

使用下方模板写 `TECHNICAL.md`. 写 `架构与组件` 前调用 `codebase-design` skill, 设计必须符合其 深模块 要求; 检查已定决策是否满足, 不满足时视为缺口, 调用 `deliberate` skill 修订决策后再写.
节名是下游引用的稳定锚, 逐字固定; 标注 (条件保留) 的节不满足保留条件时整节省略, 满足时落盘标题不写该标注.

````markdown
# <变更标题> Technical Spec

## 架构与组件

模块责任, 交互方式和关键 seam. 无变化时说明沿用的现状. 末尾一行列出涉及的模块/目录边界, 不写逐文件计划.

## 接口契约

引用机器可读契约; 不存在时精确定义端点/方法, 请求/响应字段与类型, 状态码, 错误码和兼容约束. 不适用则写"不适用".

## 数据模型与状态

引用 schema/迁移/状态机权威资产; 不存在时精确定义字段, 类型, 约束, 关系和状态转换. 不适用则写"不适用".

## 边界与异常处理

非法输入, 超时, 并发, 幂等, 一致性, 降级和兼容要求.

## 依赖与风险

外部依赖, 关键风险, 影响和防护.

## 安全策略 (条件保留)

认证, 授权, 隐私, 密钥, 加密和脱敏. 不适用项写理由; 全部不适用则整节省略.

## 非功能要求 (条件保留)

仅在有带验证口径的性能/可观测性/可用性要求时写, 否则整节省略.

## 关键流程 (条件保留)

仅在流程无法从接口契约直接读出时写: 分布式事务, 重试时序, 状态机迁移. 否则整节省略.

## 测试接缝 (条件保留)

仅当接缝设计本身需要评审时写. 一张三列映射表:
行为 (引用 PRODUCT.md 的 AC 编号), 观察边界 (端点/方法/消息/UI), 测试层级 (单元/集成/端到端/人工). 行为描述以 PRODUCT.md
验收标准为唯一来源, 本节不重写 Given/When/Then.

## 决策引用

- <账本路径>: D001, D002. 多账本时每份账本一行. 无则写"无".
````

完成 TECHNICAL.md 后, 执行本 skill 同目录的 check-tech.py (`uv run <skill 目录>/check-tech.py <TECHNICAL.md 路径>`), 退出码 0; 节名与节序校验一律以脚本结果为准, 禁止目检替代脚本.

两份 spec 落盘后, 在会话中告诉我: 已生成的路径, check-ac.py 与 check-tech.py 的机检结果, 是否发现来源冲突. 不复述文档内容, 不要求我阅读后确认.
