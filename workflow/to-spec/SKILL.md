开始前, 调用 `domain-awareness` skill 只读感知当前工作目录的领域模型.

目标: 按已启用层面编写当前变更的 spec. 层面 = deliberate 中至少判定过一个问题归属的层面: 产品层面写 `PRODUCT.md` (产品结果基线, 供 LLM 与人共用), 技术层面写 `TECHNICAL.md` (技术契约, 只供 LLM 使用). 两层皆启用或层面信息缺失时两份都写 — spec 是下游执行的权威输入, 缺一份执行链就缺信源; 调用方指明产物范围时从其指明.
从可靠信源处收集产物需要的信息, 如果发现存在缺口/冲突 就调用 `grilling` skill 盘问我.
ID 在 feature 内稳定且连续. 输出为已启用层面对应的产物 (`<产物根目录>/PRODUCT.md` 与/或 `<产物根目录>/TECHNICAL.md`), 产物根目录默认 `docs/changes/<feature-slug>/`; 调用方可指定其他根目录.

# Product Spec: PRODUCT.md

盘问仍按正常/失败/边界推进; 落盘时结论直接写成 Gherkin 场景, 不另设关键场景节.
Gherkin 的语法子集, 标签约定与书写纪律唯一来源是同目录 `GHERKIN.md`, 书写 `验收标准` 节前必读.
使用下方模板写 `PRODUCT.md`.

<product-spec-template>

# <变更标题> Product Spec

## 背景
当前问题, 真实受益者, 需求来源和现在处理的理由.

## 目标
- G-001: 可衡量或可观察的产品结果.

## 非目标
- 不做 X, 它不在本变更范围内.

## 用户故事
- US-001: 作为 <actor>, 我想要 <capability>, 以便 <benefit>.

## 业务规则
- BR-001: 产品必须遵守的规则.

## 验收标准
本节为单个 ```gherkin 代码块: 首行 `# language: zh-CN`, 次行 `功能: <变更标题>`, 其后为全部场景. 不产独立 .feature 文件.

```gherkin
# language: zh-CN
功能: <变更标题>

@AC-001 @normal @G-001 @US-001
场景: <场景名>
假定 <前提>
当 <行为>
那么 <可观察结果>
而且 <可观察结果>

@AC-002 @edge @G-001 @BR-001
场景大纲: <场景名>
假定 <前提>
当 <行为>
那么 <可观察结果>

例子:
| 输入 | 结果 |
| a    | x    |
```

## 非行为验收
审计式断言: 写不成刺激-响应行为者 (如"未引入认证"), 不进 Gherkin 场景, 落在本节; 转得了行为的断言必须写成场景.
- NB-001: <审计式断言>. 无则写"无".

## 成功指标
- 指标, 观察窗口和目标值. 不设指标时写已确认理由.

## 产品决策引用
- <账本路径>: D001, D002. 多账本时每份账本一行. 无则写"无".

## 待验证事实
- 事实:
  影响:
  验证方式:
没有则写"无".

</product-spec-template>

完成标准:
- 固定章节齐全.
- 场景覆盖盘问确认的正常/失败/边界分支; 每项验收结果可观察.
- 非行为验收仅收审计式断言.
- 每项产品结论都能追溯到源头; 无阻塞产品缺口或冲突; 每项非阻塞未知都有影响和验证方式.
- 机检通过: 执行本 skill 同目录的 check-ac.py (`uv run <skill 目录>/check-ac.py <PRODUCT.md 路径>`), 退出码 0; 机检五项校验一律以脚本结果为准, 禁止目检替代脚本.

# Technical Spec: TECHNICAL.md

使用下方模板写 `TECHNICAL.md`.

<technical-spec-template>

# <变更标题> Technical Spec

## 技术目标
- TG-001: 支撑产品结果所需的可验证技术结果. 覆盖: G-001, AC-001.

## 架构与组件
模块责任, 交互方式和关键 seam. 无变化时说明沿用的现状.

## 接口契约
引用机器可读契约; 不存在时精确定义端点/方法, 请求/响应字段与类型, 状态码, 错误码和兼容约束. 不适用则写"不适用".

## 数据模型与状态
引用 schema/迁移/状态机权威资产; 不存在时精确定义字段, 类型, 约束, 关系和状态转换. 不适用则写"不适用".

## 关键流程
复杂正常流程, 失败流程和必要时序.

## 边界与异常处理
非法输入, 超时, 并发, 幂等, 一致性, 降级和兼容要求.

## 安全策略
认证, 授权, 隐私, 密钥, 加密和脱敏. 不适用项写理由.

## 非功能要求
- NFR-001: 性能/可观测性/可用性要求及验证口径.

## 测试接缝与用例
- TC-001:
  接缝: 通过哪个公开边界观察行为.
  公开接口: 方法/端点/命令/UI 交互/消息契约等调用入口.
  用例类型: 正常/边界/异常.
  Given:
  When:
  Then:
  预期值来源: 规格字面量/手算例子/外部契约/已确认事实, 禁止同义反复.
  测试层级: 单元/集成/端到端/人工验证.
  允许的 mock/fake: 仅系统边界, 外部服务, 时间, 随机性, 文件系统或已确认 adapter. 无则写"无".
  覆盖: AC-001, TG-001, NFR-001.

## 技术决策引用
- `DECISIONS.md` 中相关决策 ID. 无则写"无".
- 相关 ADR. 无则写"无".

## 依赖与风险
外部依赖, 关键风险, 影响和防护.

## 代码边界提示
可能涉及的模块, 目录或行为边界. 不写逐文件计划.

## 待验证事实
- 事实:
  影响:
  验证方式:
  没有则写"无".
</technical-spec-template>

完成标准: 固定章节齐全; 产品验收项均有技术承载或明确标记不需要技术承载; API/schema 等事实只有一个权威来源; 每个测试用例都有已确认接缝, 公开接口, 可观察断言和覆盖 ID; mock/fake 只用于系统边界或已确认 adapter; 文档未引入来源中不存在的决定.

编写完成后, 在会话中告诉我: 已生成的路径, PRODUCT.md 机检执行结果 (未产 PRODUCT.md 时省略), 是否存在待验证事实, 是否发现来源冲突. 不复述文档, 不让我阅读后确认.
