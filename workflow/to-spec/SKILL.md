# 编写产品与技术 spec

编写当前变更的两份 spec: `PRODUCT.md` 定义产品结果, `TECHNICAL.md` 定义技术设计. 它们是下游执行的权威输入, 缺一份就缺信源; 本 skill 整理已确认的约束与事实, 区分参考做法, 需要新增或改变决策时交回我裁决.
开始时按当前明确任务说明本会话交付物和不做事项. 仅交方案时, 下游 issue 的实施范围不是即时编码授权; 已明确授权完整实施时按授权推进, 不新增逐步确认. 催收口或中断后的"继续"不单独构成阶段切换或版本采纳; 我收窄范围时同步更新仍在执行的协作任务.
产物根目录按 `software-engineering-consensus` skill 的 产物根目录 词条确定; 调用方指定时从其指定. 两份文件均写在该目录下, 各类 ID 在 feature 内稳定且连续.

## 规格约束与停止条件

调用 `decision-ledger` skill, 按其 `必须遵守` / `可调整` 约束性分类整理已确认内容. 必须遵守的内容包括已确认的产品结果, 范围与验收, 业务与安全约束, 对外兼容承诺, 必要的跨切片接口约定, 以及我明确固定的技术选择. 已确认约束不得自行降级. 调整可调整做法不必改写历史决策记录; 如需变更账本内容, 状态或约束性, 仍按账本规则确认.
内部做法只保留理解方向必需的说明, 标 `可调整`, 在不改变上述约束的前提下由实施者选择并验证. 未确定的内部做法不因模板有栏目就成为决策缺口, 参考做法不变成下游硬要求. 例如, "终止后到款不得恢复权益"是结果约束, 用哪种锁不是, 除非我明确固定它.

产物检查遵守本 skill 的[达标标准与检查边界](#达标标准与检查边界). 检查通过不等于我已采纳, 方案交付也不自动授予实施权限.

## 达标标准与检查边界

本节用于 `PRODUCT.md`, `TECHNICAL.md` 和验收草稿写出后的全部检查环节, 包括子代理自检, 主会话检查和最终独立检查. 达标指足以支撑下游设计验证方案和拆分执行. 按被检产物负责承接的要求及其引用核对:

- 问题, 目标, 范围和非目标明确; 已确认的产品结果与必须遵守的约束有完整承接, 无遗漏, 矛盾或无依据新增, 可调整做法没有变成硬要求.
- 验收用例覆盖已确认的验收范围, 每条场景的前提, 输入与可观察结果明确; 审计断言有观察入口, 足以判断通过与否.
- 产品结果有技术设计承接, 必要的模块职责, 接口与依赖明确, 下游不必猜产品或契约决策.
- 技术方向与关键前提有事实依据. 尚未证实且决定目标, 范围或契约能否成立的关键前提先调查或实验; 普通实现选择留给实施. 实施验证项写清待确认事实, 验证入口与通过标准, 未实测的不写成已验证.
- 当前产物适用的现有机检通过, 下游解析与引用依赖的稳定 ID, 路径和固定节名满足约定.

只修复会影响后续工作的问题. 发现的问题若不影响后续理解, 决策, 执行或验证, 就不修复, 不退回, 不阻塞通过, 也不另列优化建议.
检查者首次完整核对上述适用项, 只报告会影响后续工作的阻塞项; 每项须指出问题位置, 所依据的要求或事实, 以及不修改会造成的具体后果. 仅仅发现错误, 偏离推荐写法或存在更好的写法, 不构成返工理由. 现有机检失败或引用失效会影响后续处理, 仍须解决.
需要新增或改变已确认决策时交我裁决. 返修后只复查受影响内容与引用, 新证据确需扩大范围时才扩大. 没有影响后续工作的未解决问题就立即进入本 skill 的既定下一步. 已通过内容仅在新证据表明会影响后续工作, 或我明确要求重新检查时重新打开.

## 流程

1. **补齐输入.** 调用 `domain-awareness` skill 感知当前工作目录的领域模型, 调用 `codebase-design` skill 检查技术设计及术语. 按 [规格约束与停止条件](#规格约束与停止条件) 对照 [模板](TEMPLATES.md) 核对必须遵守的内容和事实依据. 只补影响当前承诺的缺口, 设计原则用于检查当前方向, 不要求穷尽替代实现. 需要裁决时调用 `deliberate` skill 敲定并固化, 先产品后技术, 再继续.
   完成标准: 必须提前裁决的决策已确认并落盘, 关键前提有事实依据, 无妨碍规格起草的输入缺口.
2. **确认验收用例.** 按 [验收标准确认](#验收标准确认) 委派子代理起草并打磨, 由主会话检查通过后展示给我.
   完成标准: 草稿已通过机检与主会话检查, 且我在 chat 明确采纳了展示的固定版本.
3. **转正并机检.** 我采纳后执行下列转正命令, 将草稿原文嵌入正式 `PRODUCT.md`; 按 [模板](TEMPLATES.md) 写 `TECHNICAL.md` 并机检. `<skill 目录>` 按当前 `SKILL.md` 所在目录解析, 不依赖工作目录.

   ```bash
   uv run <skill 目录>/ac-draft.py promote <PRODUCT暂存稿> <验收草稿> <产物根目录>/PRODUCT.md --review <review_id>
   uv run <skill 目录>/check-tech.py <产物根目录>/TECHNICAL.md
   ```

   转正脚本核对审阅版本, 原样嵌入草稿, 添加确认标记并执行正式机检, 全部通过才原子替换正式文件. 失败时按报错修正; 输入变化须重新展示并确认, 不由 LLM 复制或重写验收正文.
   完成标准: 转正 JSON 的 `success` 为 true, `check-tech.py` 退出码为 0; 可机检规则以脚本结果为准, 不用目检替代.
4. **独立检查并交付.** 两项机检通过后, 启动一名子代理, 阅读两份 spec 及相关决策账本, 只检查而不修改它们. 逐项核对已裁决的发现与决策是否落实到 `PRODUCT.md`/`TECHNICAL.md`, 找出遗漏, 无依据的新增和矛盾; 检查产品结果是否有技术设计承接, 每条验收场景与审计断言是否指得出可观察点. 此处核对落实与自洽, 决策落账本后的旧行为反查由 `deliberate` 完成.
   阻塞项中可按已有依据修正的转述错误或遗漏由主会话修正; 需要新增或改变决策时, 获我裁决后回到第 1 步. 涉及 `PRODUCT.md` 的修正回到第 2 步的暂存稿/草稿, 不直接改正式文件; 已展示输入变化须重新展示并取得采纳. 修改后重跑相关机检并独立复查.
   没有阻塞项时, 告知我两份产物路径, 两项机检结果与独立检查结论, 不复述全文.
   完成标准: 独立检查已覆盖全部适用项并有明确结论, 影响后续工作的缺陷已修正并复检, 无阻塞项, 产物与检查结果已交付.

## 验收标准确认

无论输入是否有决策缺口, 正式采用前都走此流程. 草稿先经脚本与主会话检查, 我只审检查达标后的固定版本; 展示与转正都从原文件生成, 避免反复复述和转写消耗 token 或改变内容.

1. **委派起草.** 起草前必读同目录 [GHERKIN.md](GHERKIN.md). 先用 `uv run <skill 目录>/ac-draft.py workspace` 建本次专用临时工作区, 从 stdout JSON 取 `dir` (专用目录) 与 `review` (放草稿和预览), 确认前保留目录. 按 Product 模板写 `dir/PRODUCT.base.md` 暂存稿, `验收标准` 正文留空. 草稿文件名包含专用目录名与版本号, 避免 web 服务的同名文件遮蔽. 启动一名子代理, 给它已确认来源, 暂存稿, GHERKIN.md, 本 skill 的[达标标准与检查边界](#达标标准与检查边界) 和草稿输出路径. 草稿只含一个完整的最终 Gherkin 代码块, 包括共享前提与全部场景, 不含节标题或确认标记. 子代理自行执行下列机检并修复, 只回报草稿路径, 机检结果与改动摘要, 不回贴全文.

   ```bash
   uv run <skill 目录>/check-ac.py <PRODUCT暂存稿> --draft <验收草稿>
   ```

   草稿模式读取暂存稿的目标/业务规则, 只豁免确认标记, 其他校验与正式模式相同.
   完成标准: 子代理已将最终正文写入专用临时目录, 草稿机检退出码为 0.
2. **主会话检查.** 你读取草稿, 对照已确认来源核对决策依据, 覆盖与可观察结果; 用 [GHERKIN.md 的书写纪律](GHERKIN.md#3-书写纪律) 识别会影响理解, 执行或判断结果的内容问题. 格式规则交给脚本. 将阻塞项交回同一子代理修正并重新机检; 发现必须裁决的问题时调用 `deliberate` skill 敲定并固化, 更新暂存稿后继续.
   完成标准: 草稿机检仍通过, 每条用例有依据, 输入与可观察结果足以判断通过与否, 已确认范围内应覆盖内容无遗漏, 无影响判断的待定值或矛盾.
3. **冻结版本并展示.** 运行下列命令从暂存稿与草稿生成 HTML 阅读卡片及原文预览, 以 JSON 的 `success` 判断结果, 记录返回的 `review_id`, `draft` 与 `preview` 路径. 失败时按报错修正并回到主会话检查, 不由 LLM 另写阅读版替代.

   ```bash
   uv run <skill 目录>/ac-draft.py preview <PRODUCT暂存稿> <验收草稿>
   ```

   调用 `present` skill, 仅打开/交付返回的 HTML, 保持脚本生成内容不变, 同时交付草稿原文件链接. 只挂载本次 `review/` 目录, 不挂载整个系统临时目录. chat 中说明待确认的是哪一版, 请我采纳或指出修改项, 不复述全文.
   展示后冻结这版草稿与暂存稿; 修改时生成新版并重新检查, 预览与确认. `review_id` 同时绑定两份输入的原始字节, 任一变化都不能沿用旧版确认.
   完成标准: 预览生成成功, 已交付可读取的脚本预览及草稿原文件 (展示失败时按 present 的失败出口交付文件), chat 已明确待确认的 `review_id`.
4. **等待采纳.** 只有我在 chat 明确采纳当前完整版本, 才进入主流程第 3 步转正; 沉默, 仅部分认可或展示失败都不等于整版采纳. 我要求修改时回到子代理打磨, 不在正式文件上试改.
   完成标准: 我已明确采纳当前 `review_id` 对应版本, 两份输入自展示后未变.

修订既有 PRODUCT.md 时保留稳定 ID, 用现有内容辅助核对差异, 仍提交完整草稿供我采纳. 确认前保留上次正式文件; 会话中断后如找不到原草稿或明确的版本采纳记录, 重新展示并确认. 除转正脚本添加的确认标记外, 不在正式文档写确认记录或另建确认状态文件; 标记和版本校验都不能证明我实际看过内容.

## 产物模板

两份 spec 的节名与节序是下游引用的稳定约定, 逐字照抄. 模板见 [模板](TEMPLATES.md).

先按 Product 模板写临时 `PRODUCT.base.md`, 验收正文留空; 转正脚本保留其他章节, 只填入验收正文并添加确认标记. 再按 Technical 模板写 `TECHNICAL.md`; 标注 `(条件保留)` 的节不满足条件时整节省略, 保留时标题去掉该标注.
