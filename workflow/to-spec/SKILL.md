编写当前变更的两份 spec: `PRODUCT.md` 定义产品结果, `TECHNICAL.md` 定义技术设计. 它们是下游执行的权威输入, 缺一份就缺信源; 本 skill 转述已确认的决策与事实, 需要新决策时交回我裁决.
产物根目录默认 `docs/changes/<feature-slug>/`, 调用方指定时从其指定. 两份文件均写在该目录下, 各类 ID 在 feature 内稳定且连续.

# 流程

1. **补齐输入.** 调用 `domain-awareness` skill 只读感知领域模型, 调用 `codebase-design` skill 检查技术设计及术语. 对照下方两份模板逐项核对已确认的决策与事实; 仅靠转述填不出的内容, 或与设计原则不符的内容, 都是缺口. 有缺口或冲突时调用 `deliberate` skill 敲定并固化, 先产品后技术, 再以更新后的决策与事实继续.
   完成标准: 两份 spec 的每项内容都有已确认的决策或事实支撑, 全部决策盘问已结束, 无待定项或未解决冲突.
2. **确认验收用例.** 按 [验收标准确认](#验收标准确认) 委派子代理起草并打磨, 由主会话验收后展示给我.
   完成标准: 草稿已通过机检与主会话验收, 且我在 chat 明确采纳了展示的固定版本.
3. **转正并机检.** 我采纳后执行下列转正命令, 将草稿原文嵌入正式 `PRODUCT.md`; 按模板写 `TECHNICAL.md` 并机检. `<skill 目录>` 按当前 `SKILL.md` 所在目录解析, 不依赖工作目录.

   ```bash
   uv run <skill 目录>/ac-draft.py promote <PRODUCT暂存稿> <验收草稿> <产物根目录>/PRODUCT.md --review <review_id>
   uv run <skill 目录>/check-tech.py <产物根目录>/TECHNICAL.md
   ```

   转正脚本核对审阅版本, 原样嵌入草稿, 添加确认标记并执行正式机检, 全部通过才原子替换正式文件. 失败时按报错修正; 输入变化须重新展示并确认, 不由 LLM 复制或重写验收正文.
   完成标准: 转正 JSON 的 `success` 为 true, `check-tech.py` 退出码为 0; 可机检规则以脚本结果为准, 不用目检替代.
4. **独立检查并交付.** 两项机检通过后, 启动一名子代理, 阅读两份 spec 及相关决策账本, 只检查而不修改它们. 逐项核对已裁决的发现与决策是否落实到 `PRODUCT.md`/`TECHNICAL.md`, 找出遗漏, 无依据的新增和矛盾; 检查产品结果是否有技术设计承接, 每条验收场景与审计断言是否指得出可观察点. 此处核对落实与自洽, 决策落账本后的旧行为反查由 `deliberate` 完成.
   有问题时报告位置与依据并停下, 等我裁决, 不自动修订 spec 或启动盘问. 我同意返工后, 决策问题回到第 1 步, 受影响用例回到第 2 步, 修改后重新机检和独立检查.
   无待裁决问题时, 告知我两份产物路径, 两项机检结果与独立检查结论, 不复述全文.
   完成标准: 独立检查有逐项结论, 每个问题有位置与依据; 所有问题均已裁决且必要返工已复检, 产物与检查结果已交付.

# 验收标准确认

无论输入是否有决策缺口, 正式采用前都走此流程. 草稿先经脚本与主会话验收, 我只审打磨后的固定版本; 展示与转正都从原文件生成, 避免反复复述和转写消耗 token 或改变内容.

1. **委派起草.** 起草前必读同目录 [GHERKIN.md](GHERKIN.md). 用 `tempfile.mkdtemp(prefix="to-spec-ac-")` 在系统临时目录中新建本次专用目录, 按 Product 模板写 `PRODUCT.base.md` 暂存稿, `验收标准` 正文留空; 另建 `review/` 子目录放草稿和预览, 确认前保留目录. 草稿文件名包含专用目录名与版本号, 避免 web 服务的同名文件遮蔽. 启动一名子代理, 给它已确认来源, 暂存稿, GHERKIN.md 和草稿输出路径. 草稿只含一个完整的最终 Gherkin 代码块, 包括共享前提与全部场景, 不含节标题或确认标记. 子代理自行执行下列机检并修复, 只回报草稿路径, 机检结果与改动摘要, 不回贴全文.

   ```bash
   uv run <skill 目录>/check-ac.py <PRODUCT暂存稿> --draft <验收草稿>
   ```

   草稿模式读取暂存稿的目标/业务规则, 只豁免确认标记, 其他校验与正式模式相同.
   完成标准: 子代理已将最终正文写入专用临时目录, 草稿机检退出码为 0.
2. **主会话验收.** 你读取草稿, 对照已确认来源核对决策依据与覆盖, 逐条应用 [GHERKIN.md 的书写纪律](GHERKIN.md#3-书写纪律). 格式规则交给脚本. 有问题就把具体问题交回同一子代理打磨并重新机检, 直到全部问题关闭; 发现未定决策时调用 `deliberate` skill 敲定并固化, 更新暂存稿后继续, 不让子代理自行补答案.
   完成标准: 草稿机检仍通过, 每条用例有依据且满足书写纪律, 应覆盖内容无遗漏, 无待定值或未解决矛盾.
3. **冻结版本并展示.** 运行下列命令从暂存稿与草稿生成 HTML 阅读卡片及原文预览, 以 JSON 的 `success` 判断结果, 记录返回的 `review_id`, `draft` 与 `preview` 路径. 失败时按报错修正并回到主会话验收, 不由 LLM 另写阅读版替代.

   ```bash
   uv run <skill 目录>/ac-draft.py preview <PRODUCT暂存稿> <验收草稿>
   ```

   调用 `present` skill, 仅打开/交付返回的 HTML, 保持脚本生成内容不变, 同时交付草稿原文件链接. 只挂载本次 `review/` 目录, 不挂载整个系统临时目录. chat 中说明待确认的是哪一版, 请我采纳或指出修改项, 不复述全文.
   展示后冻结这版草稿与暂存稿; 修改时生成新版并重新验收, 预览与确认. `review_id` 同时绑定两份输入的原始字节, 任一变化都不能沿用旧版确认.
   完成标准: 预览生成成功, 已交付可读取的脚本预览及草稿原文件 (展示失败时按 present 的失败出口交付文件), chat 已明确待确认的 `review_id`.
4. **等待采纳.** 只有我在 chat 明确采纳当前完整版本, 才进入主流程第 3 步转正; 沉默, 仅部分认可或展示失败都不等于整版采纳. 我要求修改时回到子代理打磨, 不在正式文件上试改.
   完成标准: 我已明确采纳当前 `review_id` 对应版本, 两份输入自展示后未变.

修订既有 PRODUCT.md 时保留稳定 ID, 用现有内容辅助核对差异, 仍提交完整草稿供我采纳. 确认前保留上次正式文件; 会话中断后如找不到原草稿或明确的版本采纳记录, 重新展示并确认. 除转正脚本添加的确认标记外, 不在正式文档写确认记录或另建确认状态文件; 标记和版本校验都不能证明我实际看过内容.

# Product Spec: PRODUCT.md

先按模板写临时 `PRODUCT.base.md`, 验收正文留空; 转正脚本保留其他章节, 只填入验收正文并添加确认标记.

````markdown
# <变更标题> Product Spec

## 背景

用一段大白话说明需求背景, 要解决的问题, 提出方和真实受益者.

## 目标

写变更后的可观察差异, 作为完成判据, 用 G-NNN 编号. 例如:

- G-001: 客服可以在后台直接为用户补发优惠券, 无需再转交技术支持.

## 非目标

只列合理角色可能误以为包含在本次变更里的事项, 写明排除理由, 用 NG-NNN 编号. 例如:

- NG-001: 不做批量补券, 一次只处理一单. (理由: 当前补券工单 95% 是单笔, 批量场景量太小.)

## 业务规则

以下两类共用 BR-NNN 连续编号, 无相应内容时不写该类条目:

- 独立于变更也成立的领域规则, 供场景以 @BR-NNN 标签引用.
- 写不成刺激-响应行为的审计式断言, 末尾标 (审计), 由下游覆盖矩阵承接, 不进 Gherkin.

例如:

- BR-001: 补发优惠券的面额不得超过原订单的实付金额. (财务)
- BR-002: 同一订单的累计补发次数不超过 3 次. (运营/风控)
- BR-003: 本变更不新增第三方依赖. (审计)

## 验收标准

## 决策引用

- <账本实际路径>: D001, D002. 多账本时每份一行, 无则写"无".
````

# Technical Spec: TECHNICAL.md

节名与节序是下游引用的稳定约定, 逐字固定. 标注 `(条件保留)` 的节, 不满足条件时整节省略; 保留时标题去掉该标注.

````markdown
# <变更标题> Technical Spec

## 模块划分

每个新增或改动的模块一行: 责任 + 藏了什么 (实现承担的复杂度). 新增模块附删除测试判定: 删掉它, 复杂度是消失还是散回调用点. 无变化时说明沿用的现状. 末尾一行列出涉及的模块/目录边界, 不写逐文件计划.

## 模块接口

逐模块定义调用者正确使用所需的一切: 类型/方法/参数, 不变量 (含超时, 幂等, 并发约束), 顺序约束, 错误模式, 必需配置, 性能特征. 端点, CLI, 持久化 schema 都写进所属模块, 不单列. 不适用则写"不适用".

## 接缝与依赖

本变更引入或移动的每个接缝: 位置 (跨模块接口或模块内部, 内部的标注"内部"). 涉及外部依赖时按类别逐个标注: 进程内/本地可替换/远程但自有/真正外部. 依赖类别决定验证时能否用替身, 所以必须写; 适配器与分层方式由实现者决定, 不在此规定. 无新接缝时写明一行即可.

每条验收场景与审计断言须指得出一个可观察点, 写进所属 issue 的 `验证入口`; 指不出就是 spec 缺口, 不留给执行者现场补.

## 安全策略 (条件保留)

认证, 授权, 隐私, 密钥, 加密和脱敏. 不适用项写理由; 全部不适用则整节省略.

## 非功能要求 (条件保留)

仅在有带验证口径的性能/可观测性/可用性要求时写, 否则整节省略.

## 关键流程 (条件保留)

仅当跨模块行为无法从单个模块接口读出时写: 状态迁移, 重试时序, 一致性, 降级链. 否则整节省略.

## 决策引用

- <账本实际路径>: D001, D002. 多账本时每份一行, 无则写"无".
````
