产出面向团队汇报和方案沟通的 `spec.md`. Spec 不是执行边界契约, 不作为 issue 拆分或 AFK 的权威输入. 需要执行边界时使用 `to-contract`.

## 流程

### 1. 收集已知输入

读取当前对话, 用户提供的文档, 原型产物, `CONTRACT.md` (如存在), `DECISIONS.md` (如存在) 和其他用户指定材料. 用户给出输出位置时使用该位置; 否则按 `docs/changes/<feature-slug>/spec.md` 输出, `<feature-slug>` 从功能标题推断.

完成标准: 已得到 Spec 来源材料清单, 已确定输出路径. 如果发现来源材料之间存在会改变方案叙事的冲突, 停止并询问用户, 不自行改写 contract 或决策账本.

### 2. 补读材料 (按需)

`to-spec` 不要求代码探索. 只有当现有材料不足以说明团队汇报所需的问题, 方案或用户故事时, 才做轻量补读. 不承担执行边界校验, 不输出允许范围, 禁止范围, 验证入口或停止条件等执行门禁章节.

完成标准: 已获得足够材料写出团队可读的产品化叙事; 不足处作为 Spec 假设或补充说明呈现.

### 3. 编写并发布 Spec

使用下方模板编写 Spec, 发布到本地议题跟踪器. Spec 可摘要 `CONTRACT.md` 和 `DECISIONS.md` 中对团队理解必要的关键取舍, 但不复制完整执行契约或完整设计树. 不记录执行状态, 不写 `Status:` 或等价状态行.

完成标准: Spec 已写入目标路径, 最终回复展示路径, 方案摘要, 关键假设和风险.

<spec-template>

# <Spec 标题>

## 问题陈述

用户所面临的问题, 从用户视角描述.

## 解决方案

问题的解决方案, 从用户视角描述.

## 用户故事

一份编号用户故事列表. 每个用户故事使用以下格式:

1. 作为一个 <actor>, 我想要 <feature>, 以便 <benefit>

<user-story-example>
1. 作为一名手机银行客户, 我想查看账户余额, 以便我能对自己的消费做出更明智的决策
</user-story-example>

用户故事应覆盖该功能的主要场景, 边界场景, 失败场景.

## 关键取舍

列出对团队理解方案必要的关键取舍摘要和决策 ID. 不复制完整设计树. 不包含逐文件实现步骤.

## 未确认假设

列出当前上下文无法确认, 但 Spec 为汇报方案而采用的假设. 每项写清影响范围和后续验证方式.

## 范围外

描述此 Spec 范围外的事项, 用下面这个模板编写:
```text
不做 ?  , 它不在本 Spec 范围内
```

## 补充说明

关于该功能的任何补充说明.

</spec-template>
