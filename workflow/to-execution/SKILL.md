# 拆分可执行 issue

本 skill 交付执行拆分, 不因 issues 已列出未来实施范围就启动编码; 是否继续实施以当前明确授权为准.
开始前, 主会话调用 `domain-awareness` skill 感知当前工作目录的领域模型.

## 检查权威输入

按调用方给定的产物根目录与输入清单核对 `PRODUCT.md` 和 `TECHNICAL.md`; navigate 调用时使用里程碑的 `inputs` 与 `output_dir`, 不从里程碑编号推算目录. 缺任一份先调用 `to-spec` skill 生成, 再继续. 在 navigate 的 execution-plan 里程碑中, 前置输入缺失应交回领航安排规格整理, 不在本节点吞掉前置阶段.
权威输入定义已确认意图, 代码事实验证可行性和既有形状. 已确认的产品结果, 范围与验收, 业务与安全约束, 对外兼容承诺, 必要的跨切片接口约定和我明确固定的技术选择必须遵守. 标为 `可调整` 的内部做法只作参考, 在上述约束内由实施者选择并验证, 不升级为执行硬要求. 必须遵守的内容冲突, 或需要新增/改变决策时, 调用 `deliberate` skill 敲定并固化, 再继续; 普通实现选择不构成输入缺口.
规格整理完成后, 实施开始前须先有产物根目录下状态为已确认的 `VERIFICATION-PLAN.md`. 缺少或来源已变化时报告输入缺口并停止, 不生成 Execution Spec; 先完成规格之后的验证方案设计, 再回来拆分执行.

## 目标

把变更拆成多个单会话可容纳的垂直切片 `ISSUES`, 再用 `EXECUTION.md` 记录任务全局视角. 每个 issue 在一个全新的上下文窗口中交付, 执行 agent 沿 `EXECUTION.md` 的任务图领取, 于是单个会话的上下文上限不再截断整个变更.

## 输出

本 skill 的产物统称为 Execution Spec, 只供 LLM 使用, 我不会阅读它们:

`<产物根目录>/EXECUTION.md`
`<产物根目录>/issues/ISSUE-<NN>-<slug>.md`, 从 `ISSUE-01` 连续编号.

产物根目录按 `software-engineering-consensus` skill 的 产物根目录 词条确定; 我调用时另行指定则按指定, 除此之外不再确认. `<slug>` 用小写 kebab-case 短语概括该 issue 的交付内容, 如 `gatekeeper-read-write`.

## 流程

拆分内容不送人工审核. 产物检查遵守本 skill 的[达标标准与检查边界](#达标标准与检查边界).

1. **委派起草.** 主会话核对权威输入后, 准备专用临时草稿目录, 启动一名子代理, 交给它权威输入清单, 已确认的 `VERIFICATION-PLAN.md`, 相关决策引用与已发现的领域信息, 最终产物根目录, 本 skill 与模板, 草稿输出路径. 子代理拆分切片后, 调用 `verification-contract` skill 确定各 issue 的变更类型, 验证方式与证据, 按下文规则起草整套 `EXECUTION.md` 和 issues; 按本 skill 的标准自检后回报草稿路径, 检查结论及待裁决缺口, 不回贴全文. 草稿保留最终目录结构, 引用按最终落盘位置解析, 检查时将拟输出路径映射到草稿; 未通过检查前不覆盖既有正式产物.
   完成标准: 整套草稿已落临时目录, 自检通过且无待裁决缺口.
2. **主会话检查.** 主会话读取整套草稿, 对照权威输入与[达标标准与检查边界](#达标标准与检查边界)检查覆盖, 切片边界, 依赖和验证承接, 将阻塞项交回同一子代理修正. 涉及新增或改变已确认决策时, 按[检查权威输入](#检查权威输入)处理并更新输入.
   完成标准: 整套草稿通过本 skill 的达标检查, 无阻塞项.
3. **固化并交付.** 主会话将检查通过的草稿原文落到最终产物根目录, 不在固化时重写内容. 核对落盘文件与通过版本一致, 引用能在最终位置解析; 搬运错误按通过版本恢复, 草稿本身有引用错误则回到第 2 步. 告知我产物路径与检查结论, 不复述全文.
   完成标准: 正式文件与通过检查的版本一致, 最终引用可解析, 产物路径与检查结论已交付.

## 起草垂直切片

把工作拆成 **tracer bullet** issues. 只有端到端可独立验证的切片, 才能让全新上下文窗口中的执行 agent 无需折返追问. 垂直切片规则:

- 每个切片都必须能从真实入口独立验证, 并能在全新上下文窗口内独立交付, 必要输入与引用齐备, 不依赖未定的业务取舍. 它走过哪些层不规定
- 完成的切片本身可以演示
- 只有当前切片无法在保持边界和验证的前提下推进时, 才创建阻塞它的预重构 issue

为每个 issue 写出 **blocking edges**: 哪些其他 issues 必须先完成, 这个 issue 才能开始, 写明缺少前置的什么结果会阻塞当前交付或验证. 没有 blockers 的 issue 可以立即开始. 仅修改同一文件不是 blocker; 文件重叠写进已有风险提示, 调度与合并时协调, 不混入产品/接口依赖.

**宽重构是垂直切片的例外**: 一次机械改动 (重命名列, 改共享符号类型) 的 blast radius 扩散到整个代码库, 没有切片能独立保持绿色. 遇到这类变更时读 [refactor-expand-contract.md](refactor-expand-contract.md), 按其中的扩展-收缩序列拆分.

## 达标标准与检查边界

本节用于 `EXECUTION.md` 和 issues 的草稿与正式产物检查, 子代理自检与主会话检查使用同一组标准. 达标指全新会话能据此领取, 实施并验证任务, 不必猜产品或契约决策. 核对以下内容:

- 执行拆分忠实承接已确认输入, 无矛盾或无依据新增; 必须遵守的约束保持不变, 可调整做法没有变成硬要求.
- 覆盖矩阵中每个 AC/BR 和实际采用的 TC 均能追溯到验证入口. 每个 AC 有 issue 承接或明确说明无需执行任务; 标 (审计) 的 BR, TECHNICAL.md 非功能要求与安全策略中的验证性要求均有 issue 或人工验证方式承接.
- TECHNICAL.md 中必须遵守的接口不变量与错误模式, 要么有 TC 承接, 要么在所属 issue 的 `验证入口` 写明不用自动化测试的理由, 实际验证方式及通过标准. 实施验证项有对应 issue 承接.
- 每个切片必要输入与引用齐备, 能在全新上下文中独立交付, 从真实入口独立验证并演示. 预重构 issue 与纯验证/非行为改动类 issue 不适用可演示判据, 改用承接 AC/BR 或验证入口证明价值.
- 任务图引用按最终落盘位置可解析; 每条 blocker 都指明必需的前置结果, 不以共享文件制造依赖, blocker 图无环.
- 每个实施 issue 有代码定位提示, `验证契约` 声明一种或多种变更类型及对应范围和证据要求, `验证入口` 明确验证路径与通过标准. 具体复跑操作可在实施中补齐, 不要求入口命令现在就存在, 该 issue 交付前必须齐备; 确需新增自动化测试时, 接缝与用例写在该 issue 的验证入口里.
- 纯验证 issue 用纯验证模板, 只填验证栏目, 写明验证入口, 通过标准和完成证据要求. 宽重构适用时按 refactor-expand-contract.md 拆分, integration 特例写明原因, 共享分支与局部证据.
- 决策引用单向完整: 每个 issue 的 `相关决策` 节引用真实存在的相关决策 ID, 或已明确无相关决策.
- 拆分依赖的代码事实与关键前提有依据. 尚未证实且决定计划能否成立的关键前提先调查或实验; 普通实现选择留给实施. 实施验证项写清待确认事实, 验证入口与通过标准, 未实测的不写成已验证.
- 下游解析与引用依赖的稳定 ID, 路径和固定节名满足约定, 适用的现有机检通过.

只修复会影响后续工作的问题. 发现的问题若不影响后续理解, 决策, 执行或验证, 就不修复, 不退回, 不阻塞通过, 也不另列优化建议.
检查者首次完整核对上述适用项, 只报告会影响后续工作的阻塞项; 每项须指出问题位置, 所依据的要求或事实, 以及不修改会造成的具体后果. 仅仅发现错误, 偏离推荐写法或存在更好的写法, 不构成返工理由. 现有机检失败或引用失效会影响后续处理, 仍须解决.
需要新增或改变已确认决策时交我裁决. 返修后只复查受影响内容与引用, 新证据确需扩大范围时才扩大. 没有影响后续工作的未解决问题就立即进入本 skill 的既定下一步. 已通过内容仅在新证据表明会影响后续工作, 或我明确要求重新检查时重新打开.

## 产物编写约定

按 [模板](TEMPLATES.md) 起草拆分出的 issues, 再生成引用真实 issue 路径的 `EXECUTION.md`, 按依赖顺序编号. 确需编写自动化测试时才分配 TC (测试用例) 编号, 不因有 AC 就生成 TC. 已采用的 TC 编号全局唯一, 各 issue 自行编号, 无需集中分配: 覆盖某 AC 的主用例与 AC 同号 (`AC-005 -> TC-005`); 已确认且确需自动化的其他要求或同一 AC 的额外用例用 `TC-<issue 两位编号>-<两位序号>`, 如 ISSUE-02 的第一条额外用例为 `TC-02-01`. 不从编号规则反推要补用例. 信源与决策的引用路径按实际位置解析, 不假设它们位于产物根目录.
存在相关 DECISIONS.md 时, 每个 issue 单向引用相关决策 ID, 见 issue 模板的 相关决策 节. 引用只从产物指向账本: DECISIONS.md 是权威信源, 产物是派生视图, 账本不记录产物引用. 不新增或改变决策内容. 无相关决策时 issue 写"无".
不复制 PRODUCT.md/TECHNICAL.md 的正文, 只引用稳定 ID (AC/BR/G/NG) 或与模板逐字一致的固定节名, 以及执行所需摘要. 全局允许范围, 禁止范围, 完成定义, 验证策略只在 `EXECUTION.md` 写一次; issue 的对应节只写本 issue 的增量, 与全局相同不必重复正文.

模板给出固定节名与节序, 保留的栏目逐字照抄. 实施 issue 的 `验证契约`, `验证入口`, `交付证据` 必须保留; 其他栏目按执行所需保留, 不因"按需"删掉专项检查或下游领取任务所需的信息. `允许范围` 与 `禁止范围` 在有增量或特有禁止项时写, 与全局相同可省略或写"同全局"; 可省略且无内容的栏目整节删掉, 模板或专项检查明确要求写"无"的情况除外.
只验证, 不修改成品的 issue 用模板里的纯验证版本: 只填验证栏目, 不套改动契约, 不新增实施分类.
