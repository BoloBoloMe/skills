开始前, 调用 `domain-awareness` skill 只读感知当前工作目录的领域模型.

目标: 编写 Technical Spec: `TECHNICAL.md`. 它将作为当前变更的技术契约. 文档只供 AI 使用.

从可靠信源处收集 `TECHNICAL.md` 需要的信息, 如果发现存在缺口/冲突 就调用 `grilling` skill 盘问我.
使用下方模板写 `TECHNICAL.md`. ID 在 feature 内稳定且连续. 输出为 `docs/changes/<feature-slug>/TECHNICAL.md`.

<technical-spec-template>

# <变更标题> Technical Spec

## 技术目标
- TG-001: 支撑产品结果所需的可验证技术结果. 覆盖: G-001, AC-001.

## 架构与组件
模块责任, 交互方式和关键 seam. 无变化时说明沿用的现状.

## 接口契约
引用机器可读契约; 不存在时精确定义端点/方法, 请求/响应字段与类型, 状态码, 错误码和兼容约束. 不适用则写"不适用".

## 数据模型与状态
引用 schema/迁移/状态机权威资产; 不存在时精确定义字段, 类型, 约束, 关系和状态转换. 不适用则写"不适用".

## 关键流程
复杂正常流程, 失败流程和必要时序.

## 边界与异常处理
非法输入, 超时, 并发, 幂等, 一致性, 降级和兼容要求.

## 安全策略
认证, 授权, 隐私, 密钥, 加密和脱敏. 不适用项写理由.

## 非功能要求
- NFR-001: 性能/可观测性/可用性要求及验证口径.

## 测试用例
测试用例列表.

## 技术决策引用
- `DECISIONS.md` 中相关决策 ID. 无则写"无".
- 相关 ADR. 无则写"无".

## 依赖与风险
外部依赖, 关键风险, 影响和防护.

## 代码边界提示
可能涉及的模块, 目录或行为边界. 不写逐文件计划.

## 待验证事实
- 事实:
  影响:
  验证方式:
  没有则写"无".
</technical-spec-template>

完成标准: 固定章节齐全; 产品验收项均有技术承载或明确标记不需要技术承载; API/schema 等事实只有一个权威来源; 文档未引入来源中不存在的决定.
编写完成后, 在会话中告诉我: 已生成的路径, 是否存在待验证事实, 是否发现来源冲突. 不复述文档, 不让我阅读后确认.
