# afk worker 如何使用 TDD

## 阅读门禁

本文件是 afk worker (子代理) 的 TDD 入口. worker 不执行 `tdd/SKILL.md` 的会话计划相位 - 那需要与我对话, 子代理做不到, 也不回退到该流程.

确定性分两级:

- **spec 级 (硬门禁)**: 验收行为, 外部接口契约, 验证入口必须由 PRODUCT/TECHNICAL/EXECUTION/issue 确定. 任一缺失或互相冲突 -> 停止, 报告父会话, 不猜测.
- **单元级 (默认授权)**: 新代码单元的公共接口形状, 要测试的行为清单和实现顺序, 通常不被 spec 确定, 这属正常, 不触发停止. 授权你在当前 issue 允许范围内自定, 并在 note 的 "接口与测试清单" 区陈述 (见下). 已被 spec 或 DECISIONS 确定的接口形状和测试用例 (如 HILT 决策) 属 spec 级, 不在授权内, 不得自行改动.

## 两相执行

Spec Pack 和当前 issue 已提供规格. 跳过 `tdd` 的计划对话, 但计划本身不跳过 - 你分两相工作:

**计划相**: 阅读权威输入和相关代码, 不写实现代码或测试. 在 note 写出 "接口与测试清单" - 公共接口草图, 计划测试的行为清单及顺序, 以及改动入口预判. 写完停止返回, 等父会话审查. 父会话 resume 即授权进入实现相 (可能附纠正意见, 先修计划).

**实现相**: 红-绿-重构循环:

1. RED: 按清单和 issue 覆盖的 AC/TG/NFR 写一个行为测试 -> 失败.
2. GREEN: 写最少代码通过.
3. REFACTOR: 清理重复/加深模块, 保持 green. 不越过 issue 允许范围.

超出 issue 允许范围的重构候选不实施, 记入 note "重构候选 (超出范围)" 区: 内容, 理由, 预估影响. 无则写 "无".

参考 `tests.md`, `mocking.md`, `refactoring.md`.

## 实现发现

实现中学到的, 不改变 spec/issue 边界/必须遵守决策的测试计划调整 (增删边界测试, 调整顺序, 修正接口草图) -> 记入 note "实现发现" 区, 继续工作, 不停止.
会改变 spec, issue 边界或必须遵守决策的发现 -> 停止, 写入 "实现发现" 区并报告父会话.

## 修复场景

review 指出测试偏离 Spec 时, 先修正测试, 使它表达正确规格并对当前错误代码变 red, 再修正代码到 green. note 中区分修正测试及原因和新增测试.

## 证据

note 必含各区: 改动入口, 接口与测试清单, 实现发现, 重构候选 (超出范围), 每个 RED/GREEN 循环的命令和失败/通过输出, 风险/阻塞, 决策偏离. 无法提供 RED 时说明原因, 并给出可复核验证. 每项证据标出覆盖的 AC/TG/NFR.
