# 测试驱动开发

## 哲学

**核心原则**: 测试应通过公共接口验证行为, 而非实现细节. 代码可以完全改变; 测试不应因此改变.
**好测试**是集成式的: 它们通过公共 API 走真实代码路径, 描述系统 *做什么*, 而非 *怎么做*. 好测试读起来像规格说明: "用户可以用有效购物车结账" 会准确告诉你存在哪种能力. 这些测试能经受重构, 因为它们不关心内部结构.
**坏测试**与实现耦合. 它们 mock (模拟) 内部协作者, 测试私有方法, 或通过外部手段验证 (例如直接查询数据库, 而非使用接口). 警示信号: 你重构时测试失败了, 但行为没变. 若重命名内部函数会让测试失败, 这些测试测的是实现, 而非行为.

示例见 [tests.md](tests.md), mock 指南见 [mocking.md](mocking.md). 
有限制条件的参考材料: 仅当 PRODUCT/TECHNICAL/EXECUTION/issue 已确定所有行为和接口, 无需再向我确认时, 才读 [worker-tdd.md](worker-tdd.md), 否则按本文件标准流程走.

## 反模式: 横向切片

**不要先写所有测试, 再写所有实现.** 这是"横向切片": 把 RED 当成"写所有测试", 把 GREEN 当成"写所有代码".
这会产生**糟糕测试**:

- 批量写出的测试测的是 *想象中的* 行为, 而非 *实际的* 行为.
- 你最终测试的是事物的 *形状* (数据结构, 函数签名), 而非面向用户的行为.
- 测试会对真实变化不敏感: 行为坏了仍通过, 行为没问题却失败.
- 在未理解实现前就承诺测试结构, 会超出认知范围.

**正确方式**: 通过曳光弹 (tracer bullets) 做纵向切片. 一个测试 -> 一个实现 -> 重复. 每个测试都回应你从上一轮学到的东西. 因为代码刚由你写出, 你清楚哪些行为重要, 以及如何验证它.

```
错误(横向):
  RED:   test1, test2, test3, test4, test5
  GREEN: impl1, impl2, impl3, impl4, impl5

正确(纵向):
  RED->GREEN: test1->impl1
  RED->GREEN: test2->impl2
  RED->GREEN: test3->impl3
  ...
```

## 工作流

### 1. 计划

探索代码库时, 使用项目的领域词汇表 (如果有), 让测试名称和接口词汇与项目语言保持一致, 并尊重你正在触碰区域的 ADR. 面向用户的测试计划和说明使用中文. 代码测试名遵循项目既有语言风格: 既有测试用中文描述时新测试也用中文; 既有测试用英文命名时延续英文, 不强行翻译 API 名称/错误原文/路径/命令/代码标识符.

写任何代码之前:

- [ ] 在会话中与我确认需要哪些接口变更
- [ ] 在会话中与我确认要测试哪些行为 (并排序优先级)
- [ ] 识别 deep module 的机会 (小 interface, 大 implementation) - 从 `codebase-design` skill 获取词汇和可测试性检查
- [ ] 列出要测试的行为 (不是实现步骤)
- [ ] 在会话中获得我对计划的批准, 不让我阅读文档后确认

询问: "公共接口应该长什么样? 哪些行为最重要, 需要优先测试?"

**你无法测试所有东西.** 在会话中与我确认哪些行为最重要. 把测试精力集中在关键路径和复杂逻辑上, 而非每种可能的边界情况.

### 2. Tracer Bullet 垂直切片

编写一个只确认系统中一件事的测试:

```
RED:   为第一个行为写测试 -> 测试失败
GREEN: 编写最小代码让它通过 -> 测试通过
```

这就是你的 tracer bullet - 证明路径端到端可行.

### 3. 增量循环

对每个剩余行为:

```
RED:   编写下一个测试 -> 失败
GREEN: 编写最小代码让它通过 -> 通过
```

规则:

- 一次只写一个测试
- 只写足够通过当前测试的代码
- 不要预判未来测试
- 让测试聚焦于可观察行为

### 4. 重构

所有测试通过后, 寻找[重构候选项](refactoring.md):

- [ ] 提取重复
- [ ] 加深模块 (把复杂度移到简单接口之后)
- [ ] 在自然适合的地方应用 SOLID 原则
- [ ] 思考新代码暴露了现有代码的哪些问题
- [ ] 每个重构步骤后运行测试

**处于 RED 时绝不重构.** 先到 GREEN.

## 每轮检查清单

```
[ ] 测试描述行为, 而不是实现
[ ] 测试只使用公共接口
[ ] 测试能经受内部重构
[ ] 代码对当前测试来说是最小的
[ ] 没有添加猜测性的功能
```

## 完成标准

- 每个已批准行为都有 red 证据和 green 证据.
- 最终测试命令已运行并通过, 或失败原因与本任务无关且已说明.
- 重构只在 green 后执行, 且每次重构后测试仍通过.
- 最终回复包含变更摘要, 测试命令, red/green 证据, 剩余风险.
