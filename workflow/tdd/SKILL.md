开始前, 调用 `domain-awareness` skill 只读感知当前工作目录的领域模型.

# 测试驱动开发

TDD 是 red -> green 循环. 本 skill 让循环产出好测试, 这些测试值得保留. 它说明好测试是什么, 也说明测试放在哪里, 还列出反模式和循环规则. 
每一轮都应用所有章节, 在循环前查阅, 在循环中继续查阅. 不要等结束后再补看.
探索代码库时, 让测试名称匹配领域语言. 让接口词汇也匹配领域语言. 同时遵守触及区域内的 ADR.

## 测试设计前置

进入 red -> green 循环前, 你先探索本次修改范围内的代码, 识别此次修改会触及哪些模块, 哪些分层, 哪些对外接口, 以及行为可被观察的接缝. 
逐个模块推进, 模块内自顶向下遍历代码分层, 针对每个层次的对外接口设计面向接缝的单元级测试用例, 同时覆盖主用例, 边界情况, 异常情况.

随后向我汇报测试设计, 包括模块, 层次, 接口, 接缝, 以及测试用例. 每条测试用例只用一句话概括. 
在我答复以前, 这些测试用例不可用, 你不得写入测试代码, 也不得把它们当作已确认约束推进实现. 
如果代码库有当前需求的决策账本/Spec 文件, 且其中的内容已经回答了测试设计需要我确认的问题, 就不必再问我.

## 好测试是什么

测试通过公开接口验证行为. 不检查实现细节. 代码可以彻底改变. 测试不应随之改变. 好测试读起来像规格.
例如 "有效购物车可以结账". 它清楚说明已有能力. 它能扛住重构. 因为它不关心内部结构.
示例见 [tests.md](tests.md). mock 规则见 [mocking.md](mocking.md).

## 接缝 - 测试放在哪里

**接缝** 是你测试的公开边界. 也就是观察行为的接口. 你无需伸进内部. 测试放在接缝上. 绝不针对内部实现.
**只测试预先确认的接缝和用例.** 写任何测试前, 先写下要测试的接缝和对应测试用例. 然后向我确认. 未确认的接缝上不写测试. 未确认的用例不进入 red -> green 循环. 你不可能测试一切. 预先同意接缝和用例. 这样测试工作才会落到关键路径和复杂逻辑上. 而不是落到每个边缘情况上.

问: "公开接口是什么, 我们要测试哪些接缝?"

## 反模式

- **绑定实现** - mock 内部协作者. 测试私有方法. 或通过旁路验证. 例如绕过接口查数据库. 识别信号: 行为没变, 重构却弄坏测试.
- **同义反复** - 断言用和代码相同的方式重算预期值. 例如 `expect(add(a, b)).toBe(a + b)`, 用同样方式手写出的 snapshot, 或断言常量等于它自己. 这种测试按构造必然通过. 它永远无法和代码产生分歧. 预期值必须来自独立真相源. 可以是已知正确的字面量. 可以是手算例子. 也可以是规格.
- **横向切片** - 先写完所有测试. 再写所有实现. 批量测试验证的是*想象中的*行为. 你测试事物形状. 而不是面向用户的行为. 测试会对真实变更失敏. 你也会在理解实现前锁死测试结构. 改用**纵向切片**: 一个测试 -> 一个实现 -> 重复. 每个测试都是 **tracer bullet**. 它会响应上一轮教给你的东西.

## 循环规则

- **先红后绿.** 先写失败测试. 再只写足够让它通过的代码. 不预判未来测试. 不加投机功能.
- **一次一个切片.** 每轮只覆盖一个接缝. 一个测试. 一个最小实现.
- **重构不属于循环.** 重构属于 review 阶段. 见 `code-review` skill. 不属于 red -> green 实现循环.
