开始前, 调用 `domain-awareness` skill 感知领域模型, 调用 `verification-contract` skill 判断是否确需红绿循环及其共用底线. 无需新增自动化测试时返回原任务的真实入口验证, 不进入本循环.

# 测试驱动开发

TDD 是 red -> green 循环, 只处理确需测试推进的切片. 重构走 `verification-contract` 的改前通过/改后保持通过, 不在此制造失败. 本 skill 让留下的测试只锁住行为, 不锁实现.
每一轮都应用所有章节, 在循环前查阅, 在循环中继续查阅. 不要等结束后再补看.
探索代码库时, 让测试名称匹配领域语言. 让接口词汇也匹配领域语言. 同时遵守触及区域内的 ADR.

## 测试设计

只从 `verification-contract` 允许的已确认用例中, 选本轮确需自动化的一个公开接缝. 优先连接测试环境的真实服务. 不逐层补主用例/边界/异常用例: 那会把实现的层数误当成需要验证的产品行为.

对选中的测试用例向我汇报. 每条测试用例都用一句话概括: `当...时, xx 要 ...`.
权威输入已确认的用例不重复问我; 未确认的须先请我确认, 不自行增加产品用例.
权威输入在而答案不在, 就是缺口: 不得现场即兴定案, 调用 `deliberate` skill 敲定并固化, 再继续.

已由权威输入或我确认的用例是 red -> green 循环的唯一输入: 本次任务由 issue 驱动时, 先补充进所属 issue 的 `测试切片` 节, 不在切片里的用例不得进入循环; 无 issue 时, 确认后直接进循环.

## 好测试是什么

测试通过公开接口验证行为. 不检查实现细节. 代码可以彻底改变. 测试不应随之改变. 好测试读起来像规格.
例如 "有效购物车可以结账". 它清楚说明已有能力. 它能扛住重构. 因为它不关心内部结构.
示例见 [tests.md](tests.md). mock 规则见 [mocking.md](mocking.md).

## 接缝 - 测试放在哪里

**接缝** 是你测试的公开边界. 也就是观察行为的接口. 你无需伸进内部. 测试放在接缝上. 绝不针对内部实现.
写任何测试前, 明确对应的公开接缝及已确认用例. 测试只观察接缝上的行为, 代码内部改变时用例仍应成立.

## 反模式

- **绑定实现** - mock 内部协作者. 测试私有方法. 或通过旁路验证. 例如绕过接口查数据库. 识别信号: 行为没变, 重构却弄坏测试.
- **同义反复** - 断言用和代码相同的方式重算预期值. 例如 `expect(add(a, b)).toBe(a + b)`, 用同样方式手写出的 snapshot, 或断言常量等于它自己. 这种测试按构造必然通过. 它永远无法和代码产生分歧. 预期值必须来自独立真相源. 可以是已知正确的字面量. 可以是手算例子. 也可以是规格.
- **横向切片** - 先写完所有测试. 再写所有实现. 批量测试验证的是*想象中的*行为. 你测试事物形状. 而不是面向用户的行为. 测试会对真实变更失敏. 你也会在理解实现前锁死测试结构. 改用**纵向切片**: 一个测试 -> 一个实现 -> 重复. 每个测试都是 **tracer bullet**. 它会响应上一轮教给你的东西.

## 循环规则

- **先红后绿.** 先写失败测试. 再只写足够让它通过的代码. 不预判未来测试. 不加投机功能.
- **一次一个切片.** 每轮只覆盖一个接缝. 一个测试. 一个最小实现.
- **分级跑测试.** 每轮跑的不是全套. 内循环只跑当前这一条用例 (单文件, 或用 `-k` 这类选择器), 秒级返回. 本次任务触及的模块在收尾时跑一遍. 全套只在交付前跑一次; 上层流程里有合并节点时, 全套归最终的集成合并节点, 本任务不跑. 全套要几分钟时, 每轮拉全套会让执行者为了省时间跳过红态确认, 或攒一批改动再验, 循环就退化成先写实现后补测试.
- **重构不属于循环.** 重构属于 review 阶段. 见 `code-review` skill. 不属于 red -> green 实现循环.
