开始前, 使用 `domain-awareness` skill 只读感知当前工作目录的领域模型.

用 `grilling` skill 沿设计树盘问我. 用 `domain-modeling` skill 在盘问期间维护领域语言文件或 ADR. 需要记录会影响代码, 测试, 外部行为, 边界或后续追溯的决策时, 调用 `decision-ledger` skill 维护本 feature 的 `DECISIONS.md`.

文档只供后续 AI 使用. 我不会通过阅读文档补齐上下文或批准方案. 每项影响产品, API, 架构, 范围, 风险或验证的决定, 必须在会话中向我说明含义, 影响和你的推荐, 再取得明确确认. 不要让我阅读生成文档后再确认.

固定首问: 要不要懒设计?

- 我说要 -> 调用 `lazy-design` skill. 盘问中若我的回答违背懒设计, 立即指出并尝试说服我改变决策.
- 我说不要 -> 走常规设计.

## 认知校准节奏

`grilling` 是认知校准规则的单一真相源. 本 skill 只规定两阶段盘点节奏:

1. 初步探索上下文并明确问题边界后, 简述即将处理的产品决策域, 询问我对问题, 受益者和业务行为已明确不确定或希望补充的部分.
2. 产品分支关闭, 进入技术分支前, 简述即将处理的技术决策域, 再询问我已明确不熟悉或希望补充的部分.

阶段内部不固定重复盘点, 按 `grilling` 中的认知信号触发. 不建立长期用户知识档案, 不把认知状态写入 `DECISIONS.md`; 客观待查事实按 Product/Technical Spec 的待验证事实规则处理.

## 盘问顺序

先关闭产品分支, 再进入依赖它的技术分支. 一次只问一个问题.

### 1. 产品分支

依次关闭: 问题和受益者, 目标和成功信号, 非目标, 用户故事, 业务规则, 正常/失败/边界场景, 验收标准.

每关闭一个分支, 在会话中用简短语言说明已确认结论及其直接影响. 不讨论尚不依赖该结论的实现细节.

完成标准: 产品目标, 非目标, 行为和验收标准无阻塞未知; 我已在会话中明确确认关键产品取舍; 重要产品分支满足 `grilling` 的分支完成标准.

### 2. 技术分支

基于已确认产品分支, 依次关闭: 架构和模块责任, API/schema/状态机, 关键流程, 异常和边界处理, 安全, 性能/可观测性/可用性, 测试策略, 代码允许/禁止范围, 风险和停止条件.

可由仓库, 配置, 测试或既有文档查明的事实先自行探索, 不转问我. 事实与已确认决策冲突时, 在会话中说明证据和影响, 再让我选择.

完成标准: 后续 `to-product-spec` 和 `to-technical-spec` 无需发明产品/API/架构/范围决策; 我已在会话中获知关键技术方案, 代价, 风险和验证方式; 重要技术分支满足 `grilling` 的分支完成标准.

## 决策记录边界

- `DECISIONS.md` 记录本 feature 的产品, 代码, 边界, 测试决策和代码追踪.
- ADR 只记录长期架构决策.
- 领域语言文件只记录领域词汇, 不承载实现决策.
- 新增, 替代, 废弃决策前必须得到我确认.
- 后续 Spec 生成 skill 只能整理这些已确认决策, 不得新增决策.

结束时在会话中给出高密度口头回顾: 产品结果, 关键技术选择, 明确不做, 主要风险, 验证方式, 已补齐的重要知识缺口, 新暴露盲区的处理结果, 被接受的不确定性. 不要求我阅读任何文档.

## 多做一步
盘问会话结束以后, 询问我是否生成 spec 文档.
如果我说不用, 跳过本节内容.
如果我说要, 那么依次执行这些 skill, 一个完成后, 再执行下一个: to-product-spec, to-technical-spec, to-execution-spec.
