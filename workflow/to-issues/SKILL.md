使用垂直切片 (tracer bullets) 把需求拆成可独立领取的议题. issue 是 AFK 的主要输入, 必须表达目标, 边界和验证入口, 但不写逐文件实现计划.

## 流程

### 1. 收集上下文

先确认已获得本地议题跟踪器约定; 如果没有, 使用 `setup-workspace` skill. 读取 PRD 和 `DECISIONS.md` (如存在). 我传入议题引用 (议题编号/URL 或路径) 作为参数时, 从议题跟踪器获取该议题, 阅读其完整正文和评论. 需要维护决策引用时, 调用 `decision-ledger` skill.

### 2. 探索代码库 (可选)

如果还没探索过代码库, 先这样做以了解代码当前状态. 议题标题和描述应使用项目领域术语, 并遵守触及区域的 ADR.

### 3. 判断拆分粒度

起草切片之前, 先判断需求适合作为单个 issue 还是多个 issues.
issues 太多会增加管理成本, 导致执行总时长增加, 过少则会增加每个 issue 的复杂度, 导致执行者上下文附载过重. 在两者之间权衡取舍是拆分粒度判断的核心.


**判断信号**:

| 信号 | 倾向单 issue | 倾向多 issues |
|------|-------------|--------------|
| 垂直切片数 | 只有 1 条自然切片 | 2+ 条独立可验证切片 |
| 变更文件数 | <=3 个文件 | >3 个文件, 或跨多个模块 |
| 是否可一次 PR 交付 | 是 | 需要分阶段合并以降低风险 |
| 是否存在独立可演示的中间状态 | 否 | 是, 每个切片可单独验证 |
| 是否涉及多种技能/角色 | 否 | 是 (如需要前端 + 后端 + DBA) |

**核心判断逻辑**: 需求天然只产生一条端到端切片, 或拆分后各切片耦合过紧无法独立验证时, 作为单 issue 处理.
- **单 issue**: 跳过步骤 4, 进入步骤 5 (简化确认)
- **多 issues**: 进入步骤 4 (起草垂直切片)

### 4. 起草垂直切片

把需求拆成 **tracer bullets** issues. 每个 issue 是一条贯穿所有集成层的端到端细窄垂直切片, 而非某一层的水平切片.
切片可以在正文中说明适合 `HITL` 或 `AFK`. `HITL` 切片需要人类交互, 例如架构决策或设计评审. `AFK` 切片可以在无人类交互的情况下实现并合并. 可行时优先 `AFK` 而非 `HITL`. 该归属只作为正文叙述, 不作为状态字段, 标签或可流转值.

<vertical-slice-rules>
- 每个切片都通过每一层 (schema/API/UI/tests) 交付一条狭窄但完整的路径
- 已完成的切片可以单独演示或验证
- 宁可创建多个薄切片, 也不要创建少量厚切片
</vertical-slice-rules>

### 5. 向我确认

#### 多 issues 路径

以编号列表展示拟定的切片, 每个切片简要说明 `要构建什么`, `相关决策 ID`, `允许/禁止范围`, `验证入口`, `覆盖的用户故事`.

询问我:

- 粒度是否合适? (太粗 / 太细)
- 依赖关系是否正确?
- 是否应进一步合并或拆分某些切片?
- 是否正确标记了 HITL 和 AFK 切片?

持续迭代, 直到我批准拆分方案.

#### 单 issue 路径

展示判断依据和拟定的 issue 草稿:

```
**拆分判断**: 单 issue
**依据**: [命中的信号, 如: 变更集中在 2 个文件 / 单条端到端切片 / 可一次 PR 交付]

**标题**: [拟定的 issue 标题]
**相关决策**: [D001, D002 或 无]
**允许范围**: [模块/目录/行为范围]
**禁止范围**: [不能碰的模块/API/schema/行为]
**验证入口**: [推荐测试命令或验收方式]
**验收标准**:
- [ ] [标准 1]
- [ ] [标准 2]
- [ ] [标准 3]
```

询问我: "需求适合作为单个 issue 处理, 你同意吗? 还是希望拆分为多个?"

- 我同意 -> 进入步骤 6 发布
- 我要求拆分 -> 回到步骤 4 走多 issues 路径

### 6. 将议题发布到议题跟踪器

为每个已批准切片, 在本地议题跟踪器中发布一个新议题. 本地 Markdown tracker 固定写入 `docs/changes/<feature-slug>/issues/<NN>-<slug>.md`. 使用下面的议题正文模板. 每个 issue 初始包含执行标记 `- [ ] 已实现`, 不写 `Status:` 或等价状态行.
按依赖顺序发布议题 (阻塞项优先), 这样就可以在"被阻塞于"字段中引用真实的议题标识符.
完成标准: 每个已批准切片都有落盘 issue 路径, 编号连续, 阻塞引用可解析, 有相关决策的 issue 已与 `DECISIONS.md` 双向引用同步, 无相关决策的 issue 明确写"无", 最终回复列出创建文件和初始执行标记.

<issue-template>
## 父级

对议题跟踪器中父议题的引用 (来源是现有议题时; 否则省略本节).

## 执行(Execution)

- [ ] 已实现

## 要构建什么

对此垂直切片的简明描述. 描述端到端行为, 而非逐层实现. 结尾用一句话说明此切片适合 AFK 或 HITL 及原因. 这是正文叙述, 不是状态字段.
避免具体文件路径或代码片段 - 它们很快会过时. 例外: 原型产出的片段比文字描述更精确地表达某个决策 (状态机/reducer/schema/类型形状) 时, 在此内联该片段, 并简要说明它来自原型. 只保留决策含量高的部分, 不是可运行演示.

## 相关决策

`DECISIONS.md` 中与此切片相关的决策 ID. 不要复述决策内容, 只列出编号. 如果没有相关决策, 写"无".

## 允许范围

可以修改的模块, 目录, 文件模式或行为范围. 写边界, 不写逐文件实现计划.

## 禁止范围

明确不能修改的模块, API, schema, 行为或非目标范围. 如果没有额外禁止项, 写"无额外禁止项, 但不得超出本 issue 目标".

## 验证入口

推荐测试命令, 测试目标或可观察验收方式. 如果当前无法确定命令, 写应探索的测试入口, 不编造命令.

## 风险提示

已知高风险点, 或 worker 必须停止上报的情况. 如果没有, 写"无已知额外风险".

## 适合 AFK 的原因

说明为什么此切片无需进一步产品/API/架构决策即可执行. 如果不适合 AFK, 写明需要 HITL 的原因.

## 验收标准

- [ ] 标准 1
- [ ] 标准 2
- [ ] 标准 3

## 被阻塞于

- 对阻塞工单的引用 (如有)

如果没有阻塞项, 则写"无 - 可以立即开始".

</issue-template>

不要关闭或修改任何父议题.
