# To Issues

使用垂直切片 (tracer bullets) 把计划拆成可独立领取的议题.

你应该已获得议题跟踪器和分流 (call `triage` skill) 标签词汇; 如果没有, 使用 `setup-workspace` skill.

## 流程

### 1. 收集上下文

基于对话上下文中已有的任何内容开展工作. 用户传入议题引用 (议题编号/URL 或路径) 作为参数时, 从议题跟踪器获取该议题, 阅读其完整正文和评论.

### 2. 探索代码库 (可选)

如果还没探索过代码库, 先这样做以了解代码当前状态. 议题标题和描述应使用项目领域术语, 并遵守触及区域的 ADR.

### 3. 判断拆分粒度

起草切片之前, 先判断计划适合作为单个 issue 还是多个 issues.

**判断信号**:

| 信号 | 倾向单 issue | 倾向多 issues |
|------|-------------|--------------|
| 垂直切片数 | 只有 1 条自然切片 | 2+ 条独立可验证切片 |
| 变更文件数 | <=3 个文件 | >3 个文件, 或跨多个模块 |
| 是否可一次 PR 交付 | 是 | 需要分阶段合并以降低风险 |
| 是否存在独立可演示的中间状态 | 否 | 是, 每个切片可单独验证 |
| 是否涉及多种技能/角色 | 否 | 是 (如需要前端 + 后端 + DBA) |

**核心判断逻辑**: 计划天然只产生一条端到端切片, 或拆分后各切片耦合过紧无法独立验证时, 作为单 issue 处理.

- **单 issue**: 跳过步骤 4, 进入步骤 5 (简化确认)
- **多 issues**: 进入步骤 4 (起草垂直切片)

### 4. 起草垂直切片

把计划拆成 **tracer bullets 式** 议题. 每个议题都是一条贯穿所有集成层的端到端细窄垂直切片, 而非某一层的水平切片.

切片可以是 `HITL` 或 `AFK`. `HITL` 切片需要人类交互, 例如架构决策或设计评审. `AFK` 切片可以在无人类交互的情况下实现并合并. 可行时优先 `AFK` 而非 `HITL`. `HITL` / `AFK` 是类型 token, 可能被机器读取时, 中文解释必须放在独立字段中.

<vertical-slice-rules>
- 每个切片都通过每一层 (schema/API/UI/tests) 交付一条狭窄但完整的路径
- 已完成的切片可以单独演示或验证
- 宁可创建多个薄切片, 也不要创建少量厚切片
</vertical-slice-rules>

### 5. 向用户确认

#### 多 issues 路径

以编号列表展示拟定的拆分方案. 对每个切片展示:

- **标题**: 简短的描述性名称
- **类型**: HITL / AFK
- **类型说明**: 需要人类交互 / 无需人类交互即可实现
- **阻塞于**: 必须先完成的其他切片 (如有)
- **覆盖的用户故事**: 该切片处理哪些用户故事 (如果源材料中有)

询问用户:

- 粒度是否合适? (太粗 / 太细)
- 依赖关系是否正确?
- 是否应进一步合并或拆分某些切片?
- 是否正确标记了 HITL 和 AFK 切片?

持续迭代, 直到用户批准拆分方案.

#### 单 issue 路径

展示判断依据和拟定的 issue 草稿:

```
**拆分判断**: 单 issue
**依据**: [命中的信号, 如: 变更集中在 2 个文件 / 单条端到端切片 / 可一次 PR 交付]

**标题**: [拟定的 issue 标题]
**验收标准**:
- [ ] [标准 1]
- [ ] [标准 2]
- [ ] [标准 3]
```

询问用户: "计划适合作为单个 issue 处理, 你同意吗? 还是希望拆分为多个?"

- 用户同意 -> 进入步骤 6 发布
- 用户要求拆分 -> 回到步骤 4 走多 issues 路径

### 6. 将议题发布到议题跟踪器

为每个已批准切片, 在议题跟踪器中发布一个新议题. 本地 Markdown tracker 固定写入 `docs/changes/<feature-slug>/issues/<NN>-<slug>.md`. 使用下面的议题正文模板. 这些议题被视为已准备好交给 AFK agent, 除非另有指示, 请用正确的分流 (triage) 标签发布. 目标 issue tracker 约定在文件中写状态行时, 使用独立纯 token 行 `Status: ready-for-agent`, 中文说明另起一行 `状态说明: 已完整说明, 适合 AFK agent 接手.`

按依赖顺序发布议题 (阻塞项优先), 这样就可以在"被阻塞于"字段中引用真实的议题标识符.

完成标准: 每个已批准切片都有落盘 issue 路径, 编号连续, 阻塞引用可解析, 最终回复列出创建文件和状态标签.

<issue-template>
## 父级

对议题跟踪器中父议题的引用 (来源是现有议题时; 否则省略本节).

## 要构建什么

对此垂直切片的简明描述. 描述端到端行为, 而非逐层实现.

避免具体文件路径或代码片段 - 它们很快会过时. 例外: 原型产出的片段比文字描述更精确地表达某个决策 (状态机/reducer/schema/类型形状) 时, 在此内联该片段, 并简要说明它来自原型. 只保留决策含量高的部分, 不是可运行演示.

- [ ] 标准 2
- [ ] 标准 3

## 被阻塞于

- 对阻塞工单的引用 (如有)

</issue-template>
