调查一个变更在别处会破坏什么, 在它合入之前发现. 用于 "这个变更的影响范围", "这改动可能弄坏什么", 或审查一个自己还没把握的小 diff.

自己调查并运行证明是我的角色. 验收指挥者不能借调用本技能亲自验收, 应派实际验收子会话来做; 大变更要求的多模型同题调查可以交给子会话.

列出调用者不是任务: agent 一秒就能 grep 出来. 任务是 grep 看不见的破坏.

## 1. 读变更并定位历史

读 diff 里新增, 修改, 删除的符号, 以及现在行为不同的地方, 包括 diff 没写出来的部分: 注册时机, 导入顺序, 运行环境. 想知道这行为什么被写成这样时, 自己跑历史定位:

```bash
git log --oneline -20                  # 近期提交, 找到本次变更的邻居
git show <变更提交>                     # diff 与提交消息
git blame -L <起始行>,<结束行> -- <文件>  # 这行由哪个提交引入
git log --follow -p -- <文件>           # 跨重命名的文件历史
git log --all --oneline -S"<符号>"      # 符号被增删的历史提交
```

从提交消息里取分支或 PR 编号, 再用实际可用的托管入口读正文与讨论, 例如 `gh pr view <编号> --comments`. 取不到这类材料时写明来源限制, 不编造 PR 或历史.

完成标准: 变更涉及的符号, 行为差异和历史来源都有实际提交或材料位置; 拿不到的材料已写明限制.

## 2. 找出关键安全事实

多数看着危险的变更之所以安全, 是因为一两个事实成立, 例如 "这个调用只丢弃已经失效的缓存项, 不做别的". 找到这条事实并验证它, 一次排除大部分危险情况, 比列一长串可能情况更值钱. 时间花在这里.

要查的范围: 调用库的源码, 固定的库版本与本地补丁, 运行时机 (注册时机, 异步, 卸载, 生命周期), JSON 返回, 数据库列, 线格式, 另一种语言读同一批字节, feature flag, 以及三跳之后的下游. 待在 grep 的命中里会漏掉这些, 所以要读源码并给出真实 file:line 或库源码位置.

完成标准: 已指名一两个关键安全事实, 每个都说明了它为什么决定本次变更的安全, 而不是列举所有看似相关的地方.

## 3. 给每个事实标证据级别

对变更安全所依赖的每个事实, 尽量往下一级, 并说明停在哪一级:

1. 我说是这样. 单独没有价值.
2. 指到真实 file:line, 或库自己的源码.
3. 逐步走查失败路径, 证明坏情况到不了.
4. 实际跑过: 调用真实代码, 判断错时会明确失败的脚本或测试.
5. 在运行中的应用里复现.

完成标准: 每个关键事实都标了级别并说明停下的理由, 没有把低级别材料说成应用实跑.

## 4. 写可失败的证明脚本

第 4 级通常是一个小脚本: 导入应用实际使用的同款库与固定版本, 调用担心的那个准确函数, 判断错时以非零退出码失败. 运行它, 贴原始输出, 不打磨成结论.

- 脚本先断言库版本与运行环境, 否则测到的不是应用实际用的那份代码.
- 判断用 assert 或显式非零退出, 不用只打印一行看着对的话.
- 临时脚本放仓库外的临时目录, 或在报告里附全文, 不改产品源码与测试. 只读调查不需要额外授权; 需要写仓库或跑有副作用的应用时先问.
- 脚本全文和输出都留在交接里, 让别人能重跑.

无法证明的事实明确写未证实, 并写清缺什么: 缺数据, 缺入口, 缺运行环境, 还是只缺权限. 靠猜测或静默略过都不算证据.

完成标准: 关键事实要么有跑过的, 判断错会失败的脚本与原始输出, 要么明确标未证实并写出缺口.

## 5. 风险与已排除项

风险与已排除项分开写. 混成一张 "注意事项" 列表, 读的人就分不清哪些是会坏的事, 哪些是已经查过没事的地方.

- 风险: 每条写清怎么坏, 真实 file:line, 发生概率, 发生时的代价, 以及检查方法 (跑什么, 看什么). 概率与代价要给依据: 数据分布, 调用频率, 能否重试, 失败是否静默.
- 已排除项: 查过并确认没事的地方, 写查了什么, 凭什么说没事. 排除靠证据或证据级别, 不靠 "看起来没事".
- 符号检索没有结果也是答案: 报出实际检索命令与范围 (路径, 符号, 排除的目录), 说明没找到调用者, 再说明这个结论覆盖不到哪里. 不编造调用者, API 或文件来把报告填满.

完成标准: 每条风险都能被人按写下的方法独立检查; 已排除项里没有混入未检查的猜测; 检索空结果写明了范围与边界.

## 6. 大或宽变更用多模型同题调查

先判断实际影响, 再看要不要多路. 判定依据是影响面, 不是 diff 行数: 跨多个模块, 跨仓库, 改了被下游共享的线格式, 数据库列或公共接口, 都算大或宽, 哪怕只改几十行.

- 大或宽: 让不同模型的会话对同一批关键事实做同题调查, 再合并答案. 合并时逐条事实对齐, 一致的事实保留最高证据级别, 分歧两说并存并标为未决, 各自的证据级别都不动. 开新会话与合并的步骤见 [reference/multimodel.md](reference/multimodel.md).
- 只有一款模型可用, 或调用方只授权一款: 交接里写明这是多模型同题调查的能力缺口, 已经真实证明的事实保留原证据级别, 不改标未证实, 也不假装多路已经做完.
- 影响确实局限, 且调用方选择单路: 正常交付单路结论, 写明这是单路, 说明后续可以加查.

完成标准: 大或宽的判断有依据; 走了多路就有会话与合并记录, 单路或缺模型能力时缺口写在交接里.

## 7. 交接

按五部分交付; 哪部分缺就写明缺, 不用别的部分顶替:

1. 做了什么: 读到的变更与历史, 查过的位置, 跑过的命令, 以及没有覆盖到的范围.
2. 关键安全事实与证据级别: 每条一句话陈述, 级别, 停下的理由, 加上证明脚本与原始输出, 或未证实的缺口.
3. 风险: 位置, 概率, 代价, 检查方法.
4. 已排除项: 查过并确认没事的地方.
5. 合并前最便宜的复现: 一条能真跑的命令或最小脚本, 抓住最要紧的问题, 脚本全文一起给.

只交接材料, 不自动合并, 不创建 PR; 对外发出前脱敏. 成文前按 [reference/report-style-zh.md](reference/report-style-zh.md) 整理一遍中文: 短句, 大白话, 事实/推断/未证实分开, 删冗但不删证据, 风险强度, 数量与边界.

**回复**: 上面这份交接, 其中关键安全事实要么已证明, 要么标为未证实.
