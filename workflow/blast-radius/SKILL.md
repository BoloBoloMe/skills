调查一个变更在别处会破坏什么. 目标是在合入前发现坏情况. 触发说法: "这个变更的影响范围", "这改动可能弄坏什么". 也可以用在你自己还没把握的小 diff.

调查与运行证明是你的角色, 你自己做. 验收指挥者不能借调用本技能亲自验收. 他要派实际验收子会话来. 大变更要求的多模型同题调查可以交给子会话.

列出调用者不算任务: agent 一秒就能 grep 出来. 任务是找出 grep 看不见的破坏.

## 1. 读变更并定位历史

读 diff 里新增, 修改, 删除的符号. 也读现在行为不同的地方. diff 没写出来的部分同样要看. 例如注册时机, 导入顺序, 运行环境.

想知道这行为什么写成现在这样时, 自己跑历史定位:

```bash
git log --oneline -20                  # 近期提交, 找到本次变更的邻居
git show <变更提交>                     # diff 与提交消息
git blame -L <起始行>,<结束行> -- <文件>  # 这行由哪个提交引入
git log --follow -p -- <文件>           # 跨重命名的文件历史
git log --all --oneline -S"<符号>"      # 找到增删该符号的提交
```

从提交消息里取分支或 PR 编号. 再用实际可用的托管入口读正文与讨论. 例如 `gh pr view <编号> --comments`. 取不到这类材料时写明来源限制. 不编造 PR 或历史.

完成标准: 每个变更符号都有实际提交或材料位置. 行为差异与历史来源同样有. 拿不到的材料写明限制.

## 2. 找出关键安全事实

多数看着危险的变更其实安全, 原因是一两个事实成立. 例如 "这个调用只丢已经失效的缓存项, 不做别的". 找到这条事实并验证它, 一次排除大部分危险情况. 这比列一长串可能情况更值钱, 时间花在这里.

要查的范围: 调用库的源码, 固定版本与本地补丁. 运行时机 (注册, 异步, 卸载, 生命周期). JSON 返回, 数据库列, 线格式. 另一种语言读同一批字节. feature flag, 以及三跳之后的下游. 只看 grep 命中会漏掉这些. 要读源码, 给出真实 file:line 或库源码位置.

完成标准: 已指名一两个关键安全事实. 每条都说明它为什么决定本次变更的安全. 不列举所有看似相关的地方.

## 3. 给每个事实标证据级别

对变更安全所依赖的每个事实, 尽量往下一级. 说明停在哪一级:

1. 你直接断言事实成立. 单独没有价值.
2. 指到真实 file:line, 或库自己的源码.
3. 逐步走查失败路径, 证明坏情况到不了.
4. 实际跑过: 调用真实代码, 判断错就失败的脚本或测试.
5. 在运行中的应用里复现.

完成标准: 每个关键事实都标了级别并说明停下的理由. 不把低级别材料说成应用实跑.

## 4. 写可失败的证明脚本

第 4 级通常是一个小脚本. 它导入应用实际用的同款库与固定版本. 它调用你担心的那个准确函数. 判断错时脚本以非零退出码失败. 运行它, 贴原始输出, 不打磨成结论.

- 脚本先断言库版本与运行环境. 否则测到的不是应用实际用的那份代码.
- 判断用 assert 或显式非零退出. 不只打印一行看着对的话.
- 临时脚本放仓库外的临时目录, 或在报告里附全文. 产品源码与测试保持原样. 只读调查不用额外授权; 要写仓库或跑有副作用的应用, 先问我.
- 脚本全文与输出都留在交接里, 让别人能重跑.

无法证明的事实明确写未证实. 写清缺什么: 缺数据, 缺入口, 缺运行环境, 还是只缺权限. 靠猜测或静默略过都不算证据.

完成标准: 关键事实都有跑过的脚本与原始输出. 脚本判断错就失败. 或者明确标未证实, 并写出缺口.

## 5. 一次性实验的边界

关键事实没有正式测试兜底时, 可以跑一次本地一次性实验. 前提是调用方批准了范围. 它只是调查手段, 不是新的正式用例. 动手前确认范围, 结束后按范围清理.

- 记录里写明这是 "非正式 TC". 写清授权范围与实验覆盖到哪一步.
- 只在批准的独立脚本与临时目录里动手. 不改产品源码, 不改既有测试, 不改项目配置. 项目配置也包括构建与运行配置.
- 临时数据放仓库外的临时目录, 或在记录里附全文.
- 按批准范围清理临时文件与后台进程. 清理结果写进交接.
- 实验只证明内部函数在给定输入下的行为. 它不等于成品入口通过. 成品真实入口没跑过, 那条产品场景仍记未运行. 不拿内部结果顶替.
- 要拿到可信结论只能改冻结目标时, 停下并报告缺口. 例如给冻结目标加计数代码. 冻结目标不改, 计数代码不进产品.
- 要新增正式测试或正式接缝才看得到目标行为时, 停下. 把决定交回既有的用例确认流程. 不自己加未经确认的用例或接缝.

完成标准: 交接里有非正式 TC 标记, 批准范围与清理结果. 还要写明哪条产品场景仍未运行. 撞上冻结目标或新接缝时, 停在报告缺口或交回. 没有顺手改产品.

## 6. 风险与已排除项

风险与已排除项分开写. 混成一张 "注意事项" 列表, 读的人就分不清. 哪些是会坏的事, 哪些是查过没事的地方.

- 风险: 每条写清怎么坏, 真实 file:line, 发生概率, 发生时的代价. 再给检查方法: 跑什么, 看什么. 概率与代价要给依据. 例如数据分布, 调用频率, 能否重试, 失败是否静默.
- 已排除项: 查过并确认没事的地方. 写查了什么, 凭什么说没事. 排除靠证据或证据级别, 不靠 "看起来没事".
- 符号检索没有结果也是答案. 报出实际检索命令与范围: 路径, 符号, 排除的目录. 说明没找到调用者. 再说明这个结论覆盖不到哪里. 不编造调用者, API 或文件来把报告填满.

完成标准: 每条风险都能按写下的方法独立检查. 已排除项里没有混入未检查的猜测. 检索空结果写明了范围与边界.

## 7. 大或宽变更用多模型同题调查

先判断实际影响, 再看要不要多路. 判定依据是影响面, 不是 diff 行数. 下面任一成立就算大或宽, 哪怕只改几十行. 条件一: 跨多个模块或跨仓库. 条件二: 改了共享线格式, 数据库列或公共接口. 这些下游会读.

- 大或宽: 让不同模型的会话做同题调查, 拿同一批关键事实. 再合并答案. 合并时逐条事实对齐. 一致的事实保留最高证据级别. 分歧两说并存并标为未决, 各自的证据级别都不动. 开新会话与合并的步骤见 [reference/multimodel.md](reference/multimodel.md).
- 只有一款模型可用, 或只授权一款时, 写清能力缺口. 缺的是第二路同题调查. 已经真实证明的事实保留原证据级别. 不改标未证实, 也不假装多路已经做完.
- 影响确实局限, 且调用方选择单路: 正常交付单路结论. 写明这是单路, 说明后续可以加查.

完成标准: 大或宽的判断有依据. 走了多路就有会话与合并记录. 单路或缺模型能力时缺口写在交接里.

## 8. 交接

按五部分交付. 哪部分缺就写明缺, 不用别的部分顶替:

1. 做了什么: 读到的变更与历史, 查过的位置, 跑过的命令. 还要写没有覆盖到的范围.
2. 关键安全事实与证据级别. 每条一句话陈述, 加级别与停下的理由. 再加证明脚本与原始输出, 或未证实的缺口.
3. 风险: 位置, 概率, 代价, 检查方法.
4. 已排除项: 查过并确认没事的地方.
5. 合并前最便宜的复现: 一条能真跑的命令或最小脚本. 它抓住最要紧的问题, 脚本全文一起给.

只交接材料. 不自动提交, 不自动合并, 不创建 PR. 对外发出前脱敏. 成文前按 [reference/report-style-zh.md](reference/report-style-zh.md) 整理一遍中文. 要求: 短句, 大白话, 事实/推断/未证实分开. 删冗但不删证据. 保留风险强度, 数量与边界.

**回复**: 上面这份交接. 关键安全事实要么已证明, 要么标为未证实.
