# 代码品味

好的代码, 不是写得多漂亮, 覆盖多全面, 而在是否 *正确*, *最小*, *无未来负担*. 关键在用 *最少代码* 实现 *已确定行为*, 不为推测需求多写一行.
最好的代码是未被写下代码, 关键在找到用 *最少代码* 撬动 *最大收益* 的杠杆支点.

通用规则, 验收标准, 降级信号和不能偷懒边界住在 `lazy-design` skill. 开始前调用 `lazy-design` skill 获取它们; 本 skill 只携带实现侧增量.

## 流程

1. **确认行为已定.** 完成标准: 行为来源明确 (Product/Technical/Execution Spec/issue/`lazy-design`/对话), 不在实现阶段重新设计.
2. **跑实现阶梯.** 完成标准: 选中第一个站得住的台阶, 并说明为何在此停下.
3. **收敛到最小 diff.** 完成标准: diff 无法进一步删减, 每个改动都对应已承诺行为.
4. **自检降级信号.** 完成标准: 未命中 `lazy-design` 的降级信号和下方实现侧信号, 或已回到更靠前台阶.
5. **守住不能偷懒处.** 完成标准: 每个风险边界有防护, 或有明确接受理由.

## 实现阶梯

在第一个站得住的台阶停下. 停下后不继续加代码.

1. **不写**: 行为已被其他代码/配置/数据库约束覆盖, 或是推测需求. 删一行说明.
2. **用标准库**: 标准库能做. 不自己实现, 不新增依赖.
3. **用平台原生**: 平台/框架/数据库原生特性覆盖. `<input type="date">` 胜过日期选择库, CSS 胜过 JS, DB 约束胜过应用代码.
4. **用已装依赖**: 已安装依赖能解决. 不新增依赖. 几行代码能做的事, 不引新依赖.
5. **一行优先**: 能一行就一行. 表达式胜过语句, 内置胜过手写.
6. **最小可工作代码**: 上面都不成立时, 写最短能工作的代码. 不抽象, 不分层, 不预留扩展点.

阶梯是实现反射, 不是研究项目. 两个台阶都能用 -> 选优先级更高的那个继续. 第一个能工作的懒方案就是正确方案.

## 实现侧规则

- 删除胜于添加. 朴素胜于聪明 - 聪明是凌晨 3 点才有人能解码的东西.
- 文件越少越好. 最短可工作 diff 胜出.
- 复杂需求: 交付最简版本, 同一回复质疑剩余部分. 能给默认值的问题不停下来等答案.
- 两个等长选项, 选边界情况正确的那个. 懒是少写, 不是选更脆弱的算法.
- 用 `lazy-code:` 注释标记刻意简化, 让简单读起来像意图而非无知. 捷径有已知上限 (全局锁, O(n²) 扫描, 朴素启发式)? 注释写明上限和升级路径: `# lazy-code: 全局锁, 吞吐成瓶颈时改按账户加锁`.
- 非琐碎逻辑 (分支/循环/解析器/金钱安全路径) 留一个且仅一个可运行自检: 能独立运行, 逻辑坏掉时就失败. 不上测试框架, 不逐函数覆盖, 除非我要求. 琐碎一行不需测试.
- 需要 `tdd` 时 (行为已明确, 测试先行): 必须调用 `tdd` skill, 按完整流程写测试, 不简化成最简自检.

实现侧降级信号: diff 含未请求的脚手架/样板/预留扩展点; 解释比代码长 (除非我明确要求解释).

## 验收增量

在 `lazy-design` 的共享验收标准之上, 代码还须:

- 新依赖为零, 除非实现阶梯第 4 级成立且无法用标准库/已装依赖替代.
- 非琐碎逻辑的可运行自检已就位.

## 输出

代码先行. 若需在回复正文里说明, 最多三行, 仅写: 跳过了什么, 何时添加. 不写未请求的说明 - 功能导览/设计说明/为简化辩护的文字, 都是把复杂度用文字塞回来. 说明比代码长就删. 我明确要的报告/逐步讲解/分阶段记录, 按要求给.

模式: `[code] -> 省略: [X], 添加条件: [Y].`

## 边界

lazy-code 只指导实现, 不重新设计. 行为未定时先用 `lazy-design`. 我坚持要完整实现 -> 实现它, 不争论. 持续到我说停止或会话结束.

最短完成路径就是正确路径.
