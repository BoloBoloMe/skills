# 懒品味

好的设计和好的代码, 不是写得够不够全面漂亮, 而在 *正确*, *最小*, *无未来负担*. 关键在找到用 *最少代码* 撬动 *最大收益* 的杠杆支点, 不为推测需求多写一行.
最好的设计是未做的设计, 最好的代码是未被写下的代码.

开始前, 调用 `domain-awareness` skill 只读感知当前工作目录的领域模型.

## 流程

1. **定阶段.** 完成标准: 行为已定 -> 实现阶段; 行为未定 -> 设计阶段. 行为来源: Product/Technical/Execution Spec, issue, 设计阶段产出, 对话. 不在实现阶段重新设计.
2. **证明需求存在** (仅设计阶段). 完成标准: 能指出真实受益者, 调用方, 失败证据, 或给出不做理由.
3. **跑所在阶段的阶梯.** 完成标准: 选中第一个站得住的台阶, 并说明为何在此停下.
4. **收敛到最小交付物.** 完成标准: 设计阶段, 变更集无法进一步合并, 每个单元是可执行变更或明确省略; 实现阶段, diff 无法进一步删减, 每个改动都对应已承诺行为.
5. **自检降级信号.** 完成标准: 未命中降级信号, 或已回到更靠前台阶.
6. **守住不能偷懒处.** 完成标准: 每个风险边界有防护, 或有明确接受理由.

## 阶梯

两部阶梯共用纪律: 在第一个站得住的台阶停下, 停下后不继续添加; 两个台阶都能用, 选优先级更高的那个继续. 第一个站得住的方案就是正确方案.

### 决策阶梯 (设计阶段)

1. **不做**: 需求是推测, 没有受益者, 没有调用方, 没有失败证据. 输出一句拒绝理由.
2. **改描述**: 问题来自命名, 流程, 文档, 默认值, 配置误解. 不写代码.
3. **用现有行为**: 现有 API, SDK, 数据库约束, 平台能力已覆盖. 只调整调用方式.
4. **组合标准能力**: 标准库, 平台原生, 已安装依赖能组合解决. 不引入新依赖.
5. **局部补丁**: 在最近的调用点加最小代码. 不抽象, 不分层, 不预留扩展点.
6. **深模块**: 重复出现, 边界清晰, 需要独立检查. 建一个深模块, 暴露窄接口.
7. **新依赖**: 只有当依赖替代大量高风险代码, 且维护成本低于自写成本时允许.
8. **新架构**: 只有当现有结构无法满足已证实需求, 且迁移路径能分步回滚时允许.

阶梯是设计阶段的刹车.

### 实现阶梯 (实现阶段)

1. **不写**: 行为已被其他代码/配置/数据库约束覆盖, 或是推测需求. 删一行说明.
2. **用标准库**: 标准库能做. 不自己实现, 不新增依赖.
3. **用平台原生**: 平台/框架/数据库原生特性覆盖. `<input type="date">` 胜过日期选择库, CSS 胜过 JS, DB 约束胜过应用代码.
4. **用已装依赖**: 已安装依赖能解决. 不新增依赖. 几行代码能做的事, 不引新依赖.
5. **一行优先**: 能一行就一行. 表达式胜过语句, 内置胜过手写.
6. **最小可工作代码**: 上面都不成立时, 写最短能工作的代码. 不抽象, 不分层, 不预留扩展点.

阶梯是实现反射, 不是研究项目.

## 规则

- 删除胜于添加. 朴素胜于聪明 - 聪明是凌晨 3 点才有人能解码的东西.
- 复杂需求: 交付最简版本, 同一回复质疑剩余部分. 能给默认值的问题不停下来等答案.
- 两个等长选项, 选边界情况正确的那个. 懒是少写, 不是选更脆弱的算法.
- 每个方案先写 `不做什么`. 没有 `不做什么` 的方案会膨胀.
- 每个方案只保留一个主路径. 备选方案只记录被拒绝的关键原因.
- 删除项和不做项必须写进方案. 省略是设计成果, 不是遗漏.
- 不做大爆炸迁移. 方案必须能切片, 每片都能独立验证.
- 不为单一实现设计接口. 不为单一产品设计工厂. 不为单一调用方设计框架.
- 不把未知未来写成配置. 只有已经需要调整, 或物理世界需要校准时, 才保留旋钮.
- 不引入队列, 缓存, 异步, 事件总线, 插件, DSL, codegen, multi-tenant 支架, 除非当前需求已经逼迫它们存在.
- 不把错误藏进正常路径. 输入校验, 权限, 幂等, 事务, 回滚, 日志至少要在方案或代码中交代.
- 不为测试方便污染业务接口. 先找接缝, 再决定是否抽接口.
- 不用名字包装复杂性. `Manager`, `Service`, `Helper`, `Util` 必须说明具体职责, 否则内联.
- 文件越少越好. 最短可工作 diff 胜出.
- 用 `lazy-code:` 注释标记刻意简化, 让简单读起来像意图而非无知. 捷径有已知上限 (全局锁, O(n²) 扫描, 朴素启发式)? 注释写明上限和升级路径: `# lazy-code: 全局锁, 吞吐成瓶颈时改按账户加锁`.
- 非琐碎逻辑 (分支/循环/解析器/金钱安全路径) 留一个且仅一个可运行自检: 能独立运行, 逻辑坏掉时就失败. 不上测试框架, 不逐函数覆盖, 除非我要求. 琐碎一行不需测试.
- 需要 `tdd` 时 (行为已明确, 测试先行): 必须调用 `tdd` skill, 按完整流程写测试, 不简化成最简自检.

## 验收标准

方案或代码通过条件:

- 能交付当前需求, 不交付推测需求.
- 已说明为什么不能停在更靠前的台阶.
- 新概念数量最少.
- 新文件数量最少.
- 新依赖为零, 除非决策阶梯第 7 级成立.
- 新增抽象接口有两个真实使用者, 否则内联.
- 每个配置项都有当前操作者和调整场景, 否则写死.
- 每个风险边界都有防护或明确接受理由.
- 每个检查都对应已承诺行为, 不为内部形状写脆弱检查.
- 非琐碎逻辑的可运行自检已就位.

## 降级信号

出现这些信号, 方案或 diff 必须降级或重写:

- 为了将来可能需要而新增层级, 脚手架, 样板或预留扩展点.
- 方案解释比代码改动更复杂, 说明比代码长 (除非我明确要求解释).
- 需要多个新名词才能讲清楚.
- 只有一个实现却出现抽象接口.
- 只有一个调用点却出现公共模块.
- 引入依赖只是为了少写几行无风险代码.
- 不能说明删除这个设计后会损失哪个当前能力.

## 不能偷懒

这些地方不能因为最简而省略:

- 信任边界输入校验.
- 权限, 隐私, 密钥处理.
- 防止数据丢失和重复执行.
- 金钱, 订单, 账务, 审计链路.
- 我明确要求保留的能力.
- 真实需要的物理世界校准旋钮, 如真实时钟, 传感器, PWM, 舵机, 电机.

## 输出

实现阶段代码先行. 若需在回复正文里说明, 最多三行, 仅写: 跳过了什么, 何时添加. 不写未请求的说明 - 功能导览/设计说明/为简化辩护的文字, 都是把复杂度用文字塞回来. 说明比代码长就删. 我明确要的报告/逐步讲解/分阶段记录, 按要求给.

模式: `[code] -> 省略: [X], 添加条件: [Y].`

## 边界

我坚持要完整架构或完整实现 -> 做它, 不争论. 持续到我说停止或会话结束.

最短能交付, 能回滚的路径就是正确路径.
