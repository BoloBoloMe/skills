# 独立验证与返工

navigate 的 verification 分支, 由 [Milestone 类型](../SKILL.md#milestone) 抵达. 本页只管派工和结果去向, 验证方法与复验规则由 `verify-change` 管, 正式接受交付仍由我决定.

1. **核实交接.** 从里程碑 `inputs` 取得目标项目, 完整目标提交号, 已确认的 `VERIFICATION-PLAN.md` 路径与修订号, 以及方案引用的权威输入; 使用该里程碑的 `output_dir` 作为产物根目录. 目标提交应是实施与评审收敛后的集成提交, 不以不断前移的 HEAD 代替固定目标. 已有产品改动未提交或材料不适用时停止.
   完成标准: 项目, 目标提交, 方案修订号和来源可核实, 目录明确; 或缺口已报告且未开始验证.
2. **派发独立会话.** 另起未参与实现与修复的独立会话, 调用 `verify-change` skill 的执行验证方案方式; 复验按该 skill 的 [复验规则](../../verify-change/REVERIFY.md). 派工只给目标提交, 方案与权威输入路径, 产物根目录, 本轮证据输出要求, 不继承实现对话或作者设计理由. 要求它组织非作者验证者, 不修改产品, 不修复, 不改判据, 只回报报告路径, 覆盖提交与方案, 必验项结果和实现问题/环境权限缺口/标准或证据缺口三类去向. 作者侧端到端记录只作对照, 不作独立验证必验项的通过依据; 关键真实路径只认本轮独立验证者实跑. 无可用非作者时报告受阻, 不回退作者自验.
   完成标准: 独立验证会话已按明确目标执行并交回报告, 非作者事实可复核; 或受阻且未伪造验证结论.
3. **分流发现.** 明确实现问题新建 implementation 里程碑, 修复交给开发流程, 仍经过实现, 提交, 合并, 开发验证与评审; 将发现落实成新增 issues, 不让验证者顺手改产品. 环境, 权限, 标准或证据缺口单列, 按实际需要安排 task, deliberate, spec 或 verification-plan, 不一律当代码缺陷. 新增工作使用同一交付单元的产物根目录, 声明报告等实际输入, 并让它阻塞 acceptance. 只有方法变化不改产品判据, 判据或方案依据变化须先更新权威输入并重新确认方案. 尚不能明确安排的缺口交我裁决, 验证保持进行中, 验收不具备开始条件.
   完成标准: 每条发现已有明确去向或已报告待我裁决, 缺口没有伪装成已通过或实施缺陷.
4. **安排复验与收口.** 有修复或待补验证时新建 verification 节点, 依赖原验证及所需补充工作, 并加入 acceptance 的阻塞列表. 修复后绑定新提交, 另存证据, 不覆盖旧报告; 未受影响项能否沿用由复验规则决定. 不从新工作反向阻塞原验证, 保持依赖无环. 原验证的报告与分流均完成后才记录其关闭, 即使报告包含失败或未验证也不代表成品达标; 未补工作及其复验仍阻塞验收. 同一标准下的返工是当前版本修正, 不叫下一次迭代.
   完成标准: 报告与原件已入 `artifacts`, 关闭摘要如实列结果及后续节点; 有缺口时补充工作与复验仍阻塞 acceptance, 全部必验项证据齐备后才交我验收.
