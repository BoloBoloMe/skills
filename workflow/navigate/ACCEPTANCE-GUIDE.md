# Navigate 验收参考

只在确认详细验收标准或领取 `acceptance` Milestone 时读取相应部分. 路线图中的验收节点及其阻塞关系由 `SKILL.md` 管, 此处只管验收依据和关闭条件.

## 验收标准

目的地已约定怎样算抵达; 当细节明朗时, 最迟在正式实施前逐项确认可验证的标准. 若目的地仅需决策或文档, 则在产物定稿前确认. 先定标准, 才不会按既成结果倒推什么算通过.
- 调用 `to-spec` 时, 由它在落盘前逐批与我确认 `PRODUCT.md` 的 `验收标准`. 直接以该节的 AC 和场景为依据, 不重复确认相同内容.
- 不调用 `to-spec` 时, 有 Roadmap 就用 HITL Milestone, 无 Roadmap 就在当前会话与我确认逐项可观察标准; 写入 `docs/changes/<feature-slug>/ACCEPTANCE.md`, 有 Milestone 时记入其 `artifacts`. 未经我确认的拟稿不算标准. 后续若生成 `PRODUCT.md`, 比对两份标准, 有差异先找我裁决, 再以已确认的 `PRODUCT.md` 为准.
若证据由 `verify-change` 产出, 判据只能是带确认标记的 `PRODUCT.md`; 只有 `ACCEPTANCE.md` 时它按输入缺口停下, 先把标准转正进 `PRODUCT.md` 再验收.
标准需要改变时, 先与我重新对齐并更新权威来源, 再按新标准验收.

## 证据与确认

**收集证据 (我可离场).** 对照已确认的每项标准及其场景逐项核对结果. 报告逐项列出依据 (有 `PRODUCT.md` 时用 AC/场景编号), 证据来源与可复核位置, 操作/命令, 实际运行结果和时间或版本范围, 标为已观察通过/失败/未验证; 代码推断单独标明, 不能充当实际通过的证据. 引用测试时指出测试代码及实际运行结果; 只有可靠的变更前失败记录才能与变更后对照. UI 用实际截图, 非可视结果用测试, 日志, 控制台输出或数据库数据等适合的材料. 未运行的测试不算通过, 不编造旧版本结果. **收集人不得自验.** 实现或修复该变更的会话不得承担证据收集与结论, 只能提供材料与说明. 由未参与的代理独立收集, 否则属作者自验, 不能作为验收依据.

**复用已有证据.** 若其他环节已产出独立核验报告, 先看它是否与本轮同一交付提交, 且所引标准版本与我确认的版本一致; 再核对其必验项是否覆盖全部标准与场景. 都满足就直接引用该报告的逐项结果与证据位置, 不重复收集; 缺项或提交已变时只补差值, 旧报告作旧观察引用并注明原提交与原时间. 未运行的测试不算通过, 引用不等于实跑. 复用只省收集, 不省逐项确认. 报告放在验收 Milestone 的产物目录; 复用别处原件时不复制正文, 只把原件路径记入 `artifacts`; 引用权威标准, 不复制一份可能过期的标准.
完成标准: 每项标准及场景都有可复核的结果或明确的证据缺口, 报告能区分观察, 推断和未验证. 关键结论缺证据时, 先说明缺什么, 影响哪项结论及可行的补证方式; 我决定补证就继续收集, 我明确同意标出缺口才将报告交给我逐项核对. 在我作出决定前暂停生成最终页面.

**逐项确认 (我必须在场).** 交给我逐项核对报告及证据, 记下每项是否经我明确确认; 我未确认的项目保持未通过. 我同意标出缺口, 只允许页面如实展示未验证项, 不等于验收通过. 失败或未验证的必验项须继续补工作/补证据, 需要返工时新增工作 Milestone 并让它阻塞验收, 然后重新交给我确认. 只有所有必验项都有充分证据且我逐项确认通过, 才能关闭验收并正式交付. 若需生成最终页面, 在我决定如何处理关键缺口之前停下; 我明确同意标出缺口后可以生成供讨论的页面, 但必须明示未通过, 不得当作正式交付.
完成标准: 每项必验项均有充分证据且已获我确认, 验收报告与关闭摘要记录确认结果; 任何缺口仍在时, 验收保持进行中, 不宣布抵达.
