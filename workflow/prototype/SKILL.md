# 原型

原型是 **用于回答一个问题的一次性代码**. 问题决定形态.

## 选择分支

从用户提示, 周边代码中识别正在回答的问题; 用户在场时可直接询问:

- **"这个逻辑 / 状态模型感觉对吗?"** -> [LOGIC.md](LOGIC.md). 构建一个微型交互式终端应用, 让状态机跑过那些纸面难推理的场景.
- **"这应该长什么样?"** -> [UI.md](UI.md). 在单一路由上生成多个差异显著的 UI 变体, 通过 URL 查询参数和浮动底栏切换.

两个分支产出差异很大的产物 - 选错会让整个原型白费. 问题确实模糊且无法联系到用户时, 默认选更匹配周边代码的分支 (后端模块 -> 逻辑; 页面或组件 -> UI), 并在原型顶部写明这个假设.

## 两者都适用的规则

1. **一次性, 且明确标记.** 原型代码放在它实际被使用的位置附近 (紧邻要验证的模块或页面), 上下文清楚; 但命名要让读者看出它是原型, 而非生产代码. 一次性 UI 路由遵守项目既有的路由约定; 不要发明新的顶层结构.
2. **一条命令即可运行.** 使用项目现有任务运行器支持的方式: `pnpm <name>`, `uv run python <path>`, `bun <path>` 等. 用户必须能不费脑子启动. 新增辅助脚本必须跨系统/跨设备可运行; 优先用项目已有运行时中的可移植 Python 或 JavaScript, 不新增只能在单一 shell 或单一操作系统上运行的脚本.
3. **默认不持久化.** 状态存在内存中. 持久化是原型要 *验证* 的点, 不应成为它的依赖. 问题明确涉及数据库时, 连接临时 DB 或本地文件, 并用清晰的 "PROTOTYPE - wipe me" 名称.
4. **跳过打磨.** 不写测试, 除让原型 *可运行* 所需的错误处理外不做额外错误处理, 不做抽象. 目标是快速学到东西, 然后删除.
5. **暴露状态.** 每次动作 (action) 后 (逻辑) 或每次切换变体时 (UI), 打印或渲染完整的相关状态, 让用户看到发生了什么变化.
6. **完成后删除或吸收.** 原型回答了问题后, 要么删除它, 要么把经过验证的决策折叠进真实代码 - 不要让它在仓库里腐烂.

## 完成时

原型 README, NOTES, 页面可见说明用中文. 代码标识符, URL/query key, 路由片段, 组件名遵循项目技术约定; 不为中文化破坏框架习惯. 页面可见变体名称优先中文, 例如 `A - 侧边栏布局`.

原型中唯一值得保留的是 *答案*. 把它连同所回答的问题一起记录到持久位置 (commit message, ADR, issue, 或原型旁边的 `NOTES.md`). 用户在场时这是一次简短对话; 不在时留下占位, 方便他们 (或你在下一轮) 在删除原型前填入结论.
