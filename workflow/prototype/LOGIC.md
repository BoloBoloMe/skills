# 逻辑原型

微型交互终端应用, 让我手动驱动状态模型.
当问题涉及业务逻辑, 状态转移或数据形态时使用, 这些在纸面上看似合理, 跑过真实 case 才发现不对劲.
默认使用 Python 编写, 只用标准库. 不引入第三方依赖, 除非环境中已有.

原型文件放在 `docs/changes/<feature-slug>/prototypes/<prototype-name>/` 下.

## 流程

### 1. 陈述问题

写代码之前, 先写下要验证的状态模型和问题.
一段话即可, 放在原型文件顶部注释中.
把问题显式写出来, 以便事后核对.
完成标准: 问题陈述已写入原型文件顶部; 我能指出它是否命中了我关心的 case.

### 2. 将逻辑隔离为可移植模块

把真正回答问题的核心逻辑放在一个小而纯的接口后面, 与外围 TUI 隔离. TUI 是一次性的; 逻辑模块是我在正式代码中重写时的参考答案.

用什么结构组织逻辑, 取决于问题长什么样:

- **如果问题核心是 "操作是否合法"** (比如订单只能从"待支付"→"已支付", 不能从"已取消"跳过去) — 用状态机: 显式列出所有状态和合法转移, 非法操作直接拒绝.
- **如果问题核心是 "数据怎么变"** (比如计算折扣, 合并两个报表, 校验一组字段) — 用纯函数: 输入数据, 返回新数据, 不改任何外部状态.

实现上很简单: 状态用 `@dataclass`, 合法转移用 `match/case` 或字典, 函数签名清晰.
保持纯净: 无 I/O, 无终端代码, 无 `print` 做控制流.
TUI 导入模块并调用它; 数据不反向流动.

完成标准: 核心逻辑是独立模块, 通过公共接口被 TUI 驱动; 模块不依赖终端/I/O; 接口干净到可作为正式实现的参照.

### 3. 构建暴露状态的最小 TUI

构建轻量 TUI. 每次操作后清屏 (`print("\033[2J\033[H")`), 重新渲染整个 frame.
我看到的是稳定视图, 不是不断增长的 scrollback.

每帧两部分:

1. **当前状态**, pretty-print 且 diff 友好 (每字段一行, 或 `json.dumps`). 字段名用粗体, 次要上下文用 dim.
2. **键盘快捷键** 列在底部: `[a] 添加  [d] 删除  [q] 退出`. 键用粗体.

行为: 初始化状态 → `input()` 读一行 (或 `sys.stdin.read(1)` 读单键) → handler 修改状态 → 重新渲染完整 frame (替换, 不追加) → 循环直到退出. 整个 frame 应能在一屏内显示.

完成标准: 启动时看到初始状态; 每次按键后 frame 刷新, 状态变化可见; frame 不增长.

### 4. 交付

把运行命令交给我. 我自行操作.
有意义的时刻是我说 "等等, 这不应该是可能的" 或 "咦, 我以为 X 会不一样" —
这些是想法里的 bug, 正是原型要找的.
完成标准: 我已启动原型并开始交互; 或我确认看到预期行为.

### 5. 捕获

按 [SKILL.md](SKILL.md) 规则 5 捕获答案和原型.
逻辑模块作为参考答案保留在工作分支 (`docs/changes/` 下), 由正式实现者参照重写;
TUI 外壳同样保留, 作为一手材料.
原型文件在合并主干前由人类清理.
完成标准: 答案已记录; 原型文件已归档; 实现 issue 上有指针.

## 反模式

- **不要加测试.** 需要测试的原型不再是原型.
- **不要泛化.** 不设想 "如果我们以后想支持 X". 原型只回答一个问题.
- **不要把逻辑和 TUI 混在一起.** reducer / 状态机引用终端 escape code 就不再可移植.
- **不要把 TUI 外壳交付到生产环境.** 外壳为终端手动操作优化, 逻辑模块的价值在于作为重写时的参考答案, 不在直接复用.
