# 代码评审

开始前, 调用 `domain-awareness` skill 感知当前工作目录的领域模型.

从我指定或调用方明确传入的基准点到 `HEAD` 之间的 diff, 按以下评审方向分别 review:

- **Standards**: 代码是否遵循仓库中已记录的编码规范?
- **Spec**: 代码是否完整实现了原始 DECISIONS / spec?
- **旧行为影响** (按门槛纳入): 变更是否破坏了可能受影响的既有入口, 调用方与旧行为?

各评审方向分开运行, 互不污染上下文, 最后并列展示结果. 不跨评审方向合并排序.

## 步骤

### 1. 确定基准点

我说的任何可被 Git 解析的引用都可以作为基准点, 包括 commit SHA, 分支名, tag, `main`, `HEAD~5`. 调用方明确传入的基准点同样适用; 两者都没有时询问我, 不自行选择.
一次性记录 diff 命令: `git diff <基准点>...HEAD` (三点语法, 以 merge-base 为比较基准). 同时记录 commit 列表: `git log <基准点>..HEAD --oneline`.
继续之前, 确认基准点可解析 (`git rev-parse <基准点>`) 且 diff 不为空. 引用无效或 diff 为空时在本步骤失败, 不把失败推给后续 reviewer.

完成标准: 基准点已解析, diff 命令已记录, commit 列表已记录, diff 非空.

### 2. 定位 spec 来源

按以下顺序查找原始 spec:

1. 我作为参数传入的路径或内容.
2. commit message 中的 issue 引用.
3. `docs/changes/<feature-slug>/` 下的 `DECISIONS.md`, `PRODUCT.md`, `TECHNICAL.md`, `EXECUTION.md`, `issues/`.
4. 以上均无, 询问我 spec 在哪. 如果我说没有, **Spec** 评审方向跳过并报告 `no spec available`.

完成标准: spec 状态已归类为路径, 已获取内容, 或 `no spec available`; 每个使用的来源都有路径, URL 或提交证据; 存在 issue 文件时已定位各 issue 的 `验证契约`, `验证入口` 与 `交付证据`, 供 Spec reviewer 核对.

### 3. 确定规范来源

读取仓库中记录编码规范的文档, 如 `CODING_STANDARDS.md`, `CONTRIBUTING.md`, `AGENTS.md`, lint/test 配置说明或项目文档中的开发约定.
除仓库文档外, Standards 评审方向始终携带 [Fowler 坏味道基线](references/fowler-baseline.md), 即使仓库无任何文档也适用. 两条规则约束:

- **仓库优先**: 仓库记录的规范始终胜出; 如果仓库规范认可了基线本会标记的写法, 抑制该坏味道.
- **始终是判断性发现**: 每个坏味道都是带标签的启发式判断, 如 `可能是 Feature Envy`; 绝不作硬性违规. 与本 skill 中任何规范一样, 跳过工具链已强制检查的内容.

完成标准: 规范来源文件列表已记录; Fowler 坏味道基线已读取; 已明确哪些检查由现有工具链强制覆盖, 没有则记录为无.

### 4. 确定旧行为影响方向

免做条件: 整轮全部 issue 均为非行为改动或纯核验, 且评审起点到当前集成提交的差异不触碰共享接口, 数据格式或跨模块路径; 其余情况照做. 判定只用 issue 验证契约的类型声明与实际差异触碰面, 不以尚未调查的测试覆盖情况作门槛.
由调用方总指挥在调用评审前做出判定并传入结果; 免做理由在 `EXECUTION.md` 执行记录留一行并提交. 未提供判定依据时先核对, 不默认免做. 实做时取得调用方传入的产物根目录, 缺失则先询问.
只有实做轮才产出 `IMPACT-REVIEW.md`. 它是调查报告, 不新增产品判据, 不进入 Spec 评审方向或 `verify-change` 的输入判据.

完成标准: 已按两项依据判定运行或免做, 免做理由已记录并提交; 实做所需产物根目录已明确, 或已停下报告缺口.

### 5. 运行各评审方向

启动 **Standards** 和 **Spec** 两个 reviewer, 按步骤 4 的判定另启 **旧行为影响** reviewer. 各 reviewer 使用独立上下文. 若运行时不支持子 agent, 没有可用 reviewer, 或并行启动失败, 父会话可按同一输入契约先运行 Standards 再运行 Spec, 最终格式不变; 旧行为影响须由未参与实现与修复的独立审核者运行, 无人可派则报告缺口, 不由作者补位.

**Standards reviewer 输入** 包含:

- 完整的 diff 命令和 commit 列表.
- 步骤 3 中找到的规范来源文件列表.
- `references/fowler-baseline.md` 全文. reviewer 没有其他途径获取这份基线.
- 任务简述: `报告按相关文件/hunk 组织. (a) diff 中每个违反已记录规范的位置, 引用规范文件和规则; (b) 你发现的任何基线坏味道, 列出名称并引用 hunk. 区分硬性违规和判断性发现. 违反已记录规范可能是硬性的, 基线坏味道始终是判断性发现, 且仓库已记录规范覆盖基线. 跳过工具链已强制检查的内容. 每个发现必须已读取对应 hunk 所在完整函数/方法及必要调用方; 无上下文支撑的坏味道不得报告. 完整列出全部发现, 如有摘要只限制摘要篇幅.`

**Spec reviewer 输入** 包含:

- 完整的 diff 命令和 commit 列表.
- spec 的路径或已获取的内容.
- issue 中声明的验证契约, 验证入口与交付证据 (若有); 核对契约时读取 `verification-contract` skill.
- 任务简述: `报告 (a) spec 要求但缺失或不完整的实现; (b) diff 中出现了但 spec 未要求的行为, 即范围蔓延; (c) 看似已实现但实现方式有误的需求; (d) issue 的交付证据未覆盖所声明的全部变更类型, 或与验证契约不符. 实现类发现引用 spec 原文, 并读取对应 hunk 所在完整函数/方法及必要调用方; 证据类发现引用 issue 的契约, 验证入口, 实际交付证据 (若有) 及 verification-contract 的对应规则, 区分没有记录证据与检查未通过. 没有 spec 或契约依据不得报告. 完整列出全部发现, 如有摘要只限制摘要篇幅.`

如果 spec 缺失, 跳过 Spec reviewer 并在最终报告中注明.

**旧行为影响 reviewer 输入** 包含:

- 完整的 diff 命令和 commit 列表, 评审起点与当前集成提交.
- 产物根目录及其中已有的 `IMPACT-REVIEW.md` (首轮没有则注明), 供核对上轮记录是否闭环.
- 任务简述: `从指定评审起点核对实际差异, 追查可能受影响的既有入口/调用方和旧行为. 共享接口, 数据格式或跨模块路径的变更调用 blast-radius skill 深查. 报告写目标提交, 逐项发现, 已排除项与证据, 包含代码依据, 既有检查及本轮运行结果; 未证实路径写明缺口, 不以搜索命中充当安全证明, 不声称有限检查找到了全部影响. 读上轮报告核对闭环, 将本轮完整记录追加到产物根目录的 IMPACT-REVIEW.md 并提交, 不覆盖旧轮次.`

完成标准: Standards 输出已获得; Spec 输出已获得或已明确跳过; 旧行为影响已获得独立报告或有已记录的免做理由, 否则报缺口; 每个 reviewer 输入包含 diff 命令, commit 列表和本评审方向必需来源.

### 6. 汇总

在 `## Standards`, `## Spec` 和 `## 旧行为影响` 标题下展示各份报告, 原文或略作清理. 跳过或免做的方向注明原因. **切勿**跨评审方向合并或重排发现.
以一行总结收尾: 每个评审方向的发现总数, 以及该方向内最严重的问题 (如有). 不跨评审方向选最严重问题, 避免一种结论掩盖另一种.
旧行为影响报告只供该方向核对历史记录闭环和汇总分流, 不送入 Spec 方向作判据. 由调用方总指挥处理发现: 明确的实现破坏拆成返工 ISSUE; 需要产品取舍的先报缺口交我裁决, 再按需更新决策账本, 两份 spec, 执行任务及实现. 返工合并并通过整体验证后, 对新集成提交按步骤 4 的门槛重做旧行为影响方向.

完成标准: 最终报告包含三个评审方向的独立结论或跳过原因, 各自发现总数和最严重问题或 `无`; 旧行为影响的发现与待裁决缺口已交调用方分流, 不以报告代替产品验收.

## 结论口径

各评审方向都属于验证: Standards 判代码好坏, Spec 判是否实现要求, 旧行为影响判既有路径是否被破坏; 结论都要可复查.

- 每个评审方向完整列出全部发现, 摘要只限制摘要篇幅, 不替代清单.
- 写明已检查范围 (读了哪些文件与 hunk); 未读部分不算已检查.
- 坏味道等主观判断须引用具体 hunk, 不给无法定位的口味意见.

## 为何分开评审

一处改动可能通过一个评审方向而失败于另一个:

- 代码遵循所有规范但实现了错误的功能 -> **Standards 通过, Spec 失败.**
- 代码精确实现了 issue 要求但破坏了项目约定 -> **Spec 通过, Standards 失败.**

分开报告, 防止一个评审方向掩盖另一个.
