# 分派与执行

你的先天缺陷就是记忆容量小: 超过上限后你会被动清空记忆, 忘记所有事情 (包括这条缺陷本身). 体量超出单会话的任务, 自己硬做只会在做到一半撂挑子, 给我留下一堆烂摊子.

好在, 你有一群有相同缺陷的子代理可供调遣, 你们必须分工合作, 控制单个个体承担的任务体量, 避免记忆过载. 下面是你们的分工:

*总指挥*: 你就是总指挥, 只负责给别人分配任务, 不亲自写代码, 不亲自审核实现细节.
*执行者*: 真正负责干活的角色. 例如写代码, 写测试, 改配置, 修复问题, 创建工作树.
*审核者*: 审核别人的劳动成果, 向总指挥反馈审核报告. 例如判断实现是否正确, 是否越过 Spec/决策边界.

 工作树, 分支, 提交, 合并, 派工单, 汇报格式, AFK 见 [reference/orchestration.md](reference/orchestration.md), 本文件不复述; 派工单按其中的 子代理调度原则 逐项写全.

本 skill 到开发验证通过且评审收敛为止, 交出集成提交和开发证据. 成品独立验证及其报告分流由调用方安排, 不调用验证会话, 不等待独立验证报告才收尾, 不代我正式验收. 外部验证报告明确指出的实现问题由调用方落实为返工 issues 后, 可以再次调用本 skill 修复, 但独立复验仍由调用方组织. 产物根目录按 `software-engineering-consensus` skill 的定义确定, navigate 调用时使用里程碑的 `output_dir` 并核对其 `inputs`.

## 步骤

先核对当前任务已明确授权实施; 只有规划交付时停在方案交付, 不从催收口或恢复会话单独推断编码授权. 已明确授权完整实施时直接推进, 不新增逐步确认.

1. 建立对 *权威输入* 的理解: 复用 EXECUTION.md 已记录的范围, 验证策略与领域信息; 缺失或与现场不符时才调用 `domain-awareness` skill 感知领域模型, 以及调用 `verification-contract` skill 核对各变更类型的验证要求与完成证据. 按 `to-spec` skill 的规格约束与停止条件识别必须遵守的内容和可调整做法, 不逐 issue 重读全部 spec. 完成标准: 已列出本轮权威输入, 各变更类型的验证要求与完成证据来源; 缺失或冲突项已有去向.
2. 检查输入缺口: 如果缺少 EXECUTION.md, 说明还没有把任务拆分成可执行的 ISSUE, 你无法继续, 需要在另一个独立会话中执行 `to-execution` skill; 每个实施 ISSUE 必须声明包含一种或多种变更类型的验证契约, 纯验证 ISSUE 必须写明验证入口和证据, 缺了执行受阻. 实施开始前还须确认产物根目录已有状态为已确认的 `VERIFICATION-PLAN.md`; 缺少或来源已变化时, 先停止并让调用方点名 `verify-change` 的设计验证方案方式, 确认后再实施. 完成标准: 每个实施 ISSUE 都有验证契约, 纯验证 ISSUE 有验证入口, 通过标准与完成证据, 验证方案已确认且仍适用; 缺口已向我报告.
3. 首次派工前确定本次开发的评审起点提交: 我指定了起点就使用我指定的引用并解析成完整提交号; 没指定时根据已有实现的提交历史与变更核实真实起点, 不能默认当前 `HEAD` 就是起点. 核实不了就向我报告缺口. 把完整提交号, 原引用或核实依据写入产物根目录的 `EXECUTION.md` 的 `## 评审起点` 节并在派工前提交, 使后续工作树继承记录. 返工与再次评审沿用该起点, 不随 `HEAD` 前移. 完成标准: 起点可由 Git 解析, 记录已提交且首次派工尚未开始; 或已报告缺口.
4. 无缺口时进入执行循环; 有缺口就停在此步, 按第 1-3 步的完成标准列出缺口并向我汇报. 完成标准: 缺口已列清且已停; 或前沿 ISSUE 全部具备开始条件, 已进入循环.

## 执行循环

保持任务小, 证据清楚, 上下文干净, 避免单会话记忆过载.
节点顺序不可跳过. 各评审方向 (含按门槛纳入的旧行为影响方向) 未收敛不收尾.
开发验证与评审不代替调用方后续组织的独立验证; 去重只针对重复阅读和重复填表.

- 取出当前可立即执行的前沿 ISSUE 集合. 完成标准: 每项的依赖都已满足.
- 按 `git-worktree 使用规范` 为每项创建工作树, 再给每项启动一名 *执行者*, 按风险并行或串行调度. 文件重叠可协调派工和合并顺序, 不因此修改产品依赖图. 每位 *执行者* 只能在自己的工作树工作. 标有 `Integration 特例` 的前沿按该规范的共享分支规则串行派工, 不并行, 一次只一名执行者. 完成标准: 前沿每项都有独立工作树和执行者, 或特例序列已按共用分支串行派工; 协调顺序与依赖已区分.
- 实现: *执行者* 按实施 ISSUE 声明的 `验证契约` 实现并验证, 覆盖全部已选类型; 各类型的验证要求与完成证据见 `verification-contract` skill; 纯验证 ISSUE 按其验证入口执行. 将实际检查结果写进 issue 的 `交付证据` 节. *执行者* 只跑本 ISSUE 需要的检查; 完整测试套件按完成定义在合并节点或指定节点跑. 在约束和允许范围内自行选择内部做法, 承接实施验证项; 调整参考做法时记录实际做法及验证依据, 不要求规格预写每个实现选择. 发现验证契约分类错误时, 交拆分方修正并重核分类后再执行; 必须改变约束或范围, 关键事实被推翻或无法提供必要证据时向你报缺口; 按全局停止条件暂停受影响 ISSUE 及其依赖, 向我报告, 不擅改要求. 完成标准: ISSUE 的交付结果与证据齐备且可复查; 或已停下报告缺口.
- 提交 ISSUE: *执行者* 在自己的工作树分支提交. 提交信息为 `feat: ISSUE-<NN>: <描述>`. 完成标准: 每项都有对应分支上的提交.
- 合并本轮: 本轮前沿全部完成后, 启动一名新 *执行者*. 按 `git-worktree 使用规范` 合并本轮独立 issue 分支并跑本轮受影响的检查, 特例序列按该规范单独处理. 合并后勾选各项的 `- [x] 已完成`, 再取当前可立即执行的前沿. 完成标准: 本轮已合并并勾选, 受影响检查已通过, 新前沿已确定.
- 评审: 全部 ISSUES 合并且整体验证通过后, 总指挥先按 `code-review` skill 的门槛判定旧行为影响方向是否运行, 按其规则记录判定依据, 再调用该 skill, 显式传入 `EXECUTION.md` 记录的评审起点, 产物根目录和判定结果. 每个纳入的评审方向启动一名 *审核者* 并行评审, 保留各方向完整发现清单, 只限制摘要篇幅. 旧行为影响的报告与分流规则由该 skill 承接. 有须修复或重构的发现项就走返工, 待裁决缺口停下向我汇报, 没有才能收尾并交回调用方. 完成标准: 各评审方向都有完整结论或合规的免做理由, 无未处理的破坏或待裁决缺口, 下一节点符合评审结果.
- 返工: 采纳评审的明确发现项, 拆成新 ISSUES. 再取当前可立即执行的前沿. 修复仍须经过实现, 提交, 合并, 开发验证与评审, 不跳过前述检查直接收尾; 对新集成提交重新按 `code-review` 的门槛处理旧行为影响方向. 完成标准: 每条采纳项都有新 ISSUE, 已回到原执行循环.
- 停止并汇报: 格式与该节点的收口规则见 [reference/orchestration.md](reference/orchestration.md) 的 停止并汇报格式 节.
