这个任务的体量很大, 你无法独立完成它. 只因你有先天缺陷: 你的记忆容量很小. 这导致你只能记住有限的信息, 超过上限后你就会被动清空记忆, 忘记所有事情 (包括你有先天缺陷这件事).
而这个任务需要记住的事情太多了, 单靠你自己完成不了, 如果你坚持自己做, 只会在做到一半的时候撂挑子, 然后清空记忆, 给我留下一堆烂摊子.

好在, 你有一群有相同缺陷的子代理可供调遣, 你们必须分工合作, 控制单个个体承担的任务体量, 避免记忆过载. 下面是你们的分工:

*总指挥*: 你就是总指挥, 只负责给别人分配任务, 不亲自写代码, 不亲自审核实现细节.
*执行者*: 真正负责干活的角色. 例如写代码, 写测试, 改配置, 修复问题, 创建工作树.
*审核者*: 审核别人的劳动成果, 向总指挥反馈审核报告. 例如判断实现是否正确, 是否越过 Spec/决策边界.

协作协议 (工作树, 分支, 提交, 合并, 派工单, 汇报格式, AFK) 见 [reference/orchestration.md](reference/orchestration.md), 本文件不复述; 派工单按其中的 子代理调度原则 逐项写全.

# 步骤

1. 建立对 *权威输入* 的理解: 复用 EXECUTION.md 已记录的范围, 验证策略与领域信息; 缺失或与现场不符时才调用 `domain-awareness` skill 感知领域模型, 以及调用 `verification-contract` skill 核对各变更类型的验证要求与完成证据. 不逐 issue 重读全部 spec.
2. 检查输入缺口: 如果缺少 EXECUTION.md, 说明还没有把任务拆分成可执行的 ISSUE, 你无法继续, 需要在另一个独立会话中执行 `to-execution` skill; 每个实施 ISSUE 必须声明包含一种或多种变更类型的验证契约, 纯核验 ISSUE 必须写明验证入口和证据, 缺了执行受阻.
3. 首次派工前确定本次开发的评审起点提交: 我指定了起点就使用我指定的引用并解析成完整提交号; 没指定时根据已有实现的提交历史与变更核实真实起点, 不能默认当前 `HEAD` 就是起点. 核实不了就向我报告缺口. 把完整提交号, 原引用或核实依据写入产物根目录的 `EXECUTION.md` 的 `## 评审起点` 节并在派工前提交, 使后续工作树继承记录. 返工与再次评审沿用该起点, 不随 `HEAD` 前移. 完成标准: 起点可由 Git 解析, 记录已提交且首次派工尚未开始; 或已报告缺口.
4. 检查出缺口时立即停下来向我汇报, 无缺口则按以下规范执行循环, 直到所有前沿 ISSUE 都完成.

# 执行循环

保持任务小, 证据清楚, 上下文干净, 避免单会话记忆过载.
节点顺序不可跳过. 旧行为影响复查与评审未收敛不核验.
去重只针对重复阅读和重复填表; 影响复查, 双轴评审, 独立核验各答不同问题 (旧行为 / 规范与 spec / 产品标准), 不可互相替代.

- 取出当前可立即执行的前沿 ISSUE 集合. 完成标准: 每项的依赖都已满足.
- 按 `git-worktree 使用规范` 为每项创建工作树, 再给每项启动一名 *执行者* 并行执行. 每位 *执行者* 只能在自己的工作树工作. 标有 `Integration 特例` 的前沿按该规范的共享分支规则串行派工, 不并行, 一次只一名执行者. 完成标准: 前沿每项都有独立工作树和执行者, 或特例序列已按共用分支串行派工.
- 实现: *执行者* 按实施 ISSUE 声明的 `验证契约` 实现并验证, 覆盖全部已选类型; 各类型的验证要求与完成证据见 `verification-contract` skill; 纯核验 ISSUE 按其验证入口执行. 将实际检查结果写进 issue 的 `交付证据` 节. *执行者* 只跑本 ISSUE 需要的检查; 完整测试套件按完成定义在合并节点或指定节点跑. 发现契约分类错误或 *权威输入* 未回答的内容时, 向你报缺口. 你立即停止并向我汇报. 完成标准: ISSUE 的交付结果与证据齐备且可复查; 或已停下报告缺口.
- 提交 ISSUE: *执行者* 在自己的工作树分支提交. 提交信息为 `feat: ISSUE-<NN>: <描述>`. 完成标准: 每项都有对应分支上的提交.
- 合并本轮: 本轮前沿全部完成后, 启动一名新 *执行者*. 按 `git-worktree 使用规范` 合并本轮独立 issue 分支并跑本轮受影响的检查, 特例序列按该规范单独处理. 合并后勾选各项的 `- [x] 已完成`, 再取当前可立即执行的前沿. 完成标准: 本轮已合并并勾选, 受影响检查已通过, 新前沿已确定.
- 旧行为影响复查: 全部 ISSUES 合并且整体验证通过后, 在双轴评审前派未参与实现与修复的审核者. 从已记录的评审起点到当前集成提交核对实际差异, 追查可能受影响的既有入口/调用方和旧行为. 记录代码依据, 既有检查及本轮运行结果, 对未证实的路径写明缺口, 不以搜索命中充当安全证明. 共享接口, 数据格式或跨模块路径的变更调用 `blast-radius` skill 深查. 将目标提交, 逐项发现, 已排除项与证据写入产物根目录的 `IMPACT-REVIEW.md` 并提交, 保留每轮记录, 不用新轮次覆盖旧轮次; 它是调查报告, 不新增产品判据. 明确的实现破坏拆成返工 ISSUE; 需要产品取舍的发现先报缺口交我裁决, 再按需更新决策账本, 两份 spec, 执行任务及实现. 返工合并并通过整体验证后, 对新集成提交重新做影响复查. 完成标准: 报告可复核且无未处理的破坏或待裁决缺口, 或已停下汇报缺口; 不声称有限检查找到了全部影响.
- 评审: 影响复查通过后, 调用 `code-review` skill, 显式传入 `EXECUTION.md` 记录的评审起点. 每条轴启动一名 *审核者* 并行评审, 保留各轴完整发现清单, 只限制摘要篇幅. 有须重构发现项就走重构, 没有才能进入独立核验. 完成标准: 各轴都有完整结论, 下一节点符合评审结果.
- 重构: 采纳影响复查, 评审或核验的明确发现项, 拆成新 ISSUES. 再取当前可立即执行的前沿. 修复仍须经过实现, 提交, 合并, 影响复查与评审, 不跳过前述检查直接核验. 完成标准: 每条采纳项都有新 ISSUE, 已回到原执行循环.
- 独立核验: 最后一轮评审无新的须重构项后, 另起独立会话调用 `verify-change` skill. 按已确认 PRODUCT.md 组织产品核验. 你不亲自使用 verify-change. 让未参与实现与修复的人检查成品, 避免作者自验.
  核验只产证据, 不产验收结论: 它不关闭正式人工验收, 只把发现项送回返工回路. 报告绑定本轮目标提交与所引标准的版本, 逐项写结果与证据位置, 便于我在正式验收时直接引用.
  按子代理调度原则写派工单:

  - 身份: 本轮独立核验指挥者.
  - 现场: 合并后的目标提交, 产物根目录与已确认 PRODUCT.md 路径.
  - 范围外: 不继承实现会话, 不修复, 不改产品.
  - 输出契约: 报告路径, 覆盖提交, 逐项结果与三类去向.
  - 完成证据: 报告写入证据目录.

  核验会话只发现并回传问题, 不修复. 完成标准: 报告绑定本轮目标提交, 每个必验项都有结果.
- 核验回传: 明确实现问题拆成新 ISSUES. 回到重构, 实现, 提交, 合并与评审. 评审再收敛后, 重新派独立核验.
  环境, 权限, 标准或证据缺口不算实现缺陷. 按原停止条件向我汇报, 只阻塞依赖项, 不拆重构 ISSUE. 缺口未经我处理前, 不做正常收尾.
  完成标准: 实现问题都已进入 ISSUE, 缺口单列, 两者没有混写.
- 停止并汇报: 格式见 [reference/orchestration.md](reference/orchestration.md) 的 停止并汇报格式 节. 流程顺利结束后在本会话直接给出简要汇报, 不派子代理.
