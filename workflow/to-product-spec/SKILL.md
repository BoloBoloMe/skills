开始前, 调用 `domain-awareness` skill 只读感知当前工作目录的领域模型.

目标: 编写 Product Spec: `PRODUCT.md`. 它将作为当前变更的产品结果基线, 供 LLM 与人共用.
从可靠信源处收集 PRODUCT.md 需要的信息, 如果发现存在缺口/冲突 就调用 `grilling` skill 盘问我.
盘问仍按正常/失败/边界推进; 落盘时结论直接写成 Gherkin 场景, 不另设关键场景节.
使用下方模板写 `PRODUCT.md`. ID 在 feature 内稳定且连续. 输出为 `<产物根目录>/PRODUCT.md`, 产物根目录默认 `docs/changes/<feature-slug>/`; 调用方可指定其他根目录.
Gherkin 的语法子集, 标签约定与书写纪律唯一来源是同目录 `GHERKIN.md`, 书写 `验收标准` 节前必读.

<product-spec-template>

# <变更标题> Product Spec

## 背景
当前问题, 真实受益者, 需求来源和现在处理的理由.

## 目标
- G-001: 可衡量或可观察的产品结果.

## 非目标
- 不做 X, 它不在本变更范围内.

## 用户故事
- US-001: 作为 <actor>, 我想要 <capability>, 以便 <benefit>.

## 业务规则
- BR-001: 产品必须遵守的规则.

## 验收标准
本节为单个 ```gherkin 代码块: 首行 `# language: zh-CN`, 次行 `功能: <变更标题>`, 其后为全部场景. 不产独立 .feature 文件.

```gherkin
# language: zh-CN
功能: <变更标题>

@AC-001 @normal @G-001 @US-001
场景: <场景名>
假定 <前提>
当 <行为>
那么 <可观察结果>
而且 <可观察结果>

@AC-002 @edge @G-001 @BR-001
场景大纲: <场景名>
假定 <前提>
当 <行为>
那么 <可观察结果>

例子:
| 输入 | 结果 |
| a    | x    |
```

## 非行为验收
审计式断言: 写不成刺激-响应行为者 (如"未引入认证"), 不进 Gherkin 场景, 落在本节; 转得了行为的断言必须写成场景.
- NB-001: <审计式断言>. 无则写"无".

## 成功指标
- 指标, 观察窗口和目标值. 不设指标时写已确认理由.

## 产品决策引用
- <账本路径>: D001, D002. 多账本时每份账本一行. 无则写"无".

## 待验证事实
- 事实:
  影响:
  验证方式:
没有则写"无".

</product-spec-template>

完成标准:
- 固定章节齐全.
- 场景覆盖盘问确认的正常/失败/边界分支; 每项验收结果可观察.
- 非行为验收仅收审计式断言.
- 每项产品结论都能追溯到源头; 无阻塞产品缺口或冲突; 每项非阻塞未知都有影响和验证方式.
- 机检通过: 执行本 skill 同目录的 check-ac.py (`uv run <skill 目录>/check-ac.py <PRODUCT.md 路径>`), 退出码 0; 机检五项校验一律以脚本结果为准, 禁止目检替代脚本.
编写完成后, 在会话中告诉我: 已生成的路径, 机检执行结果, 是否存在待验证事实, 是否发现来源冲突. 不复述文档, 不让我阅读后确认.
