为指定的代码变更生成一份丰富的 HTML 解释文档, 以帮助读者理解变更的本质. 该文档包含以下几个部分:

1. **背景**: 解释与此变更相关的现有系统. 读者水平未知, 因此同时包含面向初学者的深度背景 (熟悉者可跳过), 以及直接关联变更的窄幅背景. 需广泛探索变更周围的代码, 为了不让当前会话过长, 让子代理代劳.

2. **主旨**: 选一个最小但能说明问题的表达方式, 解释此次变更的中心主旨. 聚焦于本质, 而非完整细节. 不要长篇大论, 而是使用具体示例/toy data/插图/图表.  根据改动类型选图:
  - 改逻辑/算法 → 用伪代码
  - 改运行流程 → 用调用树
  - 改 UI → 用组件树
  - 改目录/大重构 → 用文件树
  - 改交互/数据流 → 用 Mermaid 展示组件
  - 小改动, 重点是 "变了什么" → 用 diff
  - 大部分都是新写的 → 直接贴完整代码块

3. **证据**: 搜集确凿的证据证明这种改变是有效的, 展示变更前后的对比. 证据分为两类: 屏幕截图和基于执行的证据. 屏幕截图是 S 级的, 当环境变化是可视的时候优先使用. 基于执行的证据是 A 级的, 测试结果, 控制台输出. 附上现在失败和修复后通过的确切测试代码片段. 缺乏证据时必须先和我报告缺口, 然后和我讨论如何补充证据.

4. **合并风险**: 描述一下这个变更的合并风险, 以帮助读者理解变更的潜在影响. 主要关注以下几个方面:
  - 影响范围 (Blast Radius): 用一句大白话概况影响范围, 例如: `影响了整个支付流程`, `只影响了用户登录`, `只影响了一个小组件`. 可选再补充: 合并后可能造成什么后果, 例如: `可能导致老用户无法登录`, `可能导致支付失败`, `可能导致xx流程阻断`.
  - 有没有回头路: `有` 是指合并后发现不对, 可以轻松回滚, 风险相对较低, 要说清楚回退的条件和方法. `没有` 指合并后很难回滚, 风险高. 要说清楚为什么没有回退的可能性.

5. **测验**: 出五道题, 测试读者对本次变更的理解. 难度中等: 需要真正理解变更实质才能答对, 但不出偏题怪题. 目标是帮助读者确认自己是否真正理解了. 以交互式多选形式呈现, 点击后告知对错并给出反馈.
