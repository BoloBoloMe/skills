为我指定的代码变更生成 HTML 讲解页, 帮我理解为什么改, 怎样改, 有什么证据, 合并后会影响什么. 围绕这次变更讲清因果关系, 而不是写 PR 正文或通用教程.

## 流程

1. 确定比较范围: 以我指定的差异, 分支或合并请求为准, 弄清比较的起点和终点, 以及未提交改动是否包含在内. 当前检出的代码未必是目标版本; 如果目标不明确且不同选择会改变讲解, 先问我, 否则写明采用的假设. 只查支撑新旧状态解释所需的材料. **完成标准**: 比较范围可复核, 关键旧状态和新状态各有对应来源.
2. 组织讲解主线: 从旧做法及改动理由, 到新思路, 再到代码如何落实, 边界和取舍. 按行为而非文件清单组织, 避免读者知道改了哪些行, 却不知道为何要改. **完成标准**: 每项关键改动都能说清改动缘由, 对行为或结构的影响; 预期不变的行为也已说清.
3. 核查关键效果和合并风险, 按下文的证据规则处理未证实的结论. **完成标准**: 效果的依据和缺口已逐项标清, 影响范围与回退判断有依据, 证据缺口已由我决定如何处理.
4. 调用 `present` skill 生成并展示讲解页. **完成标准**: 页面符合下文内容要求, 测验交互可用, 并按 `present` 的展示或失败出口交付.

## 页面内容

页首用短摘要交代问题和主要做法, 然后按以下顺序展开:

1. **背景**: 只解释理解本次变更所需的系统背景和旧行为, 说明有依据的改动理由与不改的后果. 动机材料不足时标明推断, 不替作者编动机; 不把讲解扩展成通用教程.
2. **思路**: 在实现细节前说明核心想法, 用一个具体输入或场景对比新旧做法. 示例若只是推演, 就标为示意, 避免被当作实测结果.
3. **代码讲解**: 按执行顺序或依赖关系分组说明关键改动, 包括跨模块约定和重要边界. 引用文件路径与符号名; 只有行号能对照目标版本核实时才引用 `文件:行号`, 交付前再核对. 摘取必要代码, 不整段照抄差异.
4. **证据**: 把已观察到的结果, 根据代码推断的效果和尚未验证的效果分开. 引用测试时指明相关测试代码及实际运行结果; 有可靠的变更前失败记录时再与变更后结果对照. UI 效果适合用实际截图, 非可视效果可用测试或日志/控制台输出/数据库数据. 未运行的测试不能写成通过, 也不能编造旧版本的运行结果. 如果关键结论缺少证据, 先告诉我缺什么, 影响哪项结论, 并讨论怎么补; 在我决定补证据或明确同意标出缺口前, 暂停生成最终页面.
5. **合并风险**: 用白话说明受影响的功能或人群及可能后果; 单独判断合并后能否低成本恢复, 说明回退条件和方法, 或难以回退的原因. 撤回代码不等于撤回已写入的数据或外部副作用.
6. **测验**: 五道中等难度的选择题, 检验对行为, 原因, 模块间约定, 边界或取舍的理解, 不考冷僻细节.

图示放在对应讲解旁, 只选能让关键关系更清楚的表达: 算法用伪代码, 运行路径用调用树, UI 用简化界面或组件树, 目录改动用浅层文件树, 交互或数据流用关系图和示例数据. 局部改动可用差异图, 大部分是新代码且上下文不可省时用完整代码块. 只放当前问题需要的元素; 首次出现的专业词用白话解释, 术语较多时再加简短词汇表.

## 测验质量

五题的干扰项要对应本次变更中真实可能的误解, 且与正确项在长度, 语法和具体程度上相近, 让读者必须理解内容才能选择. 避开玩笑选项, 明显不可能的说法, `以上皆是/以上皆非` 和页面没有依据的知识. 正确项的位置在写入页面的数据中就要打散, 不能仅靠展示时随机排列掩盖固定答案顺序; 展示时再独立打乱每题的选项. 每题作答后立即说明对错和理由, 指向相关行为或代码路径. 交付前检查整组题目, 确认不能只靠复述页面原句或选项外观答对.
