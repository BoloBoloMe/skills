为我指定的代码变更生成 HTML 讲解页, 帮我理解改动的背景, 核心想法, 实现, 证据和合并影响. 围绕这次变更讲解, 不写成 PR 正文或通用教程.

## 流程

1. 确定变更范围, 以我指定的差异, 分支或合并请求为准, 并用当前检出的代码和相关材料核实. 如果目标不明确且会实质改变讲解内容, 先问我; 如果可以合理判断, 写明采用的范围和假设. 只查足以支撑新旧行为解释的相关材料, 不为探索而扩大范围. **完成标准**: 变更范围明确, 旧行为和新行为都有相关事实支撑.
2. 先组织讲解线索, 再写页面: 从问题和旧行为讲到新做法的直觉, 再解释代码如何实现, 以及重要边界, 取舍和可观察结果. **完成标准**: 讲解从背景自然走到新做法和实现, 读者能看出改动解决了什么问题.
3. 核对效果证据和回退判断. 对关键效果区分实际观察到的结果与推断. 证据不足时按下文的证据规则处理. **完成标准**: 关键效果有依据, 风险判断说明影响范围和回退依据, 证据缺口已按下文规则处理.
4. 调用 `present` skill 生成并展示 HTML 讲解页. **完成标准**: 页面已生成并展示, 内容齐全且符合 `present` 的要求.

## 页面内容

页首用短摘要点明改动要解决的问题和主要做法, 然后按以下顺序展开:

1. **背景**: 解释理解改动所需的现有系统和旧行为. 先给必要的基础说明, 再聚焦到直接相关的组件, 模块间约定和调用关系. 不默认铺开通用教程.
2. **直觉**: 在进入实现细节前说明改动的核心想法. 尽量用具体的小例子或示例数据对比改动前后的行为, 让读者看到新做法解决了什么问题.
3. **代码讲解**: 按执行顺序或依赖关系分组说明关键改动, 不按文件列表逐个介绍. 有可靠行号时引用 `文件:行号`, 并在交付前对照目标分支或合并请求的准确版本重新核对. 行号不稳定或无法核实时, 改用文件路径和符号名, 不猜行号. 不要整段照抄差异.
4. **证据**: 用变更前后的材料说明改动效果. 环境可视时优先用截图; 也可用测试结果和控制台输出. 引用执行证据时提供相关测试代码和实际结果; 有可靠的变更前失败结果时, 与变更后的通过结果对照. 不得把未运行的测试说成通过, 也不得编造变更前的结果. 证据不足时, 先告诉我缺少什么以及它影响哪项结论, 再和我讨论如何补充. 在我决定如何处理前, 暂停生成最终页面; 只有证据已补齐, 或我明确同意页面标出证据缺口后, 才完成讲解.
5. **合并风险**:
   - **影响范围**: 用一句白话说明哪些功能或用户会受影响, 必要时补充可能后果.
   - **能否轻松回退**: 说明合并后能否低成本恢复. 能回退时写清条件和方法; 难以回退时说明不可逆的操作或影响. 仅凭代码可以撤回, 不代表数据变化或外部副作用也能轻松撤回.
6. **测验**: 出五道中等难度的选择题, 检查读者是否理解变更实质. 题目考查行为, 原因, 模块间约定, 边界或取舍, 不考冷僻细节.

把图示放在它解释的内容旁边, 按改动类型选最小且有效的表达:
- 逻辑或算法: 伪代码.
- 运行流程: 调用树.
- UI: 展示关键状态和模块边界的简化界面或组件树.
- 目录调整或大规模重构: 浅层文件树.
- 组件交互, 控制流程或数据流: Mermaid 或系统图, 并附上有助于理解的示例数据.
- 改动重点是变了什么, 且周围结构已存在: 差异图.
- 大部分内容是新写的, 或省略上下文会掩盖归属和顺序: 完整代码块.

只展示回答当前变更问题所需的调用, 文件, 状态和边界. 可以组合多种表达, 但不要为了丰富页面而堆图. 首次出现的专业词用白话解释; 术语较多时再加简短词汇表.

## 测验质量

选择题要测理解, 不要让读者靠选项外观猜答案:
- 正确项和干扰项的长度, 语法结构, 具体程度和语气保持相近. 正确项不能总是最长, 最具体或最肯定的一项.
- 干扰项应对应对本次改动的真实误解. 不用玩笑选项, 明显不可能的说法, `以上皆是/以上皆非` 或页面内容无法支持的冷知识.
- 五题的正确项位置尽量均衡, 不形成固定顺序或明显规律. 写入页面的数据中也要打散正确项位置, 不依赖页面加载时随机排列来掩盖固定答案顺序; 显示时再独立打乱每题的选项.
- 每题点击后立即说明对错和理由, 指向相关行为或代码路径. 检查整组题目, 确认问题本身不能靠复述页面句子答对.
