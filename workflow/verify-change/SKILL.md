# 验证方案与独立验证

`verify-change` 有两种调用方式, 由需求所处阶段和已有材料决定:

- **设计验证方案**: 已有完成的 `PRODUCT.md` 与 `TECHNICAL.md`, 还没有已确认的验证方案. 通常在规格整理完成后, 实施开始前调用. 只读规格, 不看实现, 输出待我确认的方案.
- **执行验证方案**: 已有我确认的验证方案, 且成品已实施. 按方案对指定提交做独立验证, 整理证据并报告结果.

方案不存在时不能直接执行验证. 已有方案但成品尚未实施时, 继续实施, 不提前执行. 规格或目标提交缺失时报告输入缺口并停止. 验证方案确认不等于成品验收.

执行方式中, 你只组织验证并复核材料, 不亲自操作成品或运行其命令与入口, 不替验证者补跑, 不组织修复, 不改产品或评审技术设计.

## 设计验证方案

1. **核对权威输入.** 确定产物根目录, 读取其中当前有效的 `PRODUCT.md` 和 `TECHNICAL.md`. `PRODUCT.md` 的 `验收标准` 节须有 `<!-- confirmed-flow: vN -->` 标记. 同时调用 `verification-contract` skill, 确认本次变更适用的验证类型与共用底线. 两份规格缺失, 冲突, 未完成或无法判断当前版本时, 报告缺口并停止; 不从会话口头要求或实现反推判据.
   完成标准: 已找到两份规格, 验收场景有确认标记, 来源与冲突均已核清; 或已报告缺口并停止.

2. **逐项设计可行步骤.** 建立覆盖表, 必须包含 `PRODUCT.md` 中每个 Gherkin 场景和每条标记 `(审计)` 的业务规则. 一个 `AC-NNN` 可能包含多个场景, 按场景逐项覆盖; 场景大纲连同其全部 `例子` 一起覆盖. 每行引用原有 `AC-NNN`/`BR-NNN` 和场景标题, 不拆改或重写验收标准.

   对每个 Gherkin 场景, 依据产品角色, 输入和预期结果, 描述如何通过产品对外提供的交互界面执行并观察结果. 步骤与场景处于同一抽象层级, 写清谁在什么前提下进行什么交互, 应观察到什么; 不写按钮点击序列, 内部方法, 数据库查询, 测试桩或测试脚本. `TECHNICAL.md` 用来确认入口与观察方式可行, 不增加产品通过判据. 模块接口若不是产品对外提供的界面, 不能代替产品入口.

   对审计规则, 按断言本身设计静态核对或真实运行步骤, 并与 Gherkin 场景分开标记. 如某项没有可行的入口或观察方式, 将其标为规格缺口并停止提交完整方案, 交回规格整理或既有决策流程; 不靠内部接口或临时实现补成可验证.

   按第 1 步调用的 `verification-contract` skill, 逐项核对方法是否符合本变更适用的验证类型与共用底线. 验证契约只约束方法, 不新增产品判据. 找不到合规方法时, 报告方法或规格缺口并停止, 不降低契约要求.
   完成标准: 每个 Gherkin 场景和审计 BR 都有一条可执行的验证步骤, 输入与预期观察明确, 覆盖表行数等于 Gherkin 场景数与审计 BR 数之和, 每项方法符合适用的验证契约; 或已列明阻塞缺口并停止.

3. **落盘方案.** 在产物根目录写 `VERIFICATION-PLAN.md`, 至少包含 `方案版本: vN`, `确认状态: 待确认/已确认`, 来源引用, 覆盖表, 必要前提与资源限制. 覆盖表列出必验项编号与标题, 适用的验证类型, 技术规格中的入口引用, 验证步骤, 预期观察, 所需证据和环境条件. 来源引用采用 `PRODUCT.md` 的 `confirmed-flow: vN`, 每个场景的 `AC-NNN` 与标题, 审计 `BR-NNN`, `TECHNICAL.md` 中相关章节和接口名称, 以及适用的验证契约要求. 不给两份规格增加整份文件的版本号, 也不复制整份规格. 编号可能在修订时保持不变, 因此执行时仍须核对被引用内容与方案是否一致.
   完成标准: `VERIFICATION-PLAN.md` 已写入约定产物根目录, 每条来源可定位, 方案修订号和待确认状态明确.

4. **请我确认固定版本.** 向我提供方案路径与修订号, 请我确认这份方案或指出修改项. 只有我明确确认该修订号对应的内容后, 才将状态改为已确认. 修改方案内容就递增修订号并重新展示, 不沿用先前确认.
   完成标准: 我已明确确认当前修订号, 方案状态为已确认; 或仍保持待确认并停止.

## 执行验证方案

1. **核对方案, 规格与成品.** 确认 `VERIFICATION-PLAN.md` 已确认, `PRODUCT.md` 的验收标记与方案来源一致, 覆盖表行数等于当前 Gherkin 场景数与审计 BR 数之和, 当前引用的规格内容仍与方案相符. 调用 `verification-contract` skill, 核对方案是否符合适用要求; 方案不符合时, 先回到设计方式更新并重新确认. `AC-NNN`/`BR-NNN` 是定位编号, 不是内容版本; 即使编号未变, 条件或预期结果发生变化也要先更新并重新确认方案. `TECHNICAL.md` 没有整份版本要求, 只核对方案引用的接口内容是否仍适用. 再确认目标项目, 指定提交和产物根目录. 目标提交须存在, 当前工作区须与它一致且没有未提交的产品文件或改动; 否则报告缺口并停止.
   验证开始后若产品标准新增或改变, 或方案引用的技术入口与观察约束发生变化, 本轮只覆盖原方案和原目标提交, 不把新内容悄悄并入. 等调用方指定包含新内容的已提交目标并确认更新后的方案, 再开始新一轮.
   完成标准: 方案修订号, 来源, 全部必验项, 目标项目和完整提交号均已核实; 或已报告缺口并停止.

2. **准备本轮执行.** 在产物根目录确定不覆盖旧材料的本轮证据目录, 名称带目标提交信息. 先读项目 README, 构建脚本和测试配置, 判断证据目录是否会进入构建, 测试发现或运行输入; 有影响时将证据放到仓库外. 根据方案里的前提和现场资源安排验证分组: 只在资源可隔离且并行有收益时分组, 不逐条用人, 共用准备只做一次并记录原件归属, 争用写入按序执行.

   写入授权与数据保留按第 1 步调用的 `verification-contract` skill 的安全底线执行. 需要性能结论时, 在对应派工单中要求承接者调用 `benchmark-checklist` skill; 需要核实关键安全事实时, 要求承接者调用 `blast-radius` skill. 这些方法不新增产品判据.
   完成标准: 证据目录位置和影响已核实, 每个必验项有执行安排, 写入授权和数据保留条件已满足; 或已停在授权之前.

3. **派发非作者验证者.** 首轮和复验都由未参与本次实现与修复的人独立操作. 每名验证者使用本轮新开的子会话, 并用可核对事实确认其未参与, 不只采信自述. 有可并行收益时按分组同时派出; 无可用非作者时报告受阻, 不回退自验.

   派工材料只给目标提交, `VERIFICATION-PLAN.md`, 相关规格路径, 证据目录和 [逐项核对规则](reference/SCENARIO-CHECK.md), [证据规则](reference/EVIDENCE.md). 不给实现对话, 作者设计理由或自证结论. 要求验证者调用 `verification-contract` skill 并遵守共用底线, 产品通过判据仍只取 `PRODUCT.md`. 明确要求验证者按方案操作并留存原件; 项目有操作配方时, 指向当前项目中的实际文件和加载入口. 启动时调用 `use-herdr` skill 并读取其 `launch.md`, 选型时调用 `llm-select` skill. 所需方法 skill 由验证者在派工单所写入口点名调用.
   完成标准: 每个必验项都有非作者承接者和明确的操作入口, 未参与事实可复核; 或已报告无可用验证者并停止.

4. **核对执行结果与原件.** 验证者按方案从产品对外入口操作, 不因现场实现与方案不符而自行降低要求或改走内部接口. 入口缺失或观察不到结果时, 受影响项记未验证并报告规格/操作缺口. 按 [逐项核对规则](reference/SCENARIO-CHECK.md) 判定结果, 再按 [证据规则](reference/EVIDENCE.md) 核对材料类型, 适用性和原件. 明确实现问题, 尚缺产品规则, 权限或环境缺口分开记录.
   完成标准: 每项必验内容都有可复核结果和原件位置, 失败与未验证缺口已分类; 或缺口已明确记录.

5. **写独立验证报告.** 报告写入本轮证据目录, 至少记录: 目标提交, 方案修订号, `PRODUCT.md` 的确认标记和标准引用, 技术规格引用, 每项的操作/材料/结果/证据位置/结论, 验证者及未参与事实, 分组依据与争用写入顺序, 写入授权与数据保留记录, 失败和未验证项的去向. 报告绑定本轮目标提交和所用方案, 不把未运行或推断写成通过.

   收尾写明: "除本次证据目录的输出外, 源码与 Spec 未变". 报告只记录独立验证结果, 不宣布正式交付或代我作正式验收决定.
   完成标准: 报告与原件绑定明确提交和方案修订号, 覆盖表逐项有结果, 未验证与失败分列, 证据可复查.

修复后的复验规则见 [复验](REVERIFY.md).

## 边界

目标项目只读. 不改产品代码, 配置, 测试或项目级配方; 不提交, 不推送, 不开 PR, 不合并. 执行验证需要超出已批准范围的写入时停止并请求批准. 需要改产品标准, 正式用例或对外接口时, 交回既有决策与规格流程.
