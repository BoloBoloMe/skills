# 验证方案与独立验证

`verify-change` 有两种调用方式, 由需求所处阶段和已有材料决定:

- **设计验证方案**: 已有当前有效且已确认的权威输入, 还没有适用的已确认方案, 或现有方案需要修订. 通常在判据确认后, 实施前调用. 不要求固定文件名或 spec 格式; 权威输入须能提供设计方案所需的判据与验证依据. 只读权威输入, 不看实现. 先与我盘问确认内容, 再成文并经独立核对交付方案.
- **执行验证方案**: 已有我确认的验证方案及其引用的当前权威输入, 且成品已实施. 按方案对指定提交做独立验证, 整理证据并报告结果.

方案不存在时不能直接执行验证. 方案已确认且仍适用但成品尚未实施时, 交实施流程, 不提前执行. 权威输入不能提供所需判据与验证依据, 或目标提交缺失时, 报告输入缺口并停止. 验证方案确认不等于成品验收.

执行方式中, 你只组织验证并复核材料, 不亲自操作成品或运行其命令与入口, 不替验证者补跑, 不组织修复, 不改产品或评审技术设计.

## 设计验证方案

1. **核对权威输入.** 确定产物根目录, 找出当前有效且已确认的权威输入. 不要求固定文件名或同时具备 `PRODUCT.md` 和 `TECHNICAL.md`. 输入须能定位全部必验要求, 场景和例子: 行为须有相关角色, 输入, 预期结果, 产品对外入口和观察依据; 审计须有对象和可核对依据. 调用 `verification-contract` skill 确定适用的验证类型, 方法和证据要求, 不因此增加或改变产品判据. 规格先确认, 不把规格结束确认当作方案确认.
   输入未确认, 当前版本不明, 欠缺或冲突时, 报告具体缺口, 停止提交完整方案, 交回权威输入维护或既有决策流程. 设计主动查证只读权威输入, 不从实现, 测试代码, 临时实验或未确认口头要求反推判据. 仅在此边界内按盘问规则查证事实.
   完成标准: 输入有效且已确认, 适用的验证契约和全部必验项可定位; 或已报告缺口并停止.

2. **按验证方式盘问.** 调用 `grilling` skill. 按 LLM 怎样验证某条或某类已确认要求归组, 用大白话说明用什么材料, 怎样验, 看什么结果, 留什么证据. 同一种方法不逐条重过用例, 不把检查内容差别或小操作拆成问题. 方法或适用条件有实质差别, 或特殊情况需要新选择, 就另问. 仅当安排能从已确认权威输入及本变更已有确认直接推出时免问; 你构造的新选择不算已有依据. 拿不准能否免问或是否同类就问我.

   行为验证从产品对外入口操作并观察, 使用契约要求的真实依赖, 不用内部接口或测试桩顶替. 权威技术或操作输入只确定入口, 观察方式和操作条件. 审计按断言对象安排静态核对或真实运行, 与行为验证分开. 方法已知可行但执行条件未齐, 可确认附条件方案并写明必备条件. 找不到合规方法, 或方法/入口/观察依据不足时, 报告具体缺口并停止提交完整方案, 交回权威输入维护或前置调查. 材料补齐并按原流程确认后再继续. 设计会话不自行读实现或做实验, 不把方法未知记作资源待备.

   调用 `decision-ledger` skill, 按现有通用格式记录已确认决定及其依据事实; 无账本时按该 skill 的规则在指定产物根目录新建 `DECISIONS.md`. 同会话继续或闭环不写交接. 换会话前先入账, 再调用 `handoff` skill 交接; 新会话读账本和交接恢复当前可问问题, 否决分支及理由, 逐题和实际方案范围的覆盖进度, 盲区扫描进度, 待裁决项及我明确提出的节奏要求. 已入账内容只引用, 不推测我的状态. 不新增盘问专用文件, 章节或格式, 免问情况不留痕. 方案不是账本, 不替代未确认决定, 不另列免问记录.
   完成标准: 需要我选择的方法和适用条件均已决定并入账, 可进入闭环; 若仍在续问或有缺口, 不成文.

3. **确认范围并让独立反方检查决定.** 按权威输入对照全部必验项和例子, 完成盲区扫描, 向我呈现覆盖清单, 跳过理由和资源条件. 清单不是已问问题列表, 也不要求我逐行阅读成文步骤. 只有我在看到这些材料后明确结束盘问才确认相应方案内容; 沉默, 部分认可或要求继续均不算确认.

   闭环并入账后, 由未参与相应盘问与落盘的独立会话调用 `opposing-viewpoint` skill, 对照权威输入攻击已入账决定. 另起反方和成文核对会话时沿用执行方式第 3 步的会话工具和选型规则, 不沿用成品执行派工材料. 主会话核实发现, 只有需要新增或改变验证决定时补问受影响分支, 入账, 核对更新后的范围并取得明确闭环. 反方或成文核对者都不替我拍板. 给两个会话的原始答复均限必要材料, 按 [安全底线的脱敏节](../verification-contract/SAFETY.md#脱敏) 处理, 保留可核对上下文; 脱敏后不足以判断就报缺口, 不猜.
   完成标准: 我明确闭环, 决定及依据已入账, 独立反方的发现已收敛, 无待裁决项才落笔.

4. **成文并独立核对.** 主会话在产物根目录写 `VERIFICATION-PLAN.md`, 至少保留 `方案版本: vN`, `确认状态: 待确认/已确认`, 来源引用与确认依据, 覆盖表, 必要前提和资源限制. 来源列每份权威输入的路径及确认依据, 以及确定入口与观察方式的技术或操作依据; 不自造来源编号或版本, 不复制整份输入.

   覆盖表按权威输入原有粒度逐项覆盖全部必验要求, 独立场景和全部例子. 每行写来源位置和现有编号或标题, 验证类型, 产品入口或审计对象, 步骤, 预期观察, 证据和环境条件. 没有编号或标题就引用原文位置. 步骤与判据同一抽象层级, 写清谁在什么前提下执行什么交互并观察什么, 不写按钮点击序列, 内部方法, 数据库查询或测试脚本. 提问归组不减少覆盖行, 不拆改或重写判据.

   另起与反方不同且未参与相应决定或写稿的独立会话, 只查不改. 从已确认权威输入及盘问决定与用户答复反查全部必验项与例子, 核对成文对原决定和判据的忠实性, 全量覆盖和可执行性. 方案是被查对象, 不能以其自身文字证明忠实或覆盖, 也不能用行数代替逐项核对. 检查结果给出来源和对应方案位置, 记录发现及其影响. 有发现按下述修订规则处理.
   完成标准: 首次全量独立核对无阻塞, 当前内容可追溯到明确的盘问闭环和独立核对, 才以已确认状态交付. 不再请我逐行阅读或采纳整份成文方案.

## 方案修订

主会话先复核发现. 误报说明驳回理由; 有依据的转述错误由主会话直接修文, 不重问原决定. 缺少或改变验证决定, 包括原先免问但核不出依据时, 只按设计验证方案补问并入账受影响的决定, 核对更新后的范围并取得明确闭环, 不重问已定决定. 需要新增或改变产品判据时先交回原权威输入维护或既有决策确认流程, 不在方案里改判据.

每次内容修订递增方案版本, 用现有来源引用和检查产物保留变更及确认依据. 仍由独立检查核对修订分类, 当前内容是否忠实于确认, 以及受影响内容与引用. 未变且未受影响部分说明适用理由后沿用旧结论; 有新证据要求或不能确定旧结论仍适用时扩大复查. 版本号, 确认状态或通知不证明内容已获确认. 当前版本可追溯确认及独立复查且无阻塞才交付, 不恢复逐版阅读和采纳整份方案.

## 执行验证方案

1. **核对方案, 权威输入与成品.** 核实 `VERIFICATION-PLAN.md` 当前内容可追溯到盘问闭环及独立核对, 引用来源仍是当前有效且已确认的输入. 逐项核对实际内容: 判据及预期取自权威输入, 入口及观察依据仍适用, 必验项与例子无缺, 方法与证据忠实于确认的决定. 不只核对文件名, 编号, 标题, 版本, 状态或行数. 调用 `verification-contract` skill 核对方法和证据仍合规. 方案或引用依据实际变化需要更新时, 先回设计验证方案按 [方案修订](#方案修订) 分流并核对更新后的内容, 只为新增或改变的验证决定补问; 不改产品判据, 不逐版重读采纳.
   再确认目标项目, 指定提交和产物根目录. 目标提交须存在, 当前工作区须与它一致且没有未提交的产品文件或改动; 否则报告缺口并停止. 开始前核对方案规定的整轮前置条件, 如尚待用户明确通知完成其环节, 停下报告, 不从状态或版本推断已完成. 验证开始后判据或方法依据变动, 本轮仍只覆盖原方案与原目标提交, 不并入新内容. 下一轮使用明确目标提交与适用的方案修订号, 并重核调用方与方案规定的前置条件.
   完成标准: 当前方案内容和修订号, 来源, 全部必验项, 目标项目和完整提交号均已核实; 或已报告缺口并停止.

2. **准备本轮执行.** 在产物根目录确定不覆盖旧材料的本轮证据目录, 名称带目标提交信息. 先读项目 README, 构建脚本和测试配置, 判断证据目录是否会进入构建, 测试发现或运行输入; 有影响时将证据放到仓库外. 按已确认方案和安全底线准备必要的隔离环境. 前置授权或本轮必备条件仍未满足时不强行执行, 标明缺口, 受影响项记未验证, 不调低标准或改用较弱证据. 根据方案里的前提和现场资源安排可执行项的验证分组: 只在资源可隔离且并行有收益时分组, 不逐条用人, 共用准备只做一次并记录原件归属, 争用写入按序执行.

   写入授权与数据保留按第 1 步调用的 `verification-contract` skill 的安全底线执行. 需要性能结论时, 在对应派工单中要求承接者调用 `benchmark-checklist` skill; 需要核实关键安全事实时, 要求承接者调用 `blast-radius` skill. 这些方法不新增产品判据.
   完成标准: 证据目录位置和影响已核实, 可执行项有安排, 相关写入授权和数据保留条件已满足; 缺条件的项已记录为未验证, 不越权执行.

3. **派发非作者验证者.** 首轮和复验都由未参与本次实现与修复的人独立操作. 首轮使用本轮新开的子会话; 复验按 [复验规则](REVERIFY.md) 决定新开或恢复. 用可核对事实确认其未参与, 不只采信自述. 有可并行收益时按分组同时派出; 无可用非作者时报告受阻, 不回退自验.

   派工材料只给目标提交, `VERIFICATION-PLAN.md`, 权威输入路径, 证据目录和 [逐项核对规则](reference/SCENARIO-CHECK.md), [证据规则](reference/EVIDENCE.md). 不给实现对话, 作者设计理由或自证结论. 要求验证者调用 `verification-contract` skill 并遵守共用底线, 产品通过判据只取已确认的权威输入原文. 明确要求验证者按方案操作并留存原件; 项目有操作配方时, 指向当前项目中的实际文件和加载入口. 启动时使用已确认的会话工具; 没有另定工具时, 调用 `use-herdr` skill 并读取其 `launch.md`. 选型时调用 `llm-select` skill. 所需方法 skill 由验证者在派工单所写入口点名调用.
   完成标准: 每个可执行项都有非作者承接者和明确的操作入口, 未参与事实可复核; 或已报告无可用验证者并停止.

4. **核对执行结果与原件.** 验证者按方案从产品对外入口验证行为, 并按已定方法核对审计项; 不因现场实现与方案不符而自行降低要求或改走内部接口. 因入口缺失或操作条件不满足而无法观察结果时, 受影响项记未验证并报告权威输入或操作缺口. 按 [逐项核对规则](reference/SCENARIO-CHECK.md) 判定结果, 再按 [证据规则](reference/EVIDENCE.md) 核对材料类型, 适用性和原件. 明确实现问题, 尚缺产品规则, 权限或环境缺口分开记录.
   完成标准: 每项必验内容都有可复核结果和原件位置, 失败与未验证缺口已分类; 或缺口已明确记录.

5. **写独立验证报告.** 报告写入本轮证据目录, 至少记录: 目标提交, 方案修订号, 权威输入的路径与确认依据, 每项判据的原文位置, 相关技术或操作依据, 每项的操作/材料/结果/证据位置/结论, 验证者及未参与事实, 分组依据与争用写入顺序, 写入授权与数据保留记录, 失败和未验证项的去向. 报告绑定本轮目标提交和所用方案, 不把未运行或推断写成通过.

   收尾写明: "除本次证据目录的输出外, 产品实现与权威输入未变". 报告只记录独立验证结果, 不宣布正式交付或代我作正式验收决定.
   完成标准: 报告与原件绑定明确提交和方案修订号, 覆盖表逐项有结果, 未验证与失败分列, 证据可复查.

## 边界

执行与复验不修改目标项目, 方案需要变更时先回设计验证方案. 不改产品代码, 配置, 测试或项目级配方; 不提交, 不推送, 不开 PR, 不合并. 执行验证需要超出已批准范围的写入时停止并请求批准. 需要改产品标准, 正式用例或对外接口时, 交回既有决策与规格流程.
