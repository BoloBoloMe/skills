# 逐场景核对规则

verify-change 执行验证方案时交给验证者的规则, 由本 skill 的执行方式抵达. 材料与证据类型见 [EVIDENCE](EVIDENCE.md); 写入授权与数据保留按 `verification-contract` skill 的安全底线执行.

判据只取 `PRODUCT.md` 的场景与业务规则原文. 编号, 具体数据与期望输出都是判据. 已确认的 `VERIFICATION-PLAN.md` 只规定如何验证, 不新增, 改写或放宽判据.

`TECHNICAL.md` 在设计方式中用于确认产品入口和观察点可行, 执行时只作操作线索; 只有产品对外提供的接口才可作为验收入口, 内部模块接口不能代替产品交互. `EXECUTION.md` 只提供命令, 测试入口与环境约束等操作线索. 技术要求不进入产品通过条件, 内部代码划分或模块拆分交回既有评审与执行验证.

没配方时仍按已确认方案, `PRODUCT.md` 与项目可靠入口操作取证. 可用 README 的启动与实例检查, 现成命令或脚本. 方案入口与现场不符时, 停下报告受影响项, 不擅自改走内部接口或改写方案. 缺技术或执行文档不算受阻, 也不自动生成配方.

配方只提供操作, 不产生判据. 得不到可用实例时, 先按配方核对健康, 版本与实例归属. 没有测试环境时, 在主文件执行方式第 2 步获批后搭建真实测试实例; 搭不起来就留环境缺口. 确认步骤与当前版本不符后, 报配方过时这一操作缺口, 写明尝试路径, 卡点与实际现象, 不当作产品缺陷, 也不改配方. 无法可靠操作就留缺口.

执行计划的勾选状态不是证据. 即使全部勾选, 最终版本上的场景失败仍记失败.

无 gherkin 场景的审计 BR 按断言对象承接:

- 静态材料可判定: 给比对命令, 前后内容与可复核位置. 标为静态核对, 不是运行结果. 例如依赖清单, 锁文件与构建材料一致, 或既有测试未改.
- 断言运行过程: 用本轮资源, 对象, 操作, 数据保留位置与必要的实例停止记录. 代码或配置不能顶替运行记录.

拿不到相应材料或无法执行的必验项, 记未验证并写缺口, 写明所缺权限或依赖. 取证只用真实实例或真实入口; 自建服务桩, 本地替身与绕过真实环境临时装上的工具链产出的结果一律按未验证记. 权限与环境缺口单列, 不算实现失败. 整体结论取最弱一项: 有失败或未验证项时为未通过.

将失败与缺口按三类去向分别记录:

- 明确实现问题: 前提与授权满足, 场景稳定失败. 原因定位到实现而非环境或输入. 交回实现流程, 你不组织修复或改代码.
- 尚缺产品规则: 判定依赖未确认的新规则. 只将受影响项标受阻, 交回既有决策流程. 其他项继续, 整体结论为未通过, 缺口留给我裁决.
- 权限或环境缺口: 缺凭据, 服务或环境不可达. 写明受影响场景.

方法运行后仍未证实的安全事实, 记未验证并写缺口. 不同时判通过, 不用方法另立标准替代 PRODUCT.md.

完成标准: 你交回的每个必验项都是运行, 静态核对或未验证结果之一, 不用勾选或推断代替, 失败与缺口按三类去向分别记录.
