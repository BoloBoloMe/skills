调用 `domain-awareness` skill 只读感知当前工作目录的领域模型. 调用 `grilling` skill 盘问我, 以下内容是对盘问的额外要求.

## 盘问顺序

先关闭产品分支, 再进入依赖它的技术分支. 分支表是 spec 最小覆盖集的决策检出清单, 非闭集, 非逐条盘问工单: 盲区扫描发现列表外高影响主题时, 插入对应分支盘问; spec 生成的闭合检查兜底.

**分支收缩**: 进入分支先分诊开放度: 内容已被上游已确认分支, 当前有效决策, 我提供的材料或代码/契约事实完全确定, 且无开放项 (无备选, 无取舍, 无冲突, 无高影响未知) -> 不逐条盘问, 说明确定依据后关闭, 跳过关闭前盲区扫描, 结论带入固化回顾统一确认; 我对某项有异议 -> 返回对应分支按未收缩重新盘问. 有开放项 -> 只对开放项盘问. 不可收缩: 方向选择 (发散点), HILT 形状决策, 测试策略专项, 与有效决策或事实冲突的分支.

### 1. 产品分支

依次关闭:

1. 问题和受益者.
2. 目标, 硬约束, 明确非目标.
3. 产品方向发散 (读取并执行 `EXPLORE-DESIGN-OPTIONS.md`).
4. 选择方向.
5. 用户故事, 业务规则.
6. 正常/失败/边界场景.
7. 验收标准.

每关闭一个分支, 在会话中简述已确认结论及直接影响; 不讨论尚不依赖该结论的实现细节.

关键完成标准:

- 步骤 2: 问题/受益者/目标/硬约束/非目标已明确确认; 可比较门槛已达到; 已简述即将处理的产品决策域.
- 步骤 3-4: 发散已按外部参考返回选中方向, 或按跳过条件保留现有方向; 取消时有未决问题和恢复位置.
- 步骤 5-7: 用户故事/业务规则/场景/验收标准无阻塞未知, 每项已获我确认 (收缩分支在固化回顾中统一确认).

总完成标准: 产品目标, 非目标, 行为和验收标准无阻塞未知; 我已在会话中明确确认关键产品取舍; 步骤 2-7 每个关键分支满足 `grilling` 的分支完成标准.

### 2. 技术分支

基于已确认产品分支, 依次关闭:

1. 技术认知校准.
2. 基线代码与契约探索.
3. 技术方向发散 (读取并执行 `EXPLORE-DESIGN-OPTIONS.md`).
4. 选择方向.
5. 架构和 module 责任. 盘问到此才调用 `codebase-design` skill, 禁止提前调用. 若需求会改动 module 或 interface 形状, 调用前必须先盘问形状决策分支 (见下); 仅当能证明需求不改动二者形状时方可跳过此盘问.
6. interface/schema/状态机, 关键流程.
7. 异常和边界处理, 安全, 性能/可观测性/可用性, 代码允许/禁止范围, 风险和停止条件.
8. 测试策略 (专项盘问, 见下).
9. 遇高影响专项决定时嵌套发散 (读取并执行 `EXPLORE-DESIGN-OPTIONS.md`).

**形状决策分支**: 盘问是否以 HILT 方式确定 module 和 interface 的形状: 我需要亲自决定二者的边界及其测试用例 - 你提候选形状/取舍/理由与边界测试用例, 逐项征询我确认, 未经确认不得固定. 非 HILT 则你按 `codebase-design` 原则提方案, 我只审阅终稿. 无论是否 HILT, 形状风险高且缺乏实现知识支撑时, 先说明风险并建议暂停盘问, 做 spike 或 prototype 抬知识后回到本分支.

**测试策略专项**: 盘问前读取 `tdd` skill 的哲学一节作为设计约束, 不另行发明或改写. 以下四类决策项逐项经我明确确认, 未经确认不得写入:

- **入口缺口**: 现有真实验证入口先盘点 (事实, 不盘问); 缺失且需新建的入口, 或外部依赖不可直连时的测试替身, 确认形态和成本.
- **层级例外**: 层级默认遵循 `tdd` 哲学; 偏离默认的项 (如新建 e2e 设施).
- **高风险加强项**: 需超出默认验证强度的 AC/TG/NFR (金钱/并发/安全/迁移等) 及加强形式.
- **人工验证项**: 无法自动化的验收及通过口径.

每个 AC/TG/NFR 到层级/入口的映射是原则加事实的推导结果, 不是盘问对象 - 由 `to-technical-spec` 编制, 闭合检查兜底; 推导不出的项即入口缺口, 必须提为决策. 不枚举逐条测试清单 - 非 HILT 时清单由 afk worker 计划相自定并经父会话审查.

事实与已确认决策冲突时, 在会话中说明证据和影响, 再让我选择.

关键完成标准:

- 步骤 1: 已说明技术决策域, 我明确的不熟悉/待补充部分已获得处理路径, 无阻塞认知缺口.
- 步骤 2: 相关代码/契约/ADR 已读取; 权威技术资产已定位.
- 步骤 3-4: 同产品分支步骤 3-4.
- 步骤 5-6: module 责任已分配; interface/schema/状态机有权威来源或精确定义; 关键正常/失败流程已描述; HILT 时我已逐项确认 module 和 interface 的边界及其测试用例.
- 步骤 7: 异常和边界处理已定义; 安全策略已说明; NFR 有验证口径; 允许/禁止范围已划定; 风险和停止条件已确认.
- 步骤 8: 测试策略已经 `tdd` skill 哲学检验; 四类决策已逐项经我明确确认 (均无则明确记录为无); 每个 AC/TG/NFR 的层级/入口可推导, 推导不出的已提为入口缺口决策; 未枚举逐条测试清单.
- 已触发的步骤 9: 每个触发专项按外部参考返回选中或取消, 或按跳过条件保留现有方向; 选中则约束已纳入设计, 取消则未决问题和恢复位置明确, 不得宣告技术关闭.

总完成标准: 后续 `to-product-spec` 和 `to-technical-spec` 无需发明产品/API/架构/范围决策; 我已在会话中获知关键技术方案, 代价, 风险和验证方式; 步骤 1-8 每个关键分支满足 `grilling` 的分支完成标准; 已触发的步骤 9 分支均已关闭.

## 发散

每个方向选择点默认发散: 读取并执行 `EXPLORE-DESIGN-OPTIONS.md`. 不得仅凭 "已有 Spec" 或 "看起来明确" 跳过; 跳过是例外, 须满足下述全部条件.
发散自动含懒设计选项 (外部参考的决策阶梯), 不在发散前单独询问; 选中懒设计方向后, 当前分支后续设计受 `lazy-design` skill 约束.
选择点: 产品方向, 技术方向, 技术分支中任一高影响专项决定:

- 改变外部 interface/schema/状态机或兼容承诺.
- 涉及迁移/数据丢失/不可逆操作/并发一致性.
- 涉及权限/隐私/密钥/金钱/审计.
- 性能/可用性/一致性等 NFR 会改变架构.
- 引入新依赖/新架构/难回滚机制.
- 关键前提证据不足, 且不同处理会改变方案.

### 跳过条件

仅当以下全部满足时跳过发散, 保留现有方向:

- 现有 Spec/方向能追溯到当前有效决策, 且与当前需求/ADR/机器可读契约/关键代码事实无冲突.
- 关键假设未因依赖版本/业务规则/运行环境变化而失效.
- 该决定已在上级或前序方案中充分比较过, 且当前上下文未引入新取舍.

纯文档/措辞/配置纠正且无技术取舍时可证明后跳过. 证据不足且可能改变方向时, 按子代理验证流程处理, 不跳过.

## 固化

产品和技术分支全部关闭后, 在会话中给出高密度口头回顾: 产品结果, 关键技术选择, 明确不做, 主要风险, 验证方式, 收缩分支的确定结论及依据, 已补齐的重要知识缺口, 新暴露盲区的处理结果, 被接受的不确定性.
然后合并询问 (替代 `grilling` 自带的结束确认, 不重复提问): `当前产品与技术分支已关闭, 以上是将被固化的决策/已接受不确定性. 是否固化当前方向并结束盘问?`

- 我回答是: 使用 `domain-modeling` 维护领域语言文件或 ADR, 调用 `decision-ledger` 维护 `DECISIONS.md`, 然后结束盘问.
- 我回答否并补充问题: 不写文件, 返回对应设计分支继续.
- 写入失败: 盘问结论仍保留, 但不得声称已固化, 报告失败并恢复写入.

## 决策记录边界

- `DECISIONS.md` 记录本 feature 的产品, 代码, 边界, 测试决策和代码追踪, 不记录认知校准状态.
- ADR 只记录长期架构决策.
- 领域语言文件只记录领域词汇, 不承载实现决策.
- 客观待查事实按 Product/Technical Spec 的待验证事实规则处理, 不另建长期知识档案.
- 新增, 替代, 废弃决策前必须得到我确认.

## Spec 生成

固化结束后, 询问我是否生成 Spec. 不用则跳过; 要则依次调用 `to-product-spec` skill, `to-technical-spec` skill, 再判断: 当前在 `probe` skill 流程内则停止 (`to-execution-spec` 由 probe 准入相位按 feature 接管); 否则继续调用 `to-execution-spec` skill.
Spec 只能整理已确认决策, 不得新增; 生成中发现的任何未定决策都属于*盲区*, 回到对应设计分支继续盘问, 该分支关闭后再继续生成.
