调用 `domain-awareness` skill 只读感知当前工作目录的领域模型. 调用 `grilling` skill 盘问我, 以下内容是对盘问的额外要求.

## 盘问顺序

先关闭产品分支, 再进入依赖它的技术分支. 分支表是 spec 所需的最小覆盖集, 非闭集; grilling 盲区扫描发现列表外高影响主题时, 插入对应分支并盘问.

### 1. 产品分支

依次关闭:

1. 问题和受益者.
2. 目标, 硬约束, 明确非目标.
3. 产品方向发散 (读取并执行 `EXPLORE-DESIGN-OPTIONS.md`).
4. 选择方向.
5. 用户故事, 业务规则.
6. 正常/失败/边界场景.
7. 验收标准.

每关闭一个分支, 在会话中用简短语言说明已确认结论及其直接影响. 不讨论尚不依赖该结论的实现细节.

关键完成标准:

- 步骤 2 完成时: 问题/受益者/目标/硬约束/非目标已明确确认; 可比较门槛已达到; 已简述即将处理的产品决策域.
- 步骤 3-4 完成时: 发散后选中方向, 或按跳过条件保留现有方向; 该方向有关键理由和约束; 取消时有未决问题和恢复位置.
- 步骤 5-7 完成时: 用户故事/业务规则/场景/验收标准无阻塞未知, 每项已获我确认.

产品分支总完成标准: 产品目标, 非目标, 行为和验收标准无阻塞未知; 我已在会话中明确确认关键产品取舍; 步骤 2-7 每个关键分支满足 `grilling` 的分支完成标准.

### 2. 技术分支

基于已确认产品分支, 依次关闭:

1. 技术认知校准.
2. 基线代码与契约探索.
3. 技术方向发散 (读取并执行 `EXPLORE-DESIGN-OPTIONS.md`).
4. 选择方向.
5. 架构和 module 责任. 当你盘问到这一点时调用 `codebase-design` skill, 禁止提前调用. 若需求会改动 module 形状或 interface 形状, 调用前必须先盘问形状决策分支 (见下); 仅当能证明需求不改动二者形状时方可跳过此盘问.
6. interface/schema/状态机, 关键流程.
7. 异常和边界处理, 安全, 性能/可观测性/可用性, 测试策略, 代码允许/禁止范围, 风险和停止条件.
8. 遇高影响专项决定时嵌套发散 (读取并执行 `EXPLORE-DESIGN-OPTIONS.md`).

**形状决策分支**: 盘问是否以 HILT 方式确定 module 和 interface 的形状. HILT 方式指我需要亲自决定二者的边界及其测试用例: 你提候选形状/取舍/理由与边界测试用例, 逐项征询我确认, 未经我确认不得固定; 选中后步骤 5-6 的形状决策不一次性提交方案. 非 HILT 方式则你按 `codebase-design` 原则提方案, 我只审阅终稿.

事实与已确认决策冲突时, 在会话中说明证据和影响, 再让我选择.

关键完成标准:

- 步骤 1 完成时: 已说明技术决策域, 我明确的不熟悉/待补充部分已获得处理路径, 无阻塞认知缺口.
- 步骤 2 完成时: 相关代码/契约/ADR 已读取; 权威技术资产已定位; 事实与已确认决策的冲突已说明.
- 步骤 3-4 完成时: 发散后选中方向, 或按跳过条件保留现有方向; 该方向有关键理由和约束; 取消时有未决问题和恢复位置.
- 步骤 5-6 完成时: module 责任已分配; interface/schema/状态机有权威来源或精确定义; 关键正常/失败流程已描述; 若选中 HILT 方式, 我已逐项确认 module 和 interface 的边界及其测试用例.
- 步骤 7 完成时: 异常和边界处理已定义; 安全策略已说明; NFR 有验证口径; 测试策略覆盖 AC/TG/NFR; 允许/禁止范围已划定; 风险和停止条件已确认.
- 已触发的步骤 8 分支完成时: 每个触发专项按外部参考返回选中或取消, 或按跳过条件保留现有方向; 选中则约束已纳入设计, 取消则未决问题和恢复位置明确, 不得宣告技术关闭.

技术分支总完成标准: 后续 `to-product-spec` 和 `to-technical-spec` 无需发明产品/API/架构/范围决策; 我已在会话中获知关键技术方案, 代价, 风险和验证方式; 步骤 1-7 每个关键分支满足 `grilling` 的分支完成标准; 已触发的步骤 8 分支均已关闭.

## 发散

每个方向选择点默认发散: 读取并执行 `EXPLORE-DESIGN-OPTIONS.md`, 比较多方案后再收敛. 不得仅凭 "已有 Spec" 或 "看起来明确" 跳过; 跳过是例外, 须满足下述全部条件.
发散比较的方案须含懒设计选项, 不在发散前单独询问; 选中懒设计方向后, 当前分支后续设计受 `lazy-design` skill 约束, 选中常规方向则沿已确认理由继续.
选择点: 产品方向 (可比较门槛达成后), 技术方向 (产品结果确定后), 以及技术分支中任一高影响专项决定:

- 改变外部 interface/schema/状态机或兼容承诺.
- 涉及迁移/数据丢失/不可逆操作/并发一致性.
- 涉及权限/隐私/密钥/金钱/审计.
- 性能/可用性/一致性等 NFR 会改变架构.
- 引入新依赖/新架构/难回滚机制.
- 关键前提证据不足, 且不同处理会改变方案.

### 跳过条件

仅当以下全部满足时跳过发散, 保留现有方向:

- 现有 Spec/方向能追溯到当前有效决策, 且与当前需求/ADR/机器可读契约/关键代码事实无冲突.
- 关键假设未因依赖版本/业务规则/运行环境变化而失效.
- 该决定已在上级或前序方案中充分比较过, 且当前上下文未引入新取舍.

纯文档/措辞/配置纠正且无技术取舍时可证明后跳过. 检查发现冲突, 失效或新取舍则发散. 证据不足且可能改变方向时, 按子代理验证流程处理, 不跳过.

## 固化

产品和技术分支全部关闭后, 在会话中给出高密度口头回顾: 产品结果, 关键技术选择, 明确不做, 主要风险, 验证方式, 已补齐的重要知识缺口, 新暴露盲区的处理结果, 被接受的不确定性.
然后合并询问 (替代 `grilling` 自带的结束确认, 不重复提问): `当前产品与技术分支已关闭, 以上是将被固化的决策/已接受不确定性. 是否固化当前方向并结束盘问?`

- 我回答是: 使用 `domain-modeling` 维护领域语言文件或 ADR, 调用 `decision-ledger` 维护 `DECISIONS.md`, 然后结束盘问.
- 我回答否并补充问题: 不写文件, 返回对应设计分支继续.
- 写入失败: 盘问结论仍保留, 但不得声称已固化, 应报告失败并恢复写入.

## 决策记录边界

- `DECISIONS.md` 记录本 feature 的产品, 代码, 边界, 测试决策和代码追踪, 不记录认知校准状态.
- ADR 只记录长期架构决策.
- 领域语言文件只记录领域词汇, 不承载实现决策.
- 客观待查事实按 Product/Technical Spec 的待验证事实规则处理, 不另建长期知识档案.
- 新增, 替代, 废弃决策前必须得到我确认.
- 后续 Spec 生成 skill 只能整理这些已确认决策, 不得新增决策.

## Spec 生成

盘问固化结束后, 询问我是否生成 Spec. 
我说不用则跳过; 
我说要则依次调用 `to-product-spec` skill, `to-technical-spec` skill.
接着判断当前是否在 `probe` skill 流程内: 不在则继续调用 `to-execution-spec` skill; 在则 spec 生成完毕, 停止 (`to-execution-spec` 改由 probe 准入相位按 feature 接管, 不在此处调用).

在生成 Spec 的过程中发现的任何未定决策都属于*盲区*, 须回到对应设计分支继续盘问, 该分支关闭后再继续生成 Spec.
