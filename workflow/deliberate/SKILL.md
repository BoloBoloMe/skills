调用 `domain-awareness` skill 只读感知当前工作目录的领域模型. 调用 `grilling` skill 盘问我, 以下是对盘问的额外要求.

# 盘问过程

先盘点已有产物, 感知当前要盘问的内容: 前沿只含缺口/未定/冲突项, 不从零重审已定部分.

逐前沿判定每个问题适用的层面, 拿不准时回问我:
- 涉及问题/受益者/目标/行为规则/场景/验收标准 → 产品层面
- 涉及技术认知/模块设计/技术约束/测试设计 → 技术层面
- 套不上任一层面 → 退回 grilling 默认行为

产品层面与技术层面只是检查维度, 不携带盘问顺序; 盘问顺序统一由 grilling 的前沿(依赖驱动)推进.

## 1. 产品层面

适用时, 从问题/受益者/目标出发, 选择产品方向, 细化到行为规则和正常/失败/边界场景, 以验收标准收口.
每关闭一个分支, 在会话中简述已确认结论及直接影响;
只讨论依赖已确认结论的实现细节.

完成标准:
产品目标, 非目标, 行为和验收标准无阻塞未知;
我已在会话中明确确认关键产品取舍;
每个关键分支都满足 grilling 的完成标准.

## 2. 技术层面

适用时, 基于已确认的相应产品决策, 盘问技术层面的问题:

先校准技术认知, 探索基线代码与契约, 让我选择技术方向.

再下沉到 *模块设计*:
架构/模块/接口 的设计必须符合 `codebase-design` skill 的原则,
必须和我逐项确认设计决策,
未经确认禁止固定.

继而明确 *技术约束收敛*:
边界情况, 安全, 风险, 质量属性, 代码允许/禁止范围;
逐项确认技术约束,
未经确认禁止默认.

最后以 *测试设计* 收口:
执行 `tdd` skill 定义的 `测试设计前置`, 与我确定测试用例集.

完成标准:
技术认知已校准, 基线代码与契约无阻塞未知;
模块设计, 技术约束, 测试设计均已与我确认, 无未确认即固定的项;
每个关键分支都满足 grilling 的完成标准.

## 3. 扫描盲区

执行 grilling 的 `扫描盲区`. 附加加以下额外检查项.
检查已启用层面 (至少判定过一个问题归属的层面) 对应的 `to-product-spec` 或 `to-technical-spec` 所需内容是否存在缺口, 缺口皆为盲区.

完成标准:
符合执行 grilling 的 `扫描盲区` 完成标准;
已启用层面对应的 spec 内容无缺口, 或每个缺口都已回到盘问逐项解决.

# 固化

各层面完成标准检查通过后, 询问 *是否结束盘问*.
我回答是: 使用 `domain-modeling` 维护领域语言文件或 ADR; 调用 `decision-ledger` 维护决策账本, 必须完整记录会话中所有确认过的决策和事实, 禁止写成摘要.
我回答否并补充问题: 不写文件, 返回对应设计分支继续.

`DECISIONS.md` 写入产物根目录, 默认 `docs/changes/<feature-slug>/`, 调用方可指定其他根目录; 领域语言文件与 ADR 由 `domain-modeling` 写入其约定位置.
已有同 slug 产物时直接修订, 无则新建.

# 检查产物

要落盘的产物都落盘之后, 启动一名子代理校验它们的内容是否正确且一致. 如果发现有问题先向我汇报, 在得到我的答复前禁止采取任何行动.
