开始前, 调用 `domain-awareness` skill 只读感知当前工作目录的领域模型, 调用 `adaptive-presentation` skill 了解回复形式.
调用 `grilling` skill 盘问我, 盘问中你的每次回答都要按信息形状选择回复形式, 直到盘问会话结束为止. 遵守 `grilling` 的认知校准和盲区扫描规则.
文档只供后续 AI 使用. 我不会通过阅读文档补齐上下文或批准方案. 每项影响产品, API, 架构, 范围, 风险或验证的决定, 必须在会话中向我说明含义, 影响和你的推荐, 再取得明确确认. 不要让我阅读生成文档后再确认.

## 建议委派给子代理完成的任务

父会话上下文窗口有限. 只读探索任务按规模分类委派:

| 规模 | 判定 | 执行 |
|------|------|------|
| 小 | 单文件/单 ADR/单一配置 | 父会话直接读取 |
| 大 | 多文件/跨模块/需搜索/需运行测试 | 委派子代理, fresh context |

子代理不设超时. 父会话自由组织任务描述, 子代理返回结构化摘要. 子代理失败时父会话降级自行探索, 最多一次修正重试, 不阻塞流程.

### HTML 渲染委派

父会话按 `adaptive-presentation` 路由决定用 HTML 回复时, 委派子代理生成 HTML. HTML 是写入临时目录的展示副产物, 非项目内容.

- 子代理与调用: 按 adaptive-presentation 的 HTML 路由生成临时展示副产物; 路径由当前运行时解析并返回可打开的位置. 同步, 禁止 `异步 + 等待` 假同步.
- 内容来源: 子代理从 fork 历史自行决定写入 HTML 的内容, 按 `HTML-GUIDE` 过滤凭据, 最小化原始日志/业务数据.
- 父会话在 task 传入 `HTML-GUIDE.md` 和 `browser_session.py` 的路径, 由当前运行时解析.
- 子代理职责: 写自包含 HTML, 调 `browser_session.py open`, 返回结构化 `{绝对路径, session-dir, 一句话说明}`.
- 父会话职责: 在 chat 给本地路径链接 + 一句话说明 + 自己的待确认问题. 关键结论和待确认决策仍须在 chat 中说明.
- 降级: 一次修正重试子代理; 仍失败则父会话回退到 Markdown 表格或 chat 文字, 不自行生成 HTML, 不阻塞盘问.

以下不委派: 技能调用与路由, 盘问交互, 审核确认, 文档起草, 决策固化.

## 认知校准节奏

`grilling` 是认知校准规则的单一真相源. 本 skill 只规定两阶段盘点节奏:

1. 初步探索上下文并明确问题边界后, 简述即将处理的产品决策域.
2. 产品分支关闭, 进入技术分支前, 简述即将处理的技术决策域.

阶段内部不固定重复盘点, 按 `grilling` 中的认知信号触发. 不建立长期知识档案, 不把认知状态写入 `DECISIONS.md`; 客观待查事实按 Product/Technical Spec 的待验证事实规则处理.

## 盘问顺序

先关闭产品分支, 再进入依赖它的技术分支. 分支表是 spec 所需的最小覆盖集, 非闭集; grilling 盲区扫描发现列表外高影响主题时, 插入对应分支并盘问.

### 1. 产品分支

依次关闭:

1. 问题和受益者.
2. 目标, 硬约束, 明确非目标.
3. 必要时产品方向发散 (读取并执行 `EXPLORE-DESIGN-OPTIONS.md`).
4. 选择方向.
5. 用户故事, 业务规则.
6. 正常/失败/边界场景.
7. 验收标准.

每关闭一个分支, 在会话中用简短语言说明已确认结论及其直接影响. 不讨论尚不依赖该结论的实现细节.

关键完成标准:

- 步骤 2 完成时: 问题/受益者/目标/硬约束/非目标已明确确认; 可比较门槛已达到.
- 步骤 3-4 完成时: 发散返回选中方向或明确取消; 选中方向有关键理由和约束; 取消时有未决问题和恢复位置.
- 步骤 5-7 完成时: 用户故事/业务规则/场景/验收标准无阻塞未知, 每项已获我确认.

产品分支总完成标准: 产品目标, 非目标, 行为和验收标准无阻塞未知; 我已在会话中明确确认关键产品取舍; 步骤 2-7 每个关键分支满足 `grilling` 的分支完成标准.

### 2. 技术分支

基于已确认产品分支, 依次关闭:

1. 技术认知校准.
2. 基线代码与契约探索.
3. 必要时技术方向发散 (读取并执行 `EXPLORE-DESIGN-OPTIONS.md`).
4. 选择方向.
5. 架构和 module 责任. 当你盘问到这一点时调用 `codebase-design` skill, 禁止提前调用.
6. interface/schema/状态机, 关键流程.
7. 异常和边界处理, 安全, 性能/可观测性/可用性, 测试策略, 代码允许/禁止范围, 风险和停止条件.
8. 遇高影响专项决定时嵌套发散 (读取并执行 `EXPLORE-DESIGN-OPTIONS.md`).

小规模直接探索, 大规模委派子代理. 事实与已确认决策冲突时, 在会话中说明证据和影响, 再让我选择.

关键完成标准:

- 步骤 1 完成时: 已说明技术决策域, 我明确的不熟悉/待补充部分已获得处理路径, 无阻塞认知缺口.
- 步骤 2 完成时: 相关代码/契约/ADR 已读取; 权威技术资产已定位; 事实与已确认决策的冲突已说明.
- 步骤 3-4 完成时: 发散返回选中方向或明确取消; 选中方向有关键理由和约束; 取消时有未决问题和恢复位置.
- 步骤 5-6 完成时: module 责任已分配; interface/schema/状态机有权威来源或精确定义; 关键正常/失败流程已描述.
- 步骤 7 完成时: 异常和边界处理已定义; 安全策略已说明; NFR 有验证口径; 测试策略覆盖 AC/TG/NFR; 允许/禁止范围已划定; 风险和停止条件已确认.
- 已触发的步骤 8 分支完成时: 每个触发专项按外部参考返回选中或取消; 选中则约束已纳入设计, 取消则未决问题和恢复位置明确, 不得宣告技术关闭.

技术分支总完成标准: 后续 `to-product-spec` 和 `to-technical-spec` 无需发明产品/API/架构/范围决策; 我已在会话中获知关键技术方案, 代价, 风险和验证方式; 步骤 1-7 每个关键分支满足 `grilling` 的分支完成标准; 已触发的步骤 8 分支均已关闭.

## 发散触发与跳过

### 产品方向发散

- 产品行为未确定时触发.
- 已有完整且当前有效的 Product Spec 时跳过.
- 模糊需求先达到可比较门槛 (问题/受益者/目标/硬约束/明确非目标清楚), 再发散.

### 技术方向发散

- 产品结果确定且存在实质实现取舍时触发.
- 已有明确且当前有效的技术方向时不重复发散, 除非新事实使其失效.
- 纯文档/措辞/配置纠正且无技术取舍时可证明后跳过.

### 高影响专项发散

满足任一项时触发, 但已在上级方案中充分比较过的同一决定不重复发散:

- 改变外部 interface/schema/状态机或兼容承诺.
- 涉及迁移/数据丢失/不可逆操作/并发一致性.
- 涉及权限/隐私/密钥/金钱/审计.
- 性能/可用性/一致性等 NFR 会改变架构.
- 引入新依赖/新架构/难回滚机制.
- 关键前提证据不足, 且不同处理会改变方案.

### 跳过前有效性检查

跳过发散前检查现有 Spec/方向:

- 能追溯到当前有效决策.
- 与当前需求/ADR/机器可读契约/关键代码事实无冲突.
- 关键假设未因依赖版本/业务规则/运行环境变化而失效.

检查通过才跳过; 发现冲突或失效则回到对应发散点. 证据不足且可能改变方向时, 按子代理验证流程处理.

## 懒设计

`是否使用懒设计` 不在发散前单独询问, 而是作为发散后的方案选项之一. 选中懒设计方向后, 当前分支后续设计受 skill `lazy-design` 规则约束. 选中常规方向后沿已确认理由继续.

## 固化

产品和技术分支全部关闭后, 在会话中给出高密度口头回顾: 产品结果, 关键技术选择, 明确不做, 主要风险, 验证方式, 已补齐的重要知识缺口, 新暴露盲区的处理结果, 被接受的不确定性. 不要求我阅读任何文档.
然后合并询问 (替代 `grilling` 自带的结束确认, 不重复提问): `当前产品与技术分支已关闭, 以上是将被固化的决策/已接受不确定性. 是否固化当前方向并结束盘问?`

- 我回答是: 使用 `domain-modeling` 维护领域语言文件或 ADR, 调用 `decision-ledger` 维护 `DECISIONS.md`, 然后结束盘问.
- 我回答否并补充问题: 不写文件, 返回对应设计分支继续.
- 写入失败: 盘问结论仍保留, 但不得声称已固化, 应报告失败并恢复写入.

## 决策记录边界

- `DECISIONS.md` 记录本 feature 的产品, 代码, 边界, 测试决策和代码追踪.
- ADR 只记录长期架构决策.
- 领域语言文件只记录领域词汇, 不承载实现决策.
- 新增, 替代, 废弃决策前必须得到我确认.
- 后续 Spec 生成 skill 只能整理这些已确认决策, 不得新增决策.

## Spec 生成

盘问固化结束后, 询问我是否生成 Spec.
如果我说不用, 就跳过本节内容;
如果我说要, 那么你要依次调用 `to-product-spec` skill , `to-technical-spec` skill. 接着你判断: 现在不是在 `probe` skill 的流程内? 如果是那么 spec 生成完毕, 如果不是那么你还要继续调用 `to-execution-spec` skill.
