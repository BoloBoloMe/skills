调用 `domain-awareness` skill 只读感知当前工作目录的领域模型. 调用 `grilling` skill 盘问我, 以下是对盘问的额外要求.

## 盘问过程

先关闭产品层面的盘问, 再进入依赖它的技术层面. 根据每个层面的要求, 组织 `grilling` - 盘问. 随分支推进和对话证据更新对我的知识判断.

### 1. 产品层面 

从问题/受益者/目标出发, 选择产品方向, 细化到行为规则和正常/失败/边界场景, 以验收标准收口. 每关闭一个分支, 在会话中简述已确认结论及直接影响; 不讨论尚不依赖该结论的实现细节.
完成标准: 产品目标, 非目标, 行为和验收标准无阻塞未知; 我已在会话中明确确认关键产品取舍; 每个关键分支满足 `grilling` 的分支完成标准.

### 2. 技术层面

基于已关闭的产品决策, 继续盘问技术层面的问题: 先校准技术认知, 探索基线代码与契约, 选择技术方向; 再下沉到*模块设计* (架构, module 责任, interface 形状和关键流程); 继而异常, 安全, 质量属性, 代码允许/禁止范围, 风险和停止条件; 最后以*测试设计*收口.

以下两项必须遵守, 其具体设计分支必须经过我确认: 
**模块设计**: module 设计和 interface 形状必须符合 `codebase-design` skill 的原则, 和我逐项确认模块设计的决策分支, 未经确认禁止固定.
**测试设计**: 测试用例必须符合 `tdd` skill 的哲学, 盘问测试策略前读取其哲学一节作为设计约束, 告诉我你打算怎样设计测试用例, 逐条与我确认, 未经确认禁止固定.

事实与已确认决策冲突时, 在会话中说明证据和影响, 再让我选择.

### 3. 盲区自扫

以上两层面的分支都闭合后, 执行 `grilling` 的盲区自扫. 
在此步骤检查 `to-product-spec` skill 和 `to-technical-spec` skill 所需的内容是否存在缺口, 这些缺口皆为盲区. 

## 4. 固化

分支完成标准检查通过后, 询问我是否同意结束盘问.
我回答是: 使用 `domain-modeling` 维护领域语言文件或 ADR, 调用 `decision-ledger` 维护 `DECISIONS.md`, 然后结束盘问.
我回答否并补充问题: 不写文件, 返回对应设计分支继续.

## Spec 生成

固化结束后, 询问我是否生成 Spec. 不用则跳过; 要则依次调用 `to-product-spec` skill, `to-technical-spec` skill, 
再判断: 当前在 `probe` skill 流程内则停止 (`to-execution-spec` 由 probe 准入相位按 feature 接管); 否则继续调用 `to-execution-spec` skill.

Spec 只能整理已确认决策, 禁止新增; 生成中发现的任何未定决策都属于遗漏的*盲区*, 回到对应设计分支继续盘问, 该分支关闭后再继续生成.
