硬 bug 的纪律: 只有理由明确时才允许跳过阶段.
探索代码库时, 调用 `domain-awareness` skill 感知领域模型, 并查阅所触及区域的 ADR.

## 脱敏

本流程要求你展示命令, 输出和捕获的工件. **先脱敏一切机密**: 原地写 `<REDACTED>`. 循环尽量基于环境变量构建, 让凭据留在环境里, 而不是出现在你展示的内容里. 捕获的工件携带 auth header: 只引用携带信号的行.
脱敏后的输出不足以诊断时, 明说并问我.

## 阶段 1: 构建反馈循环

**这是本 skill 的核心**, 其余都是机械动作. 有一个 *紧凑 (tight)* 的判红信号 — 能在这个 bug 上变 *红 (red)* 的 pass/fail 信号 — 就找得到原因: 二分, 假设检验, 插桩都只是在消费它. 没有它, 盯多久代码都没用.
在这里投入不成比例的精力. **激进, 有创造力, 拒绝放弃.**

### 构建方式, 大致按此顺序

1. **失败测试**, 打在能触及 bug 的任意接缝 (seam) 上: 单元, 集成, e2e.
2. **curl / HTTP 脚本**, 打向运行中的 dev server.
3. **CLI 调用**, 喂 fixture 输入, 把 stdout 与已知正确的快照 diff.
4. **无头浏览器脚本** (Playwright / Puppeteer), 驱动 UI 并断言 DOM/console/network.
5. **重放捕获的 trace**: 把真实网络请求/payload/事件日志存盘, 隔离地重放经过代码路径.
6. **一次性 harness**: 拉起系统的最小子集 (一个服务, mock 依赖), 用单次函数调用触发 bug 代码路径.
7. **属性/fuzz 循环**: bug 是 "输出有时错" 时, 跑 1000 个随机输入找失败模式.
8. **二分 harness**: bug 出现在两个已知状态 (commit, 数据集, 版本) 之间时, 自动化 "在状态 X 启动, 检查, 重复", 供 `git bisect run` 消费.
9. **差分循环**: 同一输入分别跑旧版本与新版本 (或两套配置), diff 输出.
10. **HITL 脚本**, 最后手段: 必须人来点时, 用 `scripts/hitl-loop.template.py` 驱动人, 循环仍保持结构化, 捕获的输出回流给你.

构建出对的反馈循环, bug 就修好了九成.

### 收紧循环

把循环当产品打磨. 有了一个循环之后, **收紧 (tighten)** 它:
- 能更快吗? 缓存 setup, 跳过无关初始化, 收窄测试范围.
- 信号能更锐利吗? 断言具体症状, 而不是 "没崩".
- 能更确定吗? 固定时间, 固定随机种子, 隔离文件系统, 冻结网络.

30 秒还 flaky 的循环比没有循环好不了多少; 2 秒确定的循环才是 *紧凑* 的, 是调试超能力.

### 非确定性 bug

目标不是干净的复现, 而是**更高的复现率**. 把触发循环 100 次, 并行, 加压, 收窄时序窗口, 注入 sleep. 50% 抖动的 bug 可调试, 1% 不行. 持续提高复现率, 直到可调试.

### 确实建不出循环时

停下并明说, 列出试过的方法. 向我要: (a) 能复现的环境的访问权, (b) 脱敏后的捕获工件 (HAR, 日志转储, core dump, 带时间戳的录屏), 或 (c) 添加临时生产插桩的许可.

### 完成标准: 一个能变红的紧凑循环

循环 *紧凑* 且 *可变红 (red-capable)*: 你能指出**一条命令** (脚本路径, 测试调用, curl), 它**已至少跑过一次** (展示调用与脱敏后的输出), 且满足:
- [ ] **可变红**: 驱动真实的 bug 代码路径, 断言**我描述的确切症状**, 因此能在这个 bug 上变红, 修好后变绿. 不是 "跑完没报错"; 必须能抓住这个具体的 bug.
- [ ] **确定**: 每次运行同一结论. flaky bug 按上文要求, 固定的高复现率.
- [ ] **快**: 秒级, 不是分钟级.
- [ ] **agent 可运行**: 你能无人值守地跑; 需要人时只通过 `scripts/hitl-loop.template.py`.

如果你发现自己在命令存在之前就读代码建理论, **停**: 直接跳假设正是本 skill 要防的失败. 没有可变红命令, 不进阶段 2.

## 阶段 2: 复现 + 最小化

跑循环, 看它随 bug 出现而变红. 确认:
- [ ] 循环产出的是**我描述的**失败模式, 不是恰好相邻的另一个失败. 诊断错 bug = 修错 bug.
- [ ] 失败多次运行可复现; 非确定性 bug 复现率达阶段 1 要求.
- [ ] 已捕获确切症状 (错误信息, 错误输出, 耗时), 供后续阶段验证修复真的对症.

### 最小化

变红后, 把复现缩减到**仍然变红的最小场景**. 输入, 调用方, 配置, 数据, 步骤, **一次只砍一个**, 每砍一刀重跑循环, 只留对失败起支撑作用 (load-bearing) 的部分.
为什么值得: 最小复现收窄阶段 3 的假设空间 (可疑的活动部件更少), 并成为阶段 5 干净的回归测试.
完成标准: **每个剩余元素都是 load-bearing** — 删掉任何一个, 循环变绿.
未复现且未最小化, 不继续.

## 阶段 3: 假设

先产出 **3-5 个排序过的假设**, 再测试其中任何一个. 只产一个假设会锚定在第一个看似合理的想法上.
每个假设必须**可证伪 (falsifiable)**: 说出它的预测.
> 格式: "若 <X> 是原因, 则 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更严重."
说不出预测的假设是直觉, 丢弃或磨利它.
**测试前把排序列表给我看.** 我常有领域知识能瞬间重排 ("我们刚部署了对 #3 的改动"), 或知道哪些已排除. 便宜的检查点, 省大量时间. 不必阻塞: 我不在时按你的排序继续.
完成标准: 每个假设都可证伪并带有预测; 排序列表已给我看过.

## 阶段 4: 插桩

每个探针必须对应阶段 3 的某个具体预测. **一次只改一个变量.**
工具偏好:
1. **调试器 / REPL 检查**, 环境支持就用. 一个断点胜过十条日志.
2. **定向日志**, 只打在能区分假设的边界上.

**每条调试日志打唯一前缀**, 如 `[DEBUG-a4f2]`. 收尾清理就是一次 grep: 没标签的日志会存活, 有标签的会死.

**性能分支.** 性能回归时日志通常是错的工具. 改为: 先建立基线测量 (计时 harness, `performance.now()`, profiler, 查询计划), 再二分. 先测量, 后修复.
完成标准: 每个假设已被证实或排除; 幸存假设指向根因, 且证据来自一次只改一个变量的探针.

## 阶段 5: 修复 + 回归测试

**先于修复**写回归测试, 但只当存在**正确的接缝 (seam)** 时.
正确的接缝: 测试能以调用点处真实发生的方式, 触发**真实的 bug 模式**. 唯一可用的接缝太浅时 (bug 需要多调用方却只能测单调用方; 单元测试复现不了触发 bug 的链条), 在那里写回归测试只会给虚假信心.
**不存在正确接缝, 本身就是发现**: 代码库架构在阻止这个 bug 被锁定. 记下来, 在阶段 6 标记出来.
存在正确接缝时:
1. 把最小复现转成该接缝上的失败测试.
2. 看它失败.
3. 应用修复.
4. 看它通过.
5. 用原始 (未最小化的) 场景重跑阶段 1 的反馈循环.

## 阶段 6: 清理

宣布完成前必须:
- [ ] 原始复现不再复现 (重跑阶段 1 循环).
- [ ] 回归测试通过, 或已记录无正确接缝的事实.
- [ ] 所有 `[DEBUG-...]` 插桩已移除 (grep 前缀验证).
- [ ] 一次性原型已删除, 或移到明确标记的调试位置.
- [ ] 被证实正确的假设写进了 commit / PR 信息, 让下一个调试者受益.
