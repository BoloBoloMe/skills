# 代码审查与反馈处理

## 适用时机

完成任务、主要功能、批次实现、review 反馈处理或合并前使用。

## 输入契约

- HILP design asset_ref。
- HILP blueprint asset_ref。
- HILP execution handoff asset_ref。
- 本次实现说明、计划或需求引用。
- BASE_SHA、HEAD_SHA、diff 范围或变更文件列表。
- 禁止越界项。

## 执行规则

请求审查工作流：记录 BASE_SHA、HEAD_SHA、diff 范围、实现说明、计划或需求引用、HILP asset_ref 和禁止越界项。

审查类型：规格符合性、代码质量、测试质量、生产就绪性、HILP 越界风险。

接收反馈流程：读完整反馈、理解、验证、评估、回应、逐项实现。外部反馈必须怀疑性验证：检查是否适合当前代码库、是否破坏现有行为、是否违反 HILP 已批准边界。

禁止表演式附和：不得用“完全正确”“好建议”替代技术判断。正确反馈直接修复并说明证据；错误反馈用代码事实说明。

YAGNI 检查：蓝图外能力不得直接实现，标记为需 HILP 重审或拒绝。

多项反馈处理顺序：先澄清不明项，再处理 Critical，再做简单修复，最后处理复杂修复；每项修复后运行相应验证。

## 禁止事项

- 不得跳过审查。
- 不得忽略 Critical 或 Important。
- 不得盲目实现未经验证的外部反馈。
- 不得以审查名义新增蓝图外功能。
- 不得在反馈不清时猜测实现。

## 输出契约

输出审查结论、Strengths、按严重级别列出的问题、每项处理结果、剩余风险和是否允许继续。处理反馈后必须给出验证命令、退出码与输出摘要。

## 检查清单

- [ ] BASE_SHA、HEAD_SHA 或 diff 范围明确。
- [ ] 审查上下文包含 HILP asset_ref。
- [ ] 已检查禁止越界项和 YAGNI。
- [ ] Critical 已清零，Important 已修复或明确阻断。
- [ ] 外部反馈已做技术验证。
